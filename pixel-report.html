01 / BUFFER IDENTITY

HDR 출력 버퍼에서 실제 JPEG 압축까지

이전 보고서에서 다룬 ApsExifCreateJpeg의 CodeGo 분기를 HDR의 실제 압축 위치로 보면 안 됩니다. 확인한 세 HDR 호출자는 이미지 descriptor의 첫 워드를 0으로 설정한 뒤 SaveJpegImage에 전달합니다. EXIF의 주 이미지 검사에 도달하면 **descriptor가 0일 때 새 압축을 건너뛰고 기존 code 크기를 사용합니다. 이 가운데 두 호출 경로에서는 그보다 앞선 SaveCompressImage가 ApsJpegDirectCompress를 호출해 실제 압축을 수행합니다. [B1: HDR 호출자와 EXIF 분기]

구체적인 연결은 HdrImageMixing → PerformImageMixSubImages → IpuToneMapRgb를 거치는 HDR 분기에서 찾았습니다. W+0x208 == 0이면 하위 이미지 출력 descriptor를 IpuToneMapRgb에 전달합니다. 이 함수는 PathSetBuffers(path, input, output, 0)로 출력 주소를 설정하고 Submit·Go·Wait 결과를 검사합니다. [B1: IPU 출력 view]

설정과 제출도 구분해야 합니다. IpuSubmit은 path+0x964 == 0이면 path+0x28의 출력 블록을 사용하며, 그 외에는 path+0x8fc의 descriptor를 복사합니다. 위 표는 PathSetBuffers가 B의 view를 설정하는 관계입니다. 실제 촬영에서 어느 제출 분기를 거쳤는지는 관측하지 않았습니다. [B1: IpuSubmit 조건]

DirectCompress는 이미지 주소 B를 그대로 복사하지 않습니다. bit 30이 켜져 있으면 B & 0x7fffffff를, 꺼져 있으면 B | 0x20000000을 사용합니다. 변환한 주소는 JPEG 생성 구조체의 입력 필드로 전달됩니다. 이는 CPU 명령에서 확인한 주소 변환이며 실제 메모리 버스 주소나 캐시 일관성을 측정한 결과는 아닙니다. [B1: 주소 변환·생성 바인딩]

T(B) = (B & 0x40000000) ? (B & 0x7fffffff) : (B | 0x20000000)
IPU output view: B + subimage offset
JPEG main input: T(B)
EXIF main descriptor: **descriptor == 0 → existing code size

이 연결은 조건이 충족되는 HDR 소프트웨어 경로입니다. IPU 출력과 JPEG 입력의 숫자가 항상 같은 것이 아니며, 주소 변환과 view 오프셋을 포함해 비교해야 합니다. 실제 픽셀 쓰기·읽기, DMA 버스 주소, 캐시 일관성은 관측하지 않았습니다.

02 / PASS SELECTION

마지막 패스와 색 필터를 구분하다

패스 수가 N이고 패스 인덱스가 i일 때 TranslateFilters는 i == N−1이면 마지막 패스 플래그를 전달합니다. 각 패스는 별도 설정 포인터와 FIPLIB wrapper를 사용합니다. 원본의 final-pass 필터 표에서 설정된 항목은 ID 0뿐입니다. CM인 ID 10과 FC1인 ID 13을 마지막 패스 전용 필터로 볼 근거는 없습니다. [P1: TranslateFilters·final-pass 표]

Commit의 모드 0은 전체 패스, 모드 1은 마지막 패스를 제외한 범위, 모드 2는 마지막 패스를 선택합니다. 선택된 범위 안에서도 task 포인터가 있는 항목을 처리합니다. 이 범위는 실행 대상으로 삼는 소프트웨어 구간입니다. 모든 촬영에서 패스 수나 모드가 같다는 뜻은 아닙니다. [P1: Commit]

유효한 N개 패스에서의 Commit 선택 범위 — 끝 인덱스 제외

task(i)    = *(processor + 0x204 + 4*i)

원본의 공통 필터 표도 확인했으며 33개 항목이 모두 0입니다. 이는 ROM 표의 내용이지 런타임 수정이 없다는 증명은 아닙니다. 마지막 패스 플래그, 촬영 모드, 필터 ID를 같은 개념으로 취급하지 않습니다.

03 / FIELD-LEVEL OVERWRITE

CM은 일부 필드만, FC1은 계수까지 갱신한다

CM과 FC1의 CreateFilter 분기는 상위 descriptor를 적용한 뒤 FIPLIB 갱신을 시도합니다. 두 호출은 같은 패스의 같은 필터 포인터 슬롯을 사용합니다. descriptor 갱신에는 포인터가 있고 dirty 또는 강제 갱신 조건이 충족되어야 합니다. FIPLIB 갱신도 wrapper 존재 여부와 별도의 dirty 또는 강제 갱신 조건을 확인합니다. [P1: CreateFilter·update gates]

2. FIPLIBwrapper ≠ 0 및 (FIPLIB dirty bit 0 또는 pass force)앞 단계에서 사용한 같은 슬롯
3. 실제 기록UID 비교, writer dirty 등 하위 조건직접 MMIO 또는 CBC 청크

CM의 FIPLIB setter는 객체의 +0xb0, +0xb4, +0xb8만 변경합니다. 아홉 행렬 계수가 있는 +0x88부터 +0xa8까지는 건드리지 않습니다. 따라서 이 setter가 실행됐다는 이유만으로 CM 행렬 전체가 덮어써졌다고 볼 수는 없습니다. 다른 호출이나 촬영 모드에서도 계수가 보존되는지는 확인되지 않았습니다. [P1: 0x803531bc]

FC1의 version 0xc FIPLIB setter는 payload에서 32비트 값 아홉 개를 읽고 하위 16비트를 객체의 행렬 필드에 저장합니다. 이 경로가 실행되면 앞서 설정한 FC1 계수가 교체됩니다. 레지스터 기록 함수는 다시 signed 16비트로 읽어 확장하므로 저장 시의 잘림과 기록 시의 부호 확장을 함께 구분해야 합니다. [P1: 0x8031f64c]

값 갱신 뒤에는 FIPLIB의 활성화 설정도 적용합니다. 필터와 wrapper가 존재하면 CM은 payload+0x30 워드의 bit 0이 0일 때, FC1은 payload+0x44 바이트가 0일 때 활성화됩니다. 이 단계는 값 갱신의 dirty gate와 별개이므로 상위 enable 설정만으로 최종 활성 상태를 확정할 수 없습니다. [P1: enable_gate]

HDR 로컬 설정도 최종 레지스터 값과 구별한다

IpuToneMapRgb는 ID 0xf, version 0xc의 로컬 설정을 만들고 아래 계수 아홉 개를 기록한 뒤 필터를 설정·활성화합니다. 이는 상위 descriptor 값입니다. FIPLIB 갱신 gate가 충족되면 FC1의 값이 교체될 수 있으므로 아래 행렬을 촬영 시 최종 레지스터 값이라고 부르지 않습니다. [B1: HDR 로컬 행렬] [P1: FC1 갱신]

ID 0xf의 설정은 원본의 dirty 표에서 FIPLIB 재계산 대상으로 지정돼 있습니다. PrepareCalculations(0x80349814)는 version 0xc의 계수 아홉 개를 descriptor +0x14..+0x24에서 FIPLIB 입력 +0x1074..+0x1084로 복사합니다. 즉 아래 값은 FIPLIB 입력이기도 합니다. 선택된 wrapper의 결과가 이 숫자를 그대로 유지하는지, 다른 값이 되는지는 이번 실행으로 확인하지 않았습니다. [P1: HDR integration]

04 / REGISTER SUBMISSION

직접 기록과 CBC는 제출 방식이 다르다

CBC 사용 여부는 processor+0x288의 값으로 결정됩니다. 값이 0이면 task 큐와 WriteAll을 거쳐 레지스터를 직접 쓰고 0이 아니면 배치를 준비해 CBC로 실행합니다. CBC의 CM·FC1 설정 청크도 같은 객체 필드를 주소·값 쌍으로 기록합니다. 이 청크 생성 과정에서 행렬을 새로 계산하는 연산은 확인되지 않았습니다. [P1: SetParam·Commit·Go·CBC]

두 경로 모두 현재 필터의 UID를 각 경로에 마지막으로 제출한 UID와 대조합니다. CBC에서 두 UID가 같으면 저장한 청크를 재사용하고, 다르면 생성 함수와 필터의 청크 추가 함수를 호출합니다. 따라서 새로운 descriptor가 항상 즉시 MMIO 쓰기로 이어진다고 볼 수 없습니다. [P1: UID·chunk cache]

표시한 CBC 순회는 processor+0x2f0 < 2 분기입니다. Go의 배치 실행에는 끝 인덱스가 0이 아닌 조건도 있습니다. 일반 필터 경로는 config 존재와 task+0x1f8 == 0을 요구합니다.

06 / VALIDATION & LIMITS

소프트웨어 연결은 확인하고 픽셀 관측과 구분하다

CM과 FC1의 FIPLIB setter를 각각 실행한 뒤 해당 레지스터 기록 함수를 이어 실행했습니다. 합성 입력에서 객체 전체 바이트와 순서가 있는 MMIO 쓰기 28회를 대조했습니다. CM의 계수 보존, FC1의 잘림과 부호 확장 결과는 예상값과 일치했습니다. 이 시험은 분기 조건을 만족한 뒤 두 함수 구간을 검사합니다. 패스 선택이나 카메라 전체 실행을 대신하지 않습니다. [V1: 재실행 결과]

이번 근거 집합은 함수 후보 70개와 명령·데이터 워드 기록 539건입니다. 함수 범위는 다음 sidecar 주소까지이며 정식 함수 크기 정보가 아닙니다. 주소·해시·분기 정보와 선택한 워드를 원본 펌웨어에서 다시 계산해 대조합니다. [검증 코드]

python -m unittest discover -s tests -v
python tools/verify_report.py --firmware path/to/fwdc603p.bin
# 합성 ELF 생성은 deep-report.html의 재현 절 참조

CPU의 디스크립터 전달과 계수 갱신을 확인했어도 ISP 내부 픽셀 연산을 재현한 것은 아닙니다. 실제 촬영에서 선택된 패스 수, FIPLIB가 산출한 최종 계수, 센서부터 저장 이미지까지의 픽셀 값은 관측하지 않았습니다. 확인한 HDR 경로를 일반 비 HDR 촬영 전체에 적용하지 않습니다.

MMIO를 일반 RAM으로 모델링한 VEX 실행입니다. 패스 스케줄러, RTOS, CBC 엔진, 센서, JPEG 하드웨어를 실제로 구동하지 않았습니다. 전체 디컴파일 원문과 원본 펌웨어는 공개하지 않습니다. 공개 CI는 원본 없이 기준값·메타데이터·HTML과 링크를 검사합니다.
