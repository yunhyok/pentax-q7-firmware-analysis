01 / RECOVERED CODE

주소·이름과 압축 코드를 연결하다

리소스 영역의 FAT16 디렉터리에서 ADR·OFT·STR 파일을 찾았습니다. 주소 배열과 문자열 오프셋을 결합하면 122,154개의 주소·이름 레코드가 나옵니다. 데이터 이름과 중복 주소도 있으므로 함수 수로 세지 않았습니다. E04·E05·E06의 네 적재 구간은 별도 Huffman 조회표와 LZ 참조를 쓰는 형식이었습니다. 448개 블록 모두 선언된 출력 길이에서 종료 표식에 도달했고 남은 비트는 0이었습니다. [S1] [S2]

02 / KERNEL INITIALIZATION

초기화와 스레드 진입점

카메라 본체의 _tx_initialize_kernel_enter는 저수준 초기화, 고수준 초기화, tx_application_define을 차례로 호출한 뒤 스케줄러로 점프합니다. CP0 EBase의 하위 10비트가 1인지에 따라 기본 컨텍스트와 Cop 컨텍스트를 고릅니다. 컨텍스트 이름만으로 두 실행 주체의 물리적 코어 배치까지 확정하지는 않았습니다. [S3: 0x800d1d88]

tx_application_define에서 CpuInit, DcuInitDram, PoolInit, OsThreadInit, TimerInit, DcuInit 호출을 확인했습니다. 일부 호출은 EBase 조건 안에 있습니다. 마지막 OsThreadCreateEx 호출은 AppBootPrimary 주소를 스레드 진입점으로 넘깁니다. 따라서 이 연결은 초기화 함수가 AppBootPrimary를 직접 호출하는 관계와 구분해야 합니다. [S3: 0x800e9470]

05 / JPEG

양자화 계산과 인터럽트까지

JPEG에서는 테이블 계산, 경로 제출과 완료 인터럽트를 분리해 추적했습니다. ApsCmpRecalcDqt는 Y·C 각각 64개 항목을 계산하고 1부터 255까지로 제한합니다. PathSetJpeg는 QtConvert를 두 번 호출해 경로 객체의 +0xc0과 +0x1c0에 테이블을 만듭니다. 두 테이블 경로가 같은 촬영에서 연결되는지와 최종 하드웨어 양자화 레지스터는 아직 확인하지 못했습니다. [S3: ApsCmpRecalcDqt, PathSetJpeg, QtConvert]

scale = input_scale & 0xffff
QY[i] = clamp((scale * baseY[i]) >> 14, 1, 255)
QC[i] = clamp((scale * baseC[i]) >> 14, 1, 255)     // i = 0..63

QtConvert: inverse-zigzag 순서로 64개 항목 변환
  mode == 1 : 원본 byte를 32비트 항목에 저장
  그 외     : max(1, 0x4000 / source_byte); 0 입력은 trap

StillCaptureImageTuneJpegEnc(0x802de3e0)는 ApsCmpRecalcDqt와 ApsJpegCreate를 호출하지만 Emulation 이름의 입출력 버퍼를 사용합니다. 일반 촬영의 유일한 JPEG 경로로 단정하지 않았습니다. PathSubmit은 경로 타입이 1일 때 JpegPathSubmit을 선택하고 이 함수는 객체 +0x3c4의 비트 0x40이 켜진 경우 IcaPathSubmit을 호출합니다. [S3: 0x801c84bc, 0x801df5a4, 0x802de574, 0x802de728]

JpegPathInit은 IsrJpegDone을 ID 0x14에 등록합니다. 완료 처리 함수는 0xb0181ca0을 읽고 값이 0이면 이벤트 비트 0x04, 아니면 0x40을 설정합니다. 끝에는 ISR 중지 함수로 향하는 꼬리 점프도 있습니다. 디컴파일된 C가 이 점프를 다른 표현으로 바꾸었으므로 호출 관계는 어셈블리를 기준으로 기록했습니다. [S3: IsrJpegDone, JpegPathInit]

ISR의 0x801df628은 호출, 0x801df644는 꼬리 점프입니다. 대상은 둘 다 _tx_isr_suspend이며 인자는 각각 0x801e3890, 0x815a1d6c입니다. 등록은 확인했지만 실기에서 인터럽트가 발생했는지는 검사하지 않았습니다.

06 / COLOR MATH

행렬 연산을 원본 명령으로 검산하다

색 처리에서는 3×3 행렬 곱, 색상 회전, Adobe RGB 조건, 화이트밸런스 사전 이득과 감마 테이블 합성을 확인했습니다. MatrixMultiplication은 합산값에 0x1000을 더하고 13비트 오른쪽 시프트한 뒤 하위 16비트를 저장합니다. HueShift의 대응 값은 0x80과 8비트입니다. 입력 행렬을 먼저 복사하므로 출력과 입력 주소가 같아도 계산할 수 있습니다. [S3: ColorMatchingService]

acc = Σ A[row,k] × B[k,col]                    // k = 0..2
MatrixMultiplication: low16(uint32(acc + 0x1000) >> 13)
HueShift:             low16(uint32(acc + 0x0080) >>  8)
// 입력 계수는 signed 16비트. MIPS의 32비트 누산·저장을 반영.

두 행렬 함수는 복원한 MIPS 명령을 angr의 VEX 엔진에서 실행했습니다. 단위 행렬, 음수 계수와 입력·출력 주소 중복을 포함한 6개 사례가 독립 계산식과 일치했습니다. 이는 해당 계산 함수의 검증이며 카메라의 픽셀 처리 결과나 색 재현을 검증한 것은 아닙니다. [S5] [재실행 코드]
