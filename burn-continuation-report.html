NAND 기록의 재시도와 마지막 마무리

블록 하나를 쓰지 못했을 때 로더는 데이터를 버리지 않고 다음 블록에 다시 씁니다. 이 재시도 규칙과, 본문을 다 쓴 뒤 첫 블록을 고쳐 쓰고 끝내는 순서를 원본 코드로 따라갔습니다.

이 문서에서

  1. 배경: 블록을 쓰는 반복과 이 문서의 시험 조건
  2. 기록이 실패하면 같은 데이터를 다음 블록에 씁니다
  3. 135개 청크를 쓰는 동안 원본과 달라지는 곳은 두 블록입니다
  4. 본문을 다 쓴 뒤 블록 0을 고쳐 쓰고 끝냅니다
  5. K-3 Mark III와 비교
  6. 한계와 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 기록이 실패하면 로더는 그 블록에 불량 표시를 요청하고, 같은 데이터를 다음 물리 블록에 다시 씁니다. 성공한 뒤에야 다음 데이터를 읽습니다.
  • 불량으로 표시된 블록과 보호 구간의 블록은 건너뜁니다. 쓸 수 있는 블록이 남지 않거나 카드 읽기가 실패하면 로더의 기록 함수는 1을 반환하고 끝납니다.
  • 기록 결과를 모두 성공으로 넣은 시험에서 로더는 135개 청크를 처리했습니다. 원본 패키지와 내용이 달라진 곳은 블록 0의 281바이트와 블록 10의 512바이트뿐입니다.
  • 그 뒤 로더는 확장 헤더를 따로 쓰고, 블록 0을 읽어 4바이트를 고친 다음 지우고 다시 씁니다. 마지막에 준비 함수를 부르고 0을 반환합니다.
  • 저장장치의 응답과 기록 결과는 모두 시험용 모델입니다. 실제 NAND에 쓴 것이 아니며, 업데이트가 완료된다는 증거도 아닙니다.

확인 원본 코드 실행으로 확인

  • 재시도·건너뛰기·중단 분기 7사례 (기록 함수를 부르는 쪽의 원본 코드)
  • 135개 청크 뒤의 마무리 4사례와 마지막 반환값
  • 블록 10, 확장 헤더, 마지막 블록 0 버퍼를 따로 계산해 해시 대조
  • 원본 워드 116개와 63개를 주소·값으로 대조

정적 분석 코드를 읽어 판단

  • 블록 맵에 불량 항목이 있을 때 확장 헤더를 더 고치는 분기

모델 시험 조건으로 정한 것

  • 기록·비교 함수의 결과 (성공 1, 실패 0)
  • 예비 영역의 내용, 불량 표시 요청의 상태값
  • 카드 읽기 함수의 반환값과 건네는 청크
  • 설치된 헤더와 저장장치 형상 (1,024블록, 보호 구간 640~1023)
  • 마무리 요청 네 개의 응답, 메모리 해제

미확인 확인하지 않은 것

  • 실제 NAND의 기록·읽기·보호·복구
  • 카드 읽기 아래의 FileX 오류, 짧게 읽힌 경우, 파일 끝
  • 지우기 실패, 다른 섹션 구성
  • 카메라의 수용·부팅·촬영

배경: 블록을 쓰는 반복과 이 문서의 시험 조건

업데이트 로더(E01)의 BurnNand 함수는 카드에서 131,072바이트(128 KiB)씩 읽어 NAND 플래시의 블록에 차례로 씁니다. NAND에는 쓸 수 없게 된 불량 블록이 생길 수 있습니다. 대부분의 NAND 칩은 데이터 옆에 딸린 예비 영역(spare)의 정해진 자리에 불량 블록 표시를 두고, 쓰는 쪽은 그런 블록을 피해 갑니다. [리눅스 커널 문서: MTD NAND, Bad block table support]

이 문서는 로더가 그 일을 어떻게 하는지를 다룹니다. 앞 단계는 다른 문서에 있습니다.

  1. 사전 검사요청 3,331개 — 저장 경계
  2. 첫 블록 버퍼 고치기281바이트 — 기록 헤더와 MD5 경로
  3. 기록과 재시도이 문서의 7사례
  4. 마무리와 반환이 문서의 4사례
  5. 실제 NAND와 부팅확인하지 않음

읽는 데 필요한 말

  • 물리 블록과 논리 블록: 물리 블록은 저장장치에서 실제로 쓰는 자리의 번호입니다. 논리 블록은 데이터의 순번입니다. 불량 블록을 건너뛰면 두 번호가 어긋납니다.
  • 블록 맵: 로더가 메모리에 두는 표입니다. 블록마다 한 글자로 상태를 적습니다. 이 문서의 시험에서는 _, x(기록 실패), B(불량), P가 나왔습니다. P는 384개로, 보호 구간의 블록 수와 같습니다.
  • 기록·비교 함수: 블록 하나를 쓰고 다시 읽어 비교하는 원본 함수(0x80011da8)입니다. 이 문서에서는 이 함수의 결과를 모델이 정했습니다. 함수 자체를 원본으로 실행한 결과는 저장 경계 문서의 8사례에 있습니다.
  • 확장 헤더: 섹션 2의 맨 앞 512바이트입니다. 로더는 이것을 따로 보관했다가 본문을 다 쓴 뒤에 기록합니다.

시험 조건

모든 사례는 첫 기록 함수가 불리기 직전의 상태를 복사해 시작합니다. 그 상태는 앞 단계를 원본 코드로 실행해 얻었고, 앞 단계의 요청 3,331개가 같은 순서로 나오는지도 다시 확인했습니다. 저장장치는 512바이트 섹터 256개가 한 블록인 1,024블록짜리 합성 장치이고, 설치된 헤더는 블록 640부터 384블록을 보호 구간으로 둔 시험용 값입니다.

기록이 실패하면 같은 데이터를 다음 블록에 씁니다

실패했을 때 넘어가는 것은 물리 블록 번호뿐입니다. 논리 블록 번호와 데이터는 성공할 때까지 그대로입니다.

기록·비교 함수가 실패값 0을 돌려주면, 원본 코드는 불량 표시 함수를 부른 뒤 다음 물리 블록을 찾습니다. 다시 시도할 때 논리 블록 번호, 카드의 읽기 위치, 131,072바이트 데이터 전체의 해시가 앞선 시도와 같았습니다. 성공값 1을 받은 뒤에야 논리 블록을 진행하고 다음 청크를 읽습니다. 실패한 블록을 건너뛴다고 그 블록에 쓰려던 데이터까지 건너뛰지는 않습니다. [근거: cases의 program-retry]

  • 불량 표시: 이 합성 핸들에서 원본 표시 함수는 예비 영역의 +4에 0, +5에 0xf0을 넣어 연산 7을 두 번 요청했습니다. 첫 요청에 오류 7을 응답하자 둘째 요청은 나오지 않았습니다. 표시가 성공한 사례와 실패한 사례 모두에서 로더는 다음 후보로 넘어갔습니다.
  • 불량 블록 건너뛰기: 블록 1의 예비 영역 +5를 0으로 응답하자, 원본 불량 판정이 블록 1을 건너뛰었습니다. 논리 블록 1의 데이터는 물리 블록 2에 배정됐습니다.
참고

예비 영역 16바이트의 +4와 +5는 SmartMedia(SSFDC) 형식에서 데이터 상태와 블록 상태 바이트가 놓이는 자리와 같습니다(리눅스 커널의 sm_common.h). 로더에는 FcuSsfdcOperationEx라는 이름의 함수도 있습니다. 다만 Q7의 NAND가 이 형식을 따른다는 것은 확인하지 않았습니다.

쓸 블록이 남지 않거나 카드 읽기가 실패하면 끝납니다

첫 기록을 실패로, 블록 1~639를 불량으로 응답한 사례입니다. 원본 보호 판정은 블록 640~1023을 모두 제외했습니다. 판정이 “보호”를 돌려준 횟수는 384회였고, 이 구간에는 기록 함수가 한 번도 불리지 않았습니다. 후보 번호가 1024가 되자 원본 코드는 후보 소진 분기(0x80014890)로 들어가 1을 반환했습니다. 보호 범위는 합성 설치 헤더에서 온 값이며, 실물 저장장치의 범위를 확인한 것은 아닙니다. [근거: cases의 candidate-exhaustion]

다른 사례에서는 로더가 다음 131,072바이트를 요구했을 때 카드 읽기 함수의 반환값을 0으로 응답했습니다. 원본 코드는 실패 분기로 들어가 1을 반환했습니다. 섹션이 정상으로 끝나는 것은 남은 바이트 수와 블록 수로 판단하므로 이 실패와는 다른 길입니다. 카드 읽기 함수 아래의 FileX 오류, 짧게 읽힌 경우, 파일 끝은 이 시험에 넣지 않았습니다. [재현 도구: next-card-read-error]

주의

여기서 반환값 1은 중간에 끝났다는 뜻입니다. 끝까지 간 사례의 반환값은 0입니다(마무리 참고). 어느 값도 업데이트의 성공이나 실패를 카메라 수준에서 확인한 것이 아닙니다.

첫 청크는 앞 단계에서 이미 읽었으므로 이 구간의 카드 읽기는 134회입니다. 블록 10이 달라지는 까닭은 확장 헤더 때문입니다.

  1. 헤더를 따로 보관 섹션 2의 첫 청크를 읽으면, 원본 코드는 맨 앞 512바이트를 별도 버퍼에 복사하고 기록할 버퍼의 같은 자리를 0xff로 채웁니다. 그래서 블록 10에는 헤더가 빠진 내용이 기록됩니다.
  2. 보관한 헤더를 고침 섹션이 끝나면 보관한 헤더의 +0x54에 그때의 물리 블록 번호 135를 쓰고, +0x58~+0xd7을 0xff로 채웁니다. 원래 헤더와 132바이트가 달라집니다.
  3. 따로 기록을 요청 고친 512바이트를 0xff로 채운 2,048바이트 버퍼 앞에 놓고, 연산 5로 섹터 0xa00부터 4섹터 기록을 요청합니다. 이 형상에서 섹터 0xa00(2,560)은 블록 10의 첫 섹터입니다. 이 요청에는 예비 영역 포인터가 없습니다.

두 버퍼의 내용은 원본 패키지에서 따로 계산해 확인했습니다. 블록 10에 넘어간 131,072바이트와 확장 헤더 요청의 2,048바이트 모두, 따로 계산한 SHA-256이 실행에서 관측한 값과 같았습니다. 이 사례의 블록 맵에는 불량 항목이 없어서 헤더를 더 고치는 일은 없었습니다. 불량 항목이 있을 때의 보정은 코드를 읽어 확인했을 뿐 실행하지 않았습니다. [근거: source_reconstruction, cases의 main-payload-to-metadata]

시험은 확장 헤더 기록 요청이 저장 계층 진입점에 도달한 자리에서 멈췄습니다. 다음 절의 네 사례는 이 상태를 복사해 이어 갑니다.

K-3 Mark III와 비교

K-3 Mark III의 자료는 업데이트 래퍼가 실행기의 결과를 돌려주고, 입력을 해제하고, 완료를 알리는 경로를 나눠서 다룹니다. Q7에서는 블록 0을 다시 쓴 뒤 준비 함수의 1을 BurnNand의 0으로 바꾸는 구간을 원본 코드로 실행했습니다. “끝내는 단계”라는 비교 항목은 같지만, 함수마다 반환값의 뜻은 따로 확인해야 합니다. 두 기종의 연산 번호나 성공 규약이 같다고 보지 않았습니다. [고정 커밋의 K-3 Mark III 업데이트 종료 근거]

한계와 재현 방법

  • 기록·비교 함수는 모델입니다. 모델은 결과값과 블록 맵의 실패 표시만 흉내 냅니다. 이 함수의 바이트 비교는 1~2섹터짜리 8사례로 따로 실행했습니다.
  • 저장장치 형상, 설치된 헤더, 예비 영역의 내용, 상태값은 모두 넣어 준 값입니다. 기록 함수를 부르는 쪽과 불량·보호 판정은 원본 명령으로 실행했습니다. 다른 섹션 구성과 물리적인 쓰기 보호는 다루지 않았습니다.
  • 카드 읽기의 실패는 읽기 함수의 반환값으로만 넣었습니다. FileX 오류, 파일 끝, 짧게 읽힌 경우는 없습니다.
  • 마무리 4사례는 135청크가 모두 성공한 사례의 상태 하나에서 시작합니다. 블록 0 읽기는 앞서 넘어간 바이트를 돌려줄 뿐이며, NAND에 보존됐다는 증거가 아닙니다.
  • 실제 플래시의 기록·읽기 비교·보호·복구, 수정 펌웨어의 수용·부팅·촬영은 확인하지 않았습니다.
  • 공개한 것은 재현 도구와 주소·해시입니다. 원본과 수정 이미지, 전체 디컴파일 결과는 공개하지 않습니다.
