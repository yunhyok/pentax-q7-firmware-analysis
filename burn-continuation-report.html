01 / SAME INPUT, NEXT PHYSICAL BLOCK

실패한 데이터를 다음 후보로 보낸다

앞선 원본 실행에서 얻은 첫 기록 직전 상태를 일곱 사례에 복사했습니다. 이전 단계의 3,331개 저장장치 요청 순서도 다시 확인했습니다. 이후 원본 호출자의 분기와 블록 상태 검사는 실행하되 카드 읽기·저장장치 응답·기록 함수의 결과는 모델로 공급했습니다. 기록 후 비교를 수행하는 하위 함수의 원본 실행은 앞선 별도 8사례에 있습니다. [B1: modeled_prefix·modeled_continuation]

기록 함수가 실패값 0을 돌려주면 원본 호출자는 블록 표시 함수를 거쳐 다음 물리 블록을 찾습니다. 재시도 때 논리 블록 번호·카드 커서·128 KiB 전체 데이터 해시는 그대로였습니다. 성공값 1을 받은 뒤에야 논리 블록을 진행하고 다음 청크를 읽습니다. 실패한 물리 블록을 건너뛴다고 입력 데이터까지 건너뛰지는 않습니다. [B1: program-retry]

이 합성 핸들에서 원본 표시 함수는 spare의 +4에 0, +5에 0xf0을 넣어 op 7을 요청합니다. 첫 op 7에 오류 7을 공급하면 둘째 요청을 생략합니다. 표시 함수가 성공하거나 실패한 두 사례 모두 호출자는 다음 후보로 진행했습니다. 별도 사례에서 블록 1의 spare +5를 0으로 공급하자 원본 불량 판정이 이를 건너뛰고 물리 블록 2에 논리 블록 1을 배정했습니다. [B1: marker-error-retry·spare-bad-block]

02 / BAD, PROTECTED, EXHAUSTED

기록 가능한 후보가 없으면 종료한다

첫 기록은 실패로, 블록 1~639는 불량으로 공급했습니다. 원본 보호 판정은 블록 640~1023을 모두 제외했습니다. 총 384번의 원본 보호 반환값을 관측했으며 이 구간에 기록 함수를 호출하지 않았습니다. 후보 1024에서 소진 분기로 들어가 반환값 1로 끝났습니다. 보호 범위는 합성 설치 헤더에서 온 값이며 실물 매체의 범위를 확인한 것은 아닙니다. [B1: candidate-exhaustion]

호출자가 다음 128 KiB를 요구했습니다. 이때 카드 콜백 반환값 0을 공급하면 실패 분기로 들어가 반환값 1로 끝납니다. 정상적인 섹션 종료는 원본의 남은 바이트·블록 수로 판단하므로 이 실패 사례와 다릅니다. 콜백 아래의 FileX 오류·짧은 읽기·EOF는 이번 실행에 포함하지 않았습니다. [B2: next-card-read-error]

03 / MAIN PAYLOAD TO LATER REQUEST

135개 청크 뒤의 요청을 분리한다

기록 결과를 모두 성공으로 공급한 사례는 섹션 1의 10개와 섹션 2의 125개, 합계 135개 청크를 처리했습니다. 첫 청크 이후 카드 읽기는 134회입니다. 원본 패키지의 대응 청크와 비교하면 블록 0에서 281바이트, 블록 10에서 512바이트가 바뀌었고 나머지 133개는 같았습니다. 원본은 섹션 2의 첫 512바이트 헤더를 별도 버퍼에 보관한 뒤 주 기록 버퍼의 같은 범위를 0xff로 채웁니다. 이 바이트 구성을 원본 패키지에서 재구성한 해시가 관측값과 일치했습니다. [B1: main-payload-to-metadata]

135개 청크 뒤에는 sector 0xa00부터 4섹터를 쓰는 별도의 op 5 요청이 나타납니다. 이 요청에는 spare 포인터가 없으며 호출자의 복귀 주소는 0x8001437c입니다. 실행은 저장장치 진입점에서 요청 인수를 확인한 뒤 op 5를 처리하기 전에 중단했습니다. 뒤의 종료 경로 4사례는 이 상태를 복사해 실행을 이어갑니다. 보관한 헤더의 +0x54에는 물리 커서 135를 쓰고 +0x58~+0xd7은 0xff로 채웁니다. 이 사례의 맵에는 불량 항목이 없어 추가 비트 보정이 없었습니다. 갱신한 512바이트를 0xff로 초기화한 2,048바이트 버퍼에 복사하면 별도 요청의 전체 해시도 일치합니다. 다른 맵 값에 따른 보정은 정적으로만 확인했습니다. [B1: pending_storage]

05 / TERMINAL RETURN WITH MODELED STORAGE

블록 0을 재기록한 뒤 준비 콜백을 호출한다

135개 청크 이후의 op 5에 성공값 0을 공급하면 원본 호출자는 확장 헤더의 임시 버퍼를 해제하고 블록 0의 256섹터를 읽습니다. 이어 블록 0 지우기와 256섹터 쓰기를 요청합니다. 읽기 모델은 처음 블록 0 기록 함수에 넘겼던 전체 데이터와 16바이트 spare를 돌려줍니다. 이 재실행에서는 원본 호출자의 후속 처리를 확인했습니다. NAND에 데이터가 실제로 보존되는지는 검증 범위 밖입니다. [B3: all-success·modeled_finalization]

최종 쓰기 버퍼는 읽은 데이터의 +0x39c~+0x39f만 바뀌었습니다. 원본 0x80014874가 리틀엔디언 0xffffffff를 확장 헤더의 첫 성공 물리 블록 번호 10으로 교체합니다. 같은 4바이트를 별도로 바꾼 뒤 131,072바이트 버퍼 전체를 관측 버퍼와 대조했습니다. 두 버퍼는 일치했으며 SHA-256은 ce8b5a7ef4d8d173b014dd27f085c1b326b998ab842044f59a03ebf30518e038입니다. spare는 읽기 모델이 돌려준 값 그대로입니다. [B4: 독립 버퍼 재구성]

마지막 쓰기에 성공값 0을 공급하면 원본은 블록 맵과 주 버퍼의 해제를 요청한 뒤 0x80019390의 준비 콜백을 호출합니다. 이 콜백은 두 명령으로 구성되며 반환값은 1입니다. 원본 0x80014d80~0x80014d88이 이를 BurnNand 반환값 0으로 바꿉니다. 호출자의 스택 포인터 복원도 확인했습니다. 이 소프트웨어 반환은 수정 펌웨어의 수용이나 부팅 결과를 뜻하지 않습니다. [B3: native_status_sites·원본 워드]

확장 헤더 쓰기, 블록 0 읽기, 최종 블록 0 쓰기에 각각 오류 7을 공급한 세 사례는 준비 콜백 없이 반환값 1로 끝났습니다. 읽기 실패 뒤에는 지우기나 재기록 요청이 없었습니다. 해제 요청의 실제 인수도 기록했습니다. 확장 헤더 쓰기가 실패한 사례에서는 해당 임시 버퍼의 해제 요청이 반환 전에 나타나지 않았습니다. 다만 해제 함수는 모델이므로 함수 밖의 수명 관리나 실제 누수를 확정하지 않습니다. 지우기 실패는 이 네 사례에 포함하지 않았습니다. [B3: 세 오류 사례·free_calls]

06 / K-3 MARK III COMPARISON

완료 단계와 기록 단계의 근거를 따로 비교한다

K-3 Mark III의 고정 커밋 자료는 업데이트 래퍼가 실행기의 결과를 반환하고 입력 해제와 완료 알림을 처리하는 경로를 구분합니다. Q7에서는 블록 0 재기록 뒤 준비 콜백 1을 BurnNand 반환값 0으로 변환하는 구간을 원본 실행으로 확인했습니다. 완료 단계라는 비교 항목은 같지만 함수별 반환값의 의미는 따로 확인해야 합니다. 두 기종의 op 번호나 성공 규약이 같다고 판단하지 않습니다. [K1: 고정 커밋의 업데이트 종료 근거]

07 / ORIGINAL CODE AND MODELED DEVICE

호출자 검증의 경계를 남긴다

재시도 7사례의 116개 워드·9개 코드 범위에 더해 종료 4사례의 63개 워드·2개 코드 범위를 원본과 대조했습니다. 코드 범위에는 앞선 BurnNand와 겹치는 부분이 있습니다. 저장장치 형상·spare·API 반환은 합성 입력이며 종료 사례는 동일한 주 페이로드 경로의 상태에서 시작합니다. 실제 플래시의 기록·읽기 비교·보호·복구, 수정 펌웨어의 수용·부팅·촬영은 미검증입니다. 공개 저장소에는 재현 도구와 주소·해시만 두고 원본 및 수정 이미지와 전체 디컴파일은 게시하지 않았습니다. [B1: limits]
