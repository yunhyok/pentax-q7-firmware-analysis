01 / EXACT INTEGER CONTRACT

32비트 넘침과 하위 16비트를 보존한다

원본은 두 행렬의 부호 있는 16비트 원소를 곱한 뒤 누산값에 0x1000을 32비트로 더합니다. 이후 논리 우측 이동 13을 적용하고 하위 16비트를 저장합니다. C에서도 누산을 부호 없는 32비트로 표현해 넘침과 반올림의 비트 동작을 보존했습니다. 이 함수는 색 처리 계수 준비에 쓰이며 픽셀별 실행 증거는 아닙니다. [C1: arithmetic]

acc = (0x1000 + Σ int16(left[r,k]) × int16(right[k,c])) mod 2^32
out[r,c] = (acc >> 13) & 0xffff

원본은 출력 쓰기 전에 두 입력을 스택으로 복사합니다. 재구성한 C는 모든 결과를 계산한 뒤 출력하므로 입력과 출력이 겹쳐도 계산 중 입력을 바꾸지 않습니다. 동일 포인터, 앞뒤 부분 겹침과 세 버퍼의 부분 겹침을 포함한 8개 배치를 검사했습니다. 동시 접근이 없는 halfword 정렬 RAM이 이번 검증의 입력 조건입니다. [C2: fixtures·leaf_fixture]

8종 경계 입력 × 8개 배치와 seed 804113의 난수 32사례입니다. 원본·교체본 각각에서 출력 halfword 쓰기 864회를 순서대로 비교했습니다. 입력 겹침으로 달라진 실제 입력을 읽은 뒤 산술 기준값을 계산했습니다. [재구성 C 소스]

02 / ISA, ABI AND PLACEMENT

호출 규약과 코드 크기를 먼저 검사한다

원본 E03·E04의 ELF 헤더와 재컴파일 객체는 모두 little-endian MIPS32 계열이며 e_flags는 0x70001001입니다. 재컴파일 대상은 MIPS32r2와 O32로 고정했습니다. 원본 carrier에는 부동소수점 ABI 태그가 없으므로 전체 펌웨어의 ABI를 확정하지 않았습니다. 선택한 함수는 정수 포인터를 받고 COP1 명령을 사용하지 않습니다. [C1: abi]

컴파일한 text는 164바이트로 원본 함수의 236바이트 범위 안에 들어갑니다. 원래 진입 주소에 이 코드만 덮어쓰고 나머지 72바이트는 보존했습니다. 실행 경계 검사에서 남은 원본 꼬리에 진입하지 않았음을 확인했습니다. 외부 import와 text 재배치는 없으며 다른 함수의 배치 가능성까지 입증한 것은 아닙니다. [C2: build·overlay]

zig cc -target mipsel-freestanding-none -mcpu=mips32r2+noabicalls
  -mabi=o32 -mfp32 -fno-pic -G0 -std=c11 -ffreestanding
  -fno-builtin -fno-stack-protector -fno-unwind-tables
  -fno-asynchronous-unwind-tables -ffunction-sections -Oz
  -Wall -Wextra -Werror -c -x c - -o q7_numeric.o

재컴파일 객체의 .MIPS.abiflags는 ISA32 revision2·GPR32·FP32·FP ABI attribute1입니다. .rel.pdr은 비적재 procedure descriptor에만 존재하며 text에는 재배치가 없습니다. 원본의 e_flags가 나타내는 MIPS32r2 계열·O32·NOREORDER 의미는 LLVM ELF 정의와 대조했습니다.

03 / ORIGINAL CALLER EQUIVALENCE

기존 MakeColorMatrix 안에서 대조한다

MakeColorMatrix는 원래 진입점에서 실제 반환까지 실행했습니다. sRGB의 두 설정 사례는 각각 14회, AdobeRGB의 두 사례는 각각 15회 Q13 함수를 호출했습니다. 두 코드 이미지에서 호출 위치·인자·입력 해시, 출력 버퍼와 scratch, 비스택 쓰기 순서를 비교했습니다. 호출부의 분기를 강제로 바꾸거나 하위 함수를 대체하지 않았습니다. [C1: caller·replay.caller_cases]

04 / COMPRESSED-PACKAGE BOUNDARY

원래 테이블과 슬롯 안에서 다시 인코딩한다

코드 영역에 들어가는 것과 압축 패키지에 들어가는 것은 별도 조건입니다. 기존 토큰·테이블·슬롯을 보존하는 재패킹에서 변경된 코드에는 9,916바이트가 필요했습니다. 9,856바이트 슬롯을 넘었습니다. 도구는 출력 전에 거부했습니다. 이 실패는 기존 토큰 보존 방식의 한계이며 다른 압축 방식으로도 불가능하다는 뜻은 아닙니다. [C1: package_attempt]

native function slot: 164 ≤ 236 bytes → in-memory placement PASS
literal repair: 9,916 > 9,856 bytes → rejected
fixed-table windows: 9,853 ≤ 9,856 bytes → software decode PASS
camera update / NAND write / boot: not executed

위 실패 이후 제한된 창에 대한 동적 계획법을 추가했습니다. 원래 테이블에서 가능한 리터럴·길이·거리 표현의 비트 수를 비교하며, 슬롯 크기나 파일 offset은 변경하지 않습니다. 블록 전체의 후보 수가 1,000,000개를 넘으면 출력 전에 거부합니다. [재패커]

후속 검증에서는 원래 테이블을 그대로 두고 교체 범위와 겹치는 토큰을 한 창에서 다시 구성했습니다. 창 밖에서 무효가 된 복사 토큰도 각각 고쳤습니다. E04의 154번 블록은 78,817비트(9,853바이트)로 줄어 9,856바이트 슬롯에 들어갔습니다. 슬롯 끝에는 0비트 31개가 남습니다. [C1: package_rebuild.blocks]

155번 블록의 한 복사 토큰은 앞 블록의 교체 범위를 참조합니다. 이 토큰을 그대로 두면 요청하지 않은 2바이트 차이가 생기므로 원래 리터럴 표현으로 보정했습니다. 전체 448블록을 다시 디코딩해 보니 실제 차이 142바이트는 164바이트 교체 범위 안에만 있었습니다. 나머지 446블록과 두 변경 블록의 헤더·테이블·슬롯 크기는 보존했습니다. [고정 테이블 창 인코더]

재패킹에서 다시 만든 분석 ELF는 96개 함수·4개 호출부 사례에서 실행한 교체 이미지와 바이트 단위로 일치합니다. 패키지는 비공개 연구 경로에만 생성했습니다. 코드와 테이블의 소프트웨어 디코딩 일치는 카메라의 하드웨어 inflate나 업데이트 수용을 입증하지 않습니다. [패키지 독립 재현]

05 / K-3 MARK III COMPARISON

같은 검증 항목, 서로 다른 호출·패키지 조건

K-3 Mark III의 C 재컴파일·원본 호출부·재패킹 자료와 같은 검증 항목으로 대조했습니다. 해당 자료는 ARM A32용 Q13 함수의 오프라인 패키지 삽입까지 다룹니다. Q7은 MIPS 호출 규약과 입력 겹침을 따로 검증했으며 기존 토큰 보존 방식은 압축 슬롯 용량 초과로 거부됐습니다. 두 기종 모두 카메라 인식·기록·부팅을 입증한 결과는 아닙니다.

06 / REPRODUCTION AND LIMITS

독립 실행과 공개 가능한 근거

96개 함수 사례와 4개 호출부 사례는 모든 설정이나 실행 환경의 동등성을 보장하지 않습니다. 인터럽트·동시성·캐시·실제 프로세서 타이밍은 검증하지 않았고 부동소수점 인자를 받는 새 함수에도 이 결과를 일반화할 수 없습니다. 수정 펌웨어는 배포하지 않으며 카메라에는 기록하지 않았습니다. [C1: limitations]

작업자와 조정자가 각각 컴파일하고 96개 함수·4개 호출부 사례를 재실행해 메타데이터 전체가 일치했습니다. 원본에서 35개 word와 7개 함수 범위의 해시·전이를 다시 계산했습니다. 원본 전체 코드나 컴파일 객체는 공개하지 않습니다.
