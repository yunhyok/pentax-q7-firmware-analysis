색 행렬 곱 함수를 C로 다시 만들어 원래 자리에 넣기

펌웨어를 고치려면 원본과 똑같이 동작하는 코드를 직접 만들 수 있어야 하고, 그 코드를 압축된 업데이트 파일에 다시 넣을 수 있어야 합니다. 색 변환 행렬을 곱하는 작은 함수 하나로 두 가지를 모두 시험했습니다.

이 문서에서

  1. 배경: 왜 작은 계산 함수 하나로 시험하는가
  2. 함수가 하는 계산과 96개 입력의 결과
  3. 컴파일 조건과 원래 자리에 넣기
  4. 원본 호출 함수 안에서도 결과가 같습니다
  5. 압축된 업데이트 파일의 원래 블록 자리에 다시 넣기
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 색 변환 계수를 준비할 때 쓰는 Q13 3×3 행렬 곱 함수를 C로 새로 작성해 MIPS 기계어로 컴파일했습니다. 새 코드는 164바이트이고, 원본 함수 구간 236바이트 안에 들어갑니다.
  • 원본 코드와 새 코드를 PC 에뮬레이터에서 같은 입력 96개로 실행했습니다. 출력과 쓰는 순서가 모두 같았습니다. 이 함수를 부르는 원본 MakeColorMatrix 안에서도 설정 4개(행렬 곱 호출 58회)의 결과가 같았습니다.
  • 새 코드를 압축된 업데이트 파일에 넣는 첫 시도는 블록 자리보다 60바이트가 커서 실패했습니다. 원래 부호표를 그대로 쓰면서 바뀐 부분만 다시 인코딩하는 방법으로 자리에 맞췄습니다. 448개 블록을 모두 다시 풀어, 바꾸려던 164바이트 범위 밖은 한 바이트도 달라지지 않았음을 확인했습니다.
  • 수정한 파일은 공개하지 않고 연구용 비공개 경로에만 둡니다. 카메라에 넣은 적이 없으며, 카메라가 이 파일을 받아들이는지와 부팅하는지는 확인하지 않았습니다.

확인 원본 코드 실행·파일 대조로 확인

  • 함수 96사례에서 출력과 16비트 쓰기 864회의 순서가 일치
  • 원본 호출 함수 4사례에서 호출 인수, 출력 버퍼, 쓰기 순서가 일치
  • 보존 레지스터, 스택 포인터, 복귀 주소, 다섯째 스택 인수가 그대로
  • 다시 만든 파일의 448블록을 모두 풀어 바이트와 배치를 대조
  • 원본 워드 35개와 함수 구간 7개를 주소·해시로 대조

정적 분석 코드를 읽어 판단

  • 원본 ELF 헤더의 플래그가 뜻하는 명령 체계와 호출 규약
  • 원본 MakeColorMatrix 구간에 HI/LO를 읽는 명령이 없음

모델 시험 조건으로 정한 것

  • 입력 행렬: 경계값 8종을 버퍼 배치 8가지로, 난수 32개
  • 호출 함수에 준 합성 설정 객체 4개
  • CPU와 메모리: angr/VEX 에뮬레이터와 합성 RAM

미확인 확인하지 않은 것

  • 다른 픽처 스타일과 선택 객체가 있는 분기
  • 인터럽트, 동시 접근, 캐시, 실제 프로세서의 실행 시간
  • 카메라의 압축 해제, 업데이트 수용, NAND 기록, 부팅
  • 다른 함수도 이렇게 넣을 수 있는지

배경: 왜 작은 계산 함수 하나로 시험하는가

제조사의 원본 소스 코드는 공개되어 있지 않습니다. 펌웨어를 고치는 방법은 두 가지입니다. 기계어 몇 바이트를 직접 바꾸거나, 함수를 C로 새로 작성해 컴파일한 결과로 원본 함수를 대체하는 것입니다. 두 번째 방법이 유지하기 쉽지만, 아래 순서로 확인할 것이 있습니다.

  1. 같은 결과를 내는가원본과 새 코드를 같은 입력으로 실행해 비교 — 함수, 호출 함수
  2. 제자리에 들어가는가함수 자리와 호출 규약 — 컴파일과 배치
  3. 업데이트 파일에 들어가는가압축 블록 자리의 크기 — 재패킹
  4. 카메라가 받아들이는가확인하지 않음

시험 대상은 다른 함수를 부르지 않고 계산만 하는 작은 함수(leaf 함수)입니다. 입력과 출력이 분명해서 원본과 나란히 실행해 비교하기 쉽습니다. 같은 실험을 K-3 Mark III에서도 했습니다. 그쪽 기록은 수치 함수 두 개를 C로 다시 만들어 원본과 대조하기에 있습니다.

읽는 데 필요한 말

  • Q13 고정소수점: 소수를 정수로 다루는 방법입니다. 실제 값에 8,192(213)를 곱해 16비트 정수로 보관합니다. 이런 값 둘을 곱하면 8,192가 한 번 더 곱해진 결과가 나오므로, 곱한 뒤 반올림하고 13비트를 내립니다.
  • 호출 규약(o32): 함수가 인수를 어느 레지스터로 받고 어떤 레지스터를 보존해야 하는지 정한 약속입니다. 32비트 MIPS의 o32 규약에서는 인수 넷까지 a0~a3로, 그 뒤는 스택으로 넘깁니다. 호출 뒤에도 값이 남아 있어야 하는 범용 레지스터는 $16~$23(s0~s7)과 $28~$30(gp, sp, s8)뿐입니다. [System V ABI MIPS 보충판 3판, 3장]
  • 압축 블록과 블록 자리: 업데이트 파일 안에서 본 프로그램은 압축 구간 4곳, 블록 448개로 나뉘어 있습니다. 블록마다 파일 안에서 차지하는 자리의 크기가 정해져 있습니다. 블록의 압축 비트열은 바이트를 그대로 적는 리터럴과 앞의 내용을 가져오는 복사 토큰의 나열이고, 블록마다 딸린 부호표로 적혀 있습니다. 자세한 설명은 재패킹 검증과 업데이트 검사에 있습니다.

함수가 하는 계산과 96개 입력의 결과

새 C 코드는 96개 입력 모두에서 원본과 같은 바이트를 같은 순서로 썼습니다. 넘침과 반올림, 입력과 출력이 겹치는 경우까지 포함합니다.

대상 함수는 ColorMatchingService_MatrixMultiplication입니다. 인수는 포인터 셋으로, 출력 행렬, 왼쪽 행렬, 오른쪽 행렬의 순서입니다. 행렬은 행 우선으로 놓인 부호 있는 16비트 값 9개입니다. 원소마다 다음을 계산합니다.

acc = (0x1000 + Σ int16(left[r,k]) × int16(right[k,c])) mod 2^32
out[r,c] = (acc >> 13) & 0xffff
  • 세 곱의 합에 0x1000(4,096, Q13에서 0.5)을 더합니다. 합은 32비트로 잘립니다.
  • 오른쪽으로 13비트 논리 시프트한 뒤 하위 16비트를 저장합니다. 결과가 16비트를 넘어도 최댓값으로 고정하지 않습니다.
  • C에서는 누산을 부호 없는 32비트로 적어 넘침과 반올림이 원본과 비트까지 같게 했습니다.

이 함수는 색 처리 계수를 준비할 때 쓰입니다. 픽셀마다 실행된다는 증거는 아닙니다. [근거: arithmetic] · [새로 작성한 C 소스]

입력과 출력이 겹쳐도 같은 결과

원본은 출력을 쓰기 전에 두 입력을 스택에 복사해 둡니다. 그래서 출력 버퍼가 입력 버퍼와 겹쳐도 계산 도중에 입력이 바뀌지 않습니다. 새 C 코드는 아홉 원소를 모두 계산한 뒤에 출력하는 방식으로 같은 성질을 지킵니다. 이를 확인하려고 경계 입력 8종을 버퍼 배치 8가지로 실행하고, 난수 32개를 배치에 고루 나눠 실행했습니다.

컴파일 조건과 원래 자리에 넣기

새 코드는 원본과 같은 명령 체계·호출 규약으로 컴파일했고, 164바이트여서 원본 함수 구간 236바이트의 앞부분만 차지합니다.

컴파일 조건

컴파일러는 Zig 0.15.2에 든 C 컴파일러(Clang 20.1.2)입니다. 대상은 리틀엔디언 MIPS32r2, o32 호출 규약으로 고정했고, 크기를 줄이는 최적화(-Oz)를 썼습니다.

zig cc -target mipsel-freestanding-none \
  -mcpu=mips32r2+noabicalls -mabi=o32 -mfp32 -fno-pic -G0 \
  -std=c11 -ffreestanding -fno-builtin -fno-stack-protector \
  -fno-unwind-tables -fno-asynchronous-unwind-tables \
  -ffunction-sections -Oz -Wall -Wextra -Werror -c -x c - \
  -o q7_numeric.o
  • 원본 E03·E04의 ELF 헤더와 새로 만든 객체 파일은 모두 32비트 리틀엔디언 MIPS이고 e_flags가 0x70001001로 같습니다. 이 값은 MIPS32r2 계열(0x70000000), o32(0x1000), NOREORDER(0x1)를 합친 것입니다. [LLVM의 ELF 정의]
  • 새 객체의 .MIPS.abiflags는 ISA 32 리비전 2, 32비트 범용 레지스터, 32비트 부동소수점 레지스터, 부동소수점 ABI 속성 1을 적고 있습니다. 원본 ELF에는 부동소수점 ABI를 적은 곳이 없습니다. 그래서 펌웨어 전체의 ABI는 확정하지 않았습니다. 이 함수는 정수 포인터만 받고 부동소수점 명령을 쓰지 않습니다.
  • 새 코드에는 밖의 함수를 부르는 곳이 없고, 코드 영역에 재배치 항목도 없습니다. 재배치 항목 하나(.rel.pdr)는 메모리에 올리지 않는 정보 구역에만 있습니다.

[근거: abi, replay.build]

원래 자리에 넣기

236바이트는 이 함수의 시작부터 다음 심볼 앞까지의 구간입니다. 컴파일한 코드를 원래 진입 주소에 덮어쓰고 나머지 72바이트는 건드리지 않았습니다. 실행 범위 검사에서 새 코드가 남은 꼬리로 들어가지 않는 것을 확인했습니다. 이 결과는 부르는 함수도 데이터도 없는 이 함수에 한정됩니다. 다른 코드를 이렇게 놓을 수 있다는 뜻은 아닙니다.

HI/LO 레지스터는 값이 다릅니다

출력과 메모리는 같았지만 곱셈 결과가 남는 HI/LO 레지스터의 값은 달랐습니다. 모든 원소가 −32,768이고 세 버퍼가 떨어져 있는 사례에서, 18바이트 출력은 같았습니다. 그런데 함수가 끝났을 때 (HI, LO)는 원본이 (0, 0xc0000000), 새 코드가 (0, 0)이었습니다.

o32 규약에서 HI/LO는 호출 뒤에 보존되는 레지스터가 아닙니다. 원본 MakeColorMatrix 구간에도 이 값을 읽는 명령(MFHI, MFLO)이 없습니다. 다만 이 결과는 검사한 출력, 메모리, 호출 규약의 범위에서만 같다는 뜻입니다. 다른 호출 함수, 보존 대상이 아닌 레지스터, 쓰지 않는 스택 바이트, 기계 상태 전체가 같다고 보지 않습니다. [근거: replay.machine_state_probe]

원본 호출 함수 안에서도 결과가 같습니다

행렬 곱 함수를 실제로 부르는 원본 MakeColorMatrix를 처음부터 끝까지 실행했습니다. 네 설정에서 호출 58회의 인수와 그 뒤의 쓰기가 두 이미지에서 모두 같았습니다.

MakeColorMatrix(0x8041c180)는 색공간과 픽처 스타일 설정에 따라 여러 행렬을 차례로 곱합니다. 원래 진입점에서 실제 반환까지 실행했고, 아래 단계의 함수를 대체하거나 분기를 강제로 바꾸지 않았습니다. 원본의 색상 회전 함수와 조회 표도 그대로 썼습니다. 실행은 관찰만 하는 방식으로 기록했습니다.

이 네 설정이 모든 픽처 스타일이나 둘째 객체가 있는 분기를 지나가는 것은 아닙니다. 확인한 것은 함수가 주고받는 값의 범위에서 같다는 것이며, 영상의 픽셀이나 카메라에서의 실행은 다루지 않았습니다. [근거: caller, replay.caller_cases] · [재현 도구: replay_caller]

압축된 업데이트 파일의 원래 블록 자리에 다시 넣기

함수 자리에 들어가는 것과 압축 블록 자리에 들어가는 것은 다른 문제입니다. 첫 방법은 60바이트가 모자랐고, 바뀐 부분만 다시 인코딩하는 방법으로 3바이트를 남기고 들어갔습니다.

코드를 바꾸면 그 블록의 압축 비트열도 바뀝니다. 바뀐 자리의 리터럴이 달라지고, 그 자리를 가져다 쓰던 복사 토큰이 틀린 내용을 가리키게 됩니다. 고친 비트열이 블록 자리보다 길어지면 파일의 배치를 바꾸지 않고는 넣을 수 없습니다.

  1. 첫 시도: 틀어진 토큰을 리터럴로 바꾸기 기존 토큰·부호표·자리를 그대로 두고, 틀어진 복사 토큰만 리터럴로 풀어 쓰는 기존 재패킹 도구를 썼습니다. 바뀐 코드에는 9,916바이트가 필요했고 자리는 9,856바이트였습니다. 도구는 파일을 쓰기 전에 거부했습니다. 이 실패는 이 방법의 한계이며, 다른 압축 방법으로도 안 된다는 뜻이 아닙니다.
  2. 창 재인코딩 원래 부호표는 그대로 두고, 바뀐 범위와 겹치는 토큰들을 “창” 단위로 묶어 다시 구성했습니다. 창마다 원래 부호표로 적을 수 있는 리터럴·길이·거리 표현의 비트 수를 비교해 가장 짧은 조합을 고릅니다(동적 계획법). 블록 154는 창 21개에서 토큰 102개를 새로 구성했고, 새 복사 토큰 48개 가운데 16개는 앞 블록의 내용을 가리킵니다. 창 밖에서 틀어진 복사 토큰도 따로 고쳤습니다. 결과는 78,817비트(9,853바이트)이고, 자리 끝에 0비트 31개가 남습니다.
  3. 다음 블록의 참조 고치기 블록 155의 복사 토큰 하나가 앞 블록의 바뀐 범위를 가리킵니다. 그대로 두면 바꾸려던 곳 밖에서 2바이트가 달라집니다. 이 토큰을 원래 내용의 리터럴로 바꿨습니다.
  4. 전체 확인 448블록을 모두 다시 풀었습니다. 원본과 달라진 142바이트는 전부 바꾸려던 164바이트 범위 안에 있었습니다. 나머지 446블록과, 두 블록의 헤더·부호표·자리 크기는 그대로입니다. 파일 길이도 18,743,520바이트로 같습니다.

주의

한계와 재현 방법

  • 함수 96사례와 호출 함수 4사례가 모든 설정과 실행 환경에서 같다는 것을 보장하지는 않습니다.
  • 인터럽트, 동시 접근, 캐시, 실제 프로세서의 실행 시간은 확인하지 않았습니다. 새 C 코드는 원본의 명령 순서나 스택 내용까지 따라 하지 않습니다.
  • 부동소수점 인수를 받는 함수에는 이 결과를 넓혀 적용할 수 없습니다.
  • 재패킹은 원래 부호표, 블록 자리, ELF 안의 위치, 파일 크기를 지키는 범위에서만 됩니다. 코드를 다른 곳으로 옮기거나 부호표를 새로 만드는 일은 하지 않습니다.
  • 수정한 펌웨어는 배포하지 않으며 카메라에 기록하지 않았습니다. 원본 코드 전체와 컴파일한 객체 파일도 공개하지 않습니다.

컴파일과 96 + 4사례의 실행은 서로 독립해서 두 번 했고, 기록 전체가 같았습니다. 원본에서 워드 35개와 함수 구간 7개의 해시·분기를 다시 계산했습니다. 실행 엔진은 angr 10.0.5 / VEX입니다.
