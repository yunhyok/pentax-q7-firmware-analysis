# 2026년 11월 문서 검수 기록 — Q7

v0.2.0에서 HTML 문서를 다시 쓰면서 페이지마다 내용을 검수했습니다. 이 문서는 그 결과입니다. 무엇을 어떻게 확인했는지, 무엇을 고쳤는지, 저장소 주인의 판단이 필요한 것은 무엇인지 적었습니다.

## 검수 방법과 한계

- 개편 전 HTML의 수치·주소·해시·사례 수를 그 페이지가 근거로 삼는 JSON(`analysis/*.json`)과 검사 스크립트(`tools/check_*.py`, `tools/verify_*.py`)에 대조했습니다. 합계는 다시 계산했습니다.
- 보고서는 템플릿과 근거 JSON에서 만들어집니다. 이번에 표와 합계를 되도록 빌더가 JSON에서 직접 만들도록 바꿨고, 템플릿에 손으로 적은 숫자는 빌더가 JSON과 같은지 확인합니다. 숫자가 근거와 어긋나면 문서 생성이 멈춥니다.
- 사용설명서의 메뉴 이름, 규격, 공개 소스의 상수 같은 외부 사실은 1차 자료로 확인했습니다.
- 개편 전 문서에 있던 16진수·해시·큰 수·식별자가 새 문서에 남아 있는지 도구로 비교했습니다. 빠진 것은 이유를 확인했습니다.
- **하지 못한 것**: 이 작업 환경에는 원본 펌웨어가 없습니다. 그래서 검사 스크립트를 원본 펌웨어에 다시 돌리지 못했습니다. "근거 JSON과 일치한다"는 말은 공개된 JSON·스크립트와 맞는다는 뜻이며, 펌웨어 바이트를 다시 확인했다는 뜻이 아닙니다. 펌웨어 없이 도는 검사(`tools/verify_report.py`, 단위 시험)는 통과했습니다.

수치·주소·해시에서는 오류를 찾지 못했습니다. 고친 것은 메뉴 이름 하나, 링크와 꼬리표, 잘못 읽히기 쉬운 표현 두 곳, 그리고 뒤 문서가 이미 해결했거나 좁힌 서술입니다.

## 판단이 필요한 항목

근거가 부족해 고치지 않았거나, 이번에 새로 넣은 해석이라 빼도 되는 것들입니다.

**해석의 수위**

- FC1 필터의 역할. HDR 경로에서 FC1이 받는 계수 9개를 2048로 나누면 RGB를 YCbCr로 바꾸는 계수(ITU-R BT.601, JFIF)와 항목마다 1/2048 미만의 차이로 맞습니다. 펌웨어 안의 내장 계수 이름도 "ITU-R 601/709 RGB-to-YUV"입니다. 그래서 FC1을 색 변환 단계로 "보인다"고 적었습니다. 분모 2048, 행의 순서, 보조값의 뜻은 회로 문서로 확인한 것이 아닙니다.
- `pixel-report.html`: 버퍼 주소에 `0x20000000`을 더하는 연산은 MIPS의 kseg0 주소를 캐시를 거치지 않는 kseg1 주소로 바꾸는 것으로 읽힙니다. 측정 근거는 없어 "해석"으로 표시했습니다.
- 리코는 HDR을 노출이 다른 세 장의 합성이라고 설명합니다. 펌웨어에서 입력 장 수는 추적하지 않았습니다.
- HDR 메뉴의 선택지(Auto / HDR 1 / HDR 2)와 내부 설정 ID `0x1f`("보조 설정")의 대응은 확인하지 않았습니다.
- `guide-af.html`: 콘트라스트 AF가 "언덕 오르기" 방식으로 동작한다는 설명은 일반적인 배경 지식입니다. 펌웨어에서 확인한 것은 대비 값 배열에 포물선을 맞추는 계산입니다. `WobbCalcFocus`가 워블링이라는 것은 이름에서 추정했습니다.
- `main-burn-prefix-report.html`: 매체 열기 결과를 `0xf1`과 비교하는데, 이 값의 뜻을 모릅니다. FileX 드라이버 요청 번호와 seek 옵션은 지금 공개된 FileX 헤더에 대조했습니다. 2013년 당시 버전은 확인하지 못했습니다.
- `loader-lens-report.html`: 속도 상수 `0x3b888889`가 1/240에 가깝다는 것은 이번에 계산해 넣은 것입니다.
- `update-service-report.html`: MAIN의 HostAck 콜백과 E01의 준비 확인 콜백이 같은 SHA-256(앞 8바이트)을 가진다는 관찰은 이번에 넣은 것입니다. 빌더가 근거 JSON으로 확인합니다.
- E01이 언제 실행되는지, MAIN의 업데이트 경로와 어떻게 이어지는지는 모릅니다. E01은 "별도 실행 파일(로더)"로만 불렀습니다.
- `deep-report.html`: "CP0 EBase의 하위 10비트가 1"이라는 조건은 해석하지 않고 그대로 두었습니다.
- `colorspace-ui-report.html`: "GUI 컴포넌트 26개"는 근거 JSON에서 찾지 못했습니다. 위젯 ID 범위 `0x0191d000`–`0x0191d019`의 개수와는 맞습니다.

**이번 개편에서 새로 넣은 비교** (모두 "Q7에서 확인하지 않음"이라고 한정했습니다. 원 연구 범위만 남기려면 해당 참고 상자를 지우면 됩니다.)

- `burn-continuation-report.html`: 예비 영역의 +4, +5 자리가 SmartMedia(SSFDC) 규격의 데이터 상태·블록 상태 자리와 같다는 것.
- `storage-readiness-report.html`: 지우기 경로의 `0xd0`이 표준 NAND 지우기 명령의 둘째 바이트와 같은 값이라는 것.
- `loader-hash-report.html`: 파티션 항목의 자리 이름(BootIndicator, OSType, StartingLBA, SizeInLBA)을 UEFI 규격의 MBR 설명에서 가져온 것.
- `recompiled-numeric-report.html`: "새 코드 164바이트 가운데 22바이트는 원본과 값이 같다"는 164 − 142에서 계산한 문장이며 JSON에 직접 적힌 값이 아닙니다. "236바이트"는 ELF의 함수 크기가 아니라 다음 심볼 앞까지의 구간이어서 그렇게 적었습니다.

**용어와 단위**

- 설치 헤더의 `+0x310`, `+0x314` 필드를 `loader-foundation.json`은 "User physical start / User actual sectors"라고 부르는데, `loader-storage.json`과 코드는 블록 번호(640, 384)로 씁니다. 문서에는 "사용자 영역의 시작·길이(블록)"로 적었습니다.
- 같은 바이트를 `loader-lens-report.html`은 "map-read-OK", `storage-readiness-report.html`은 "표 준비 플래그(map_ready)"라고 부릅니다.

**세 문서가 서로 다른 K-3 Mark III 커밋을 가리킴**

- `final-color-report.html`, `hdr-control-report.html`, `hdr-task-report.html`의 비교 절이 각각 다른 커밋을 고정해 인용합니다. 조사 시점이 달라서 생긴 것으로, 의도된 고정입니다.

**그 밖에**

- 리코의 펌웨어 사용 조건에는 수정·리버스 엔지니어링을 제한하는 조항이 있습니다. 공개 범위에 대한 판단은 저장소 주인의 몫입니다.
- 첫 화면의 카메라 사진은 Wikimedia Commons의 CC BY 4.0 그림입니다. 원본이 작고(583×470), 파일 설명의 저작자 표기와 올린 사람의 이름이 다릅니다. 더 확실한 사진이 있으면 바꾸는 편이 좋습니다. 출처는 `assets/photos/CREDITS.md`에 적었습니다.

## 외부 자료로 확인한 사실 (요약)

- 펌웨어 1.01은 2013-12-05 배포. 변경 내용 네 가지와 설치 절차 (리코 다운로드 페이지).
- Q7: 1/1.7인치 이면조사 CMOS, Q ENGINE, 콘트라스트 검출 AF, 3.0인치 약 46만 도트 LCD, HDR(노출이 다른 세 장 합성), sRGB/AdobeRGB (리코 보도자료와 사용설명서).

- AF가 되는 렌즈는 01·02·06·08, 수동 초점은 03·04·05·07과 Adapter Q (리코 FAQ와 제품 자료).
- ThreadX와 FileX: Express Logic 제품, 2019년 Microsoft 인수, 2024년부터 Eclipse ThreadX로 공개. 초기화 순서와 FileX 상수 (공개 소스).
- MIPS: JAL 명령의 뜻, 지연 슬롯, kseg0·kseg1 주소 구간 (MIPS 아키텍처 문서, NetBSD `cpuregs.h`).
- ITU-R BT.601의 휘도식, JFIF의 YCbCr 변환식.
- NAND 플래시의 READ ID 명령과 예비 영역, 지우기 명령 바이트, SmartMedia의 예비 영역 배치 (Linux 커널 소스와 문서). ELF 헤더 상수와 MIPS `e_flags` 값, MD5(RFC 1321), MBR 파티션 표(UEFI 규격).
- MIPS o32 호출 규약의 인수 레지스터와 보존 레지스터. 규격의 원래 게시처를 열지 못해 같은 문서의 사본으로 확인했습니다.

## 2026-11-13 후속 대조

v0.2.0 ZIP의 218개 파일이 태그의 Git 바이트와 일치했습니다. 다음 게시에서는 원격의 기존 일반·주석 태그가 현재 커밋을 가리키는지 검사하고, 원격 조회 실패도 거부합니다. 보고서 생성과 탐색 검사는 해당 저장소의 Git 체크아웃에서 실행하도록 명시하고 검사합니다.

글자 크기 요청, 합성 렌더링, 합성 등록표의 컨텍스트 선택을 구분했습니다. JFIF 비교는 계수에 2048을 곱한 값과 펌웨어 정수값의 비교로 단위를 맞췄습니다. MAIN Burn의 설치 헤더 응답은 원본 패키지의 페이로드 `0x1000c0`에서 빌린 합성 입력입니다. 기존 근거 JSON과 실행 검증기는 유지했습니다.

단위 시험 51개, 전체 HTML 재생성과 출판 검사가 통과했습니다. 실제 NAND 내용이나 화면 출력, 카메라 부팅을 새로 확인한 결과는 아닙니다.
