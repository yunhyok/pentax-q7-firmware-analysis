MAIN Burn의 첫 구간: 매체 열기와 설치 헤더 요청

본 프로그램의 기록 함수 Burn은 NAND에 쓰기 전에 먼저 저장 매체를 열고, 이미 설치된 헤더를 읽고, 카드에서 첫 덩어리를 읽습니다. 이 앞부분을 서로 다른 두 조건에서 원본 코드로 따라갔습니다.

이 문서에서

  1. 배경: 기록 함수가 쓰기 전에 하는 준비
  2. 두 시험의 출발점은 앞 문서에서 관측한 호출 인수입니다
  3. 시험 1: 원본 매체 열기는 BurnNand보다 먼저 NAND에 요청을 보냅니다
  4. 시험 2: 열기 결과를 넣어 주면 설치 헤더를 읽고 카드 읽기에 들어갑니다
  5. MAIN과 E01의 BurnNand는 닮았지만 같은 코드가 아닙니다
  6. 한계와 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 시험 1 — 저장 매체를 여는 원본 코드를 그대로 실행하면, NAND 기록 함수가 불리기도 전에 NAND에 식별 정보를 묻는 요청이 먼저 나옵니다. 실행은 그 요청 직전에서 멈췄습니다. 장치의 응답은 넣지 않았습니다.
  • 시험 2 — 열기 결과와 저장장치 크기를 모델로 넣어 주면, 원본 BurnNand가 설치된 헤더를 읽으려고 요청 두 개를 차례로 보냅니다. 모델이 답하자 카드에서 첫 128KiB를 읽는 함수에 진입했고, 거기서 멈췄습니다.
  • 두 시험은 이어진 실행이 아닙니다. 각각 새로 만든 합성 상태에서 시작했습니다.
  • 본 프로그램(MAIN)과 로더(E01)의 BurnNand는 크기가 같고 명령 워드의 약 78%가 완전히 같습니다. 그래도 호출 주소와 핸들의 칸 위치가 달라, E01에서 확인한 결과를 MAIN의 동작 증거로 옮길 수 없습니다.
  • NAND의 실제 응답, 카드에서 읽힌 데이터, 그 뒤의 섹션 맵과 기록은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 두 시험 모두 원본 BurnGetHandle과 MAIN Burn을 실행
  • 시험 1: 매체 열기에서 NAND 요청 직전까지(블록 이벤트 281개)
  • 시험 2: HostAck, BurnNand, 설치 헤더 요청, 카드 읽기 진입(134개, 누적 156개)
  • MAIN 워드 98개와 함수 후보 범위 24개, E01 워드 11개를 대조

정적 분석 코드를 읽어 판단

  • MAIN과 E01 BurnNand의 워드 비교(2,760개 중 2,166개 일치)
  • 매체 정보 초기화의 플래그 2가 건너뛰는 분기

모델 시험 조건으로 정한 것

  • 메모리 할당, 뮤텍스, 진단 출력(두 시험 공통)
  • 시험 2의 열기 결과 0xf1과 저장장치 크기
  • 시험 2의 두 요청에 대한 응답(FF 16바이트, 빌려 온 헤더 0x600바이트)

미확인 확인하지 않은 것

  • NAND 식별 요청에 대한 장치의 응답과 그 뒤의 진행
  • 카드 읽기의 결과와 파일 위치
  • 둘째 설치 헤더, 섹션 맵, 기록·재부팅·복구

배경: 기록 함수가 쓰기 전에 하는 준비

메인 업데이트 진입과 반환값은 메뉴에서 시작한 업데이트가 본 프로그램의 Burn에 닿는 곳까지 따라갔고, Burn 자체는 모델로 바꿨습니다. 이 문서는 그 Burn의 앞부분을 원본 코드로 실행합니다.

  1. 업데이트 진입래퍼에서 DownloadCard까지 — 앞 문서
  2. 매체 열기설치된 저장 매체를 FileX로 엶 — 시험 1
  3. 설치 헤더 읽기BurnNand가 기존 배치 정보를 요청 — 시험 2
  4. 카드 첫 읽기업데이트 파일의 첫 덩어리 — 시험 2는 진입까지
  5. 섹션 맵과 기록MAIN 쪽에서는 아직 실행하지 않음

읽는 데 필요한 배경 지식입니다.

  • NAND 플래시의 식별 요청: NAND 칩은 제조사와 종류를 알려 주는 식별 정보(ID)를 갖고 있습니다. 저장장치 드라이버는 보통 초기화할 때 이 값을 읽어 어떤 칩인지 구분합니다. 일반 NAND 명령 체계에서는 READ ID(명령 바이트 0x90)가 이 일을 합니다.
  • 예비 영역: NAND의 각 페이지에는 데이터 외에 작은 예비 영역이 붙어 있습니다. 보통 오류 정정 부호와 불량 블록 표시를 여기에 둡니다.
  • 연산 번호: 이 문서의 “연산 2·4·6”은 펌웨어 안의 저장 계층이 쓰는 내부 번호입니다. NAND 칩에 보내는 명령 바이트가 아닙니다. 연산 2는 식별 요청, 4는 데이터 읽기, 6은 예비 영역 읽기에 쓰였습니다. 내부 번호가 칩의 어떤 명령으로 바뀌는지는 이 문서에서 따라가지 않았습니다.
  • FileX: 이 펌웨어의 파일시스템입니다. 매체를 열 때 등록된 드라이버 함수에 요청 번호를 넘겨 일을 시킵니다.

두 시험의 출발점은 앞 문서에서 관측한 호출 인수입니다

두 시험 모두 원본 헤더로 BurnGetHandle을 실행해 핸들을 만든 다음, 앞 문서에서 관측한 인수 그대로 MAIN Burn을 불렀습니다.

원본 업데이트 헤더 192바이트로 BurnGetHandle을 실행하면 MAIN BurnNand의 주소 0x805dd7b8이 핸들 +0xca4에 들어갑니다. 그 핸들과 덩어리 크기 0x20000, 카드 함수 표 sCardFunc의 주소 0x805e8854를 MAIN Burn에 넘겼습니다. 이 인수는 DownloadCard 실행에서 확인한 값입니다. 다만 두 시험은 DownloadCard에서 이어진 것이 아니라 각각 새로 시작한 실행입니다. [근거: call_contract, handle_fields] · [앞 문서의 근거]

MAIN Burn은 먼저 매체 정보 초기화 함수 FcuMediaInfoInit을 타입 1, 플래그 2로 부릅니다. 플래그 2는 이 초기화 함수 내부의 “cold ID” 경로(식별 정보를 읽는 경로)를 건너뛰게 합니다. 그렇다고 그 뒤 FileX 열기에서 나오는 장치 요청까지 없어지는 것은 아닙니다. 시험 1이 이 점을 보여 줍니다. [근거: source.main_words]

시험 1: 원본 매체 열기는 BurnNand보다 먼저 NAND에 요청을 보냅니다

설치 매체를 여는 원본 코드는 FileX, NAND 드라이버, 저장 계층을 차례로 거쳐 NAND 식별 요청에 도달했습니다. 이때까지 HostAck와 BurnNand는 실행되지 않았습니다.

시험 1에서는 설치 매체의 FileX 열기를 원본 코드로 실행했습니다. FileX는 NAND 드라이버에 요청 4를 보냈고, 드라이버는 TlMediaInit과 TlFcuOperation을 거쳐 NAND 연산 2를 요청했습니다. Burn 진입부터 VEX 블록 이벤트 281개 뒤에 FcuNandOperationEx(0x80053124)에 도달했고, 그 본문을 실행하기 전에 멈췄습니다. 이때 식별 정보를 받을 8바이트 버퍼는 모두 FF였습니다. 장치의 응답을 넣지 않았으므로 HostAck와 BurnNand는 아직 실행되지 않았습니다. [근거: native_open]

참고

현재 공개된 FileX 헤더에서 드라이버 요청 번호 4는 FX_DRIVER_INIT(드라이버 초기화)입니다. Q7에 들어 있는 FileX가 같은 번호를 쓰는지는 따로 확인하지 않았지만, 요청 4가 매체 초기화 함수 TlMediaInit으로 이어진 관측과 맞습니다. [FileX fx_api.h]

VEX 블록 이벤트는 에뮬레이터가 센 실행 블록 수입니다. 실물 CPU의 명령 수나 실행 시간이 아닙니다.

시험 2: 열기 결과를 넣어 주면 설치 헤더를 읽고 카드 읽기에 들어갑니다

매체 열기 결과와 저장장치 크기를 모델이 답하자, 원본 BurnNand는 설치 헤더를 읽는 요청 두 개를 보낸 뒤 카드의 첫 읽기에 진입했습니다.

  1. 열기와 크기 FileX 열기 모델이 0xf1을 반환하고, 크기 조회 모델이 블록당 256섹터, 총 262,144섹터를 답했습니다.
  2. HostAck와 BurnNand 원본 HostAck가 1을 반환했고, 이어 원본 BurnNand가 실행됐습니다.
  3. 첫 요청: 연산 6 BurnNand가 설치 헤더를 읽으려고 보낸 첫 요청은 NAND 연산 6, 섹터 0, 개수 1이었습니다. 여기까지 VEX 블록 이벤트는 134개입니다. 모델은 예비 영역 16바이트를 모두 FF로 답했습니다.
  4. 둘째 요청: 연산 4 그러자 원본 코드가 연산 4, 섹터 0, 개수 3을 요청했습니다. 모델은 업데이트 파일 0x1000c0에서 빌려 온 0x600바이트를 답했습니다.
  5. 카드 첫 읽기 원본 카드 읽기 함수가 _fx_file_read에 0x20000바이트를 요청했습니다. 그 진입점에서 실행을 멈췄고, 누적 블록 이벤트는 156개입니다.

BurnNand가 여기서 요청한 것은 첫째 설치 헤더(선택 값 0, 일반 헤더)입니다. 둘째 설치 헤더(선택 값 1)와 섹션 맵은 멈춘 지점 뒤에 있습니다. [근거: installed_header]

시험 조건

연산 4에 답한 0x600바이트는 실제 카메라의 저장장치에서 읽은 것이 아닙니다. 업데이트 파일의 헤더 부분을 빌려 온 시험값입니다. 카드 읽기의 목적지는 합성 기본 버퍼이고, 읽기 함수는 결과를 받기 전에 멈췄습니다. 그래서 카드 파일의 위치와 읽힌 내용은 관측하지 않았습니다. 근거 JSON의 intended_payload_offset은 시험의 의도와 앞선 헤더 읽기 위치를 적어 둔 값이며, 파일 구조체에서 관측한 실제 위치가 아닙니다. [근거: fixture, first_card_filex] · [재현 도구: replay_mode]

확인하지 못한 값의 뜻

열기 모델이 돌려준 0xf1은 원본 Burn이 열기 결과와 비교하는 값입니다. 현재 공개된 FileX 헤더의 상태 코드 목록에는 이 값이 없습니다. 이 값이 무엇을 뜻하는지는 확인하지 못했습니다.

MAIN과 E01의 BurnNand는 닮았지만 같은 코드가 아닙니다

두 함수는 크기가 같고 명령의 종류가 자리마다 같습니다. 그러나 워드의 5분의 1쯤은 호출 주소와 핸들 칸이 달라 서로 다릅니다.

MAIN과 E01의 BurnNand는 각각 11,040바이트입니다. 같은 위치의 워드 2,760개 가운데 2,166개가 같고, 상위 6비트의 명령 종류 필드는 전부 같습니다. 이 비교는 레지스터, 주소, 오프셋, 세부 기능 필드를 빼고 본 것입니다. 명령 종류의 배열이 같다고 동작이 같다고 검증된 것은 아닙니다. 이 수치는 구조를 비교한 결과일 뿐, E01의 기록·종료 실행 결과를 MAIN의 동작 증거로 옮길 수 있다는 뜻이 아닙니다. [근거: source.comparison]

K-3 Mark III와 비교

K-3 Mark III 자료의 고정 커밋은 업데이트 래퍼가 실행 결과를 보존하는 경로와, 종료·자원 해제 조건을 다룹니다. Q7의 이 문서는 그보다 아래쪽인 매체 열기와 저장장치 요청의 진입을 따라갔습니다. 두 기종 모두 어디부터가 모델인지 밝혀야 하며, 반환값이나 NAND 형식, 기록 순서가 같다고 가정하지 않습니다. [고정 커밋의 K-3 Mark III 종료·반환 근거]

한계와 재현 방법

  • 두 시험은 따로 만든 프로젝트, 미리 넣은 뮤텍스와 장치 상태, 범위를 제한한 메모리에서 실행했습니다. 블록 이벤트 수는 MAIN Burn 진입부터 센 값입니다.
  • 두 시험 모두 메모리 할당, 뮤텍스, 진단 출력을 모델로 바꿨습니다. 어느 시험도 DownloadCard에서 시작하지 않았고, 실제 저장장치·카드 입출력·NAND 컨트롤러를 다루지 않았습니다.
  • 장치 연산의 본문, 카드 데이터 읽기, 둘째 설치 헤더(선택 값 1)와 섹션 맵, 기록·재부팅·복구는 확인하지 않았습니다.
  • 다음 단계는 MAIN의 설치 헤더와 저장장치 크기를 바꿔 가며 뒤따르는 분기를 따로 검증하는 일입니다. 카드 읽기의 재시도와 바이트 비교도 MAIN 쪽에서 따로 시험해야 합니다. [근거: limits, next_actions]
