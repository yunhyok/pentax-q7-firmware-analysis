메인 프로그램의 업데이트 진입 경로와 반환값

메뉴에서 업데이트를 시작하면 카메라 본 프로그램이 파일을 준비한 뒤 저장장치 기록 코드로 넘어갑니다. 그 길을 원본 코드로 따라가며, 각 단계가 돌려주는 값이 무엇을 뜻하는지 확인했습니다.

이 문서에서

  1. 배경: 기록 코드가 두 벌 있습니다
  2. 파일 준비: 업데이트 파일을 읽어 I:\UPG_FILE.ELF로 쓰기를 요청합니다
  3. 기록 코드 진입: MAIN의 DownloadCard가 헤더를 읽고 기록 함수를 고릅니다
  4. 반환값: 맨 위의 1은 아래 단계의 성공을 뜻하지 않습니다
  5. K-3 Mark III와 비교
  6. 한계와 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 본 프로그램은 업데이트 파일을 읽어 I:\UPG_FILE.ELF라는 이름으로 다시 쓰도록 요청합니다. 이 준비 단계를 11가지 조건으로 실행했습니다.
  • 그 뒤 호출이 여러 단계를 내려가 본 프로그램 안의 DownloadCard에 닿습니다. 이 함수는 헤더 192바이트를 읽고 종류 값 3에 맞는 NAND 기록 함수를 고릅니다.
  • 본 프로그램에 든 기록 코드는 E01 로더에 든 같은 이름의 코드와 별개 구현입니다. 주소도, 작업용 구조체의 칸 위치도 다릅니다.
  • 맨 위 함수는 동기 방식일 때 아래 단계가 실패해도 1을 돌려줍니다. 그래서 맨 위의 1만 보고 기록이 성공했다고 판단할 수 없습니다. 호출과 반환을 12가지 조건으로 실행했습니다.
  • 기록 함수의 본문과 NAND 쓰기는 이 문서에서 실행하지 않았습니다. 그 자리는 정해 둔 값을 돌려주는 모델로 바꿨습니다.

확인 원본 코드 실행으로 확인

  • 파일 준비 함수의 분기 11사례
  • 맨 위 래퍼에서 DownloadCard, BurnGetHandle까지의 호출과 인수
  • 단계별 반환값의 변환 12사례
  • 원본 워드 98개와 함수 범위 12개를 주소·해시로 대조

정적 분석 코드를 읽어 판단

  • 본 프로그램의 Burn·BurnNand 범위(본문은 실행하지 않음)
  • MAIN과 E01의 함수 주소·핸들 칸 비교(E01 값은 다른 문서의 근거)

모델 시험 조건으로 정한 것

  • 합성 96바이트 입력 파일, 입력 경로 F:\fwdc603p.bin
  • 파일시스템(FileX)·저장 매체·메모리 할당·LED·재부팅·스레드 생성
  • Burn의 결과(0 또는 7), 백업 플래그 0
  • 디렉터리 항목 upg_file.elf와 원본 헤더 192바이트 공급

미확인 확인하지 않은 것

  • 파일 준비에서 기록 코드 진입까지 이어진 연속 실행
  • 본 프로그램 Burn 본문과 NAND 기록(앞부분만 다음 문서에서 다룸)
  • 조정값 백업 경로, 실제 업데이트 인식·부팅·복구

배경: 기록 코드가 두 벌 있습니다

리코의 공식 안내에 따르면 사용자는 fwdc603p.bin을 SD 카드의 최상위 폴더에 복사하고 카메라 메뉴의 펌웨어 버전 화면에서 업데이트를 시작합니다. [리코: Q7 펌웨어 업데이트 안내] 이 문서는 그 뒤 카메라 본 프로그램 안에서 일어나는 일을 다룹니다.

Q7 펌웨어에는 저장장치에 기록하는 코드가 두 벌 들어 있습니다.

MAIN
카메라 본 프로그램 안에 든 기록 코드입니다. 메뉴에서 시작한 업데이트가 이 코드를 거칩니다. 이 문서의 대상입니다.
E01
업데이트 파일 맨 앞에 든 별도 실행 파일(로더)입니다. 입력 검증부터 최종 반환까지 여러 문서에서 자세히 실행해 본 쪽은 E01입니다.

두 벌에는 DownloadCard, BurnGetHandle, Burn, BurnNand처럼 이름이 같은 함수가 있습니다. 이름이 같다고 같은 코드로 취급하면 안 됩니다. E01에서 확인한 결과를 MAIN의 동작 근거로 옮길 수 없기 때문입니다.

읽는 데 필요한 말 몇 가지를 먼저 풉니다.

  • 래퍼: 다른 함수를 감싸 부르는 함수입니다. 준비와 뒷정리를 맡습니다.
  • 동기와 비동기: 작업이 끝날 때까지 기다리면 동기, 다른 스레드에 맡기고 바로 돌아오면 비동기입니다.
  • 핸들: 작업 상태를 모아 둔 구조체입니다. 여기서는 어떤 기록 함수를 쓸지가 이 안에 적힙니다.
  • FileX: 이 펌웨어가 쓰는 파일시스템 코드입니다.

파일 준비: 업데이트 파일을 읽어 I:\UPG_FILE.ELF로 쓰기를 요청합니다

준비 함수는 파일 크기를 재고 저장 공간을 마련한 뒤 파일 전체를 읽어 다른 이름으로 쓰도록 요청합니다. 중간 조건 하나라도 실패하면 0을 돌려줍니다.

준비를 맡는 함수는 UpdateFW_LoadFirmware입니다. 원본 코드가 밟는 순서는 다음과 같습니다.

  1. 파일 크기 재기 전역 변수에 들어 있는 경로에서 파일 크기의 하위 32비트를 읽습니다. 시험에서는 이 변수에 F:\fwdc603p.bin을 넣었습니다.
  2. 드라이브 글자 정하기 보드 버전이 3보다 작으면 입력 경로의 드라이브를 F로, 그렇지 않으면 E로 바꿉니다. 보드 버전 3인 사례는 F 경로에서 크기를 재고 E 경로를 열었습니다.
  3. 공간 마련 요청 크기에 0x2000000을 더합니다. 이 덧셈은 32비트 범위에서 순환합니다. 그 결과를 512로 나눠 올림한 값을 파라미터 0x11e에 적습니다.
  4. 준비 확인, 포맷, 마운트 파라미터를 되읽어 준비됐는지 확인하고 저장 매체를 포맷하고 마운트합니다.
  5. 읽기 메모리를 할당하고 입력 파일을 열어, 처음에 잰 길이만큼 읽습니다. 읽힌 길이가 모자라면 실패로 처리합니다.
  6. 쓰기 요청 I:\UPG_FILE.ELF를 쓰기용으로 열어 읽은 내용을 쓰도록 요청하고 닫습니다.

시험 조건

입력은 합성 96바이트 파일입니다. 실제 파일시스템이나 18MB짜리 파일을 버퍼에 담아 쓰는 동작을 검증한 것이 아닙니다. 업데이트 파일 전체의 합계 검사는 재패킹 검증과 업데이트 검사의 별도 근거입니다.

기록 코드 진입: MAIN의 DownloadCard가 헤더를 읽고 기록 함수를 고릅니다

맨 위 래퍼에서 기록 함수 선택까지 원본 코드가 그대로 이어졌습니다. 실제 기록을 맡는 Burn부터는 모델로 바꿨습니다.

파일을 찾고 헤더를 읽기

I43_UpgradeFlashFromCard는 AppUpgradeFlashFromCard와 BurnUfcMain을 거쳐 MAIN의 DownloadCard에 인수 (0xfe, 0, 1)을 넘깁니다. DownloadCard는 저장 매체의 디렉터리를 훑습니다. 시험에서는 디렉터리 모델이 upg_file.elf라는 항목을 내놓았습니다. 원본 코드는 이름을 대문자로 바꾼 뒤 .ELF가 들어 있는지 찾아 이 파일을 골랐습니다.

이어 파일 오프셋 0x100000에서 헤더의 앞 64바이트를 읽고 +0x3e가 0x55aa인지 확인한 다음 128바이트를 더 읽습니다. 읽기 모델은 원본 업데이트 파일의 같은 위치 192바이트를 그대로 내놓았습니다. [근거: bridge_cases]

기록 함수를 고르기

원본 BurnGetHandle은 헤더의 종류 값 3을 보고 MAIN의 BurnNand 주소를 핸들 +0xca4에, 장치 함수의 주소를 +0xca8에 적습니다. 핸들 +0xcc8의 해시 플래그는 0입니다. 그다음 원본 호출부가 Burn에 핸들, 덩어리 크기 0x20000(128KiB), 카드 읽기용 함수 표를 넘깁니다. 이 문서의 실행은 여기까지입니다. Burn의 진입점에서 모델이 대신 값을 돌려주므로, MAIN Burn의 본문과 NAND 쓰기는 실행 범위 밖입니다.

이어지는 문서

메인 Burn의 매체 열기는 여기서 관측한 인수로 새 실행을 시작해 MAIN Burn의 앞부분을 따라갑니다. 이 문서의 DownloadCard 상태를 이어받은 연속 실행은 아닙니다.

반환값: 맨 위의 1은 아래 단계의 성공을 뜻하지 않습니다

아래 단계의 결과는 한 단계 올라갈 때마다 다른 숫자로 바뀌고 동기 방식의 맨 위 래퍼에서는 성공과 실패의 차이가 사라집니다.

동기 방식의 UpdateFW_UpdateFirmware는 두 경우 모두 I43 어댑터의 결과를 로그 함수에 넘겼습니다. 그리고 “업데이트 중” 표시를 지운 뒤 1을 반환했습니다. 이 결과는 백업 플래그를 0으로 둔 합성 상태에서 얻었습니다. [근거: bridge_cases]

비동기 방식

비동기 분기는 원본 UpdateFirmwarePerform의 주소를 스레드 생성 함수 Thread_Create에 넘깁니다. 스레드 생성 모델이 0을 돌려주면 래퍼도 0을 반환하지만 “업데이트 중” 표시는 1로 남습니다. 모델이 1을 돌려준 사례에서도 표시는 1입니다. 두 사례 모두 스레드의 본문을 실행하지 않았으므로, 실제 스케줄링이나 작업 완료를 뜻하지 않습니다.

파일 닫기가 실패한 경우

Burn 모델이 0을 돌려준 뒤 파일 닫기 모델이 상태 7을 돌려준 사례(8번)에서, 원본 코드는 재부팅 함수 호출을 건너뛰었습니다. 그런데도 DownloadCard는 1, I43 어댑터는 0을 반환했습니다. 닫기 실패가 실제 장치에 어떤 영향을 주는지는 이 모델로 판단하지 않습니다.

주의

여기서 확인한 것은 소프트웨어가 값을 주고받는 규칙입니다. 업데이트가 실제로 성공했는지를 보여 주는 결과가 아닙니다.

K-3 Mark III와 비교

K-3 Mark III 자료의 고정 커밋에서는 종류 2·6·7의 래퍼가 종료 처리를 호출한 뒤 실행기의 32비트 결과를 그대로 보존합니다. Q7의 동기 방식 경로는 아래 결과가 서로 다른 두 사례에서 모두 1을 반환했습니다. 비교하는 계층과 숫자의 뜻이 달라, 두 기종의 값을 공통 성공 코드로 묶지 않습니다. Q7 안에서도 E01의 핸들 칸 +0x1254와 MAIN의 +0xca4를 구분해야 합니다. [고정 커밋의 K-3 Mark III 종료·결과 보존 근거]

한계와 재현 방법

  • 원본 호출부와, 합성 입력에 따라 갈리는 분기를 검증했습니다. 업데이트 파일 전체의 합계 검사는 별도 근거입니다.
  • 96바이트 파일 준비와 원본 헤더 공급은 서로 다른 상태에서 따로 실행했습니다. 둘을 이어서 실행하지 않았습니다.
  • FileX, 저장장치, MAIN Burn, 재부팅, 실제 스레드 생성은 모델입니다. 본 프로그램의 Burn·BurnNand 범위는 위치와 해시만 대조했습니다.
  • 경로에 나오는 F·E·I 드라이브가 실제로 어떤 저장장치를 가리키는지는 이 문서에서 확인하지 않았습니다.
  • 백업 플래그 0과 할당 성공은 시험 조건입니다. 조정값 백업 경로, MAIN의 NAND 실행, 실제 업데이트 인식·부팅·복구는 남은 검증 항목입니다.
