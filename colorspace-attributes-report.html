01 / OBSERVATION AND RE-INPUT

요청은 관측했고 컨텍스트 연결은 가정했다

네 번의 원본 갱신에서 속성 72건과 텍스트 25건의 순서를 기록했습니다. sRGB 위젯 0x0191d00b는 매번 종류 7에 48·48, 종류 12에 0·0, 종류 4에 2를 전달한 뒤 텍스트를 요청했습니다. 속성의 그리기 ID는 17·18·17·18로 바뀌고 텍스트의 ID는 0입니다. 이 단계에서는 두 API를 관측 모델로 대체했습니다. [A1: refresh]

02 / NATIVE ATTRIBUTE DISPATCH

크기·간격·색 설정의 원본 분기를 실행했다

별도 실행에서 원본 속성 분기와 setter를 복원했습니다. 종류 7은 context+0x82c·0x82e에 폭과 높이를, 종류 12는 +0x824·0x828에 문자 간격 값을 씁니다. 종류 4는 색 테이블의 슬롯 1에 인덱스 2를 씁니다. 나머지 팔레트 슬롯은 시험 컨텍스트의 입력값입니다. [A1: attribute_dispatch]

03 / HORIZONTAL SCALE AND WHOLE-FRAME CHECK

절반 간격에서 소스 열을 고른다

원본 코드는 Q16 가로 배율을 floor(48×65536/64)로 계산하며 값은 0xc000입니다. 글리프 폭 24·29·34·29는 각각 18·21·25·21로 줄어들며 x 좌표는 96·114·135·160입니다. 높이 48과 y 좌표 64는 유지됩니다. 소스 열은 역배율 간격의 절반에서 시작해 선택하므로 단순히 각 구간의 왼쪽 열을 고르는 계산과 다릅니다. [A1: scale_oracle·evidence]

factor = (48 << 16) // 64
destination_width = (source_width * factor) >> 16
inverse_step = (source_width << 16) // destination_width
source_column = (column * inverse_step + (inverse_step >> 1)) >> 16

원본 축소 실행은 68,969개의 VEX 블록 이벤트 뒤 1을 반환했습니다. 전체 129,536바이트와 양끝 8바이트 보호 구간을 독립 계산과 대조했습니다. 바뀐 바이트 2,464개 중 인덱스 1은 1,297개, 인덱스 2는 1,167개입니다. 이 값은 색상 인덱스이며 실제 RGB 색은 확인하지 않았습니다. [A2: scaled_oracle·check_scaled]

04 / FIXED K-3 MARK III REFERENCE

UI 동작 비교와 Q7 렌더러 근거를 구분한다

K-3 Mark III의 고정 커밋에서 확인한 Color Space 선택·확정·취소 구조를 비교 기준으로 유지합니다. Q7은 초점 이동 때 값을 쓰고 취소 때 백업을 복구하지만 K-3 Mark III는 확정 전 보류 값을 사용합니다. 이번 결과는 Q7의 텍스트 속성과 렌더러 분기의 근거를 보강합니다. K-3 Mark III의 글꼴 크기·팔레트·화면 버퍼가 같은지는 미확인입니다. [K1: 입력·확정·취소] · [Q1: Q7 값 쓰기·복구]

05 / CONDITIONAL NATIVE CONTEXT SELECTION

등록된 컨텍스트를 원본 선택기가 연결한다

후속 시험에서는 서로 다른 두 컨텍스트를 합성 등록 테이블에 넣고 원본 버퍼 교체와 선택기를 실행했습니다. ID 17→18→17의 두 교체와 다음 슬롯이 비어 있는 대조 사례를 검증했습니다. 17·18은 시험에서 지정한 ID이며 실제 카메라의 할당값은 미확인입니다. [B1: 합성 등록·세 대조 조건]

원본 ScreenOsdLayer_Roll은 SetOsd를 거쳐 I43_SetParam(0x1bc, drawID)을 호출합니다. AppOsdSetDrawBuffer는 등록 테이블에서 해당 포인터를 읽어 0x800eb4d8에 씁니다. 명령어 주소는 0x8024a614이며 MIPS 지연 슬롯 때문에 VEX 쓰기 이벤트는 0x8024a610으로 기록됩니다. 텍스트의 ID 0·플래그 1 경로는 이 전역 포인터를 읽습니다. [B1: 원본 명령어·선택 경로]

두 슬롯이 등록된 조건에서는 원본 교체마다 활성 포인터가 해당 컨텍스트로 바뀌었습니다. 교체 전후에 명시적 속성 ID를 쓰는 호출과 텍스트 ID 0을 쓰는 호출이 같은 포인터를 GDI 진입점에 전달했습니다. 이 시험에서는 크기 setter와 텍스트 GDI 본문을 대체했습니다. 앞선 축소 픽셀 실행은 별도 시험입니다. [B2: 원본 교체와 두 조회 경로]

다음 ID 18의 등록 슬롯을 비우면 화면의 draw ID는 18로 바뀌지만 활성 컨텍스트 쓰기는 일어나지 않았습니다. 명시적 속성 ID 18로 호출했을 때는 이전 컨텍스트를 대신 사용했습니다. 텍스트 ID 0도 그 포인터를 사용했습니다. 화면 ID 교체만으로는 컨텍스트 선택 성공을 판단할 수 없습니다. [B1: missing_slot]

원본 초기 레이어별 할당 구간은 0–7, 32–39, 64–71입니다. 조회기가 등록된 17·18을 받아들이는 것과 초기 설정 코드가 그 ID를 할당하는 것은 별개입니다. 이번 시험은 등록 테이블과 두 컨텍스트를 공급했습니다. 실제 초기화·할당과 글꼴 설정, UI 갱신부터 최종 픽셀까지의 연속 실행, LCD 출력은 여전히 미검증입니다. [B1: 초기 범위·한계]

python tools/check_context_binding.py <original fwdc603p.bin> .private/main-expanded.elf --output .private/context-binding-new.json

모델 설명 정정: 0x800ec08c는 진단 함수가 아니라 I43_SetParam입니다. 이 시험은 해당 호출에서 0을 반환하므로 매개변수 0x1bc의 활성 그리기 컨텍스트 선택을 실행하지 않습니다. 기존 요청·픽셀 결과는 그대로이며, 그 결과로 실제 ID 연결을 입증할 수는 없습니다. [R1: ScreenOsdLayer_SetOsd 전달 관계·모델 경계]
