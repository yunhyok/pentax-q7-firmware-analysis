화면과 글꼴 · ⑤ 글자 크기와 그리기 컨텍스트

48×48 글자 크기 요청과 그리기 컨텍스트 선택

색공간 화면의 원본 갱신에서 sRGB 글자에 48×48 크기를 요청하는 것을 관측했습니다. 별도 합성 컨텍스트에서 이 요청에 따른 렌더러 선택을 확인했고, 합성 등록표를 사용한 별도 시험에서 속성 호출과 텍스트 호출에 전달되는 컨텍스트를 비교했습니다.

이 문서에서

  1. 배경: 글자 크기는 컨텍스트에 기록됩니다
  2. 갱신에서 관측한 요청과 별도 시험의 경계
  3. 크기 속성이 렌더러를 바꿉니다
  4. 가로만 4분의 3으로 줄여 그린 결과가 버퍼 전체와 일치
  5. 등록된 컨텍스트를 원본 선택기가 고르는 조건
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 원본 화면 갱신 4회에서 sRGB 글자 앞에 크기 48×48, 간격 0, 색 2 속성이 매번 요청되는 것을 기록했습니다. 속성 요청은 72건, 글자 요청은 25건입니다.
  • 이 속성을 별도 컨텍스트에 적용하자 원본 코드가 기본 렌더러 대신 축소 렌더러를 골랐습니다. 네 글자의 폭은 24·29·34·29에서 18·21·25·21로 줄었고 프레임 전체(129,536바이트)가 독립 계산과 같았습니다.
  • 서로 다른 컨텍스트 두 개를 시험용으로 등록하면, 원본 버퍼 교대 코드가 다음 그리기 ID의 컨텍스트로 활성 포인터를 바꿉니다. 다음 슬롯이 비어 있으면 ID만 바뀌고 포인터는 이전 컨텍스트에 머뭅니다.
  • ID 17·18은 시험에서 정한 입력입니다. 카메라가 실제로 처음 할당하는 값, 갱신부터 픽셀까지 이어진 실행, 화면 출력은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 갱신 4회의 속성·글자 요청 순서와 인수
  • 속성 분기와 크기·간격·색 설정 함수, 렌더러 선택
  • 48×48 축소 그리기 한 번의 프레임 전체 일치
  • 버퍼 교대와 활성 컨텍스트 선택(두 교대와 빈 슬롯 사례)

모델 시험 조건으로 정한 것

  • 갱신 단계의 속성·글자 API는 기록 모델
  • 축소 그리기: 합성 컨텍스트, 그리기 ID 17과 기본 ID 0을 같은 컨텍스트로 연결
  • 컨텍스트 선택: 등록 테이블과 컨텍스트 두 개(ID 17·18)
  • 글꼴 파일 읽기·메모리·캐시·진단 경계

미확인 확인하지 않은 것

  • 카메라 시작 때 실제 할당되는 버퍼 ID와 등록 내용
  • 갱신부터 픽셀까지 한 번에 이어진 실행, 메뉴 전체 합성
  • 실제 팔레트 색, 화면 전송, LCD 출력

배경: 글자 크기는 컨텍스트에 기록됩니다

글꼴 로딩과 글리프 픽셀은 “sRGB”를 글꼴의 기본 크기(셀 64×48)로 그렸습니다. 원본 화면 갱신을 재실행했을 때는 텍스트 요청 직전에 크기·간격·색 속성 요청이 관측됐습니다. 이 속성은 그리기 컨텍스트에 기록되고 이후 글자 출력은 컨텍스트를 보고 렌더러를 고릅니다.

그래서 두 가지를 확인해야 했습니다. 하나는 48×48 요청이 어떤 렌더러를 고르게 하는지, 다른 하나는 속성과 글자가 같은 컨텍스트를 보는지입니다. 앞의 것은 축소 렌더러 시험, 뒤의 것은 컨텍스트 선택 시험에서 다룹니다.

  1. ① 선택·확정·취소색공간 화면: 선택·확정·취소
  2. ② 그리기 요청그리기 경로
  3. ③ 강조 픽셀선택 강조의 픽셀
  4. ④ 글자 픽셀글꼴 로딩과 글리프 픽셀
  5. ⑤ 글자 크기·컨텍스트이 문서
  6. 팔레트·LCD미확인

단계 번호는 문서를 읽는 순서입니다. 카메라 안의 실행 순서로는 이 문서의 속성 적용이 ④ 글자 픽셀보다 앞에 옵니다.

갱신에서 관측한 요청과 별도 시험의 경계

48×48 요청은 원본 갱신에서 직접 관측했습니다. 그 요청을 축소 렌더러에 넣은 시험은 따로 만든 컨텍스트에서 실행했으므로, 둘 사이의 연결은 시험 조건입니다.

sRGB 선택지 위젯 0x191d00b은 갱신마다 속성 세 개를 요청한 뒤 글자를 요청했습니다. 속성 요청의 그리기 ID는 갱신마다 17·18·17·18로 바뀌었고 글자 요청의 ID는 0입니다. 이 시점에서는 속성 API와 글자 API를 기록 모델로 대체했습니다.

네 갱신의 요청 기록은 그리기 경로의 관측과 정규화한 메타데이터 기준으로 바이트 단위까지 일치합니다. 그리기 경로의 갱신 기록 SHA-256 43856af97a6702886aeadf8cad85564a5f5f25c3e964b3a247dd2584d9731143, 순서 기록 SHA-256 2e8a9f3ea98670c10d59087ff45d97af2e2d9674ee86424c3883b3c3dd0de9de. [근거: bounded_replay.refresh]

크기 속성이 렌더러를 바꿉니다

속성을 적용하지 않은 컨텍스트는 기본 렌더러 BlitFont로, 48×48을 적용한 컨텍스트는 축소 렌더러 StretchBlitFont로 들어갑니다.

별도 실행에서 원본 속성 분기표와 설정 함수를 실행했습니다. 종류 7은 컨텍스트의 폭·높이 칸에, 종류 12는 글자 간격 칸에, 종류 4는 색 테이블의 슬롯 1에 번호 2를 씁니다. 나머지 팔레트 슬롯은 시험 컨텍스트의 입력값입니다.

같은 축소 렌더러의 화면 가장자리 동작은 색공간 글자의 가장자리 처리에서 확인했습니다. 단일 글리프를 음수 좌표에 놓았을 때의 행 주소 검사와 픽셀 저장 순서를 대조했습니다.

가로만 4분의 3으로 줄여 그린 결과가 버퍼 전체와 일치

축소 렌더러는 높이 48을 그대로 두고 가로만 48/64로 줄입니다. 네 글자를 끝까지 그린 프레임 전체와 양끝 보호 영역이 독립 계산과 같았습니다.

원본 코드는 Q16 가로 배율을 floor(48 × 65536 / 64)로 계산하며 값은 0xc000(0.75)입니다. 글자 폭 24·29·34·29는 18·21·25·21로 줄고 x 좌표는 96·114·135·160이 됩니다. 높이 48과 y = 64는 그대로입니다.

factor = (48 << 16) // 64
destination_width = (source_width * factor) >> 16
inverse_step = (source_width << 16) // destination_width
source_column = (column * inverse_step + (inverse_step >> 1)) >> 16

소스 열은 역배율 간격의 절반 지점에서 고릅니다. 각 구간의 왼쪽 열을 고르는 단순한 계산과는 결과가 다릅니다. [근거: scale_oracle]

등록된 컨텍스트를 원본 선택기가 고르는 조건

화면 버퍼를 교대할 때 원본 코드는 다음 그리기 ID의 등록 슬롯에서 컨텍스트를 꺼내 활성 포인터에 씁니다. 속성과 글자는 모두 이 포인터를 따라가므로, 슬롯이 비어 있으면 둘 다 이전 컨텍스트를 씁니다.

앞의 축소 시험에서는 그리기 ID 17과 기본 ID 0을 같은 합성 컨텍스트에 연결했습니다. 별도의 선택 시험에서는 합성 등록표에 서로 다른 컨텍스트를 넣고 명시적 속성 ID와 텍스트 ID 0의 호출이 어느 조건에서 같은 포인터를 받는지 확인했습니다. 원본 버퍼 교대와 선택기를 실행해 ID 17→18→17의 두 교대와 다음 슬롯이 비어 있는 사례를 대조했습니다.

  1. 교대와 매개변수 설정 원본 ScreenOsdLayer_Roll은 등록 테이블에서 현재 그리기 버퍼를 꺼내고 그리기·표시 ID를 맞바꿉니다. 일반 ScreenOsdLayer_SetOsd 분기는 표시 요청을 먼저 내보낸 뒤 I43_SetParam(0x1bc, 다음 그리기 ID)를 부릅니다.
  2. 활성 포인터 쓰기 매개변수 점프표가 AppOsdSetDrawBuffer로 보냅니다. 범위 안의 ID이고 슬롯이 0이 아니면 활성 포인터(hdcAppOsd, 0x800eb4d8)에 컨텍스트를 씁니다. 이 저장 명령은 호출의 지연 슬롯 0x8024a614에 있고 VEX는 쓰기 이벤트를 0x8024a610으로 기록합니다.
  3. 같은 포인터 사용 명시적 ID를 쓰는 속성 호출과, ID 0·플래그 1인 글자 호출이 모두 이 활성 포인터를 GDI 입구에 넘겼습니다.

처음 I43_SetParam은 17을 골랐고 두 번의 원본 교대가 18과 17을 차례로 골랐습니다. 다음 ID 18의 슬롯을 비우면 화면의 그리기 ID는 18로 바뀌었지만 활성 컨텍스트 쓰기는 일어나지 않았습니다. 명시적 속성 ID 18은 이전 컨텍스트로 대체됐고 글자 ID 0도 그 포인터를 썼습니다. 화면 ID가 바뀐 것만으로는 컨텍스트 선택이 성공했다고 판단할 수 없습니다. [근거: findings, bounded_replay.replay]

17·18은 시험 입력입니다

원본 펌웨어의 초기 레이어별 할당 범위는 0~7, 32~39, 64~71(최대 ID 71)입니다. 원본 AppOsdCreateBuffer는 고른 레이어 범위를 훑어 첫 빈 컨텍스트를 등록하고 보조 ScreenOsdLayer_Setup은 레이어 0을 씁니다. 초기 등록 테이블의 슬롯 17과 18은 0입니다. 선택기가 등록된 17·18을 받아들이는 것과 초기 설정 코드가 그 ID를 할당하는 것은 별개입니다. 다음 과제는 첫 색공간 갱신 전의 시작 시 등록 내용과 레이어 0 생성 경로를 추적하는 것입니다.

K-3 Mark III와 비교

K-3 Mark III 고정 커밋에서 확인한 색공간 선택·확정·취소 구조를 비교 기준으로 둡니다. Q7은 포커스 이동 때 값을 쓰고 취소 때 백업을 되돌리지만 K-3 Mark III는 확정 전 보류값을 씁니다. 이 문서의 결과는 Q7의 글자 속성과 렌더러 분기에 대한 근거입니다. K-3 Mark III의 글꼴 크기·팔레트·화면 버퍼가 Q7과 같은지는 확인하지 않았습니다. [K-3 Mark III 입력·확정·취소] · [Q7 값 쓰기·복원]

한계와 재현 방법

  • 갱신 요청 기록, 속성 적용·픽셀 실행, 컨텍스트 선택은 서로 분리된 시험입니다. 갱신부터 픽셀까지 이어진 실행, 메뉴 전체 합성, 실제 팔레트, 화면 전송, DMA, 카메라 실행은 확인하지 않았습니다.
  • 축소 실행이 다룬 것은 글자 네 개, 가로 축소, 세로 1:1, 시작점 하나, 투명 모드 하나입니다.
  • 글꼴 매체와 FileX 호출, 메모리 할당, 캐시, 진단은 아래 목록의 모델입니다. 컨텍스트와 이어받은 팔레트 슬롯도 시험 입력입니다.
  • 컨텍스트 선택 시험은 정상 교대 분기(0x80c6aea1의 값 0)를 따랐습니다. 표시 자원 잠금, 캐시, 표시 요청, GDI 설정 함수와 글리프 본문, 빈 슬롯 진단은 모델입니다.
정정

모델 목록의 0x800ec08c는 진단 함수가 아니라 I43_SetParam입니다. 갱신 요청 기록 시험은 그 호출에서 0을 돌려주므로 매개변수 0x1bc의 활성 그리기 컨텍스트 선택을 실행하지 않습니다. 기존 요청·픽셀 결과는 그대로이며 그 선택은 위 절의 별도 시험에서 원본 코드로 실행했습니다.
