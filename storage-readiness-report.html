01 / NATIVE PREFLIGHT

첫 기록 요청 앞까지 실행한다

BurnNand는 원본 페이로드의 첫 131,072바이트와 합성 설치 헤더·geometry를 받아 섹션 맵을 만든 뒤 사전 검사를 진행했습니다. 1,024블록 가운데 0…639에는 블록당 spare 읽기 3회와 erase 요청 1회, 640…1023에는 spare 읽기 2회를 보냈습니다. 추가 읽기 3회를 합쳐 요청 3,331개의 순서와 인자를 확인했습니다. [L1: findings.preflight·replay.preflight]

이 합성 설치 헤더의 사용자 영역은 시작 640블록, 길이 384블록입니다. BlockUserArea는 헤더의 모드 바이트와 길이가 0이 아닌지 확인한 뒤 시작과 끝을 포함하는 범위를 검사합니다. 경계·모드·길이 7사례를 실행했습니다. 해당 영역에 erase 요청이 없었다는 결과는 이 합성 조건에 한정되며 실제 미디어 보호를 보장하지 않습니다. [L1: user_area·user_range_cases]

BurnNand 0x80012654 → BurnGetSectionsMap 0x8001a710
blocks   0…639: op6 at sector B×256, B×256+1, B×256 → op8 at block B
blocks 640…1023: op6 at sector B×256, B×256+1
then op6 at sectors 0, 1, 0 → stop before first op5
2,691 spare reads + 640 erase requests = 3,331 modeled requests

설치 헤더는 +0x310=640, +0x314=384, +0x234 byte=1이며 별도 handle+0x1268도 1입니다. BlockUserArea는 모드 2도 0이 아닌 값으로 처리합니다. 다른 보호 helper의 정확히 1 비교와 혼동하지 않았습니다. 순서 있는 (operation, location, count) triple의 해시를 L1에 기록했습니다.

02 / PROGRAM, READBACK AND COMPARE

요청 성공과 실제 바이트 일치를 분리한다

첫 op 5 요청은 sector 0, count 256과 16바이트 extra 버퍼를 전달하기 직전에 멈췄습니다. 이때 원본 입력 청크와 기록 대상으로 준비한 버퍼는 281바이트가 다릅니다. 별도로 실행한 기록 helper는 op 5 성공 뒤 op 4로 다시 읽고 count × 512바이트를 순서대로 비교했습니다. 상태 오류나 첫 불일치에서 0을 반환하고 맵 포인터가 있으면 해당 블록에 0x78을 씁니다. [L1: program_boundary·program_helper]

FcuNandOperation의 기본 경로는 FcuNandOperationEx로 이어집니다. op 4·5·6·8의 분기는 각각 데이터 읽기·기록·spare 읽기·erase 요청 구성으로 구분했습니다. op 4는 전역 바이트가 1이면 별도 SSFDC 경로를 탑니다. 이 역할 구분은 원본 명령과 분기표에 근거하며 FCU 아래의 물리 프로토콜이나 타이밍을 실행한 결과는 아닙니다. [L1: storage_dispatch]

03 / TWO READINESS GATES

AF 지원과 검색 전달 여부가 다를 수 있다

렌즈의 통신 상태 비트 0x08과 명령별 허용 맵은 별도 조건입니다. AF 지원 getter는 비트 0x08과 group 2·operation 4를 검사하지만 map-ready는 검사하지 않습니다. 상위 통신 함수는 map-ready가 정확히 1일 때만 연산 맵으로 요청을 제한하고 비트 0x08은 검사하지 않습니다. 따라서 AF 지원 판정과 검색 요청 전달 여부가 항상 같지는 않습니다. [R1: two_gates]

초기화의 primary 응답이 성공하고 regular 결과가 1 또는 7이면 비트 0x08을 설정합니다. regular 연산이 맵에서 거부됐고 반환값은 7이었습니다. 이 사례에서도 AF 지원은 1이고 VDRC 상태는 0이었습니다. 반대로 regular 응답 실패나 primary spec 실패 사례에서는 AF 지원이 0이어도 검색 요청이 하위 모델 경계까지 전달됐습니다. 이는 합성 응답으로 실행한 소프트웨어 상태이며 실제 직렬 전송이나 렌즈 이동의 증거는 아닙니다. [R1: startup·startup_disagreement]

04 / CACHE FAILURE AND RESET

실패 응답이 전체 상태를 지우지는 않는다

실패 뒤 캐시와 유효 상태의 변화는 함수마다 다릅니다. SingleRegular 실패는 세 VDRC 버퍼를 0으로 만들지만 기존 유효 상태 1은 남깁니다. VD-sync 실패는 이전 값이나 이전 꼬리와 새 접두부가 섞인 값을 보존할 수 있습니다. Primary refresh 실패 사례는 유효 상태를 0으로 바꾸면서 이전 VDRC 바이트를 남겼습니다. 데이터 값과 유효 상태를 함께 추적해야 합니다. [R1: cache_failure·vd_failure]

SingleRegular 0x80115f50은 세 버퍼, VD-sync 0x80115c8c는 이전 256바이트와 다른 수신 버퍼의 첫 5바이트, Primary 0x80113eac는 PLC 및 유효 상태를 다르게 처리합니다. LensCommunication 0x80111214의 RX 복사는 nonzero 수신 길이를 기준으로 하며 반환 상태로 차단하지 않습니다. 실패 상태와 함께 5바이트 접두부를 공급한 사례는 가능한 합성 관측일 뿐 실제 렌즈의 응답 형식이나 빈도를 뜻하지 않습니다. [R2: cache fixtures]

전체 control reset은 통신 상태·기능 맵·map-ready와 PLC·VDRC 데이터 및 유효 상태를 지웁니다. 장착 스위치·detect 경로는 핀 입력과 latch 조건에 따라 이 리셋을 선택합니다. 시간 초과 event mask 0x100은 두 사례 모두 결과 5로 돌아왔지만 map-ready가 1이던 사례만 전체 리셋과 초기화 재진입까지 갔습니다. 중첩 초기화는 진입 상태를 기록하고 멈췄습니다. [R1: dismount·timeout]

핀 기반 경로는 PowerOffSequence 0x8010fa10, LensSwControl 0x80110b34와 LensDetInt 0x8011045c를 실행했습니다. detect ISR은 latch가 없는 사례에서 기존 캐시를 보존했습니다. timeout은 LensCommunicationBase의 실제 event 분기를 실행하되 재진입한 초기화는 모델 경계에서 멈춥니다.

05 / PINNED K-3 MARK III REFERENCES

같은 검증 구분을 적용하고 내부 형식은 따로 해석한다

06 / INDEPENDENT REPLAY AND LIMITS

원본 명령과 모델 입력을 구분한다

저장 요청의 반환 상태와 spare 내용, 렌즈 응답·전원·핀·큐·타이머 경계는 모델 입력입니다. 실제 NAND 기록·재읽기, 렌즈 교체·이동, 인터럽트와 동시 접근은 검증하지 않았습니다. 기록 직전 버퍼의 281바이트 변경 이유와 전체 저장·복구 루프, AF 검색부터 실제 완료까지 이어지는 동작은 후속 분석 범위로 남습니다.

저장 재실행은 작업자와 조정자의 결과 전체가 일치했습니다. L1의 원본 word 83개, E01 typed 함수 8개와 익명 범위 3개의 해시를 다시 계산했습니다. R1의 word 153개와 함수 33개도 원본에서 재계산했습니다. 렌즈 17사례도 조정자가 독립 재실행해 메타데이터 전체가 일치했습니다. 공개 검사 기록은 연구 상태에 기록합니다.
