02 / RESOLVED INDIRECT RECIPIENT

AF 초기화가 수신자를 정한다

CAutoFocusService_Initialize는 GetOnNotifyCommand의 반환값 0x8040a008을 전역 포인터 0x80c17e00에 저장합니다. LensDriveControl은 이 포인터를 읽어 명령 0x6003c와 인자 0을 전달합니다. 초기화가 끝나고 포인터 값이 유지되면 간접 수신자는 CaptureProcessService_OnNotifyCommand입니다. [R1: binding]

GetOnNotifyCommand  0x8040cc60 → return 0x8040a008
Initialize          0x8037e14c → [0x80c17e00] = v0
LensDriveControl    jr t9      → callback(0x6003c, 0)
switch table        0x804a2bdc → 0x8040a458
call                0x8040a458 → ExecuteFocusControl(0x8042e040)

0x8037e14c의 저장은 다음 getter 호출의 지연 슬롯입니다. 두 번째 getter의 반환값으로 오해하지 않도록 원본 명령 실행으로 확인했습니다.

수신 함수는 명령에서 0x60001을 뺀 값으로 분기표를 조회합니다. 0x6003c의 항목은 0x8040a458이며 ExecuteFocusControl을 호출합니다. 송신자와 수신자는 tFocusControlInfo를 공유합니다. 모드 0·2·1은 각각 검색·위치 이동·정지 요청에 해당합니다. 구동 제한 상태가 1이면 요청을 내보내지 않습니다. 구동이 허용되면 큐 메시지 6·7·8을 사용합니다. 모드 3은 검색 정보를 보류하며 별도 VD 동기화 메시지 2를 처리할 때 이 정보를 소비합니다. [R1: dispatch, queue]

03 / DESCRIPTORS TO MMIO

색 행렬은 객체를 거쳐 기록된다

SetupColorMatrix는 행렬을 만든 뒤 ID 0xe와 0xf의 설정 구조체를 전달합니다. StillOnSetImageProcessingEx는 이를 모드별 캐시에 보관하고 StillSetImageProcessing은 같은 캐시를 읽습니다. 경로 타입이 0이면 PathSetImageProcessing에서 IpuSetFilter로 이어집니다. 여기까지는 설정값을 RAM에 복사하는 단계입니다. [R2: matrix_route]

CTranslatorC12의 분기와 객체 생성자를 대조하면 상위 ID 0xe는 저수준 필터 10인 CCmFilter로, ID 0xf는 필터 13인 CFc1Filter로 연결됩니다. CFc2Filter는 별도 필터 20입니다. CFc1과 CFc2는 이름이 비슷하지만 레지스터는 구분해 분석했습니다. 작업 함수 WriteAll은 필터의 UID를 비교해 필요한 경우 가상함수를 호출합니다. 각 기록 함수는 객체의 갱신 플래그를 확인합니다. [R2: factory, translator, virtual slots]

CCmFilter의 vtable 0x804ff828에서 +0x20은 설정 함수 0x803531e4, +8은 레지스터 기록 함수 0x803537a4입니다. CFc1Filter의 대응 슬롯은 0x804ffa10 → 0x80321be8, 0x804ff9f8 → 0x8031f750입니다. [R2: evidence]

WriteAll의 일반 필터 순회는 config가 존재하고 task+0x1f8 == 0일 때 수행합니다. UID 비교와 object+0x29 != 0 조건도 통과해야 실제 쓰기가 일어납니다.

설정 전달 경로는 확인했지만 모든 촬영에서 최종 계수가 그대로 유지된다고 단정할 수는 없습니다. FIPLIB 경로가 같은 필터를 다시 갱신할 수 있고 CBC를 통한 설정 제출도 존재합니다. 최종 패스의 선택 조건과 덮어쓰기 이후 값은 추가 추적 대상입니다. 레지스터 주소와 CPU의 쓰기 순서만으로 ISP 내부의 행렬·감마·클리핑 순서를 확정하지 않았습니다. [R2: limitations]

05 / OUTPUT BOUNDARIES

최종 픽셀과 파일을 구분해 추적하다

최종 픽셀 출력은 세 경계로 나누어 판단했습니다. 첫째는 CPU가 계수와 버퍼 주소를 전달하는 경계, 둘째는 ISP·JPEG 하드웨어가 메모리를 읽고 쓰는 경계, 셋째는 압축 결과를 파일에 저장하는 경계입니다. 현재 근거는 첫째와 셋째의 일부를 설명합니다. 둘째의 내부 산술과 실기 출력은 확인하지 않았으므로 하나의 완성된 픽셀 파이프라인으로 그리지 않았습니다.

직접 호출을 찾은 촬영 경로는 HDR입니다. StillCaptureHdrImageSave / StillCaptureHdrRunProcessing에서 StillCaptureSaveJpegImage(0x802d33d0)를 호출하는 세 위치를 확인했습니다. 저장 함수는 0x802d349c에서 ApsExifCreateJpeg(0x802c3454)를 호출하고, 이후 ApsPipePost(0, 0x1005, context, 1)를 수행합니다. 일반 비 HDR 촬영 전체로 확대하지 않았습니다. [R4: capture_entry]

ApsExifCreateJpeg의 descriptor가 새 압축을 요구하는 분기에서는 ApsJpegCreateCodeGo와 ApsJpegCreateCodeWait를 호출합니다. 이미 준비된 크기를 사용하는 분기도 있습니다. CodeGo는 기존 path가 있으면 입력·출력 버퍼를 갱신하고, 없으면 새 path를 구성합니다. 두 경우 모두 제출 뒤 PathGo로 실행을 요청합니다. [R4: jpeg_code_path]

렌즈 분석과 출력 경로 분석을 나누어 진행하고 ISP 레지스터 재실행은 별도 검증 작업으로 수행했습니다. 코디네이터가 중요 명령·분기표·vtable을 원본과 대조했습니다. 레지스터 재실행 10개 조건에서 순서까지 대조한 MMIO 쓰기 126회와 클록 대체 함수 호출 8회를 포함해 164개 검사가 통과했습니다. MMIO는 일반 RAM으로, 클록 함수는 대체 함수로 모델링했습니다. 카메라나 ISP를 구동한 시험은 아닙니다. [R3: 실행 결과] [검증 코드]

렌즈 재실행은 초기 바인딩과 모드 0·1·2·3의 분기를 검사합니다. 큐 대기 후 수신 지점에서 상태를 이어 붙이며 모드 3의 선행 주기 통신은 건너뜁니다. RTOS 전체나 렌즈 통신 자체를 실행한 것은 아닙니다. [렌즈 검증 코드] [R1: bounded_replay]

ISP 조사에서 선별한 90개 함수의 C 출력을 얻었습니다. 이는 이전 보고서의 300개 함수와 일부 중복되는 조사 집합이며 합산하지 않습니다. C 출력에 다른 함수의 꼬리 점프가 펼쳐질 수 있어, 호출 관계와 쓰기 순서는 원본 명령으로 다시 확인했습니다.

원본 파일을 다시 읽어 명령·데이터 워드 근거 265건을 대조했습니다. ISP 90개와 출력 경로 17개 함수 후보의 주소 범위·해시·분기 기록도 재현했습니다. 범위는 다음 sidecar 주소까지이며 정식 함수 크기 정보는 아닙니다. [대조 코드] [R4: selected_functions]
