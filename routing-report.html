색 처리와 HDR · 설정이 하드웨어에 닿는 지점

AF 명령의 수신자, 색 행렬 레지스터, JPEG 저장 경로

카메라 소프트웨어가 렌즈와 영상 처리 회로에 “무엇을 하라”고 전달하는 마지막 지점을 찾았습니다. 렌즈 구동 요청, 색 행렬과 감마 설정, 압축된 JPEG의 파일 저장을 각각 따라갔습니다.

이 문서에서

  1. 배경: 이 문서가 다루는 세 갈래
  2. AF 구동 요청이 렌즈 통신까지 가는 길
  3. 색 행렬 설정이 ISP 레지스터에 기록되는 경로
  4. 압축된 JPEG가 파일 쓰기 함수에 닿기까지
  5. 원본 명령으로 다시 실행한 결과
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • AF 구동 요청의 수신자를 확정했습니다. AF 초기화가 저장한 함수 포인터를 따라가면 촬영 처리 서비스의 명령 수신 함수에 닿고, 네 가지 구동 모드가 각각 렌즈 통신 요청으로 이어집니다.
  • 색 행렬 설정은 설정 캐시, 필터 객체, 레지스터 기록 함수를 차례로 거쳐 ISP 레지스터에 기록됩니다. 다만 같은 필터를 뒤에서 다시 갱신하는 경로(FIPLIB)와 다른 제출 방식(CBC)이 있어, 이 경로가 모든 촬영의 최종값이라고 볼 수는 없습니다.
  • 감마 표 쓰기로 확인한 것은 통계용 표입니다. 최종 JPEG에 같은 표가 쓰인다는 근거는 없습니다.
  • HDR 촬영의 JPEG가 파일 쓰기 함수에 전달되는 소프트웨어 경로를 연결했습니다. ISP 기록 함수는 원본 명령으로 10개 조건을 다시 실행해 164개 검사가 모두 통과했습니다. 실제 픽셀 출력과 저장된 파일은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • AF 콜백 포인터의 저장과 네 모드의 분기·렌즈 요청 인자
  • CM·FC1·FC2 레지스터 기록 함수와 감마 표 기록 함수 10개 조건
  • 근거로 인용한 원본 명령·데이터 워드 265건의 바이트 대조

정적 분석 코드를 읽어 확인

  • 색 행렬 설정이 캐시와 필터 객체를 거치는 경로
  • JPEG 압축 분기, 큐 전달, 파일 쓰기 함수까지의 연결
  • 감마 설정 함수의 호출 순서

모델 시험 조건으로 정한 것

  • 레지스터(MMIO)는 일반 RAM으로, 클록 함수는 대체 함수로 처리
  • 렌즈 큐 수신과 모드 3의 VD 동기화 이벤트는 입력으로 공급
  • 행렬 계수·감마 값은 경계값을 담은 합성 입력

미확인 확인하지 않은 것

  • ISP 안의 픽셀 계산(행렬·감마·클리핑의 순서와 비트 폭)
  • 모든 촬영에서 남는 최종 계수, FIPLIB·CBC 경로의 실제 선택
  • 렌즈 모터의 실제 움직임과 통신 파형, 저장 매체의 파일

배경: 이 문서가 다루는 세 갈래

펌웨어의 함수는 결국 하드웨어 레지스터에 값을 쓰거나 다른 작업에 메시지를 보내는 것으로 끝납니다. 이 문서는 그 마지막 지점을 세 곳에서 찾았습니다.

주소 읽는 법

이 문서의 주소는 모두 Q7의 MIPS 가상주소입니다. 원본 파일 오프셋이나 K-3 Mark III의 주소와 섞어 쓰지 않습니다.

  • 0x80…으로 시작하는 주소는 코드와 RAM입니다.
  • 0xb…로 시작하는 주소는 하드웨어 레지스터입니다. MIPS32에서 0xa0000000~0xbfffffff는 kseg1이라 부르는 구간으로, 캐시를 거치지 않고 물리 주소에 그대로 대응합니다(NetBSD의 MIPS 주소 정의). 그래서 장치 레지스터를 읽고 쓰는 MMIO에 이 구간을 씁니다.
  • 레지스터의 이름(CM, FC1 등)은 펌웨어의 클래스·함수 이름에서 왔습니다. 공개된 칩 문서에서 확인한 이름이 아닙니다.

설정 전달과 픽셀 처리는 다른 문제입니다

CPU가 레지스터에 계수를 쓰는 것과 ISP 회로가 그 계수로 픽셀을 계산하는 것은 별개입니다. 이 문서는 아래 네 단계 중 첫째와 셋째·넷째의 일부를 설명합니다.

  1. 계수·주소 설정캐시 → 필터 → 레지스터. 조건부 경로
  2. ISP 픽셀 처리내부 계산과 실제 출력은 미확인
  3. JPEG 버퍼압축 입력과 압축 결과의 전달
  4. 파일 저장저장 함수와 파일 쓰기 호출

네 단계를 하나의 검증된 픽셀 흐름으로 이어 그리지 않았습니다. ISP 출력 버퍼와 JPEG 입력의 연결은 HDR 버퍼와 색 처리 패스에서 다룹니다.

AF 구동 요청이 렌즈 통신까지 가는 길

AF 초기화가 전역 함수 포인터에 수신 함수를 저장하고, 구동 요청은 이 포인터를 거쳐 촬영 처리 서비스로 갑니다. 거기서 네 모드가 각각 렌즈 통신 요청으로 갈라집니다.

수신자를 정하는 것은 AF 초기화입니다

CAutoFocusService_Initialize는 GetOnNotifyCommand가 돌려준 수신 함수 주소를 전역 포인터에 저장합니다. LensDriveControl은 이 포인터를 읽어 명령 0x6003c와 인자 0으로 간접 점프합니다. 따라서 초기화가 끝나고 포인터 값이 유지되는 한, 수신자는 CaptureProcessService_OnNotifyCommand입니다. [근거: binding]

수신 함수는 명령에서 0x60001을 뺀 값으로 분기표를 찾습니다. 0x6003c의 항목은 ExecuteFocusControl을 호출합니다. 송신 쪽과 수신 쪽은 tFocusControlInfo 구조체를 함께 씁니다. [근거: dispatch, notification]

쉽게 말하면

AF 서비스는 렌즈 구동 요청을 “전화번호부에 적힌 번호”로 겁니다. 그 번호를 적어 넣는 쪽이 초기화 코드이고, 적힌 번호의 주인이 촬영 처리 서비스입니다.

네 구동 모드

구동 제한 상태가 1이면 모드 0·1·2는 요청을 보내지 않습니다. 허용되면 렌즈 통신 스레드의 큐에 메시지를 넣습니다. 모드 3은 검색 정보를 보류만 하고, 별도로 발생하는 VD 동기화 메시지 2가 처리될 때 그 정보가 쓰입니다. 모드 3이 VD 이벤트를 만드는 것은 아닙니다.

색 행렬 설정이 ISP 레지스터에 기록되는 경로

색 행렬은 바로 레지스터에 쓰이지 않습니다. 설정 캐시와 필터 객체를 거쳐, 갱신 표시가 있을 때만 레지스터 기록 함수가 값을 씁니다.

화살표는 설정 데이터와 객체의 관계입니다. 픽셀이 회로를 지나는 순서가 아닙니다.

단계별로 하는 일

  1. 행렬 만들기 ImageQualityService_SetupColorMatrix가 MakeColorMatrix로 행렬을 만든 뒤 설정 ID 0xe(version 2)와 0xf(version 0xc)의 설정 구조체를 내보냅니다.
  2. 캐시에 보관 StillOnSetImageProcessingEx가 촬영 모드별 캐시에 넣고, StillSetImageProcessing이 같은 캐시를 읽습니다. 경로 타입이 0이면 PathSetImageProcessing을 거쳐 IpuSetFilter로 갑니다.
  3. 처리기에 복사 CImageProcessor::SetFilter가 설정을 따로 할당한 RAM에 복사합니다. 여기까지는 레지스터가 아니라 RAM에 쓰는 단계입니다.
  4. 필터로 변환 CTranslatorC12가 상위 ID 0xe를 저수준 필터 10(CCmFilter)으로, 0xf를 필터 13(CFc1Filter)으로 바꿉니다. 이름이 비슷한 CFc2Filter는 별도의 필터 20입니다.
  5. 레지스터 기록 CIpuTaskC12::WriteAll은 필터의 UID가 드라이버에 기록된 UID와 다를 때 기록 함수를 부릅니다. 기록 함수는 객체의 갱신 표시(object+0x29)가 0이 아닐 때만 씁니다.

[근거: matrix_route, evidence]

아홉 계수가 놓이는 자리

3×3 행렬의 계수 아홉 개는 설정 구조체에 부호 있는 16비트로 들어 있고, 레지스터에는 32비트로 확장되어 기록됩니다. CM은 객체의 32비트 필드 +0x88~+0xa8을, FC1은 16비트 필드 +0x30~+0x40을 읽습니다. FC1의 추가 필드 +0x42/+0x44/+0x48은 0xb60000e4/0xb60000e8/0xb60000fc에 기록됩니다.

FIPLIB 경로가 같은 필터를 다시 갱신할 수 있고, CBC를 통한 제출도 있습니다. 레지스터 주소와 CPU의 쓰기 순서만으로 ISP 안의 행렬·감마·클리핑 순서를 정할 수도 없습니다. FIPLIB가 CM과 FC1을 어디까지 덮어쓰는지는 HDR 버퍼와 색 처리 패스에서, HDR에서 FC1에 남는 값은 HDR 제출 분기와 FC 계수에서 이어집니다. [근거: limitations]

감마 표는 통계용 고정 포트에 반복해서 씁니다

감마 설정은 AppImageProcessingSetIppGammaContext → SensorSetGammaWithId → SensorUpdateIppIpsGamma 순서로 이어집니다. 마지막 함수는 상태 레지스터의 하위 5비트가 0이 될 때까지 기다린 뒤, 조건에 따라 통계용 감마 표(LUT)를 기록합니다.

  1. 감마 지정감마 문맥 → 센서 감마 함수
  2. 바쁨 대기상태 레지스터 하위 5비트 검사
  3. GC 표 기록값 77개를 한 포트에 연속 쓰기
  4. DCI 표 기록개수 인자만큼 쓰기 (0이면 쓰지 않음)

일반 통계 표(GC)는 77개 값을 서로 다른 주소가 아니라 같은 데이터 포트에 차례로 씁니다. GC는 동기화 플래그가 0이 아닐 때, DCI는 감마 버퍼 +0x3f4가 0x4d일 때 기록합니다. DCI는 개수가 0이어도 색인 초기화와 클록 켜기·끄기는 합니다.

픽셀을 재현했는가설정·버퍼 재실행과 실제 픽셀 출력을 구분렌즈 분기와 ISP 기록 함수만 재실행. 센서에서 최종 픽셀까지의 대조는 하지 않음

한계와 재현 방법

  • 렌즈: 모터 이동량, 통신 파형, 렌즈 응답은 재지 않았습니다. 콜백 포인터가 실행 중 바뀔 가능성을 배제하지 않았습니다.
  • 색: 설정 전달 경로는 조건부입니다. 촬영마다 남는 최종 계수, FIPLIB와 CBC의 실제 선택, ISP 내부의 누산 폭·클리핑 순서·디모자이크는 확인하지 않았습니다.
  • 감마: 확인한 표는 통계 경로의 것입니다. 최종 JPEG에 쓰이는 감마는 이 문서의 범위가 아닙니다.
  • 출력: HDR 저장의 소프트웨어 경로입니다. 저장 매체에 쓰인 파일, DMA 완료, 일반 촬영 경로는 확인하지 않았습니다.

공개 CI는 펌웨어 없이 메타데이터, 시험 기준값, HTML 재생성, 링크를 검사합니다. 원본 바이트 대조와 VEX 재실행은 원본 펌웨어가 있는 로컬에서 합니다. 원본 BIN, 복원한 전체 ELF, 디컴파일 원문은 공개 저장소에 넣지 않습니다. 분석용 ELF를 만드는 절차는 압축 복원과 주요 함수 300개의 재현 절에 있습니다.
