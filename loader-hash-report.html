첫 블록 버퍼의 281바이트와 MD5 검사 경로

업데이트 로더는 카드에서 읽은 첫 블록을 그대로 기록하지 않고 일부를 고쳐 씁니다. 어디를 무엇으로 고치는지, 그리고 읽은 데이터를 MD5로 확인하는 선택 경로가 어떻게 동작하는지 원본 코드를 실행해 확인했습니다.

이 문서에서

  1. 배경: 로더가 카드의 데이터를 저장장치에 쓰기까지
  2. 첫 블록 버퍼에서 바뀌는 281바이트
  3. MBR 파티션 표에 쓰는 네 항목
  4. MD5 계산 코드와 해시 작업자
  5. MD5 결과에 따라 카드 읽기를 다시 시도하는 규칙
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 로더는 첫 블록(131,072바이트)을 저장장치에 쓰기 직전에 281바이트를 바꿉니다. 바뀌는 곳은 모두 맨 앞 1,536바이트 안의 헤더와 파티션 표입니다.
  • 281바이트를 전부 원본 코드의 쓰기 명령에 연결했습니다. 그 쓰기만 원본 데이터에 적용해도 로더가 준비한 버퍼와 SHA-256이 같았습니다.
  • 로더에 들어 있는 MD5 코드는 26개 입력에서 표준 MD5와 같은 값을 냈습니다. 이 코드를 부르는 해시 작업자와 카드 읽기 함수까지 이어 실행했습니다. 값이 맞으면 성공하고, 다르면 되감아 한 번만 더 읽습니다.
  • 실제 업데이트 파일은 이 MD5 경로를 켜지 않습니다. MD5 시험은 설정값을 바꾼 합성 조건입니다. 설치된 헤더, 저장장치 크기, 큐 전달도 시험용 값이며 카메라의 저장장치에는 아무것도 쓰지 않았습니다.

확인 원본 코드 실행으로 확인

  • 첫 블록 버퍼의 변경 281바이트와, 그것을 만든 쓰기 이벤트 170개
  • 파티션 쓰기 함수 7사례
  • MD5 계산 26사례, 해시 작업자 8사례, 해시 래퍼 9사례
  • 카드 읽기 함수 7사례 (해시 작업 9건)
  • 원본 워드 101개와 71개, 함수 구간 15개를 주소·해시로 대조

모델 시험 조건으로 정한 것

  • 카메라에 이미 설치된 헤더와 저장장치 크기 (1,024블록)
  • 저장장치의 응답 (예비 영역은 모두 FF, 상태는 성공)
  • 해시 플래그 1, 80바이트 시험 레코드, 파일 읽기·되감기의 결과
  • 큐 전달 순서 (RTOS 대신 시험 도구가 차례로 전달)

미확인 확인하지 않은 것

  • 실제 카메라의 설치 헤더와 NAND 배치
  • 짧게 읽힌 경우, 실제 RTOS 스케줄링, 캐시의 영향
  • 해시 플래그가 실제로 켜지는 조건
  • 실제 NAND 기록과 카메라의 수용·부팅

배경: 로더가 카드의 데이터를 저장장치에 쓰기까지

Q7의 업데이트 파일 맨 앞에는 로더(E01)가 들어 있습니다. 로더의 BurnNand 함수는 카드에 있는 펌웨어 본문을 131,072바이트씩 읽어 카메라 안의 NAND 플래시에 씁니다. 이 문서는 그 과정의 두 지점을 다룹니다.

  1. 카드에서 읽기두 번 읽어 비교하거나 MD5로 검사 — Loader 입력 검증, 이 문서의 MD5
  2. 배치표와 사전 검사어디에 쓸지 정하고 블록을 살핌 — 저장 경계
  3. 첫 블록 버퍼 고치기이 문서의 281바이트
  4. 기록·재시도·마무리저장장치 응답은 모델 — NAND 재시도와 최종 반환
  5. 실제 NAND와 부팅확인하지 않음

읽는 데 필요한 말

  • 블록과 섹터: 섹터는 512바이트입니다. 시험 조건에서는 256섹터, 곧 131,072바이트를 블록 하나로 두었습니다. 로더가 카드에서 한 번에 읽는 크기(청크)와 같습니다.
  • 설치된 헤더: 카메라의 저장장치에 이미 기록돼 있는 배치 정보입니다. 업데이트 파일에 든 헤더와 구분합니다. 이 문서에서는 시험용으로 만든 값을 넣었습니다.
  • 섹션: 저장장치를 용도별로 나눈 구역입니다. 로더는 번호 0~6으로 다루고, 섹션마다 36바이트짜리 정보를 헤더에 둡니다.
  • 해시 플래그: 업데이트 헤더의 값 하나입니다. 0이면 카드를 두 번 읽어 비교하고, 1이면 MD5 검사를 씁니다. 실제 파일의 값은 0입니다.
  • 다이제스트: MD5가 입력에서 계산해 내는 16바이트 값입니다. 데이터가 도중에 바뀌었는지 확인하는 데 씁니다.
  • 연산 번호: 로더가 저장 계층에 보내는 요청의 내부 번호입니다. 이 문서에는 연산 5(기록)가 나옵니다. 번호별 역할은 저장 경계 문서의 표에 있습니다.
시험 조건

실제 카메라의 저장장치 내용은 알지 못합니다. 그래서 512바이트 섹터 256개가 한 블록인 1,024블록짜리 저장장치와, 사용자 영역이 640번 블록에서 시작해 384블록인 설치 헤더를 만들어 넣었습니다. 아래 결과는 이 조건에서 원본 코드가 한 일입니다.

크기 값의 계산

①의 새 값은 원본 코드가 다음 식으로 계산합니다.

+0x214 = 0x1367b + 0x982 − 0xa00 + 3 = 0x13600

0x1367b는 업데이트 헤더 +0x214의 원래 값이고 0x982는 +0x224의 값입니다. 0xa00은 코드 영역 크기를 올림한 값입니다. 마지막의 3은 원본 명령에 들어 있는 상수이며, 섹터 규칙을 추정해 넣은 값이 아닙니다. [근거: findings.map_size]

쓰기 이벤트 3,242개 가운데 170개가 차이를 만듭니다

첫 기록 요청 직전까지 에뮬레이터는 이 버퍼에 쓰는 이벤트를 3,242개 기록했습니다. 이 수는 에뮬레이터(VEX)가 센 메모리 쓰기 횟수입니다. SWL·SWR 명령은 에뮬레이터 안에서 바이트 단위 쓰기 여러 개로 나뉘므로, MIPS 저장 명령이 실행된 횟수와는 단위가 다릅니다.

  • 앞의 170개가 헤더·섹션 표·파티션 표를 바꿉니다. 이 170개만 원본 청크에 적용해도 최종 버퍼와 같은 SHA-256이 나왔습니다.
  • 뒤의 3,072개는 명령 8개가 맨 앞 1,536바이트를 통째로 다시 복사하는 구간입니다. 이 사례에서는 값이 하나도 바뀌지 않았습니다.

그림의 회색 칸(0x318~0x397, 128바이트)과 +0x230의 4바이트는 설치된 헤더에서 복사하는 곳입니다. 이 입력에서는 원래 값과 같아서 차이에 들지 않았습니다. [근거: header_replay.trace, findings.copied_fields]

어디까지 실행했나

첫 기록 요청은 연산 5, 섹터 0, 256섹터, 예비 영역 16바이트였습니다. 이 요청을 부르는 명령과 그 지연 슬롯까지 실행하고, 저장 계층의 진입점 0x8008249c에서 멈췄습니다. 기록 자체는 실행하지 않았습니다. 기록이 실패했을 때의 재시도와, 135개 청크를 다 쓴 뒤의 마무리를 모델로 이어 본 결과는 NAND 재시도와 최종 반환에 있습니다.

MBR 파티션 표에 쓰는 네 항목

파티션 쓰기 함수는 섹션마다 16바이트 항목 하나에 시작값과 길이, 고정 값 1을 씁니다. 0번 항목에만 0x80을 직접 씁니다.

버퍼 안 MBR의 위치는 업데이트 헤더가 정합니다. 헤더 +0x200의 값 2에 512를 곱한 0x400입니다. 파티션 항목은 그 안 +0x1be부터 16바이트 간격으로 네 개가 놓입니다. 원본 함수 UpdatePartitionInMBRTable(0x8001a3a8)이 섹션 정보에서 값을 꺼내 항목을 채웁니다.

MD5 계산 코드와 해시 작업자

로더 안의 MD5 코드는 표준 MD5와 같은 값을 냅니다. 해시 작업자는 큐로 받은 세 가지 명령으로 이 코드를 부르고, 계산한 값이 기대값과 같은지 응답합니다.

MD5 계산 코드

MD5는 길이가 얼마든 입력을 받아 128비트, 곧 16바이트의 다이제스트를 냅니다. 입력을 64바이트 블록으로 나눠 처리하고, 마지막에 패딩과 64비트 길이 값을 붙입니다. 그래서 55바이트까지는 패딩과 길이가 한 블록에 들어가고, 56바이트부터는 블록이 하나 더 필요합니다. [RFC 1321, 3.1~3.4절]

원본 md5_init·md5_append·md5_finish와 내부 압축 함수를 아무것도 대체하지 않고 실행했습니다. 입력 길이는 블록 경계 앞뒤인 0·1·3·55·56·63·64·65·119·120·127·128·129바이트입니다. 길이마다 한 번에 넣은 경우와 나눠 넣은 경우를 실행해 모두 26사례입니다. 결과는 Python 표준 라이브러리의 MD5와 전부 같았습니다.

MD5("")    = d41d8cd98f00b204e9800998ecf8427e
MD5("abc") = 900150983cd24fb0d6963f7d28e17f72

이 두 값은 RFC 1321 부록 A.5의 시험값과 같습니다. 입력·작업 영역·출력 주변의 보호 바이트가 그대로인지, 마무리 직전의 비트 수가 맞는지도 확인했습니다. [근거: hash_replay.primitive_cases]

MD5 결과에 따라 카드 읽기를 다시 시도하는 규칙

해시 플래그가 1이면 카드 읽기 함수는 요청받은 길이보다 16바이트를 더 읽어 뒤 16바이트를 기대값으로 씁니다. 값이 다르면 읽은 만큼 되감고, 한 번만 더 시도합니다.

이 분기를 7사례로 실행했습니다. 이 시험에서는 MD5의 판정을 값으로 넣어 주지 않았습니다. 카드 읽기 함수가 만든 메시지를 원본 해시 작업자에게 그대로 넘기고, 작업자가 실제로 계산해 낸 응답을 돌려받았습니다. 해시 작업은 모두 9건이었습니다.

  • 길이 계산: 원본은 읽기가 성공했을 때 실제로 읽힌 길이에서 16을 뺀 값을 해시할 길이로 씁니다. 기대값의 주소는 읽은 데이터의 끝에서 16바이트 앞입니다. 64+16은 시험 입력이며, 모든 패키지의 고정 크기가 아닙니다.
  • 되감기: 불일치하면 실제로 읽힌 길이(여기서는 80)만큼 되감기를 요청합니다. 상위 워드는 0, 옵션은 3입니다. 두 번 불일치한 사례에서는 되감기를 두 번 요청한 뒤 0을 반환했습니다.
  • 실행 방식: 래퍼가 결과를 기다릴 때마다 시험 도구가 작업자를 따로 실행했습니다. 작업자에는 카드 읽기 함수의 메모리 복사본과 실제 메시지를 넘겼습니다. 두 코드가 동시에 도는 상황은 만들지 않았습니다.

판정 결과를 모델로 넣어 분기만 본 시험은 Loader 입력 검증과 렌즈 정책에 있습니다. 이 절은 그 판정 자리를 원본 MD5 계산으로 채운 것입니다. [근거: findings.request, findings.retry, replay.cases]

주의

이 시험은 해시 플래그를 1로 넣었습니다. 실제 업데이트에서 이 값이 언제 0이 아니게 되는지, 어떤 패키지가 읽기마다 다이제스트를 담고 있는지는 알아내지 못했습니다. 이 자리에서 MD5가 맞았다는 사실이 패키지의 인증이나 로더의 수용을 뜻하지도 않습니다.

K-3 Mark III와 비교

K-3 Mark III 자료도 기록·재읽기와 내부·외부 검사를 나눠서 다룹니다. Q7에서는 작은 헤더 필드의 변환과 선택적인 MD5 큐 경로를 원본 MIPS 코드로 실행했습니다. 두 기종은 프로세서, 패키지 형식, 업데이트 절차가 다릅니다. 한쪽에서 통과한 결과를 다른 쪽에 적용하지 않았습니다.

한계와 재현 방법

  • 설치된 헤더와 저장장치 형상은 합성 값입니다. 첫 기록 요청은 저장 계층 진입점에서 멈췄고, 연산 5의 처리는 실행하지 않았습니다.
  • 카드 읽기 시험은 80바이트가 전부 읽힌 경우만 다뤘습니다. 짧게 읽힌 경우, 읽힌 길이가 16보다 작은 경우, 큰 청크, 실제 RTOS의 스케줄링은 확인하지 않았습니다.
  • BurnNand의 기록·복구 반복 전체, 하드웨어 캐시, 카메라의 패키지 수용·기록·부팅은 확인하지 않았습니다.
  • 파티션 필드에 쓰는 값만으로 파일시스템 종류를 판단하지 않았습니다.
  • 전체 펌웨어, 자원 데이터, 디컴파일 결과, 수정한 업데이트 파일은 공개하지 않습니다.
