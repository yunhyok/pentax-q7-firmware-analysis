색공간 글자가 화면 가장자리에 걸칠 때

글자 일부가 화면 밖에 놓이면 그리기 함수는 밖으로 나간 픽셀을 버려야 합니다. Q7의 원본 글자 그리기 코드가 이 경계를 어떻게 처리하는지 합성 화면에서 일곱 가지 위치로 시험했습니다.

핵심 요약

  • Color Space 화면의 sRGB 글자 하나를 원본 축소 글리프 함수로 일곱 위치에 그렸습니다. 화면 안쪽 하나, 네 가장자리, 좌상단 두 곳입니다. 일곱 건 모두 화면 버퍼 전체가 따로 만든 계산과 일치했습니다.
  • 원본 코드는 픽셀마다 가로 좌표를 보기 전에 글리프 한 행의 시작 주소가 화면 버퍼 안에 있는지부터 검사합니다.
  • 그래서 글자를 (−9, −12)에 놓으면 화면 첫 행에 들어오는 픽셀 8개도 그리지 않습니다. 단순한 사각형 잘라내기라면 228번 써야 할 것을 원본은 220번만 씁니다.
  • 원본 기계어를 PC 에뮬레이터에서 실행한 결과이며 화면 버퍼·글꼴 준비는 시험 조건입니다. 실제 메뉴가 음수 좌표를 쓰는지, LCD에 어떻게 보이는지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 축소 글리프 함수의 쓰기 횟수·순서·값, 버퍼 전체(129,536바이트)와 앞뒤 보호값
  • 행 시작 주소 검사와 가로 좌표 검사의 순서
  • 원본 글꼴 선택과 속성 설정 코드

모델 시험 조건으로 정한 것

  • 736바이트 피치, 176행의 8비트 인덱스 합성 화면(초기값 0xA5)
  • 글자를 놓는 일곱 좌표(음수 좌표 포함)
  • 합성 ID 0·17 연결, 미디어·FileX·할당·캐시 응답

미확인 확인하지 않은 것

  • 실제 메뉴가 음수 좌표를 넘기는지
  • 회전·반전·세로 배율 모드, 보조 클리핑 비트맵
  • 실제 팔레트 색과 LCD 표시

배경: 글자를 화면 밖에 걸쳐 그리면

화면 버퍼 밖에 쓰면 다른 메모리를 망가뜨리므로 그리기 함수는 범위를 벗어난 픽셀을 걸러야 합니다.

Q7 메뉴 화면은 픽셀마다 팔레트 번호 1바이트를 담는 화면 버퍼에 그립니다. 글자가 화면 가장자리에 걸치면 일부 픽셀의 좌표가 음수가 되거나 폭·높이를 넘습니다. 이런 픽셀을 버리는 처리를 클리핑이라고 합니다.

보통은 글자 사각형과 화면 사각형이 겹치는 부분만 그린다고 생각하기 쉽습니다. 이 문서는 원본 코드가 정말 그렇게 하는지 확인합니다. 시험한 글자는 48×48 축소 그리기에서 쓴 LatinFont의 Color Space sRGB 행 첫 글자(내부 코드 84)입니다.

행 시작 주소를 먼저 검사합니다

원본 함수는 열을 고른 뒤 그 글리프 행의 시작 주소부터 검사합니다. 픽셀마다 가로 좌표를 보는 검사는 통과한 행에서만 합니다.

원본 열은 (j × 87381 + 43690) >> 16으로 고릅니다. 역스텝 87381은 floor(24 × 65536 / 18)이고 43690은 그 절반을 버림한 값입니다. 이 식으로 샘플을 먼저 고르기 때문에 왼쪽이나 위가 잘려도 남은 부분의 첫 픽셀을 기준으로 다시 샘플링하지 않습니다. 이 설정에서 코드 1·2·3은 각각 팔레트 번호 2·1·3으로 바뀝니다.

네 가장자리와 좌상단 두 위치

네 가장자리에서는 사각형 잘라내기와 같은 결과가 나옵니다. 차이는 글자 획이 화면 첫 행에 걸치는 좌상단에서만 드러납니다.

각 행의 네 수를 더하면 864입니다. 위·아래 배치에서 행 주소로 빠진 수는 화면 밖 행 수에 18열을 곱한 값(19행, 29행)과 같습니다. 왼쪽은 9열, 오른쪽은 7열이 가로 검사에서 빠졌습니다.

좌상단 두 배치에서는 화면 0행의 행 시작 주소가 버퍼보다 9바이트 앞에 놓입니다. (−9, 0)에서는 글리프 0행 하나(18픽셀)가 통째로 빠지지만 그 행의 보이는 열에 칠할 픽셀이 없어 쓰기는 왼쪽 배치와 같은 244번입니다. (−9, −12)에서는 화면 0행에 닿는 글리프 12행에 칠할 픽셀이 8개 있습니다. 좌표 사각형의 겹침만 보면 X=0~7에 써서 228번이 되어야 하지만 원본은 이 8곳을 건너뛰어 초기값 0xA5를 남겼습니다.

일곱 건 모두에서 864개 샘플의 원본 열과 2비트 코드, 쓰기 순서와 값, 129,536바이트 화면 전체가 독립 계산과 같았습니다. 앞뒤 16바이트 보호값도 그대로였습니다. 획이 걸친 좌상단 1건은 따로 다시 실행해 기록 전체가 같은지 확인했습니다. 나머지 6건은 저장된 원본 실행 기록을 독립 계산과 대조했습니다. 사례별 해시와 원본 구간

준비 단계와 원본 실행 범위

글꼴 선택과 속성 설정은 원본 코드로 준비했습니다. 글자 그리기 함수는 모델 호출 없이 끝까지 실행됐습니다.

기존 시험과 같은 합성 ID 0·17 연결에서 원본 글꼴 선택과 속성 설정을 실행했습니다. 준비 단계의 미디어·FileX·할당·버퍼 메타데이터·캐시는 모델이 응답합니다. 준비된 컨텍스트에서 0x80226748에 직접 들어가면 모델 호출 없이 호스트가 넣은 반환 센티널 0x0BADF000에 도달하고 스택 포인터가 돌아옵니다.

일곱 기록 모두 컨텍스트의 최종 바이트가 바뀌지 않았습니다. 하네스는 최종 차이 검사에서 팔레트 슬롯 영역 +0x24~+0x33의 변화를 허용합니다. 글꼴과 스테이징 입력도 그대로였습니다. 원본 컨텍스트 선택과 합성 등록표의 관계는 48×48 요청과 컨텍스트 선택에 있습니다.

한계와 남은 과제

Color Space의 글자 하나와 합성 화면에서 본 동작입니다.

  • 실제 메뉴가 음수 좌표를 공급하는지 확인하지 않았습니다. 이 문서의 좌표는 원본 함수에 직접 넣은 시험값입니다.
  • 다른 회전·반전·세로 배율 모드와 보조 클리핑 비트맵의 동작은 시험하지 않았습니다.
  • 물리 팔레트나 LCD에 무엇이 표시되는지는 확인하지 않았습니다. 실물 카메라에서 실행한 실험은 없습니다.

기록 검사와 단계별 재현

기록 검사에는 펌웨어와 에뮬레이터가 필요 없습니다. 원본 재현에는 Q7 v1.01 패키지와 그 패키지로 만든 분석 ELF가 필요합니다.

검증한 환경은 Python 3.12.3, angr 10.0.5, pyelftools 0.33입니다. CLI는 두 입력의 크기와 해시를 고정하고 패키지의 E04를 다시 풀어 분석 ELF의 해당 영역과 대조합니다. 원본 재현은 두 단계로 나뉩니다. 안쪽 대조를 포함한 edges 여섯 건은 몇 분이 걸립니다.

원본 패키지에서 분석 ELF 준비 
python -B tools/decode_segments.py <package> --output-dir decoded-q7
python -B tools/build_analysis_elf.py <package> --decoded-dir decoded-q7 --output analysis-q7.elf

새 로컬 경로를 씁니다. 이 두 명령의 출력은 분석 입력이며 카메라 업데이트 파일이 아닙니다.

python -B tools/check_colorspace_clip.py check
python -B tools/check_colorspace_clip.py replay <package> <analysis-elf> --stage corner --output corner.json
python -B tools/check_colorspace_clip.py replay <package> <analysis-elf> --stage edges --output edges.json
python -B tools/check_colorspace_clip.py project edges.json corner.json --output clip-summary.json

두 단계의 전체 실행 기록을 각각 고정 해시와 비교한 뒤에만 일곱 건의 공개 요약을 만듭니다. 이미 있는 출력 경로와 python -O 실행은 거부합니다. 공개 요약에는 원본 글꼴이나 프레임 바이트가 들어 있지 않습니다.

근거 파일과 참고 자료

  • analysis/colorspace-clip.json — 공개 요약: 일곱 건의 쓰기 수·해시·걸러진 수, 원본 구간, 준비 단계 모델
  • tools/check_colorspace_clip.py — 재현 코드: 기록 검사, 원본 재실행, 요약 생성
  • tests/test_colorspace_clip.py — 기록 고정값과 입력 보호 시험
  • 48×48 요청과 컨텍스트 선택 — 같은 축소 렌더러와 Q16 배율
  • 용어집: 클리핑
