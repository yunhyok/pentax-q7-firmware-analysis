펌웨어 파일 구조: 공식 파일 확인과 ELF 12개

코드를 읽기 전에 두 가지를 먼저 확인했습니다. 분석하는 파일이 정말 공식 배포본인지, 그리고 그 안에 무엇이 어떤 형식으로 들어 있는지입니다.

핵심 요약

  • 분석한 fwdc603p.bin은 리코 공식 배포 ZIP 안의 파일과 크기·SHA-256·모든 바이트가 같습니다.
  • 파일 안에서 32비트 리틀엔디언 MIPS ELF 12개를 찾았습니다. 실행형이 10개, 재배치형이 2개입니다.
  • RTOS인 ThreadX와 파일시스템 FileX의 식별 문자열과 심볼 이름이 남아 있습니다. 코드를 읽을 출발점이 됩니다.
  • 이 문서는 파일의 구조만 다룹니다. 함수가 실제로 무슨 일을 하는지는 압축 복원과 주요 함수 300개부터 이어지는 문서들이 다룹니다.

분석 대상이 공식 배포본인지 확인

제공받은 파일은 리코 공식 q7_101.zip에 든 fwdc603p.bin과 완전히 같습니다.

두 파일의 크기와 SHA-256을 비교하고 모든 바이트를 대조했습니다. 따라서 이 연구의 대상은 공식 배포 v1.01입니다. 이 확인은 “같은 파일인가”를 본 것입니다. 카메라가 업데이트할 때 하는 서명 검증을 대신하지는 않습니다.

조사 순서와 K-3 Mark III와의 차이

K-3 Mark III를 조사할 때 쓴 순서를 그대로 따랐습니다.

  1. 원본 식별SHA-256, 공식 ZIP과 대조
  2. 파일 구조ELF 헤더, 구간과 경계 검사
  3. 분석 지점 확보진입점, 심볼, 문자열 위치
  4. 코드 분석호출 관계와 함수 동작 — 이후 문서

순서는 같지만 파일 형식은 다릅니다. K-3 Mark III용 LZ 압축 해제기를 고치지 않고 Q7 파일의 0x80 위치에 적용하면 실패합니다. 그 위치와 형식이 맞지 않는다는 뜻이며 Q7에 압축 데이터가 없다는 뜻은 아닙니다. 실제로 Q7의 본 프로그램은 다른 위치에 압축되어 있고 그 복원은 압축 복원과 주요 함수 300개에서 다룹니다. [근거: k3_lz_probe]

ELF 12개가 가리키는 파일 구간

ELF 서명은 13곳에서 나왔고 헤더와 참조 범위 검사를 통과한 것은 12개입니다.

통과하지 못한 한 곳(0x1DC2C4)은 ELF 식별 바이트 뒤에 DllMutex라는 문자열이 이어져 있어 제외했습니다. 아래 그림은 각 ELF가 참조하는 마지막 바이트까지의 범위입니다.

검사를 통과한 ELF는 모두 32비트(ELFCLASS32), 리틀엔디언(ELFDATA2LSB), MIPS(EM_MIPS)입니다. 종류는 두 가지입니다.

  • 실행형(ET_EXEC) 10개 — 주소가 정해진 프로그램입니다.
  • 재배치형(ET_REL) 2개: 심볼 값이 섹션 기준입니다. 실제 메모리 주소로 옮기려면 로더와 재배치 처리를 확인해야 합니다.

일부 ELF는 섹션 표가 없는데도 e_shstrndx 값이 13으로 남아 있어 경고로 기록했습니다. [근거: elfs, rejected_candidates, warnings]

ThreadX와 FileX의 흔적

RTOS와 파일시스템 라이브러리의 이름이 문자열과 심볼로 남아 있어, 코드를 읽기 시작할 지점을 얻었습니다.

원본 파일에 ThreadX LX4180/Green Hills와 FileX LX4180/Green Hills 문자열이 있습니다. 첫 번째 ELF(E01)에는 ThreadX와 FileX 함수 이름으로 보이는 심볼도 있습니다. ThreadX 계열 코드가 들어 있다는 근거입니다.

이 근거로 말할 수 없는 것

문자열과 심볼만으로는 실제 칩의 모델이나, 카메라에서 실행되는 구성 요소 전체를 확정할 수 없습니다.

심볼의 수와 한계

E01의 심볼 표에는 2,121개 항목이 있고 그중 정의된 함수 심볼(STT_FUNC)은 1,437개입니다. ELF 전체를 합치면 심볼 2,569개, 정의된 함수 심볼 1,504개입니다. 같은 함수가 여러 번 나올 수 있으므로 이 수를 “함수의 개수”로 읽으면 안 됩니다.

심볼 이름은 어디를 조사할지 알려 줄 뿐입니다. 그 함수가 실제로 이름대로 동작한다는 증거는 아닙니다.

파일 전체의 바이트 분포

파일을 65,536바이트(64 KiB)씩 나눠 구간마다 Shannon 엔트로피를 계산했습니다. 값이 높은 구간은 압축 데이터나 영상 자원일 가능성이 있어 조사할 후보가 됩니다. 엔트로피만으로 암호화 여부를 판정하지는 않았습니다.

재현 방법

Python 3.10 이상의 표준 라이브러리만 씁니다. 원본 파일은 읽기만 하고 결과는 새 경로에 씁니다.

python -m unittest discover -s tests -v
python tools/pentax_lz.py --self-test
python tools/inspect_q7.py path/to/fwdc603p.bin --output .private/recheck.json --private-dir .private/recheck-elf
python tools/verify_report.py --firmware path/to/fwdc603p.bin
python tools/build_report.py

검증 도구는 파서를 합성 입력으로 시험하고 공개 근거가 서로 맞는지, 보고서가 근거에서 다시 생성되는지, 문서 안 링크가 살아 있는지 확인합니다. 원본 파일을 지정하면 공개한 측정값 전체를 다시 계산해 비교합니다.

이 단계에서 쓴 도구

이 문서의 결과는 Python으로 파일 바이트와 ELF 헤더를 직접 읽어 얻었습니다. Binwalk·Unblob 같은 펌웨어 스캐너나 디컴파일러는 이 단계에서 쓰지 않았습니다. [근거: 도구 가용성 기록]
