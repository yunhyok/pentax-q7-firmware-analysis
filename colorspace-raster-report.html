선택 강조 사각형이 픽셀로 칠해지는 과정

선택된 줄을 둘러싼 강조 표시는 사각형 다섯 개로 그려집니다. 이 사각형들이 화면 버퍼에 어떤 번호로, 어떤 코드 경로를 거쳐 칠해지는지 원본 코드로 확인했습니다.

이 문서에서

  1. 배경: 강조 표시가 만들어지는 곳
  2. 테두리마다 다른 쓰기 경로를 탑니다
  3. GDI 채우기는 원본 8비트 컨텍스트로 실행했습니다
  4. 경계 조건까지 버퍼 전체를 대조했습니다
  5. K-3 Mark III와 비교
  6. 한계와 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 그리기 요청 단계에서 기록한 사각형 다섯 개를 원본 도형 함수에 넣어 실행했습니다. 테두리는 폭과 x 좌표에 따라 직접 쓰기 루프 또는 GDI 사각형 채우기로 나뉘어 칠해집니다.
  • 두 강조 위치(sRGB, AdobeRGB) 모두 요청 하나마다 129,536바이트 버퍼 전체를 독립 계산과 비교했고 전부 같았습니다. 최종적으로 바뀐 바이트는 각각 34,560개(720×48)입니다.
  • 경계 조건 시험 5개(정렬된 word·halfword 쓰기, 홀수 x, 오른쪽·아래 잘림, 높이 0)도 같은 방식으로 대조했습니다.
  • 쓴 값은 팔레트 번호 0x4d·0x4e·0x4f입니다. 이 번호가 실제 어떤 색인지, 버퍼가 LCD로 나가는 과정은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 도형 함수의 경로 선택과 직접 쓰기 루프
  • 원본 8비트 컨텍스트 템플릿 복사, 비트맵 생성·선택, 좌표 변환·잘림·memset
  • 7개 사례의 버퍼 전체와 앞뒤 보호 영역 일치

모델 시험 조건으로 정한 것

  • 사각형 인수: 그리기 경로에서 기록한 값을 다시 입력
  • 736×176 합성 버퍼(초기값 165), 좌표 배율 0(항등 변환)
  • 기본 컨텍스트와 버퍼 ID 17을 같은 컨텍스트로 연결
  • 메모리 할당·버퍼 정보·캐시 API 3곳

미확인 확인하지 않은 것

  • 화면 갱신부터 픽셀까지 한 번에 이어진 실행
  • 실제 팔레트 RGB, 화면 전송(DMA), LCD
  • 다른 도형 스타일, 배율 변경, 직접 쓰기 경로의 범위 초과

배경: 강조 표시가 만들어지는 곳

색공간 화면에서 선택된 줄은 가로로 긴 강조 사각형으로 표시됩니다. 그리기 경로에서 이 강조가 위·왼쪽·아래·오른쪽 테두리와 안쪽, 모두 사각형 다섯 개의 요청이라는 것을 확인했습니다. 이 문서는 그 요청이 화면 버퍼의 바이트로 바뀌는 단계를 다룹니다.

  1. ① 선택·확정·취소색공간 화면: 선택·확정·취소
  2. ② 그리기 요청그리기 경로
  3. ③ 강조 픽셀이 문서
  4. ④ 글자 픽셀글꼴 로딩과 글리프 픽셀
  5. ⑤ 글자 크기·컨텍스트48×48 요청과 컨텍스트 선택
  6. 팔레트·LCD미확인

읽는 데 필요한 말은 세 가지입니다.

인덱스 버퍼
픽셀 하나가 1바이트이고, 그 값은 색이 아니라 팔레트 번호입니다. 이 시험의 버퍼는 가로 736바이트 × 세로 176줄입니다.
GDI
그리기 기능을 모아 둔 계층입니다. 좌표 변환과 화면 밖 잘라내기를 한 뒤 메모리를 채웁니다.
컨텍스트
그릴 버퍼, 브러시 색, 그리기 함수 표를 담은 구조체입니다. 8비트 화면용 템플릿 sDcOsd8을 복사해 만듭니다.

테두리마다 다른 쓰기 경로를 탑니다

도형 함수는 사각형의 폭과 x 좌표를 보고 세 경로 중 하나를 고릅니다. 강조의 위·아래 테두리는 halfword 루프로, 왼쪽·오른쪽 테두리와 안쪽은 GDI 채우기로 칠해집니다.

폭 720은 32의 배수가 아니므로(720 = 32 × 22.5) 첫 조건을 통과하지 못하고, 16의 배수(16 × 45)라서 halfword 루프로 갑니다. 폭 4와 712는 16의 배수가 아니어서 GDI로 갑니다. word 루프의 저장 명령은 0x8043ecfc, halfword 루프는 0x8043ed94에 있습니다. 이 시험은 좌표 배율을 0으로 초기화해 좌표가 바뀌지 않는 항등 변환 경로를 썼습니다. 다른 스타일과 실물 CPU의 비정렬 쓰기 동작은 이 사례로 확인하지 않습니다. [근거: findings.branches]

강조 하나를 칠하는 다섯 단계

sRGB 강조(y = 64)의 다섯 요청은 halfword·GDI·halfword·GDI·GDI 순서로 실행됐습니다. 요청 하나가 끝날 때마다 버퍼 전체를 따로 계산한 결과와 비교했습니다. “바뀐 바이트”는 처음 상태와 다른 바이트의 누적 개수입니다.

누적 수가 사각형 넓이의 합보다 작은 것은 겹치는 부분 때문입니다. 예를 들어 왼쪽 테두리(4×44 = 176)는 위 테두리와 4×6 = 24바이트가 겹치므로 152만 늘었습니다. 안쪽이 마지막에 칠해지면서 위 테두리의 아래 두 줄을 덮고, 최종 결과는 강조 영역 전체 720×48 = 34,560바이트입니다. 겹쳐 쓴 곳과 그대로 남은 곳 모두 비교에 들어갔습니다. [근거: findings.highlight, replay.cases]

GDI 채우기는 원본 8비트 컨텍스트로 실행했습니다

GDI가 어느 함수로 채울지는 컨텍스트 안의 함수 포인터가 정합니다. 원본 템플릿을 복사해 컨텍스트를 만들었더니 8비트 화면용 FillRect가 선택됐습니다.

원본 GdiCreateDisplayContextEx가 sDcOsd8 템플릿을 복사하고, 원본 비트맵 생성·선택 함수가 합성 버퍼의 주소와 크기를 연결합니다. 일반 FillRect 0x8022cf9c는 컨텍스트 +0x880의 포인터를 따라 8비트 FillRect 0x80225820을 부릅니다. 좌표 변환, 경계 잘림, memset은 원본을 실행했고, 메모리 할당·버퍼 정보(GetBuffer)·캐시 API 세 곳만 대체했습니다. [근거: context_template, findings.gdi]

시험 조건: 두 컨텍스트 포인터를 같게 맞춤

시험은 기본 컨텍스트 포인터 0x800eb4d8과 버퍼 ID 17의 조회 결과를 같은 컨텍스트로 맞췄습니다. 원본 속성 설정 함수 AppOsdSetAttributeByBufferID는 기본 포인터가 0이면 고른 컨텍스트 대신 psDcOsd를 쓸 수 있습니다. 이 조건을 빼면 브러시 설정과 채우기가 서로 다른 컨텍스트를 볼 수 있으므로 재현 조건에 적었습니다. 카메라 초기화에서 오류를 발견했다는 뜻이 아니며, 실제 연결은 조건부 컨텍스트 선택에서 따로 다룹니다. [근거: findings.binding]

메모리 검사 방식과 VEX 이벤트 읽는 법
  • 메모리 검사는 기호식 주소와 허용 범위를 벗어난 접근을 거부합니다. 원본 이미지 범위와 미리 넣은 전역 값은 읽을 수 있고, 쓰기는 스택·컨텍스트·비트맵 설명자·합성 프레임에만 허용합니다. 요청마다 앞뒤 8바이트 보호 영역도 확인했습니다.
  • 기록한 쓰기 횟수는 VEX의 메모리 이벤트 수이며 실물 버스 트랜잭션 수가 아닙니다.
  • VEX 이벤트의 pc는 scratch.ins_addr입니다. 그래서 지연 슬롯의 저장 명령이 앞의 분기 주소로 기록될 수 있습니다. 0x800fb7b8·0x800fb7d8·0x800fb7ec로 기록된 쓰기는 실제로 0x800fb7bc·0x800fb7dc·0x800fb7f0의 MIPS 저장 명령입니다.
  • 홀수 x 사례에서는 SWR 변환 때문에 이벤트 크기의 합이 66바이트이지만 바뀐 픽셀은 64바이트입니다. 판정 기준은 버퍼 전체 대조입니다.

K-3 Mark III와 비교

K-3 Mark III의 색공간 자료는 기종별 텍스트 ID·아이콘·보류 선택값과 화면 갱신 경계를 알려 줍니다. Q7에서는 즉시 기록·취소 복원 방식에 더해 선택 강조의 인덱스 쓰기를 확인했습니다. 이 결과는 화면을 다시 만들 때 쓰기 순서와 강조 모양을 정하는 근거가 됩니다. K-3 Mark III의 렌더러나 자원 형식을 Q7에 그대로 옮길 수 있다는 근거는 아닙니다. [고정 커밋의 K-3 Mark III 색공간 근거]

한계와 재현 방법

인덱스 RAM에 쓰인 번호까지는 확인했고, 그 뒤 실제 색과 화면 출력은 남아 있습니다.

  • 사각형 인수는 앞선 원본 갱신에서 얻은 값을 입력으로 썼습니다. 화면 갱신부터 도형 픽셀까지 한 번에 이어서 실행하지는 않았습니다.
  • 합성 인덱스 RAM은 팔레트 번호가 쓰였다는 것만 보여 줍니다. 실제 RGB나 LCD 출력은 아닙니다.
  • 글자, 0이 아닌 다른 스타일, 배율 변경, 실제 팔레트, 장치 등록, 화면 전송, DMA, LCD는 확인하지 않았습니다. 컨텍스트를 만든 것이 장치 등록을 뜻하지는 않습니다.
  • 글자 픽셀은 글꼴 로딩과 글리프 픽셀에서 별도로 확인했습니다. 같은 “sRGB” 글자를 새 기본 배율 컨텍스트에 넣은 시험이며, 실제 화면 상태를 이어받은 실행은 아닙니다.
