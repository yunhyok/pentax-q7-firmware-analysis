01 / DIRECT STORES OR GDI

강조 테두리는 서로 다른 쓰기 경로를 사용한다

원본 DrawShape_Line의 style 0 분기는 변환된 폭과 x 좌표로 쓰기 경로를 고릅니다. 폭이 32의 배수이고 x가 짝수이면 word 루프를, 그 밖에서 폭이 16의 배수이고 x가 짝수이면 halfword 루프를 사용합니다. 나머지는 브러시 색을 설정하고 GDI 사각형 채우기로 보냅니다. 다른 style과 실물 CPU의 비정렬 쓰기는 이번 사례에 포함하지 않았습니다. [R1: findings.branches·evidence]

Color Space에서 얻은 다섯 요청은 halfword·GDI·halfword·GDI·GDI 순서로 실행됐습니다. y=64와 y=112 두 사례에서 요청 하나가 끝날 때마다 버퍼 전체를 대조했습니다. 최종 변경 영역은 각각 34,560바이트이며 겹쳐 쓰는 부분과 그대로 남는 부분도 비교에 포함했습니다. 인덱스 0x4d·0x4e·0x4f가 실제로 어떤 RGB 색인지는 아직 확인하지 않았습니다. [R2: CASES·ordered rectangle oracle]

02 / ORIGINAL 8-BIT CONTEXT

간접 채우기의 수신자를 원본 템플릿으로 정한다

원본 GdiCreateDisplayContextEx가 sDcOsd8 템플릿을 복사하고 원본 비트맵 생성·선택 함수가 합성 버퍼의 주소와 크기를 연결합니다. 컨텍스트 +0x880의 함수 포인터는 8비트 FillRect인 0x80225820을 선택합니다. 좌표 변환·경계 잘림·memset은 원본을 실행했고 메모리 할당·GetBuffer·캐시 API 세 곳만 대체했습니다. [R1: context_template·findings.gdi]

시험에서는 기본 컨텍스트 포인터 0x800eb4d8과 버퍼 ID 17의 조회 결과를 같은 컨텍스트로 맞췄습니다. 원본 속성 설정 코드는 기본 포인터가 0이면 선택한 컨텍스트 대신 psDcOsd를 사용할 수 있습니다. 이 조건을 빼면 브러시 설정과 채우기가 다른 컨텍스트를 볼 수 있으므로 재현 조건에 명시했습니다. 실제 카메라 초기화의 오류를 발견했다는 뜻은 아닙니다. [R1: findings.binding·evidence]

03 / WHOLE BUFFER COMPARISON

겹침·경계·그대로 남은 픽셀을 모두 대조한다

추가 다섯 사례는 word·halfword 직접 쓰기, 홀수 x의 GDI 선택, 오른쪽·아래 경계 잘림, 높이 0을 확인합니다. 736×176 버퍼의 (733,174)에 7×4 GDI 사각형을 요청하면 경계 안의 3×2, 총 6바이트만 바뀝니다. 직접 쓰기 경로의 범위 초과는 시험하지 않았으며 GDI의 잘림 동작을 그 경로에도 적용할 수는 없습니다. [R1: replay.cases]

04 / K-3 MARK III COMPARISON

공통 UI 동작과 기종별 렌더러를 구분한다

K-3 Mark III의 Color Space 자료는 기종별 텍스트 ID·아이콘·pending 선택값과 표시 갱신 경계를 제공합니다. Q7에서는 즉시 설정·취소 복원 방식에 더해 선택 강조의 인덱스 쓰기를 확인했습니다. 이 결과는 UI 동작을 재구현할 때 쓰기 순서와 강조 형상을 정하는 근거이며 K-3의 렌더러나 리소스 ABI를 Q7에 그대로 이식할 수 있다는 근거는 아닙니다. [K1: 고정 커밋의 Color Space 근거]

05 / REMAINING OUTPUT BOUNDARIES

인덱스 RAM에서 실제 표시까지는 남아 있다

이번 도구는 앞선 원본 갱신에서 얻은 도형 인수를 입력으로 사용합니다. 전체 UI 생산자부터 도형 픽셀까지 한 번에 연속 실행하는 과정은 이번 검증 범위 밖입니다. 글리프·실제 팔레트·비단위 배율·장치 등록·DMA·LCD는 미검증입니다. 다음 단계는 글꼴 리소스와 간접 렌더러를 잇고 전체 갱신 경로에 픽셀 검사를 연결하는 것입니다. [R1: limitations]
