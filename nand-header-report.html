NAND 식별값과 부트 헤더의 재지정 분기

MAIN의 기록 함수는 매체를 열다가 NAND 칩의 식별값을 요청합니다. 그 요청에 시험값을 넣고 원본 코드를 이어 실행해, 식별값과 부트 헤더가 다음 읽기 위치를 어떻게 정하는지 살폈습니다.

이 문서에서

  1. 배경: NAND 식별값과 부트 헤더
  2. 세 종류의 시험은 각각 새로 시작합니다
  3. 식별값의 네 번째 바이트가 헤더 검색 간격을 바꿉니다
  4. 헤더 +0x14의 최상위 비트가 두 번째 읽기 위치를 고릅니다
  5. 저장장치 크기 계산과 헤더 +0x200은 다른 필드를 씁니다
  6. K-3 III와는 저장 계층만 대조했습니다

  8. 재현 방법

핵심 요약

  • 식별값 해석 함수를 시험용 식별값 12가지로 실행했습니다. 제조사·장치 번호·네 번째 바이트·종류 인수에 따라 수락 여부와 핸들에 남는 값이 달라졌습니다.
  • 원본 매체 열기에 네 번째 바이트만 다른 식별값 두 개를 넣었더니 부트 헤더를 찾는 간격이 32와 256으로 갈렸습니다.
  • 부트 헤더의 한 워드에서 최상위 비트가 1이면 원본 코드는 나머지 값으로 두 번째 읽기 위치를 계산합니다. 같은 값 291이 간격에 따라 위치 288과 256이 됐습니다(4사례).
  • 위치·개수·간격은 펌웨어 내부 호출의 인수입니다. 실제 NAND의 페이지·블록 단위와 연결했다는 뜻은 아닙니다.
  • 식별값, 예비 영역, 헤더, 응답 상태는 모두 시험용으로 넣은 값입니다. 실제 NAND를 읽거나 쓰지 않았고 카메라에서 실행하지도 않았습니다.

확인 원본 코드 실행으로 확인

  • 식별값 해석 12사례, 매체 열기에서 헤더 함수 진입까지 2사례
  • 헤더 재지정 분기 4사례(헤더 함수가 호출자로 돌아올 때까지)
  • 원본 파일과 분석 ELF의 11개 구간·67개 워드 바이트 대조

정적 분석 코드를 읽어 판단

  • 장치 번호 0xf1의 분기 대상
  • 저장장치 크기 계산 함수가 읽는 필드
  • 헤더 +0x200을 복사하는 위치

모델 시험 조건으로 정한 것

  • NAND 식별값 8바이트와 응답 상태
  • FF로 채운 예비 영역 16바이트, 합성 헤더
  • 메모리 할당·뮤텍스·진단 출력, 해제 요청(기록만 함)

미확인 확인하지 않은 것

  • 장착된 NAND의 실제 식별값·용량·헤더
  • 내부 위치와 물리 주소의 대응
  • 헤더 함수가 돌아온 뒤의 실행, 기록·부팅·복구

배경: NAND 식별값과 부트 헤더

NAND 플래시 칩은 READ ID 명령(명령 바이트 0x90)을 받으면 몇 바이트짜리 식별값을 돌려줍니다. 첫 바이트는 제조사, 둘째 바이트는 장치 번호입니다. 리눅스 커널의 표에서 0xec는 Samsung, 0xad는 Hynix, 0x98은 Toshiba입니다. 커널의 일반 드라이버는 넷째 바이트에서 페이지·블록 크기를 풀어냅니다. Q7의 해석 함수가 같은 규칙을 쓰는지는 확인하지 않았습니다.

식별값 해석 함수
FcuNandParseId. 식별값을 읽고 칩을 받아들일지 정한 뒤 핸들(드라이버가 쓰는 상태 구조체)에 용량·간격 값을 적습니다.
부트 헤더
펌웨어가 NAND 앞부분에서 찾는 0x400바이트 블록입니다. 후보 위치마다 예비 영역을 먼저 읽고 조건이 맞을 때만 데이터를 읽습니다.
예비 영역
NAND에서 데이터 옆에 딸린 작은 영역입니다. 보통 오류 정정 부호와 불량 블록 표시를 둡니다. 이 문서의 요청에서는 16바이트입니다.
연산 번호
펌웨어가 저장 계층에 보내는 요청의 내부 번호입니다. 2는 식별, 4는 데이터 읽기, 6은 예비 영역 읽기입니다. 칩에 보내는 명령 바이트와는 번호 체계가 다릅니다.
VEX 이벤트
에뮬레이터가 실행한 코드 블록 수로, CPU 명령 수나 실행 시간과는 다릅니다.

이 문서는 MAIN Burn의 매체 열기가 멈춘 자리에서 시작합니다. 거기서는 원본 FileX 매체 열기가 식별 요청 직전에서 멈췄습니다. 같은 초기 상태에서 그 구간을 다시 실행했습니다. 요청 인수를 확인한 다음 응답을 넣었습니다.

세 종류의 시험은 각각 새로 시작합니다

식별값 해석 12건, 헤더 함수 진입 2건, 재지정 4건은 서로 이어진 실행이 아닙니다. 시험마다 새 상태에서 출발하고 멈추는 자리도 다릅니다.

재지정 사례 안에서는 매체 열기 상태를 유지한 채 헤더 함수까지 이어 실행합니다. 매체 열기 쪽 시험은 드라이버가 미리 넣은 핸들 값을 가지고 시작합니다. 식별값 해석만 하는 시험의 핸들은 0으로 채워져 있습니다. 두 시험의 숫자가 다른 이유는 이 초기 상태 차이입니다. [근거: native_open_entries, header_redirect]

식별값의 네 번째 바이트가 헤더 검색 간격을 바꿉니다

참고

장치 번호 분기표에는 0x33부터 0xf1까지 191개 항목이 있습니다. 그중 161개는 같은 거부 경로를 가리킵니다. 0xf1 항목은 정적으로만 확인했으며 실행 사례에는 넣지 않았습니다. 이 0xf1은 앞 문서에서 모델로 넣은 FileX 반환값 0xf1과 관계없는 값입니다. [근거: parser.device_table_groups, source.f1]

헤더 +0x14의 최상위 비트가 두 번째 읽기 위치를 고릅니다

헤더 +0x14 워드의 bit 31이 0이면 첫 헤더를 그대로 돌려줍니다. 1이면 하위 31비트를 간격으로 나눴다가 다시 곱한 위치에서 헤더를 한 번 더 읽습니다.

재지정 여부는 0x80055c28의 분기가 워드의 부호를 보고 정합니다. 헤더 함수는 0x400바이트 버퍼를 요청합니다. 모델이 버퍼를 내주면 원본 코드는 연산 6으로 FF 16바이트를 받고 연산 4로 합성 헤더를 받습니다. 나눈 몫에 간격을 다시 곱하는 일은 다음 검색 함수가 합니다. 예비 영역을 FF로 준 조건에서는 그 결과가 두 번째 데이터 읽기의 위치로 나타났습니다. [근거: header_redirect.branch, io, source.words]

주의

관측한 개수 2는 부트 헤더 함수가 0x80055bb4와 0x80055c20에서 넣는 상수입니다. 호출자도 0x80056710에서 0x400 >> 9 = 2를 계산하지만 그 값은 다른 호출 분기에서 씁니다. 이 2를 실제 매체의 페이지 크기나 블록 크기로 읽지 않습니다.

저장장치 크기 계산과 헤더 +0x200은 다른 필드를 씁니다

식별값 해석이 채운 용량 필드와 부트 헤더에서 복사되는 값은 핸들 안에서 서로 다른 칸에 들어갑니다. 두 값을 하나로 묶어 설명하지 않습니다.

크기 계산 함수 _fx_nand_get_geometry(0x80064040)는 인수 포인터 +0x2c를 읽습니다. 드라이버가 넘기는 포인터는 핸들 +0xbc8이므로 이 입력은 해석 함수가 쓰는 +0xbf4입니다. 헤더 반환 이후의 코드는 헤더 +0x200을 핸들 +0xc10에 복사합니다. [근거: source.words의 geometry_calculation_static_only, native_flags_and_header_call]

이 문서의 18건은 크기 계산과 헤더 +0x200 소비를 실행하지 않았습니다. 그 뒤 이야기는 부트 헤더 값과 별도 읽기 요청에서 이어집니다.

K-3 III와는 저장 계층만 대조했습니다

K-3 III의 부팅·저장소 문서는 M0·BOOT·RTOS 단계와 Emmc 드라이버, FwPartition 객체를 다룹니다. Q7의 이 경로는 FileX에서 NAND 식별 응답과 부트 헤더로 내려가는 MIPS 코드입니다. K-3 III의 bank 필드나 eMMC 단위를 Q7에 옮길 근거는 찾지 못했습니다.

검증 방식은 같습니다. 코드의 분기·인수·반환은 실행해서 확인합니다. 저장장치 응답을 대신한 모델과 실기에서 보지 않은 값은 따로 적습니다. K-3 III에서 단계 사이 주소 대응이 미확인인 것처럼 Q7도 KSEG 별칭·TLB·캐시·DMA를 포함한 물리 주소 대응을 증명하지 못했습니다.

한계와 남은 과제

  • 장착된 NAND의 실제 식별값·용량·헤더는 모릅니다. 표의 식별값은 모두 시험용입니다.
  • 요청의 위치와 개수는 펌웨어 내부 인수입니다. 섹터·페이지·블록과의 대응은 관측하지 않았습니다.
  • 평평한 ELF 가상 주소와 합성 포인터로 실행했습니다. KSEG 별칭, TLB, 캐시, DMA는 모델에 없습니다.
  • 헤더 함수가 돌아온 뒤의 필드 복사와 다음 FileX 드라이버 요청이 다음 확인 지점입니다.
  • 플래시 기록, 카메라 부팅, 촬영, 렌즈 동작은 하나도 실행하지 않았습니다.

재현 방법

실행 엔진은 angr 10.0.5의 VEX이며 원본 MIPS32 리틀엔디언 명령을 실행했습니다. 이 환경에서는 Unicorn 라이브러리와 REA의 네이티브 분석 공급자를 쓸 수 없었습니다. 결과의 근거는 원본 바이트 대조와 VEX 실행입니다.

python tools/check_nand_headers.py <원본 fwdc603p.bin> <분석 main-expanded.elf> --output <새 결과.json>
python tools/build_all.py
python tools/verify_report.py --firmware <원본 fwdc603p.bin>
python -m unittest discover -s tests

재현기는 원본 펌웨어와 분석 ELF의 SHA-256을 먼저 확인합니다. 결과는 새 파일로만 만들고 기존 파일·입력 경로·링크를 덮어쓰지 않습니다. assertion이 꺼지는 python -O 실행은 거부합니다. 분석 ELF는 기존 생성 도구로 원본에서 복원합니다. 원본 파일과 ELF는 저장소에 없으며 보고서 빌드와 저장된 결과 검사는 원본 없이 돌아갑니다. 원본 명령 18건의 재실행은 check_nand_headers.py가 맡습니다.

시험 조건

매체 열기 시험은 합성 전역값을 준비합니다. 열린 매체 목록 포인터 _fx_system_media_opened_ptr(0x81547f10)에 32비트 0, bDebugPrint(0x8008c2dc)에 1바이트 0, gulTlErrorStatus(0x8008c2f4)에 32비트 0을 넣고 뒤의 두 주소는 쓰기도 허용합니다. 분석 ELF의 적재 구간에는 읽기·쓰기·실행 권한(RWX)을 줍니다. 원본 바이트 대조와 이 합성 상태는 별개이며 카메라의 실제 메모리 내용·권한을 검증한 것이 아닙니다.
