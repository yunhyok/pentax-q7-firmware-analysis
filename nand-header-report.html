NAND 식별값과 부트 헤더의 재지정 분기

원본 매체 열기에서 멈췄던 NAND 식별 요청에 시험값을 넣고 실행을 이어 갔습니다. 식별값에 따라 헤더 검색 간격이 달라졌고 헤더의 한 비트가 다음 읽기 위치를 바꾸었습니다.

이 문서에서

  1. 18개 사례의 출발점과 종료 지점
  2. 식별값의 네 번째 바이트가 헤더 검색 간격에 영향을 줍니다
  3. 헤더 +0x14의 bit 31이 다음 읽기 위치를 선택합니다
  4. 저장장치 크기 계산의 입력과 헤더 +0x200은 다른 필드입니다
  5. K-3 III와는 저장 계층과 검증 범위를 대조했습니다
  6. 재현 방법과 근거 파일

핵심 요약

  • 식별값 해석 함수 FcuNandParseId를 12가지 입력으로 실행했습니다. 제조사·장치 ID·네 번째 바이트·종류 인수에 따라 반환값과 핸들 필드가 달라졌습니다.
  • 원본 매체 열기에 ec dc 00 00 또는 ec dc 00 01로 시작하는 식별값을 넣으면 헤더 함수의 간격 인수가 각각 32, 256이 됩니다. 별도 실행 2건은 함수 본문 진입 직전에서 멈췄습니다.
  • 후속 실행 4건에서는 합성 헤더 +0x14의 bit 31을 확인했습니다. 비트가 1이면 하위 31비트의 값 291을 간격으로 나눴다가 다시 곱하여, 위치 288 또는 256에 두 번째 읽기를 요청했습니다.
  • 이 값들은 펌웨어 내부 호출의 위치·개수·간격입니다. 실제 NAND의 섹터·페이지·블록 단위와 연결되었다는 뜻은 아닙니다.

확인 원본 코드 실행

ID 해석 12건, 헤더 함수 진입 2건, 재지정 분기 4건. 원본 파일과 분석 ELF의 11개 범위·67개 워드를 대조했습니다.

정적 분석 실행하지 않은 코드

장치 ID 0xf1의 분기 대상, 저장장치 크기 계산 함수의 입력 필드, 헤더 +0x200의 후속 복사 위치.

모델 제공한 시험 조건

합성 RAM, NAND ID·응답 상태, FF 16바이트, 합성 헤더, 할당·뮤텍스·진단 출력. 해제 요청은 기록만 했습니다.

미확인 실기와 이후 경로

장착 NAND의 실제 ID·용량·헤더, 물리적 주소 대응, 헤더 반환 이후의 실행, 기록·부팅·복구 성공 여부.

18개 사례의 출발점과 종료 지점

앞 문서의 시험 1은 원본 FileX 매체 열기를 실행하다 FcuNandOperationEx의 식별 요청 직전에서 멈췄습니다. 이번 매체 열기 사례들은 같은 초기 상태에서 그 구간을 다시 실행했습니다. 요청 인수를 확인한 뒤 응답을 넣었습니다. 각 사례는 독립적으로 시작합니다. 재지정 사례 안에서는 매체 열기 상태를 유지한 채 헤더 함수까지 이어집니다. [근거: native_open_entries, header_redirect]

식별값의 네 번째 바이트가 헤더 검색 간격에 영향을 줍니다

종류 인수 1의 ec dc 시험에서 네 번째 바이트가 0 또는 dc이면 핸들 +0xc14에 5, 시험값 1이면 8이 들어갔습니다. 이 결과를 다른 종류 인수나 시험하지 않은 바이트에 일반화하지 않습니다. 뒤의 호출은 이 필드를 1 << 값으로 바꾸어 헤더 함수에 32 또는 256을 넘깁니다. [근거: parser.cases, native_open_entries, source.words]

종류 인수 0x102에서는 +0xbf4에 0xf9c80(1,023,104)이 들어갔습니다. 종류 2의 반환값은 0xf2입니다. 핸들 +0x1cc에 남은 상태는 0x90입니다. 함수 반환값과 저장된 상태를 구분해야 합니다.

매체 열기 실행에는 드라이버가 미리 넣은 +0xc18 = 0x100이 있습니다. 따라서 파서 단독 시험의 3·5가 매체 열기에서는 0x103·0x105가 됩니다. 두 시험의 초기 핸들이 다릅니다.

장치 분기 표에는 ID 0x33부터 0xf1까지 191개 항목이 있습니다. 161개는 같은 거부 경로를 가리킵니다. 0xf1 항목 0x80063e9c는 0x8005590c를 가리킵니다. 이 항목은 정적으로만 확인했으며 12개 실행 사례에는 포함하지 않았습니다. 실제 장착 칩의 ID나 용량은 알 수 없습니다. 앞 문서에서 모델로 제공한 FileX 반환값 0xf1과도 별개의 값입니다. [근거: parser.device_table_groups, source.f1]

헤더 +0x14의 bit 31이 다음 읽기 위치를 선택합니다

원본 헤더 함수는 0x400바이트 버퍼를 요청합니다. 모델이 버퍼를 내주면 원본 코드는 연산 6으로 FF 16바이트를 받고 연산 4로 합성 헤더를 받습니다. 이번 연산 번호는 펌웨어 내부 ABI 값입니다. 하드웨어 명령 번호와 대응시킨 것은 아닙니다.

0x80055c28의 분기는 헤더 +0x14 워드의 부호를 검사합니다. bit 31이 0이면 첫 헤더를 반환합니다. 1이면 하위 31비트를 간격으로 나눕니다. 다음 검색 함수가 그 몫에 간격을 곱합니다. 스페어 영역의 응답을 FF로 제공한 이번 조건에서는 결과가 두 번째 데이터 읽기의 위치로 나타났습니다. [근거: header_redirect.branch, io, source.words]

성공 시 반환된 주소는 모델이 만든 0x24400000입니다. 두 번째 데이터 읽기가 실패한 사례에서는 해제 모델이 호출만 기록하고 메모리를 실제로 해제하지 않습니다. 네 사례 모두 0x80084114에서 멈췄습니다. 호출자가 헤더 +0x200을 읽는 0x80084120과 복사 지점 0x80084128은 실행하지 않았습니다.

이번 부트 헤더 경로는 0x80055bb4와 0x80055c20에서 개수 인수에 상수 2를 넣습니다. 호출자도 0x80056710에서 0x400 >> 9 = 2를 계산합니다. 그 값은 다른 호출 분기에서 그대로 씁니다. 실제 관측한 개수 2는 부트 헤더 함수의 상수에서 왔습니다. 이를 실제 매체의 페이지 크기·블록 크기로 해석하지 않습니다.

저장장치 크기 계산의 입력과 헤더 +0x200은 다른 필드입니다

정적 분석에서 _fx_nand_get_geometry(0x80064040)는 인수 포인터 +0x2c를 읽습니다. 드라이버가 전달하는 포인터는 핸들 +0xbc8이므로 이 입력은 ID 해석 함수가 쓰는 핸들 +0xbf4입니다. 반면 헤더 반환 이후의 코드는 헤더 +0x200을 핸들 +0xc10(0xbc8 + 0x48)에 복사합니다. 같은 필드로 합쳐 설명할 수 없습니다. [근거: source.words의 geometry_calculation_static_only, native_flags_and_header_call]

이번 18건은 크기 계산 함수와 헤더 +0x200 소비 경로를 실행하지 않았습니다. 다음 확인 지점은 0x80084114 이후의 헤더 필드 복사와 다음 FileX 드라이버 요청입니다.

K-3 III와는 저장 계층과 검증 범위를 대조했습니다

K-3 III의 부팅·저장소 문서는 M0·BOOT·RTOS, Emmc 드라이버와 FwPartition 객체를 다룹니다. Q7의 이번 경로는 FileX에서 NAND 식별 응답과 부트 헤더로 내려가는 원본 MIPS 코드입니다. K-3 III의 bank 필드나 eMMC 단위를 Q7에 적용할 근거는 확보하지 못했습니다.

두 분석에 같은 검증 방식을 적용했습니다. 실제 코드의 분기·인수·반환을 확인하되 저장장치 응답을 대신한 모델과 실기에서 관측하지 않은 값은 구분합니다. K-3 III의 단계 사이 주소 대응이 미확인인 것처럼, Q7도 KSEG 별칭·TLB·캐시·DMA를 포함한 물리적 주소 대응은 이번 시험으로 증명하지 못했습니다.

재현 방법과 근거 파일

실행 엔진은 angr 10.0.5의 VEX이며 원본 MIPS32 little-endian 명령을 실행했습니다. 이 환경에서는 Unicorn 라이브러리를 불러오지 못해 사용하지 않았습니다. REA의 네이티브 분석 공급자도 사용할 수 없었습니다. 아래 결과의 근거는 로컬 원본 바이트 대조와 VEX 실행입니다.

공유 매체 열기 시험은 합성 전역값도 준비합니다. 0x81547f10(_fx_system_media_opened_ptr, 열린 매체 목록 포인터)에는 32비트 0, 0x8008c2dc(bDebugPrint)에는 1바이트 0, 0x8008c2f4(gulTlErrorStatus)에는 32비트 0을 넣습니다. 뒤의 두 주소는 실행 중 쓰기도 허용합니다. 분석 ELF의 적재 구간에는 읽기·쓰기·실행 권한(RWX)을 부여했습니다. 따라서 원본 파일·E03 코드의 바이트 대조와, 이 ELF 위에 만든 합성 전역 상태를 구분해야 합니다. 실제 카메라의 메모리 내용·권한이나 실행 중 코드 불변성을 검증한 것은 아닙니다. [공유 시험 상태·접근 범위] · [분석 ELF 적재 권한]

공개 재현기는 원본 펌웨어와 분석 ELF의 전체 SHA-256을 먼저 확인합니다. 결과 파일은 새 파일로만 만들며 기존 파일·입력 경로·링크를 덮어쓰지 않습니다. 검증에 필요한 assertion이 꺼지는 python -O 실행도 거부합니다.

python tools/check_nand_headers.py <원본 fwdc603p.bin> <분석 main-expanded.elf> --output <새 결과.json>
python tools/build_all.py
python tools/verify_report.py --firmware <원본 fwdc603p.bin>
python -m unittest discover -s tests

분석 ELF는 기존 생성 도구로 원본에서 복원합니다. 원본 파일과 ELF는 공개 저장소에 포함하지 않습니다. 보고서 빌드와 저장된 결과 검사는 원본 없이도 실행할 수 있습니다. verify_report.py는 저장된 결과·HTML을 검증합니다. 원본 명령 18건의 재실행은 check_nand_headers.py가 담당합니다.
