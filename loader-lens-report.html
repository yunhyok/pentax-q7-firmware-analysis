01 / FILE INPUT CALLBACK

일반 입력은 두 번 읽어 비교한다

원본의 hash flag는 0입니다. 이때 카드 입력 콜백은 같은 구간을 두 번 읽어 실제 읽은 길이와 내용을 비교합니다. 불일치하면 되감아 한 번 더 시도합니다. hash flag가 1이면 요청 길이에 16바이트를 더하고 해시 작업자의 결과를 사용합니다. 이번 재실행에서는 MD5 계산 결과를 모델로 대체했습니다. [L1: replay.card_cases]

콜백 테이블은 E01의 0x800a74dc이며 읽기 함수는 0x80019014, 준비 함수는 0x80019390입니다. 준비 함수는 1을 반환합니다. 읽기 실패, 되감기 실패, 길이 불일치, 바이트 불일치와 재시도를 14개 사례로 확인했습니다. [원본 재실행 도구]

두 번 읽은 실제 길이가 모두 8바이트 또는 0바이트이고 FileX 결과가 성공이면, 이 콜백만은 1을 반환했습니다. 이는 짧은 업데이트가 전체 검사를 통과한다는 증거가 아닙니다. 해시 분기의 계산 결과와 파일 I/O는 모델 입력입니다.

02 / INSTALLED HEADER AND SECTION POLICY

업데이트 헤더만으로 목적지를 정하지 않는다

원본 페이로드 헤더의 +0x234 하위 바이트는 1입니다. 이 분기에서 BurnGetSectionsMap은 업데이트에 담긴 헤더와 이미 설치된 저장장치의 헤더를 함께 사용합니다. 기존 섹션 배치와 일부 값을 보존하며 크기와 보호 조건을 검사합니다. 따라서 업데이트 파일만으로 실제 카메라의 NAND 배치를 확정할 수는 없습니다. [L1: header·section_map_cases]

03 / LENS INFORMATION TO AF POLICY

AF 지원은 통신 상태와 연산 비트맵을 함께 본다

렌즈 초기 통신은 기능 그룹과 연산의 비트맵을 받아 하위 비트부터 바이트 배열로 펼칩니다. AF 지원 getter는 통신 상태의 0x08 비트와 group 2 / operation 4의 값을 함께 검사합니다. 렌즈 ID만으로 AF 지원 여부를 결정하는 함수는 아닙니다. 이후 명령 전송 경로도 해당 연산의 허용 여부를 확인합니다. [A1: discovery]

LLC startup 0x80111448:
  (0, 1, 0, 1)     → 8-byte function-group bitmap
  (0, 1, group, 0) → 32-byte operation bitmap
  LSB-first expansion → operation_flags[u8(group)*256 + u8(operation)]
ExGetAfEnable 0x80114b08:
  (communication_state & 0x08) != 0 AND operation_flags[2*256 + 4] != 0

명령 전송 함수는 map-read-OK가 정확히 1일 때 연산 비트맵을 검사하고, 허용값이 0이면 하위 전송 전에 7을 반환합니다. 이 전송 함수는 AF 지원 getter의 통신 상태 0x08 검사를 반복하지 않습니다. 두 검사를 같은 조건으로 합치지 않았습니다. [A1: transport_admission]

AF 계산은 렌즈가 보고한 위치·속도·이동 한계와 캐시의 유효 상태를 사용합니다. 일부 값은 big-endian으로 해석합니다. 값이 0일 때 렌즈 ID 1·2에 따라 다른 보정값을 쓰는 분기도 확인했습니다. 이 숫자를 렌즈의 물리 이동 거리나 모터 속도로 환산할 근거는 아직 확보하지 못했습니다. [A1: cached_fields·af_policy]

04 / REQUEST ACKNOWLEDGEMENT AND MOTION COMPLETION

큐 응답과 이동 완료를 구분한다

명령 응답 대기와 라이브뷰의 이동 완료 판정은 서로 다른 경로입니다. mode 2 setter의 대기는 100회까지 허용되지만 101회가 되면 같은 회차에서 대기 플래그가 해제돼도 status 6을 반환합니다. 라이브뷰는 이동 시작 대기 상태를 거친 뒤 이동 상태가 0일 때 완료 통지를 보냅니다. 명령이 수락됐다는 결과만으로 이동이 끝났다고 판단하지 않습니다. [A1: commands·completion·replay]

05 / K-3 MARK III COMPARISON

검증 항목을 대조하고 수치 의미는 분리한다

K-3 Mark III 자료에서도 요청 전달과 AF 완료를 분리해 다룹니다. 업데이트 형식과 기계어, 렌즈 제어 구조는 Q7과 다르므로 검증 항목과 추적 방법을 대조했습니다. K-3의 이벤트 값이나 capability 비트를 Q7의 연산 번호와 같은 의미로 해석하지 않았습니다.

공개 비교 기준은 a736ff253a1c528e31c08afa23ad4ebe37d1fbbb의 업데이트 근거와 요청·AF 경로입니다. 파일 해시도 L1에 기록했습니다.

06 / REPRODUCIBILITY AND LIMITS

실행한 코드와 모델 입력을 함께 기록했다

원본 코드의 조건을 살피고 합성 입력에 대한 결과를 확인했습니다. 실제 통신 응답, NAND 기록, 렌즈 이동, LCD 출력과 촬영은 검사하지 않았습니다. 재패킹의 삽입·삭제·재배치, 전체 loader 실행과 렌즈 상태 변화의 연속 추적은 후속 오프라인 연구로 남아 있습니다.

  • 워드 대조: VA 331개 + 원본 파일 20개; 메인 함수 67개, typed E01 함수 17개와 익명 콜백 범위 2개.
  • 원본 재실행: 렌즈 32건, loader helper 114건, BurnNand 진입부 1건.
  • 공통 모델: 파일 읽기·되감기, 할당·캐시·진단, 비동기 MD5 결과. BurnNand 진입부에는 카드 페이로드·기존 헤더·geometry 모델 3개를 추가.
  • 재패킹 도구: 오류·짧은 쓰기 시 생성 파일만 정리하고 보고서는 마지막에 기록. 강제 종료·전원 손실에 대한 원자성은 보장하지 않음.
