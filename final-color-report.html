HDR 출력 선택과 FC1 색 변환 계수

HDR로 합친 사진은 저장 전에 색 변환 단계를 거칩니다. 합성 결과가 어느 버퍼로 넘어가는지, 그리고 그 색 변환에 쓰이는 계수가 펌웨어 안에서 바뀌지 않고 하드웨어 레지스터까지 가는지를 확인했습니다.

이 문서에서

  1. 배경: 카메라의 HDR과 FC1 단계
  2. HDR 결과는 일반 출력 블록으로 제출됩니다
  3. HDR 계수는 FC 블록에 그대로 복사됩니다
  4. 계수 9개와 보조값 2개가 레지스터까지 보존됩니다
  5. K-3 Mark III와 비교
  6. 한계와 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 분석한 HDR 경로(합성용으로 새로 만드는 처리 경로)에서는 제출 함수가 대체 출력 대신 HDR 작업 버퍼 안의 일반 출력 블록을 고릅니다. 원본 코드로 두 분기를 모두 실행해 확인했습니다.
  • HDR이 넣는 색 변환 계수 9개와 보조값 2개는 패스 계산 라이브러리(FIPLIB)를 거쳐 FC1 레지스터 쓰기까지 값이 바뀌지 않습니다. 이 구간에는 계수를 곱하거나 다시 계산하는 단계가 없습니다.
  • 이 구간의 원본 함수 5개를 6개 사례로 이어서 실행했고, 순서가 있는 레지스터 쓰기 72회가 예상값과 모두 일치했습니다.
  • 계수가 보존된다는 사실과 FC1이 실제로 켜진다는 사실은 별개입니다. 패스별 활성화는 다음 문서에서 다루며, 실제 촬영의 픽셀은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 출력 선택 분기 2사례: 일반 출력과 대체 출력이 각각 선택됨
  • FC 생성·설정·내보내기와 FC1 setter·writer의 연속 실행 6사례, MMIO 쓰기 72회
  • 함수 후보 72개와 원본 워드 499건을 주소·해시로 대조

정적 분석 코드를 읽어 판단

  • HDR 설정 함수들이 대체 출력 디스크립터를 채우지 않음
  • 새 HDR 경로에 ID 0x1d 설정이 없어 계수가 FC1 쪽 포인터로 연결됨
  • 직접 실행 경로와 COP 작업자 경로가 같은 계산·내보내기 함수를 부름

모델 시험 조건으로 정한 것

  • 메모리 할당, RTOS, IPU 초기화, processor 생성자 등 대체 함수 13개
  • 합성 버퍼 주소, 합성 패스 입력
  • 하드웨어 레지스터 대신 RAM에 기록(MMIO 모델)

미확인 확인하지 않은 것

  • 실제 촬영에서 쓰인 패스 수와 패스별 FC1 활성 상태
  • CBC 배치 실행, DMA·캐시 동작, JPEG에 들어간 실제 픽셀
  • 제어 비트와 보조값 2개의 하드웨어 의미

배경: 카메라의 HDR과 FC1 단계

Q7의 HDR 촬영은 노출이 다른 사진 세 장(부족·표준·과다)을 연달아 찍어 한 장으로 합칩니다. 밝은 곳과 어두운 곳의 계조를 함께 남기려는 기능입니다(리코 Q7 소개). 메뉴의 HDR 촬영 설정은 Auto·HDR 1·HDR 2입니다(Imaging Resource 사양표, 제조사 설명서 원문은 확인하지 못했습니다).

합친 결과는 보통 사진과 마찬가지로 IPU(이미지 처리 하드웨어)의 색 처리를 거쳐 JPEG로 저장됩니다. 펌웨어는 이 처리를 여러 번의 패스로 나눠 하드웨어에 맡깁니다. 이 문서와 뒤의 두 문서는 그중 FC1이라는 색 단계를 따라갑니다.

FC1은 무엇으로 보이는가

펌웨어 안의 이름은 CFc1Filter입니다. 계수 9개, 보조값 2개, 제어 워드 하나, 켜고 끄는 값 하나를 하드웨어 레지스터에 씁니다. 계수가 주어지지 않으면 내장 계수를 고르는데, 그 함수 이름이 “ITU-R 601 RGB-to-YUV”와 “ITU-R 709 RGB-to-YUV”입니다. HDR이 넣는 9개 값도 내장 601 값과 똑같습니다.

그래서 FC1은 RGB 색을 JPEG가 쓰는 밝기·색차(YUV, YCbCr) 형식으로 바꾸는 색 변환 단계로 보입니다. 다만 “FC”가 무엇의 약자인지는 펌웨어에 적혀 있지 않습니다. 이 해석은 함수 이름과 계수 값에서 끌어낸 추정이며, 하드웨어 문서로 확인한 것이 아닙니다.

세 문서는 같은 질문을 단계별로 이어 갑니다.

  2. 출력 선택과 계수이 문서
  3. 패스별 활성화와 제출네 패스 중 어디서 FC1이 켜지나 — FC1 활성화와 제출 패스
  4. 제어 비트와 task 완료제어 비트의 출처, task 생성·큐 제출, IRQ부터 PathWait 통과까지의 완료 — FC1 비트와 HDR task

HDR 결과는 일반 출력 블록으로 제출됩니다

대체 출력 디스크립터의 타입 필드가 0이면 일반 출력 블록이 선택되고, 새 HDR 경로에서는 이 값이 제출 때까지 0으로 남습니다.

path+0x964는 따로 있는 경로 플래그가 아닙니다. path+0x8fc에 놓인 대체 출력 디스크립터의 +0x68, 즉 이미지 타입 필드입니다. 새 경로를 만들 때 이 필드는 0으로 초기화됩니다. 값이 0이면 IpuSubmit은 path+0x28의 출력 블록으로 디스크립터를 만들고, 0이 아니면 대체 디스크립터를 복사합니다. [근거: hdr_output_selector, type_0_registry]

HDR 제출 전에 불리는 설정 함수를 따라가 보면, 필터 설정은 별도의 processor 객체를 고치고 형식·배율·버퍼 설정은 경로 앞쪽 필드를 고칩니다. 분석한 호출 순서에는 대체 출력 디스크립터를 채우는 함수가 없습니다. 이 조건에서 형식 0x0f01은 type 8 출력 디스크립터로 바뀌고, 원래 출력 블록 주소는 surface의 첫 워드에 남습니다. [근거: HDR 설정·surface 바인딩]

HDR 버퍼 문서는 HDR 작업 버퍼 B 안의 view가 IPU 출력 주소로 설정되는 과정을 다룹니다. 이 결과를 더하면, 새 HDR 경로는 그 view를 일반 출력 디스크립터로 제출합니다. DMA 완료와 JPEG가 읽은 실제 픽셀은 여전히 확인 범위 밖입니다.

HDR 계수는 FC 블록에 그대로 복사됩니다

HDR이 만든 색 변환 설정의 값 11개는 FIPLIB 입력, 패스 입력, FC 블록, 내보내기 payload를 거쳐 FC1 레지스터까지 가며, 그 사이에 계산이 끼지 않습니다.

FC 객체는 mode 1에서 패스 입력 +0x68의 포인터를 읽습니다. 포인터가 있으면 행렬 계수 9개와 추가 필드 2개를 그대로 복사하고, 없으면 내장 계수를 고릅니다. 이어지는 Export는 16비트 값 11개를 부호 확장해 32비트 필드로 내보냅니다. 이 경로는 계수를 새로 곱하지 않고 복사하거나 내장값을 고를 뿐입니다. [근거: fc1_generator]

새 HDR 경로에서 계수가 FC1 쪽으로 가는 이유

processor 생성자는 디스크립터 슬롯을 비우고 기본값으로 ID 0xf와 0x19만 설치합니다. IpuToneMapRgb는 HDR 보조 설정 ID 0x1f와 로컬 ID 0xa·0xf를 설치합니다. 보조 설정은 HDR 캐시 생성부와 HdrSetZLightFilter에서 ID 0x1f, version 0xc로 제한됩니다. 분석한 새 경로에는 ID 0x1d가 없습니다. [근거: hdr_case]

PrepareCalculations는 FIPLIB 입력을 0으로 지운 뒤, ID 0x1d가 있을 때만 그 디스크립터의 +0x18로 입력 +1을 채웁니다. 그래서 이 HDR 경로에서는 입력 +1이 0입니다. 각 IPU 패스의 준비 함수는 이 값이 1이 아니면 입력 +0x1074를 패스 입력 +0x68(FC1이 읽는 자리)에 연결합니다. 값이 1인 다른 경로는 +0x68을 비우고 +0x6c에 연결하므로 같은 결론을 쓸 수 없습니다. [근거: pass_dispatch.prepare]

계수 9개와 보조값 2개가 레지스터까지 보존됩니다

HDR 설정의 값 11개는 FC1 객체와 레지스터 쓰기까지 같은 숫자로 남습니다. 켜짐 여부와 제어 워드는 따로 정해집니다.

이 값들은 HDR의 상위 디스크립터에서 FIPLIB 입력, FC 블록, 출력 payload를 거쳐 FC1 객체까지 유지됩니다. FC1 writer는 계수와 보조값을 부호 확장해 0xb60000c0부터 0xb60000e8까지 쓰고, 제어 워드는 0xb60000fc에 씁니다. [근거: hdr_case.source] [근거: cases]

K-3 Mark III와 비교

K-3 Mark III의 공개 커밋 a6b84f4e2e81213e54f1fe4d19beea9e93a6bbd9을 고정해 출력 디스크립터 분기와 계수 계산을 대조했습니다. 로컬의 커밋되지 않은 파일은 빼고, 그 커밋의 원본 파일 4개를 SHA-256으로 확인했습니다. K-3의 JPEG 용량 분기와 Q13 행렬 준비는 같은 질문을 검토할 때 참고가 되지만, Q7의 제출 조건이나 FIPLIB 계수 경로를 대신 증명하지는 않습니다. [근거: claims, source_blobs]

한계와 재현 방법

  • 전체 FIPLIB 패스 구성과 스케줄러를 한 번에 실행하지 않았습니다. 확인한 것은 명시한 분기 조건에서의 소프트웨어 연결과 계수 설정값입니다.
  • 특정 촬영에서의 패스 수와 최종 활성 상태, CBC 실행 완료, DMA와 캐시 동작, JPEG 픽셀의 정확성은 확인하지 않았습니다. 패스 수와 활성화는 FC1 활성화 문서에서 분석한 HDR 경로에 한해 정리했습니다.
  • 다른 경로가 대체 디스크립터를 채우거나 외부 설정으로 디스크립터·토폴로지를 바꾸면 선택, 활성화, 출력이 달라질 수 있습니다.
  • 최종 픽셀을 확인하려면 하드웨어 실행이나, 확보한 입력·출력 영상과의 대조가 따로 필요합니다.

검증 대상은 함수 후보 72개와 원본 명령·데이터 워드 499건입니다. 함수 후보의 범위는 다음 심볼 주소까지이며 공식 함수 크기가 아닙니다. 원본 펌웨어에서 워드, 함수 해시, 분기 정보를 다시 계산해 확인합니다. [검증 코드]

각 재실행 도구는 입력 ELF의 SHA-256을 검사하고, 이미 있는 출력 파일은 덮어쓰지 않습니다. 실행 엔진은 VEX이며 선택 사항인 Unicorn 엔진은 쓰지 않았습니다. 공개 CI는 원본 펌웨어 없이 메타데이터, 기준값, 도구 테스트, HTML, 링크를 검사합니다. 원본 명령 재실행과 원본 펌웨어 대조는 로컬에서 합니다. 원본 BIN, 추출 ELF, 전체 디컴파일은 공개하지 않습니다.
