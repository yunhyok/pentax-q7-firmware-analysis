배경: 업데이트 파일에서 읽을 수 있는 코드까지

업데이트 파일을 그대로 디스어셈블하면 압축된 바이트만 나옵니다. 압축을 풀고 주소에 이름을 붙이고 볼 함수를 고르는 세 단계를 거쳐야 코드를 읽을 수 있습니다.

Q7의 업데이트 파일 fwdc603p.bin({{input_size}}바이트)은 리코 공식 배포본과 바이트 단위로 같습니다. 파일 안에는 MIPS용 ELF 12개가 들어 있습니다. 파일 구조와 12개 ELF는 펌웨어 파일 구조에서 다룹니다. 이 문서는 그 다음 단계를 다룹니다. 카메라 본 프로그램의 코드를 읽을 수 있게 만드는 과정과 그 코드로 처음 알아낸 것을 정리합니다.

이 문서를 읽는 데 필요한 네 가지

MIPS 명령과 jal
Q7의 CPU는 32비트 리틀엔디언 MIPS 명령을 씁니다. 함수 호출은 jal 명령이며 돌아올 주소를 31번 레지스터에 넣고 점프합니다. 점프 바로 뒤 명령 하나는 점프보다 먼저 실행됩니다. 이 자리를 지연 슬롯이라 부릅니다. 이 문서의 "호출 관계"는 이런 명령어를 하나씩 읽어 얻은 것입니다.
ThreadX
카메라 본 프로그램의 실시간 운영체제(RTOS)입니다. 펌웨어에 ThreadX LX4180/Green Hills 식별 문자열이 있고 파일시스템은 같은 계열의 FileX(FAT12·16·32 호환)입니다. 작업은 스레드 단위로 나뉘고 커널이 우선순위에 따라 스레드를 번갈아 실행합니다.
심볼 복원
코드 주소에 함수 이름을 다시 붙이는 일입니다. Q7은 주소 배열, 문자열 오프셋 배열, 문자열 모음을 별도 파일 세 개로 펌웨어에 넣어 두었습니다. 셋을 이으면 "주소 → 이름" 레코드가 됩니다. 이름은 개발자가 붙인 원래 이름이지만 그 함수의 범위나 종류(함수인지 데이터인지)는 알려 주지 않습니다.
디컴파일 기록
디컴파일 도구가 만든 C 코드와 그 해시를 말합니다. 원래 소스 코드가 아니라 도구의 재구성입니다. C 출력이 생겼다고 해서 변수 형식이나 간접 호출 대상까지 맞게 복원됐다는 뜻은 아닙니다.
이 문서의 화살표가 뜻하는 것

그림의 실선은 명령어에서 읽은 직접 호출·점프입니다. 점선은 주소를 넘기거나 처리 함수를 등록하는 관계입니다. 어느 쪽도 카메라에서 실제로 그 순서로 실행됐다는 관측이 아닙니다.

압축 블록 448개를 풀어 분석용 코드 만들기

카메라 본 프로그램의 네 적재 구간은 블록 단위로 압축되어 있었고 {{block_total}}개 블록을 모두 끝까지 풀었습니다. 그 결과를 원래 주소에 놓은 분석용 ELF가 이후 모든 분석의 바탕입니다.

E04·E05·E06에 해당하는 네 구간은 블록마다 별도의 Huffman 조회표를 씁니다. 여기에 앞서 나온 바이트를 다시 가리키는 LZ 참조가 더해집니다. 펌웨어 자신의 압축 해제 코드(InflateStreamData, InflateProcessor)가 블록 머리를 읽는 방식을 확인했습니다. 그리고 같은 형식을 소프트웨어로 풀었습니다. 펌웨어는 이 해제를 하드웨어 블록에 맡기는 것으로 보입니다(표 데이터를 0xb9800000 영역의 레지스터에 씀).

  1. 블록 머리 읽기16바이트 머리, 조회표 크기
  2. 조회표 + 비트열 해제Huffman 부호와 LZ 참조
  3. 끝 검사선언된 출력 길이에서 끝 표식, 뒤는 0만
  4. 분석용 ELFELF 가상주소에 배치

모든 블록이 선언된 파일 범위를 다 쓰고 선언된 출력 길이에서 끝 표식에 닿았습니다. 끝 표식 뒤에는 0만 있었고 구간마다 풀린 길이가 ELF가 선언한 메모리 크기(p_memsz)와 같았습니다. [근거: segment-decode.json validation]

ThreadX가 첫 스레드를 띄우기까지

Q7의 커널 진입 함수는 ThreadX 공식 소스와 같은 순서로 저수준 초기화, 고수준 초기화, 앱 정의 함수를 호출한 뒤 스케줄러로 넘어갑니다. 첫 앱 스레드 AppBootPrimary는 앱 정의 함수가 "등록"하고 스케줄러가 실행합니다.

ThreadX 문서에 따르면 초기화는 다음 순서로 진행됩니다. 리셋 뒤 개발 도구의 시작 코드, main, 커널 진입(tx_kernel_enter), 앱 정의 함수(tx_application_define), 스케줄 루프입니다. tx_kernel_enter는 공식 헤더에서 _tx_initialize_kernel_enter의 다른 이름입니다. 앱 정의 함수는 첫 스레드·큐·이벤트 같은 자원을 만듭니다. 이 함수가 돌아오면 스케줄러가 준비된 스레드 중 우선순위가 가장 높은 것을 실행합니다. 초기화 동안 인터럽트는 꺼져 있습니다.

앱 정의 함수 안에서는 CpuInit, DcuInitDram, PoolInit, OsThreadInit, TimerInit, DcuInit 호출을 확인했습니다. 일부 호출은 아래 EBase 조건 안에 있습니다. 마지막 OsThreadCreateEx 호출은 AppBootPrimary를 직접 부르지 않고 그 주소를 스레드 진입점 인자로 넘깁니다. "초기화 함수가 AppBootPrimary를 호출한다"고 읽으면 안 되는 이유입니다. [근거: deep-evidence.json tx_application_define]

jal은 32비트 워드의 위 6비트가 3(000011)입니다. 아래 26비트에는 대상 주소를 4로 나눈 값이 들어 있습니다. 첫 줄의 워드 0c03674e에서 아래 26비트 0x03674e에 4를 곱하면 0xd9d38입니다. 여기에 현재 주소의 위쪽 비트(0x80…)를 붙이면 0x800d9d38, 곧 저수준 초기화 함수입니다. 넷째 줄은 위 6비트가 2인 j(돌아오지 않는 점프)입니다. 그래서 스케줄러로 넘어간 뒤 커널 진입 함수로는 돌아오지 않습니다.

커널 진입 함수는 CP0 EBase 레지스터의 하위 10비트가 1인지에 따라 기본 컨텍스트와 Cop 컨텍스트 중 하나를 고릅니다. 컨텍스트 이름만으로 두 실행 주체가 물리적으로 어느 코어에 놓이는지까지는 확정하지 않았습니다. [근거: _tx_initialize_kernel_enter]

주의

첫 ELF(E01)는 Zburn/Main.c 이름이 들어 있는 별도 이미지(업데이트 프로그램)입니다. 위 주소는 모두 카메라 본체 E03 기준이며 E01의 초기화 주소와 섞지 않았습니다. 리셋 벡터에서 커널 진입 함수까지의 경로는 분석하지 않았습니다.

AF와 셔터: 명령이 렌즈와 레지스터에 닿는 곳

AF 명령 수신에서 피크 검사·초점 계산·렌즈 구동 요청까지의 직접 호출을 찾았습니다. 이 문서에서 미확정이던 렌즈 요청의 수신자는 이후 렌즈 명령·ISP 레지스터 문서에서 확인됐습니다.

AF 명령 수신 함수는 명령 값 0x000e0001이면 CAFSequenceStart로 진행하고 0x000e0002이면 중단 상태를 처리합니다. 0x000e0004는 별도 제어 상태와 인자를 저장한 뒤 같은 시작 경로를 씁니다. AF 작업 함수에서는 영역별 PeakCheck, 초점 계산, LensDriveControl 호출을 확인했습니다. 콘트라스트와 피크를 다루는 경로는 따라갈 수 있지만 K-3 Mark III의 위상차 상관·디포커스 알고리즘과 같다고 볼 근거는 없습니다. [근거: OnNotifyCommand, AfMain_Thread_sub]

JPEG: 양자화 테이블 계산과 완료 인터럽트

JPEG의 양자화 테이블 계산식, 경로 제출, 완료 인터럽트 처리를 각각 따로 찾았습니다. 셋이 실제 촬영 한 번에서 어떻게 이어지는지는 이 문서 범위 밖이며 HDR 사진의 실제 압축 위치는 이후 문서에서 확인됐습니다.

양자화 테이블은 JPEG 압축률을 정하는 64개 값의 표입니다. ApsCmpRecalcDqt는 밝기(Y)와 색차(C)용으로 각각 64개 값을 계산하고 1부터 255까지로 제한합니다. PathSetJpeg는 QtConvert를 두 번 호출해 경로 객체의 +0xc0과 +0x1c0에 테이블을 만듭니다. [근거: ApsCmpRecalcDqt, PathSetJpeg, QtConvert]

scale = input_scale & 0xffff
QY[i] = clamp((scale * baseY[i]) >> 14, 1, 255)
QC[i] = clamp((scale * baseC[i]) >> 14, 1, 255)     // i = 0..63

QtConvert: inverse-zigzag 순서로 64개 항목 변환
  mode == 1 : 원본 byte를 32비트 항목에 저장
  그 외     : max(1, 0x4000 / source_byte); 0 입력은 trap

PathSubmit은 경로 타입이 1일 때 JpegPathSubmit을 고릅니다. 이 함수는 객체 +0x3c4의 비트 0x40이 켜져 있으면 IcaPathSubmit을 호출합니다. PathSubmit의 진입점은 0x801c83c8이고 0x801c84bc는 그 안의 호출 위치입니다. [근거: 0x801c84bc, 0x801df5a4]

완료 처리는 이렇습니다. JpegPathInit이 IsrJpegDone을 인터럽트 ID 0x14에 등록합니다. IsrJpegDone은 상태 레지스터 0xb0181ca0을 읽어 0이면 이벤트 비트 0x04(정상), 아니면 0x40(오류)을 설정합니다. 끝에는 ISR 중지 함수로 가는 꼬리 점프가 있습니다. 디컴파일된 C가 이 점프를 다른 모양으로 바꾸었으므로 호출 관계는 어셈블리를 기준으로 적었습니다. 등록은 확인했지만 실제로 인터럽트가 발생하는지는 검사하지 않았습니다. [근거: IsrJpegDone, JpegPathInit]

이후 문서에서 갱신

이 문서가 본 StillCaptureImageTuneJpegEnc(0x802de3e0)는 ApsCmpRecalcDqt와 ApsJpegCreate를 호출합니다. 하지만 이름에 Emulation이 붙은 입출력 버퍼를 쓰므로 이 문서는 일반 촬영의 JPEG 경로로 단정하지 않았습니다. 실제 촬영 버퍼와의 연결은 남겨 두었습니다. HDR 버퍼와 색 처리 패스는 HDR 사진의 주 이미지가 SaveCompressImage → ApsJpegDirectCompress에서 압축되는 것을 확인했습니다. HDR 처리 결과 버퍼가 JPEG 입력 주소로 설정되는 연결도 확인했습니다. 압축 결과를 파일로 저장하는 경로는 렌즈 명령·ISP 레지스터·출력 경계에 있습니다. 두 결과 모두 HDR 경로에 한정됩니다. 양자화 테이블이 들어가는 하드웨어 레지스터는 아직 확인하지 않았습니다.

색 처리: 행렬 계산을 원본 명령으로 검산

3×3 색 행렬 곱과 색상 회전 함수의 고정소수점 계산식을 읽었습니다. 두 함수의 원본 MIPS 명령을 에뮬레이터에서 실행하자 {{math_count}}개 사례가 모두 계산식과 일치했습니다. 이것은 계수를 만드는 함수의 검증이지 픽셀 처리의 검증이 아닙니다.

MatrixMultiplication은 세 항의 곱을 더한 값에 0x1000을 더하고 13비트 오른쪽으로 민 뒤 하위 16비트를 저장합니다. 이것은 Q13 고정소수점 곱셈입니다. 8192가 1.0을 뜻하고 시프트 전에 212(0x1000)를 더해 반올림합니다. HueShift는 같은 구조에 0x80과 8비트를 씁니다. 함수가 입력 행렬을 먼저 복사하므로 출력과 입력 주소가 같아도 계산이 깨지지 않습니다. [근거: ColorMatchingService]

acc = Σ A[row,k] × B[k,col]                    // k = 0..2
MatrixMultiplication: low16(uint32(acc + 0x1000) >> 13)
HueShift:             low16(uint32(acc + 0x0080) >>  8)
// 입력 계수는 signed 16비트. MIPS의 32비트 누산·저장을 반영.

구조·심볼·압축 해제·전이 도구는 Python 표준 라이브러리만 씁니다. 함수 디컴파일에는 Ghidra 12.1과 JDK 21, 계산 재실행에는 angr 10.0.5(VEX)를 썼습니다. 출력 경로는 새 경로여야 합니다. original.bin은 공식 fwdc603p.bin입니다.

python -m unittest discover -s tests -v

python tools/decode_segments.py original.bin --output-dir .private/decoded
python tools/build_analysis_elf.py original.bin --decoded-dir .private/decoded --output .private/analysis.elf
python tools/trace_q7.py original.bin --selected analysis/deep-selected-functions.json --decoded-dir .private/decoded --output .private/deep.json --ghidra-dir .private/ghidra-input

# JDK 21 경로를 이 프로세스의 JAVA_HOME으로 지정한 뒤 실행합니다.

python tools/check_color_math.py .private/analysis.elf --output .private/math.json
