Loader의 입력 검증·섹션 배치와 렌즈의 AF 정책

이 문서에는 서로 다른 두 조사가 들어 있습니다. 1부는 업데이트 로더가 카드에서 읽은 데이터를 검증하고 기록할 영역을 정하는 방법입니다. 2부는 렌즈가 알려 준 정보가 AF 지원 판정과 구동 요청, 완료 판정에 쓰이는 방법입니다.

이 문서에서

  1. 배경: 두 부분을 읽는 데 필요한 것
  2. 1부 Loader ① 카드에서 읽은 데이터를 두 번 읽어 비교합니다
  3. 1부 Loader ② 기록할 위치는 카메라에 설치된 헤더까지 보고 정합니다
  4. 2부 렌즈 ① AF 지원 판정과 명령 허용은 서로 다른 검사입니다
  5. 2부 렌즈 ② 명령이 접수됐다는 것과 이동이 끝났다는 것은 다릅니다
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 1부 Loader — 로더는 카드에서 읽은 데이터를 바로 믿지 않습니다. 같은 구간을 두 번 읽어 길이와 내용을 비교하고, 다르면 되감아 한 번 더 시도합니다.
  • 1부 Loader — 어느 영역에 기록할지는 업데이트 파일의 헤더만으로 정해지지 않습니다. 카메라에 이미 설치된 헤더와 저장장치 크기를 함께 써서 배치표(섹션 맵)를 만듭니다. 그래서 업데이트 파일만 보고는 실제 카메라의 저장 배치를 확정할 수 없습니다.
  • 2부 렌즈 — 렌즈가 AF를 지원하는지는 렌즈 번호로 정하지 않습니다. 통신 상태 비트 하나와 렌즈가 알려 준 기능 표의 한 칸을 함께 봅니다. 명령을 보낼지 정하는 검사는 이와 별개입니다.
  • 2부 렌즈 — 구동 명령이 접수됐다는 응답과 렌즈가 이동을 마쳤다는 판정은 서로 다른 경로에서 나옵니다.
  • 로더 쪽 115사례와 렌즈 쪽 32사례를 원본 코드로 실행했습니다. 파일 내용, 설치된 헤더, 렌즈의 응답은 모두 시험용으로 넣은 값이며 카메라와 렌즈는 연결하지 않았습니다.
이 문서의 2부는 다른 주제에 속합니다

2부(렌즈)는 AF와 렌즈 제어 주제의 문서입니다. 그 주제의 지도는 AF·렌즈 안내에 있습니다. 1부(Loader)는 이 주제, 곧 업데이트와 재패킹에 속합니다. 두 부분은 서로 기대지 않으므로 필요한 쪽만 읽어도 됩니다. 1부로 가기 · 2부로 가기

확인 원본 코드 실행으로 확인

  • Loader: 카드 읽기 14사례, 보호 판정 84조합, 섹션 위치 계산 8사례, 섹션 맵 8사례, BurnNand 진입부 1사례
  • 렌즈: 기능 표 6사례, 캐시 값 3사례, 속도 변환 7사례, 요청 응답 7사례, 이동 완료 9사례
  • 주소로 가리킨 원본 워드 331개와 파일 오프셋으로 가리킨 워드 20개를 대조

정적 분석 코드를 읽어 판단

  • Loader: 헤더 필드의 이름(진단 출력 함수와 값을 쓰는 코드에서 가져옴), 페이로드 135청크의 산술 대조
  • 렌즈: AF 계산이 캐시 값을 읽는 지점, 렌즈 번호 1·2에 쓰는 대체값

모델 시험 조건으로 정한 것

  • Loader: 파일 읽기·되감기의 결과, MD5 판정 결과
  • Loader: 설치된 헤더와 저장장치 크기(512바이트 섹터 262,144개)
  • 렌즈: 렌즈의 응답, 스케줄러, 이동 상태 값

미확인 확인하지 않은 것

  • Loader: 실제 카메라의 설치 헤더와 저장 배치
  • Loader: 섹션 맵 이후의 지우기·기록(이어지는 문서에서 다룸)
  • 렌즈: 위치·속도 값의 물리 단위, 실제 통신과 렌즈 이동

배경: 두 부분을 읽는 데 필요한 것

    두 번 읽어 비교합니다. 기록 위치는 설치된 헤더까지 보고 정합니다.

  • 2부

    렌즈: AF 지원 판정에서 완료 판정까지

    렌즈가 알려 준 정보는 AF의 어느 판단에 쓰입니까?

    지원 판정, 명령 허용, 이동 한계와 속도, 완료 판정에 따로따로 쓰입니다.

1부에 필요한 말

  • 로더(E01): 업데이트 파일 맨 앞에 든 별도 실행 파일입니다. 저장장치에 기록하는 코드를 담고 있습니다. 카메라 본 프로그램에도 이름이 같은 코드가 따로 있는데, 이 문서가 실행한 것은 E01 쪽입니다.
  • 섹터와 블록: 섹터는 512바이트입니다. 시험 조건에서는 256섹터(128KiB)를 블록 하나로 두었습니다.
  • 섹션: 저장장치를 용도별로 나눈 구역입니다. 로더는 번호 0~6으로 다룹니다.
  • 설치된 헤더: 카메라의 저장장치에 이미 기록돼 있는 배치 정보입니다. 업데이트 파일에 든 헤더와 구분합니다.
  • 해시 플래그: 업데이트 헤더의 값 하나입니다. 0이면 “두 번 읽어 비교”를, 1이면 MD5 검사를 씁니다. 실제 파일의 값은 0입니다.

2부에 필요한 말

  • 기능 표: 렌즈가 초기 통신에서 “어떤 그룹의 어떤 연산을 할 수 있다”고 알려 주는 비트 묶음입니다. 카메라는 이를 칸마다 0 또는 1이 든 표로 펼쳐 둡니다.
  • 캐시: 렌즈가 보낸 위치·속도 같은 값을 카메라가 메모리에 보관해 둔 것입니다. 값과 별도로 “유효한지”를 나타내는 상태가 있습니다.
  • 빅엔디언: 여러 바이트로 된 수에서 높은 자리 바이트가 앞에 오는 표기입니다. Q7의 프로세서는 리틀엔디언이지만 렌즈가 보낸 값 일부는 빅엔디언으로 해석합니다.

1부 Loader ① 카드에서 읽은 데이터를 두 번 읽어 비교합니다

실제 업데이트 파일의 설정(해시 플래그 0)에서 카드 읽기 함수는 같은 구간을 두 번 읽고, 읽힌 길이와 내용이 같을 때만 성공으로 처리합니다.

로더는 카드의 파일을 직접 읽지 않고 함수 표에 등록된 읽기 함수에 맡깁니다. 이 함수는 핸들에 적힌 해시 플래그에 따라 두 방식 가운데 하나로 동작합니다.

플래그가 0이면 함수는 요청받은 구간을 기본 버퍼에 읽고, 읽은 만큼 되감은 뒤 같은 구간을 비교용 버퍼에 다시 읽습니다. 두 번 읽힌 길이가 같고 내용이 같으면 1을 반환합니다. 내용이 다르면 되감아 전체를 한 번 더 시도하고, 그래도 다르면 0을 반환합니다. 시도는 많아야 두 번입니다.

플래그가 1이면 요청 길이에 16바이트를 더해 읽습니다. 뒤의 16바이트는 앞부분의 MD5 값이고, 판정은 해시 작업자에게 맡깁니다. 이 문서의 실행에서는 작업자의 판정 결과를 모델이 공급했습니다. 실제 MD5 계산까지 원본 코드로 실행한 결과는 기록 헤더와 MD5 경로에 있습니다. [근거: replay.card_cases] · [재현 도구]

1부 Loader ② 기록할 위치는 카메라에 설치된 헤더까지 보고 정합니다

업데이트 파일 헤더의 모드 바이트는 1입니다. 이 값일 때 로더는 설치된 헤더를 함께 읽어 기존 배치와 일부 값을 보존하고, 크기와 보호 조건을 검사합니다.

업데이트 파일에는 페이로드의 구성을 적은 헤더가 있습니다(파일 오프셋 0x1000c0). 이 헤더 +0x234의 하위 바이트(모드 바이트)가 1입니다. 이 분기에서 로더의 BurnGetSectionsMap은 업데이트 헤더와 카메라에 이미 설치된 헤더를 함께 읽어 섹션 맵을 만듭니다. 그래서 업데이트 파일만으로는 실제 카메라의 NAND 배치를 확정할 수 없습니다.

시험 조건

설치된 헤더는 실제 카메라에서 읽어 온 것이 아닙니다. 연구자가 업데이트 헤더를 바탕으로 섹션의 시작과 길이를 채워 넣은 합성 값입니다. 저장장치는 섹터 512바이트, 블록 256섹터, 총 0x40000(262,144)섹터로 두었습니다. 위 막대의 숫자와 출력 주소는 실제 Q7의 NAND에서 얻은 값이 아닙니다.

BurnNand의 첫 구간

섹션 맵 계산을 따로 떼어 실행한 것에 더해, 로더의 BurnNand를 처음부터 실행해 섹션 맵 호출에서 돌아오는 곳까지 갔습니다. 진입 주소는 0x80012654, 멈춘 곳은 맵 호출의 복귀 주소 0x80012ff0입니다. 그 사이에 원본 코드는 설치된 헤더를 두 번 요청하고, 카드에서 첫 131,072바이트를 읽고, 저장장치 크기를 물었습니다. 세 요청 모두 모델이 답했고 맵 계산은 0을 반환했습니다. 지우기와 기록은 이 실행에 들어 있지 않습니다. 이어지는 구간은 저장 경계와 렌즈 준비 상태에서 다룹니다. 2부 렌즈 ① AF 지원 판정과 명령 허용은 서로 다른 검사입니다

AF 지원 판정은 통신 상태 비트와 기능 표의 한 칸을 함께 봅니다. 명령을 실제로 보낼지 정하는 검사는 기능 표만 보며, 통신 상태 비트는 다시 확인하지 않습니다.

여기서부터는 AF와 렌즈 제어 주제의 내용입니다. 카메라는 렌즈를 초기화할 때 통신으로 렌즈가 할 수 있는 일을 묻고, 답을 표로 만들어 둡니다.

기능 표를 만드는 순서

렌즈 초기 통신 함수(0x80111448)는 먼저 8바이트짜리 기능 그룹 비트맵을 받습니다. 그리고 1로 표시된 그룹마다 32바이트짜리 연산 비트맵을 받습니다. 두 비트맵 모두 낮은 비트부터 한 비트를 한 바이트로 펼쳐 표에 넣습니다.

렌즈 초기 통신(LLC startup) 0x80111448:
  요청 (0, 1, 0, 1)      → 기능 그룹 비트맵 8바이트
  요청 (0, 1, group, 0)  → 그 그룹의 연산 비트맵 32바이트
  낮은 비트부터 펼침     → operation_flags[u8(group)*256 + u8(operation)]
AF 지원 판정 ExGetAfEnable 0x80114b08:
  (communication_state & 0x08) != 0  AND  operation_flags[2*256 + 4] != 0

AF 지원 판정 함수는 통신 상태의 0x08 비트와 그룹 2·연산 4의 값을 함께 검사합니다. 렌즈 번호만으로 AF 지원 여부를 정하는 함수가 아닙니다. [근거: discovery]

명령 전송 함수는 map-read-OK 바이트가 정확히 1일 때 표를 검사하고, 해당 칸이 0이면 아래 단계로 보내기 전에 7을 반환합니다. 이 함수는 통신 상태 0x08 검사를 다시 하지 않습니다. 검색 명령이 쓰는 연산이 바로 그룹 2·연산 4여서 두 검사가 같은 칸을 보지만, 조건은 서로 다릅니다. 그래서 두 검사를 하나의 조건으로 합쳐 쓰지 않았습니다. [근거: discovery.transport_admission]

검색 명령의 결과 7은 “표에서 허용되지 않아 보내지 않음”입니다. 둘째 줄은 표의 칸이 1이어서 명령은 통과하지만, 통신 상태 비트가 꺼져 있어 AF 지원 판정은 0입니다.

2부 렌즈 ② 명령이 접수됐다는 것과 이동이 끝났다는 것은 다릅니다

K-3 Mark III와 비교

K-3 Mark III 자료도 요청 전달과 AF 완료를 나눠 다룹니다. 업데이트 형식, 기계어, 렌즈 제어 구조가 Q7과 달라서, 무엇을 검증했는지와 어떻게 추적했는지만 대조했습니다. K-3의 이벤트 값이나 기능 비트를 Q7의 연산 번호와 같은 뜻으로 읽지 않았습니다.

비교 기준은 K-3 Mark III 저장소의 커밋 {{k3_commit}}에 있는 업데이트 근거와 요청·AF 경로입니다. 두 파일의 해시는 analysis/loader-foundation.json의 comparison에 적어 두었습니다.

한계와 재현 방법

원본 코드의 조건을 읽고, 합성 입력을 넣었을 때의 결과를 실행으로 확인했습니다. 실제 통신 응답, NAND 기록, 렌즈 이동, LCD 출력, 촬영은 검사하지 않았습니다.

1부 Loader

  • 실행한 것: 카드 읽기 14사례, 보호 판정 84조합, 섹션 위치 8사례, 섹션 맵 8사례로 보조 함수 114사례와 BurnNand 진입부 1사례.
  • 모델: 파일 읽기와 되감기, 메모리 할당, 캐시 처리, 진단 출력, MD5 판정 결과. BurnNand 진입부에는 카드 페이로드, 설치된 헤더, 저장장치 크기 모델 세 개를 더했습니다.
