부트 헤더 값의 소비와 별도 읽기 요청

부트 헤더에서 읽은 값 하나가 핸들에 복사된 뒤 어디에 쓰이는지 따라갔습니다. 원래 흐름에서는 그 값을 쓰는 부트 읽기 요청이 건너뛰어지므로, 요청을 따로 넣어 원본 코드가 값을 어디로 넘기는지 확인했습니다.

이 문서에서

  1. 배경: FileX 드라이버 요청
  2. 이어진 실행 하나와 따로 넣은 요청 둘
  3. 헤더 값은 복사되지만 정보 조회는 그 값을 쓰지 않습니다
  4. 원래 Burn의 흐름은 부트 읽기 요청을 건너뜁니다
  5. kind 1 경로는 복사된 값을 첫 읽기의 위치로 넘깁니다
  6. K-3 III와는 저장 계층과 근거의 범위를 대조했습니다
  7. 한계와 남은 과제
  8. 재현 방법

핵심 요약

  • 원본 코드는 선택된 부트 헤더의 한 워드를 핸들의 한 칸으로 복사합니다. 바로 이어지는 매체 정보 조회는 다른 칸에서 크기와 간격을 읽으며 이 값은 쓰지 않았습니다.
  • 원래 MAIN의 Burn은 FileX에 특수값을 넘깁니다. 그 값 때문에 FileX는 부트 읽기 요청을 건너뜁니다. 그래서 헤더 소비와 부트 읽기는 원본 코드 안에서 서로 다른 길입니다.
  • 매체 정보 조회 상태의 사본에 부트 읽기 요청과 시험용 컨텍스트를 넣자 복사된 값이 NAND 읽기 요청의 위치 인수로 그대로 전달됐습니다({{positive_count}}조건). 컨텍스트가 비어 있으면 읽기 없이 오류를 돌려줬습니다.
  • 따로 넣은 크기 계산 요청은 식별값에서 나온 용량 칸을 읽었고 복사된 값은 읽지 않았습니다.
  • 모든 실행은 NAND 응답 직전에서 멈췄습니다. 식별값·헤더·컨텍스트는 시험용 값이며 실제 NAND를 읽지 않았습니다. 위치 값은 내부 인수이고 섹터·페이지·블록 단위와 연결하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 따로 넣은 크기 계산 요청 {{info_count}}조건
  • 따로 넣은 부트 읽기 요청 {{boot_count}}조건(NAND 연산 진입까지)

정적 분석 코드를 읽어 판단

  • Burn이 넘기는 특수값과 FileX가 부트 읽기를 건너뛰는 분기
  • 특수값이 아닐 때 필요한 드라이버 초기화 조건

모델 시험 조건으로 정한 것

  • 시험용 식별값, FF 예비 영역, 합성 헤더 두 개와 실패 상태 7
  • 재시도 정보·세마포어 API의 성공 응답
  • 요청 번호, 컨텍스트 포인터, PC·RA·SP 재설정

미확인 확인하지 않은 것

  • NAND 연산 본문과 응답, 재시도, 파티션·부트 버퍼 해석
  • 원래 초기화 경로가 만든 컨텍스트
  • 실제 위치 단위와 유효한 위치 범위

배경: FileX 드라이버 요청

FileX는 저장 매체를 직접 다루지 않고 매체마다 드라이버 함수를 부릅니다. 무엇을 할지는 요청 번호로 알려 줍니다. 드라이버는 결과를 상태 칸에 적습니다. 공개 FileX 헤더에서 4는 FX_DRIVER_INIT, 5는 FX_DRIVER_BOOT_READ(부트 섹터 읽기)입니다. 상태 0x90은 FX_IO_ERROR입니다. Q7의 NAND 드라이버(_fx_nand_driver)도 요청 4에서 초기화를, 요청 5에서 부트 읽기를 합니다. 이 문서의 요청 9는 공개 목록(0~8)에 없는 번호입니다.

핸들
FileX 매체 구조체와 NAND 드라이버 상태를 함께 담은 메모리 블록입니다. +0xc10 같은 표기는 그 안의 위치입니다.

컨텍스트
NAND 변환 계층이 쓰는 전역 상태 구조체. 전역 변수 hNandTlInfo가 이 구조체를 가리키며 처음 값은 0입니다.
특수값
Burn이 FileX의 일곱째 인수로 넘기는 0x80000000입니다. 공개 FileX의 fx_media_open 인수 목록에는 없는 자리입니다.

이 문서는 NAND 식별값과 부트 헤더 재지정이 멈춘 자리에서 이어집니다. 그 문서의 마지막 실행은 헤더 함수에서 돌아온 직후(0x80084114)에서 멈췄고 호출자는 아직 헤더 +0x200을 읽지 않았습니다.

이어진 실행 하나와 따로 넣은 요청 둘

헤더 소비는 매체 열기에서 이어진 실행입니다. 크기 계산 요청과 부트 읽기 요청은 그 결과 상태를 각각 복사해 따로 시작한 시험입니다. 실제 FileX에서 연달아 일어난 요청으로 보면 안 됩니다.

참고

따로 넣은 요청 9의 크기 계산은 ceil(0x100000 / (16 × 63)) = {{geometry_value}}을 핸들 +0xbc8에 씁니다. {{info_count}}조건 모두 반환값 1, 드라이버 상태 0, VEX 이벤트 {{geometry_vex}}건이었습니다. 시험용 식별값에서 나온 수이며 실제 NAND 용량이나 물리 구조를 잰 값이 아닙니다.

원래 Burn의 흐름은 부트 읽기 요청을 건너뜁니다

Burn이 넘긴 특수값 때문에 FileX는 요청 5를 드라이버에 보내지 않습니다. 아래의 요청 5 시험은 연속 실행에서 저절로 생긴 호출이 아닙니다.

Burn은 FileX의 일곱째 인수로 0x80000000을 넘깁니다. FileX는 요청 4의 결과 상태가 0이면 요청 5를 준비합니다. 그런데 0x80066bb4에서 인수가 이 특수값이면 두 번째 드라이버 호출을 건너뜁니다. 다른 값이면 0x80066bc0에서 드라이버를 부릅니다. 0xffffffff도 먼저 드라이버를 거치고 그 뒤의 FileX 대체 경로에서 따로 검사됩니다. [근거: static_dispatch, source.decoded_burn]

특수값이 아닐 때 요청 4는 TlDriverInit이 성공해야 통과합니다. 이 함수의 성공과 kind 1 컨텍스트의 확보는 별개 조건입니다. 원래 초기화부터 요청 5까지 이어지는 전체 경로는 실행하지 않았습니다.

시험 조건

정보 조회 상태의 사본에서 요청 번호를 5로 바꾸고 전역 hNandTlInfo(0x8008c14c)에 빈 포인터 또는 kind 1 합성 컨텍스트를 넣었습니다. PC·RA·SP도 새 호출에 맞게 맞췄습니다. 이 포인터는 원래 등록 경로나 TlDriverInit의 성공을 입증하지 않습니다. 원래 등록 경로는 컨텍스트 등록과 별도 매체 발견에서 다룹니다.

kind 1 경로는 복사된 값을 첫 읽기의 위치로 넘깁니다

TlBootRead는 핸들 +0xc10을 읽어 아래 함수들에 위치 인수로 넘깁니다. 네 단계를 거치는 동안 값은 바뀌지 않았고 NAND 연산 진입점에서 멈췄습니다.

조건복사된 워드헤더 탐색 간격NAND 연산 위치VEX 이벤트결과와 멈춘 자리

정렬되지 않은 값 0x123은 간격 32와 256에서 모두 그대로 전달됐습니다. 헤더 +0x14의 재지정 위치가 간격에 맞춰 내려가던 것과 다른 동작입니다. 재지정된 두 번째 헤더의 값과 0xffffffff도 그대로 전달됐습니다. 유효한 위치 범위는 검증하지 않았습니다.

빈 컨텍스트 조건은 NAND 연산으로 들어가지 않고 반환값과 드라이버 상태 0xf2를 남깁니다. 이 경로도 빈 포인터 검사보다 DATA[1]을 먼저 읽으므로 읽을 수 있는 합성 버퍼가 필요했습니다. [근거: boot_read.cases, source.selected_e03_ranges]

NAND 연산 인수와 확인한 조건
  • TlBootRead의 0x80084598이 핸들 +0xc10을 읽습니다. kind 1 분기의 0x800847f0이 그 값을 위치 인수로 옮기고 0x80084800이 TlMediaOperation을 부릅니다.
  • 양성 {{positive_count}}조건의 NAND 연산 인수는 {{nand_ex_args}}이고 복귀 주소는 0x80053f0c입니다.
  • 예비 영역 버퍼 주소는 TlFcuOperation 진입 SP − 0x78 + 0x20과 같습니다.
  • 중간 함수의 분기 조건은 핸들 +0xc24=0과 ELF 모드 바이트 0x80059a59=0입니다.
  • 읽기 대상 버퍼 8 KiB의 SHA-256은 실행 전후가 같습니다. 멈춘 시점의 드라이버 상태 0x90은 FileX가 미리 넣어 둔 값이며 끝난 읽기의 오류 결과가 아닙니다.
  • JSON의 arguments는 ABI 칸 8개를 그대로 저장합니다. 의미 있는 인수는 TlBootRead 앞 2개, TlFcuOperation·FcuNandOperation 앞 7개, TlMediaOperation·NAND 연산 8개입니다.
  • JSON의 PC는 VEX 콜백 기준이라 MIPS 지연 슬롯의 정확한 명령 주소와 다를 수 있습니다.

K-3 III와는 저장 계층과 근거의 범위를 대조했습니다

K-3 III의 부팅·저장소 분석은 M0·BOOT·RTOS 사이의 적재와 bank 선택값을 구분합니다. 그 자료에도 단계 사이 주소 대응과 bank 값의 출처에 미확정 항목이 남아 있습니다. Q7의 결과는 FileX 아래 NAND 부트 읽기의 위치 인수까지입니다. K-3 III의 bank나 eMMC 단위를 이 Q7 칸에 대응시킬 근거는 없습니다.

원본 코드의 분기·인수·반환과 공급한 저장장치 응답을 나눠 적는 방식은 두 분석이 같습니다. Q7 시험은 NAND 응답 전에 멈추므로 실제 부트 데이터나 그 뒤 실행 이미지까지 연결된다고 말하지 않습니다.

한계와 남은 과제

  • 실제 NAND의 식별값·헤더·응답, 섹터·페이지·블록 단위, 카메라 부팅·기록·복구는 확인하지 않았습니다.
  • 위치 값이 그대로 전달된다는 사실만으로 유효한 위치 범위나 읽기 성공을 말할 수 없습니다.
  • 크기 계산 요청 9와 부트 읽기 요청 5는 레지스터를 다시 맞춰 따로 넣은 시험입니다.
  • 원래 특수값 경로는 TlDriverInit, 크기 계산, 요청 5를 모두 건너뜁니다. 특수값이 아닌 원래 열기와 실제 재시도·세마포어 구현은 실행하지 않았습니다.
  • 평평한 가상 주소와 합성 포인터를 썼습니다. KSEG 별칭, TLB, 캐시, DMA는 모델에 없습니다.
  • 다음 확인 대상은 NAND 연산 응답 이후의 재시도와 파티션 해석, 그리고 원래 초기화가 만든 컨텍스트입니다.

재현 방법

실행 엔진은 angr 10.0.5 / MIPS32 리틀엔디언 / VEX입니다. 이 환경에서는 Unicorn과 REA의 네이티브 공급자를 쓸 수 없어 원본 바이트 대조와 VEX 실행을 근거로 삼았습니다.

python tools/check_nand_boot_read.py <원본 fwdc603p.bin> <분석 main-expanded.elf> --output <새 결과.json>
python tools/build_nand_boot_read_report.py
python -m unittest discover -s tests -p test_nand_boot_read.py

재현기는 원본 펌웨어와 분석 ELF의 SHA-256을 확인합니다. 그다음 E03의 {{range_count}}개 구간·{{range_bytes}}바이트를 고정 해시 및 ELF와 대조합니다. E05는 원본 압축 스트림에서 새로 풀어 Burn 호출 구간 216바이트를 대조합니다. 헤더 시험의 구간·워드 검증도 다시 씁니다. 결과는 새 파일로만 만들고 입력·기존 출력·파일 별칭을 덮어쓰지 않으며 python -O는 거부합니다. 재현은 순차 실행을 전제로 합니다. 보고서 생성에는 원본이나 angr가 필요 없습니다. [근거: source]

분석 ELF는 기존 도구로 복원합니다. 펌웨어와 ELF는 공개 저장소에 없습니다.

분석 ELF는 RWX로 적재하고 RAM·식별값·헤더는 합성 입력입니다. 공유 시작 상태는 전역 0x81547f10에 32비트 0, 0x8008c2dc에 1바이트 0, 0x8008c2f4에 32비트 0을 넣고 뒤의 두 주소는 쓰기를 허용합니다. 원본 코드 바이트 대조와 실제 메모리 내용·권한의 검증은 별개입니다. [공유 상태와 모델]
