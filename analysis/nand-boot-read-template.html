부트 헤더 값의 소비와 별도 읽기 요청

헤더 +0x200의 값이 핸들에 복사되는 지점과, 그 값을 첫 부트 읽기 요청에 넘기는 지점을 확인했습니다. 다만 원래 Burn/FileX 흐름은 이 읽기를 생략하므로 읽기 경로에는 요청과 context를 별도로 공급했습니다.

이 문서에서

  1. 연속 실행과 두 별도 요청을 구분했습니다
  2. 헤더 값은 복사되지만 정보 조회의 크기는 바꾸지 않았습니다
  3. 원래 Burn/FileX 흐름은 부트 읽기 요청을 건너뜁니다
  4. kind 1 경로는 +0xc10을 첫 읽기의 위치로 전달합니다
  5. K-3 III와는 저장 계층과 증거의 경계를 대조했습니다
  6. 원본 검증과 재현 방법

핵심 요약

  • 원본 코드는 선택한 헤더 +0x200의 값을 핸들 +0xc10으로 복사합니다. 이어진 정보 조회는 다른 필드에서 크기·간격을 읽으며, 이번 경로에서는 +0xc10을 사용하지 않았습니다.
  • 성공 상태 사본에 별도로 공급한 요청 9는 geometry 계산을 실행했습니다. 계산 입력은 +0xbf4이며, +0xc10은 읽지 않았습니다.
  • 별도 요청 5와 kind 1 context를 공급한 6조건에서 +0xc10 값은 NAND Ex 진입까지 위치 인수로 그대로 전달됐습니다. Null context 대조군은 0xf2를 반환했습니다.
  • 관측한 값은 내부 호출 인수입니다. 실제 NAND의 sector·page·block 단위, 유효한 위치 범위, 읽기 성공을 뜻하지 않습니다.

연속 실행과 두 별도 요청을 구분했습니다

앞선 헤더 재지정 분석의 종료 지점은 헤더 함수에서 돌아온 직후인 0x80084114였습니다. 호출자는 아직 헤더 +0x200을 읽지 않았습니다. 이번 시험은 그 뒤의 복사·정보 조회까지 이어 갑니다. 요청 9와 요청 5는 이 성공 상태에서 각각 사본을 만들고 호출 상태를 재설정한 시험입니다. 실제 FileX에서 연달아 발생한 요청들이 아닙니다.

헤더 값은 복사되지만 정보 조회의 크기는 바꾸지 않았습니다

원본 0x80084120은 헤더 +0x200을 읽고 0x80084128은 핸들 +0xc10에 씁니다. 값 0도 쓰기 이벤트로 확인했습니다. 재지정 성공에서는 첫 헤더 값 대신 두 번째 헤더 값이 복사됩니다. 이후 정보 조회는 +0xbf4·+0xc14를 읽어 +0xc8c·+0xc88에 씁니다. [header_information.cases]

조건복사된 +0xc10정보 간격 / 크기별도 geometry누적 VEX 이벤트

두 번째 데이터 응답을 7로 공급한 실패 조건은 헤더 함수의 실패 해제 요청만 실행합니다. 호출자의 복사는 실행하지 않고 driver 상태 0x90을 저장한 뒤 0x80066b88에서 멈춥니다. 성공 해제의 반환 주소 0x8008413c와 실패 해제의 반환 주소 0x80056744를 구분해 기록했습니다. 해제 모델은 실제로 메모리를 해제하지 않습니다.

별도 요청 9의 geometry 계산은 ceil(0x100000 / (16 × 63)) = 1041을 핸들 +0xbc8에 씁니다. 5조건 모두 반환값 1, driver 상태 0, 별도 VEX 이벤트 17건입니다. 이 수치는 실제 NAND 용량이나 물리적 geometry의 측정값이 아닙니다.

원래 Burn/FileX 흐름은 부트 읽기 요청을 건너뜁니다

Burn은 FileX의 7번째 인수로 0x80000000을 전달합니다. FileX는 요청 4의 callback 상태가 0일 때 요청 5를 준비합니다. 0x80066bb4에서 이 특수값이면 두 번째 driver callback을 생략합니다. 따라서 아래 요청 5 시험은 연속 실행에서 자연스럽게 발생한 호출이 아닙니다. [static_dispatch·source.decoded_burn]

다른 인수는 앞선 초기화가 성공하면 callback 0x80066bc0을 실행합니다. 0xffffffff도 callback을 먼저 거치고 뒤의 FileX fallback에서 따로 검사합니다. 다만 특수값이 아닌 요청 4는 TlDriverInit을 요구합니다. 이 함수의 성공과 kind 1 context 확보는 별개 조건입니다. 자연 초기화부터 요청 5까지의 전체 경로는 실행하지 않았습니다.

이번에는 정보 조회 상태의 사본에서 요청 번호를 5로 바꾸고 전역 hNandTlInfo(0x8008c14c)에 null 또는 kind 1 합성 context를 공급했습니다. PC·RA·SP도 새 호출에 맞게 설정했습니다. 원본 전역의 초기값은 0입니다. 공급한 포인터는 원본 등록 경로나 TlDriverInit 성공을 입증하지 않습니다.

kind 1 경로는 +0xc10을 첫 읽기의 위치로 전달합니다

TlBootRead의 0x80084598은 핸들 +0xc10을 읽습니다. kind 1 분기에서 0x800847f0이 이 값을 위치 인수로 옮깁니다. 0x80084800이 TlMediaOperation을 호출합니다. 아래 함수들을 거쳐도 값은 바뀌지 않았습니다. [boot_read.cases·source.selected_e03_ranges]

비정렬 값 0x123은 헤더 탐색 간격 32와 256에서 모두 그대로 전달됐습니다. 이는 앞선 헤더 +0x14의 재지정 위치 정렬과 구분됩니다. 재지정된 두 번째 헤더의 값도 그대로 사용했습니다. 0xffffffff의 전달까지 확인했습니다. 유효한 주소 범위는 검증하지 않았습니다.

양성 6조건의 NAND Ex 인수는 [1, 0x24002000, 4, word, 1, 0x24006000, 0x70000eb0, 16], 반환 주소는 0x80053f0c입니다. spare는 TlFcuOperation 진입 SP − 0x78 + 0x20과 일치합니다. wrapper 분기는 핸들 +0xc24=0과 ELF mode byte 0x80059a59=0 조건입니다.

읽기 목적 버퍼 8 KiB의 SHA는 실행 전후 동일합니다. 이 경계에서 남아 있는 driver 상태 0x90은 FileX가 앞서 준비한 값입니다. 완료된 읽기의 오류 결과가 아닙니다. Null context 경로도 null 검사보다 먼저 DATA[1]을 읽으므로 읽기 가능한 합성 버퍼가 필요합니다. 이 조건에서는 NAND 연산 체인에 진입하지 않고 반환값·driver 상태 0xf2를 확인했습니다.

K-3 III와는 저장 계층과 증거의 경계를 대조했습니다

K-3 III의 부팅·저장소 분석은 M0·BOOT·RTOS 사이의 적재와 bank 선택값을 구분합니다. 그 자료에서도 단계 사이 주소 대응과 bank 값의 생산 경로에는 미확정 항목이 남아 있습니다. Q7의 이번 결과는 FileX 아래 NAND 부트 읽기의 위치 인수까지입니다. K-3 III의 bank나 eMMC 단위를 이 Q7 필드에 대응시킬 근거는 확보하지 못했습니다.

두 분석에서 원본 코드의 분기·인수·반환과 공급한 저장장치 응답을 구분하는 방법은 같습니다. 이번 Q7 시험은 NAND 응답 전에 멈추므로 실제 부트 데이터나 이후 실행 이미지까지 연결됐다는 결론은 내리지 않습니다.

원본 검증과 재현 방법

실행 엔진은 angr 10.0.5 / MIPS32 little-endian / VEX입니다. 이 환경에서는 Unicorn을 사용할 수 없었습니다. REA의 네이티브 공급자도 사용할 수 없어 원본 바이트 대조와 VEX 실행을 근거로 삼았습니다.

원본 펌웨어·분석 ELF의 전체 SHA-256을 검사하고 추가 E03 {{range_count}}개 범위·{{range_bytes}}바이트를 고정한 해시 및 ELF와 대조합니다. E05는 원본 압축 스트림에서 새로 복원해 Burn 호출 구간 216바이트를 대조합니다. 공유 헤더 시험의 원본 범위·워드 검증도 재사용합니다. [source]

공개 CLI는 새 결과 파일만 만들며 입력·기존 출력·파일 별칭을 덮어쓰지 않습니다. python -O도 거부합니다. 재현은 순차 실행을 전제로 합니다. 보고서 생성에는 원본이나 angr가 필요하지 않습니다.

python tools/check_nand_boot_read.py <원본 fwdc603p.bin> <분석 main-expanded.elf> --output <새 결과.json>
python tools/build_nand_boot_read_report.py
python -m unittest discover -s tests -p test_nand_boot_read.py

분석 ELF는 RWX이고 RAM·ID·헤더는 합성 입력입니다. 공유 prefix는 전역 0x81547f10에 32비트 0, 0x8008c2dc에 1바이트 0, 0x8008c2f4에 32비트 0을 넣고 뒤 두 주소의 쓰기를 허용합니다. 원본 코드 바이트 대조와 실제 메모리 내용·권한의 검증은 별개입니다. [공유 상태와 모델]

JSON의 PC는 VEX 콜백 문맥이므로 MIPS 지연 슬롯의 정확한 명령 주소와 다를 수 있습니다. arguments는 raw ABI 슬롯 8개를 저장합니다. 의미 있는 인수는 TlBootRead 앞 2개, TlFcuOperation·FcuNandOperation 앞 7개, TlMediaOperation·NAND Ex 8개입니다. VEX 이벤트 수는 명령 수나 실행 시간이 아닙니다.

장착 NAND의 응답·물리 단위·주소 별칭·TLB·캐시·DMA, 카메라 쓰기·부팅·복구는 검증하지 않았습니다. NAND Ex 응답 이후의 retry와 partition 해석, 자연 초기화로 만든 context가 다음 확인 대상입니다.
