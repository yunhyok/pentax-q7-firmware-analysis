색 처리와 HDR · 버퍼와 패스

HDR 결과 버퍼가 JPEG가 되는 경로와 색 필터의 덮어쓰기

HDR 모드로 합성한 사진이 어느 메모리를 거쳐 JPEG로 압축되는지, 그리고 색 변환 계수가 처리 도중 누구에 의해 바뀔 수 있는지 추적했습니다.

이 문서에서

  1. 배경: HDR 모드와 이 문서의 질문
  2. HDR 결과 버퍼에서 JPEG 압축까지
  3. 처리 패스의 선택과 레지스터 제출 방식
  4. FIPLIB가 덮어쓰는 범위: CM은 일부, FC1은 계수까지
  5. 두 setter·writer 구간의 재실행
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 분석한 HDR 경로에서 합성 결과를 담는 버퍼 하나(B)가 톤 매핑 출력, 렌즈 왜곡 보정(LDC)의 입력·출력, JPEG 압축 입력으로 차례로 쓰입니다. 소프트웨어가 넘기는 주소를 이어 본 결과이며 실제 픽셀 이동은 관측하지 않았습니다.
  • HDR 주 이미지의 실제 압축은 EXIF 조립 전에 ApsJpegDirectCompress가 합니다. EXIF 단계는 이미 만든 압축 결과의 크기를 씁니다.
  • 처리는 여러 패스로 나뉘고 제출 모드에 따라 전체·마지막 제외·마지막만을 고릅니다. 색 필터 CM과 FC1은 마지막 패스 전용 필터가 아닙니다.
  • 뒤에서 값을 다시 계산하는 FIPLIB는 CM에서는 보조 필드 세 개만, FC1에서는 행렬 계수 아홉 개까지 바꿉니다. 두 setter·writer 구간을 원본 명령으로 실행해 객체 바이트와 MMIO 쓰기 {{handoff_mmio}}회를 대조했습니다.

확인 원본 코드 실행으로 확인

  • CM·FC1의 FIPLIB setter 다음 레지스터 기록 함수를 이어 실행한 결과
  • CM 계수 보존, FC1 계수 교체와 16비트 잘림·부호 확장
  • 근거 워드 {{word_count}}건과 함수 후보 {{function_count}}개의 원본 대조

정적 분석 코드를 읽어 확인

  • HDR 버퍼 B에서 JPEG 입력 T(B)까지의 주소 전달
  • 패스 선택 범위, 마지막 패스 플래그, 덮어쓰기 조건
  • 레지스터 직접 쓰기와 CBC 배치 제출의 갈림

모델 시험 조건으로 정한 것

  • 필터 객체와 FIPLIB 결과(payload)는 합성 값
  • 갱신 표시는 1로 두고 분기 조건을 통과한 상태에서 시작
  • 레지스터는 일반 RAM으로 처리

미확인 확인하지 않은 것

  • DMA로 실제로 읽고 쓴 픽셀, 버스 주소, 캐시 일관성
  • 실제 촬영에서 고른 패스 수와 FIPLIB가 낸 최종 계수
  • ISP 내부 픽셀 계산, HDR이 아닌 일반 촬영 경로

배경: HDR 모드와 이 문서의 질문

Q7에는 노출을 달리한 세 장을 한 장으로 합쳐 밝은 곳과 어두운 곳을 함께 살리는 HDR 촬영 기능이 있습니다. 설정 값은 Auto, HDR 1, HDR 2이고 장면 모드의 HDR·야경 HDR은 JPEG로만 저장됩니다(리코의 Q7 발표 자료). 펌웨어에서 이 기능은 이미지를 섞는 HdrImageMixing, 톤을 맞추는 IpuToneMapRgb 같은 함수로 나타납니다.

이 문서는 두 가지를 묻습니다.

  1. 합성 결과는 어느 버퍼에 담기고 그 버퍼가 정말 JPEG 압축의 입력이 되는가
  2. 색 변환 계수는 처리 도중 누가, 어느 패스에서, 어디까지 바꿀 수 있는가
IPU
펌웨어가 영상 처리 회로를 부르는 단위(Ipu… 함수, CIpuTask). 회로의 정식 명칭은 확인하지 못했습니다.
LDC
StillCaptureLDCPass. 일반적으로 렌즈 왜곡 보정(Lens Distortion Correction)을 뜻하며 픽셀을 다시 배치해 왜곡을 펴는 처리입니다(TI의 LDC 설명 참고). Q7 사양에도 “Distortion Correction”이 있습니다. 펌웨어의 이 패스가 같은 일을 하는지는 함수 이름으로 추정한 것입니다.
CM, FC1
3×3 계수를 쓰는 색 필터 클래스 CCmFilter, CFc1Filter. 역할 이름은 클래스 이름에서 왔습니다.
FIPLIB
패스 구성과 필터 값을 계산하는 라이브러리(CFIPLIB, FipLibCalculate). 상위 설정을 입력으로 받아 패스마다 결과(payload)를 만듭니다.
CBC
레지스터에 직접 쓰는 대신 주소·값 쌍을 묶어 한꺼번에 제출하는 경로(CbcBatchExec).
범위

모든 결론은 분석한 HDR 성공 경로 하나에 대한 것입니다. HDR이 아닌 일반 촬영에 그대로 적용하지 않습니다. 이 문서의 내용을 이어받는 문서는 색 처리·HDR 안내에 순서대로 정리했습니다.

HDR 결과 버퍼에서 JPEG 압축까지

합성 버퍼 B의 주소가 톤 매핑 출력, HDR 결과, 렌즈 왜곡 보정, JPEG 압축 입력으로 이어집니다. 압축 입력에는 B를 규칙에 따라 바꾼 주소 T(B)가 들어갑니다.

화살표는 같은 주소(또는 그 안의 위치)가 넘어가는 관계입니다. 픽셀이 실제로 이동하는 것을 관측하지는 않았습니다. 첫 줄의 하위 이미지 출력은 B 안에서 반복마다 앞으로 나아가므로, 모든 하위 이미지 주소가 B와 같은 것은 아닙니다.

IPU 제출 단계의 조건

IpuSubmit은 path+0x964 == 0이면 path+0x28의 출력 블록을 쓰고 아니면 path+0x8fc의 대체 설명자를 복사합니다. 이 문서는 PathSetBuffers가 B의 view를 설정하는 관계까지 다룹니다. 새로 만든 HDR 경로에서 +0x964가 0으로 남아 path+0x28이 선택된다는 것은 HDR 제출 분기와 FC 계수에서 원본 명령으로 확인했습니다. [근거: ipu_output_descriptor]

실제 압축은 EXIF 전에 일어납니다

ApsExifCreateJpeg 안의 새 압축 분기(CodeGo)를 HDR의 압축 위치로 보면 안 됩니다. 확인한 세 HDR 호출자는 모두 주 이미지 설명자의 첫 워드가 0인 상태로 SaveJpegImage에 넘깁니다. 한 경로는 이미 압축 결과가 있는 경우로 처음부터 0을 넣습니다. 나머지 두 경로에서는 그보다 앞서 SaveCompressImage가 ApsJpegDirectCompress로 압축합니다. 그 뒤 결과가 가리키는 설명자의 첫 워드를 0으로 지웁니다. EXIF의 주 이미지 검사는 이 0을 보고 새 압축을 건너뛰어 기존 압축 크기를 씁니다. [근거: hdr_exif_existing_code, hdr_direct_jpeg_input]

압축 입력 주소의 변환 규칙

DirectCompress는 B를 그대로 쓰지 않습니다. bit 30이 켜져 있으면 최상위 비트를 지우고 꺼져 있으면 bit 29를 켭니다.

T(B) = (B & 0x40000000) ? (B & 0x7fffffff) : (B | 0x20000000)
IPU 출력 view : B + 하위 이미지 오프셋
JPEG 주 입력  : T(B)
EXIF 주 설명자: **descriptor == 0 → 기존 압축 크기 사용

그래서 IPU 출력과 JPEG 입력의 숫자는 그대로 같지 않습니다. 주소 변환과 view 오프셋을 함께 넣어 비교해야 합니다. [근거: jpeg_input_transform]

해석 (확인하지 않음)

MIPS32 주소 규칙(NetBSD의 정의)으로 보면 캐시를 쓰는 kseg0 주소 0x8…에서 bit 29를 켠 값이 0xa…입니다. 이 주소는 같은 물리 메모리를 캐시 없이 가리키는 kseg1 주소입니다. 압축 회로가 읽을 메모리를 캐시를 거치지 않는 주소로 넘기는 것으로 읽을 수 있습니다. 다만 이것은 주소 규칙에 비춘 해석입니다. 실제 버스 주소나 캐시 동작은 측정하지 않았습니다.

버퍼 연결 단계별 원문 관찰
  • hdr_output_allocation: HdrImageMixing이 W+0x70(W는 sp+0x20)에 블록 버퍼 설명자를 둡니다. HdrAllocBlockBufTag가 할당 주소 B를 설명자 워드 0에 저장합니다. PerformImageMixSubImages 동안 B를 보존했다가 성공하면 context+0x3dc에 씁니다.
  • hdr_ipu_output_binding: PerformImageMixSubImages가 W+0x70을 출력 커서로 쓰고 출력 설명자 sp+0x138의 워드 0에 복사합니다. W+0x208 == 0이면 format 0xf01로 IpuToneMapRgb에 넘깁니다. 이웃한 톤 매핑 호출 두 곳도 같은 설명자를 씁니다.
  • hdr_in_place_ldc: StillCaptureSaveIcaCreateThumbnail이 D를 StillCaptureLDCPass의 원본과 대상으로 함께 넘기고 되복사 플래그를 켭니다. type 8 생성 인자의 +0x18과 +0x34에 모두 D[0]이 들어갑니다.
  • hdr_direct_jpeg_input: 기존 압축이 없는 갈래가 D를 SaveCompressImage에 넘기고 D[0]이 압축 인자 +0x8·+0xc에 들어갑니다. DirectCompress는 +0x8을 B로 읽어 T(B)를 P+0x8에 씁니다. P+0x24에는 압축 결과 버퍼 주소가 따로 들어갑니다. 크기는 PathGetCodeSize로 돌려받습니다.
  • jpeg_path_creation: JpegPathInit이 type 1 생성 콜백 0x801df114를 등록합니다. 콜백은 P[0]을 path+0xb8에, P+0x8을 첫 표면 설명자(path+0x8)에 복사합니다.

할당 함수 HdrAllocBlockBufTag를 비롯한 함수 후보 20개가 근거 집합에 있습니다. [근거: selected_functions]

처리 패스의 선택과 레지스터 제출 방식

처리는 N개의 패스로 나뉘고 제출 모드가 그중 어느 범위를 실행할지 정합니다. 마지막 패스 플래그는 따로 있으며 CM·FC1은 마지막 패스에만 쓰이는 필터가 아닙니다.

패스 수 N은 FIPLIB 결과 객체의 첫 워드에서 읽습니다. 제출 모드는 SetParam으로 정하는 처리기 파라미터 ID 0xa(processor+0x284)이고 Commit이 모드에 따라 시작·끝 번호를 정합니다. 선택한 범위 안에서도 task 포인터가 있는 패스만 처리합니다. 이 범위는 실행 대상으로 삼는 소프트웨어 구간이며 모든 촬영에서 N이나 모드가 같다는 뜻은 아닙니다. 분석한 HDR 경로의 실제 값(N = 4, 모드 0)은 HDR FC1 활성화와 제출 패스에서 확인했습니다. [근거: pass_selection]

마지막 패스 플래그와 필터는 별개입니다

TranslateFilters는 i가 N−1일 때 마지막 패스 플래그를 넘깁니다. 각 패스는 자기 설정 포인터와 FIPLIB wrapper를 씁니다. 원본의 “마지막 패스 전용” 필터 표에서 설정된 항목은 ID 0 하나뿐입니다. CM(필터 10)과 FC1(필터 13)을 마지막 패스 전용으로 볼 근거는 없습니다.

task(i)    = *(processor + 0x204 + 4*i)
config(i)  = *(*(processor+0x34) + 0x370 + 0x374*i)
wrapper(i) = *(*(processor+0x40)+4) + 0x24*i
is_final   = (i == *(processor+0x308)-1)

공통 필터 표({{common_ids}}개 항목)는 모두 0이고 마지막 패스 전용 표({{final_ids}}개 항목)는 ID 0만 0이 아닙니다. 이는 ROM 표의 내용이며 실행 중 수정이 없다는 증명은 아닙니다. 마지막 패스 플래그, 촬영 모드, 필터 ID를 같은 개념으로 다루지 않습니다. [근거: final_selector, filter_tables]

레지스터 직접 쓰기와 CBC 배치 제출

같은 필터 객체의 값은 두 방식 중 하나로 하드웨어에 갑니다. 갈림은 처리기 파라미터 ID 0xb(processor+0x288)가 정합니다.

두 제출 방식
processor+0x288경로값이 가는 곳
0Go가 task를 큐에 넣고 CIpuDriver::RunTask가 WriteAll을 부름 → UID 비교 → 필터 vtable+8CM·FC1 기록 함수가 레지스터에 직접 store
0이 아님Commit이 배치를 만들고 SubmitToBatch → CollectCbcChunks → UID 비교 → 청크 재사용 또는 생성같은 객체 필드를 주소·값 쌍으로 RAM 청크에 담아 CbcBatchExec로 실행

두 경로 모두 현재 필터의 UID를 각 경로에 마지막으로 제출한 UID와 비교합니다. CBC에서 UID가 같으면 저장해 둔 청크를 다시 쓰고 다르면 새로 만듭니다. 따라서 새 설정이 늘 즉시 MMIO 쓰기로 이어진다고 볼 수 없습니다. 청크를 만드는 과정에서 행렬을 새로 계산하는 연산은 보이지 않았습니다. 청크 배치를 하드웨어가 실행하는 과정은 재현하지 않았습니다. [근거: emission]

표시한 CBC 순회는 processor+0x2f0 < 2 분기입니다. Go의 배치 실행은 끝 번호가 0이 아닐 것도 요구합니다. 일반 필터 경로는 config가 있고 task+0x1f8 == 0일 것을 요구합니다. CBC 청크 생성 함수는 CM 0x8035330c, FC1 0x8031f8c8입니다.

FIPLIB가 덮어쓰는 범위: CM은 일부, FC1은 계수까지

한 패스 안에서 상위 설정이 먼저 필터 값을 채우고 그 뒤 FIPLIB 결과가 같은 필터 객체를 갱신합니다. CM에서는 보조 필드 세 개만, FC1에서는 행렬 계수 아홉 개와 보조 필드까지 바뀝니다.

갱신은 세 번의 시도로 이루어집니다

CM과 FC1의 CreateFilter 분기는 상위 설정을 적용한 뒤 FIPLIB 갱신을 시도합니다. 두 호출은 같은 패스의 같은 필터 포인터 슬롯을 씁니다.

갱신 순서와 각 단계의 조건(gate)
단계조건대상
1. 상위 설정설정 포인터가 있고 (슬롯+9의 bit 0 또는 패스 강제 갱신)같은 패스의 CM·FC1 필터 포인터 슬롯
2. FIPLIB 값wrapper가 있고 (FIPLIB 갱신 비트 0 또는 패스 강제 갱신)1단계와 같은 슬롯

그 뒤 실제 기록UID 비교, 기록 함수의 갱신 표시 등직접 MMIO 또는 CBC 청크

활성화 단계는 값 갱신의 조건과 별개입니다. 그래서 상위 설정의 활성화 값만으로 최종 활성 상태를 정할 수 없습니다. 원본 표 bFiplibFilterCnange(0x80359448)는 ID 0xe에 0, ID 0xf에 1을 적어 둡니다. 그래서 FC1 설정이 들어오면 FIPLIB 재계산 표시가 켜집니다. [근거: overwrite, enable_gate]

CM: 행렬은 남고 보조 필드만 바뀝니다

CM의 FIPLIB setter(0x803531bc)는 객체의 +0xb0, +0xb4, +0xb8만 바꿉니다. 행렬 계수가 있는 +0x88~+0xa8은 건드리지 않습니다. 이 setter가 실행됐다는 사실만으로 CM 행렬 전체가 덮어써졌다고 볼 수 없습니다. 다른 호출이나 촬영 모드에서도 계수가 보존되는지는 확인하지 않았습니다.

FC1: 계수가 교체되고 16비트로 잘립니다

FC1의 version 0xc FIPLIB setter(0x8031f64c)는 payload에서 32비트 값 아홉 개를 읽습니다. 그중 하위 16비트를 객체의 행렬 필드에 저장합니다. 이 경로가 실행되면 앞서 설정한 FC1 계수가 바뀝니다. 기록 함수는 이 16비트 값을 다시 부호 있는 수로 읽어 32비트로 확장합니다. 저장할 때의 잘림과 기록할 때의 부호 확장을 함께 고려해야 합니다. 같은 분배 함수는 version 0xf도 받습니다. 이때는 값을 2비트 오른쪽으로 민 뒤 하위 16비트를 남깁니다(0x8031f6bc). 분석한 FipLibCalculate는 version 0xc를 냅니다.

FIPLIB wrapper+0x1c가 가리키는 payload와 필터 객체의 대응
필터payload필터 객체기록 주소

HDR 톤 매핑이 넣는 FC1 계수

IpuToneMapRgb는 ID 0xf, version 0xc의 로컬 설정을 만들고 아래 계수 아홉 개와 보조값 두 개를 넣습니다. 그 뒤 필터를 설정하고 활성화합니다. 이 값은 상위 설정이면서 동시에 FIPLIB의 입력입니다. PrepareCalculations(0x80349814)가 계수 아홉 개를 설정 구조체 +0x14~+0x24에서 FIPLIB 입력 +0x1074~+0x1084로 복사하기 때문입니다. [근거: hdr_local_matrix] [근거: hdr_integration]

이 계수가 최종 FC1에 남는지

이 문서의 근거만으로는 FIPLIB 결과가 이 숫자를 유지하는지 알 수 없습니다. 이어진 분석은 이를 원본 명령 실행으로 확인했습니다. 분석한 새 HDR 경로에서는 FIPLIB의 FC 블록이 이 11개 값을 그대로 복사해 FC1 객체까지 같은 값이 유지됩니다. 이 결론은 마지막 패스에 해당합니다(HDR 제출 분기와 FC 계수). 패스별로 FC1이 켜지는지는 HDR FC1 활성화와 제출 패스에서 다룹니다.

숫자가 뜻하는 것 (해석)

JFIF의 RGB→YCbCr 변환식에서 R·G·B의 계수에 2048을 곱해 표의 펌웨어 정수 계수와 비교했습니다. 아홉 항의 절대 차이는 모두 1 미만이며 최댓값은 0.5024입니다. 예를 들어 Y의 R 계수는 펌웨어에서 612이고 JFIF의 대응 계수에 2048을 곱하면 약 612.4입니다. 이 비교는 계수 항에 한정됩니다. JFIF의 Cb·Cr 상수항 +128이 적용되는지와 FC1의 실제 연산 및 고정소수점 분모는 미확인입니다. 펌웨어에도 “601”이라는 이름의 내장 계수가 같은 값으로 들어 있어 FC1의 색 변환 역할을 추정할 근거가 됩니다. [JFIF 1.02, 3쪽] · [HDR 제출 분기와 FC 계수]

K-3 Mark III와 비교

K-3 Mark III 자료도 버퍼 주소의 일치와 처리 순서를 구분합니다. 고정한 공개 커밋 {{k3_commit}}에는 B2r·R2y 버퍼의 조건부 일치와 별도의 JPEG 입력 필드 분석이 있습니다. 두 결과만으로 ISP에서 JPEG까지의 연결을 확인했다고 보지는 않았습니다. Q7에서도 주소·구조체·선택 조건을 원본에서 따로 확인했습니다. 로컬 작업 중 변경은 쓰지 않았습니다. [근거: 커밋과 파일 해시]

한계와 재현 방법

  • CPU가 설명자를 넘기고 계수를 갱신하는 것은 확인했지만 ISP 내부 픽셀 계산은 재현하지 않았습니다.
  • 버퍼 연결은 분석한 HDR 성공 경로의 주소 전달입니다. HDR 보정, 사진 프레임, LDC 같은 선택 처리가 픽셀을 바꿔도 주소 연결은 유지될 수 있으므로, 이 결과는 픽셀이 같다는 증명이 아닙니다.
  • 실제 촬영에서 선택된 패스 수, FIPLIB가 낸 최종 계수, 센서부터 저장 이미지까지의 픽셀 값은 관측하지 않았습니다. EXIF 분류는 주 JPEG 설명자에 대한 것이며 보조 이미지는 별도 경로입니다.
  • 재실행은 MMIO를 일반 RAM으로 둔 VEX 실행입니다. 패스 스케줄러, RTOS, CBC 엔진, 센서, JPEG 하드웨어는 구동하지 않았습니다.
