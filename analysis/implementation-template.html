재패킹 검증과 업데이트 검사, AF·UI 기초 조사

펌웨어를 고쳐 보려면 먼저 두 가지를 알아야 합니다. 업데이트 파일을 한 바이트도 틀리지 않게 다시 만들 수 있는지, 그리고 카메라가 그 파일의 무엇을 검사하는지입니다. 이 문서는 그 두 가지를 확인하고, 이후 연구의 발판이 된 AF 계산과 화면 아이콘의 기본 구조를 함께 정리합니다.

이 문서에서

  1. 배경: 펌웨어를 고치기 전에 확인할 것
  2. 448개 압축 블록을 원본과 똑같이 다시 만들었습니다
  3. 카메라는 파일 끝 32바이트를 검사하고, 로더는 헤더로 기록 방식을 고릅니다
  4. AF 기초: 초점 위치 추정 함수의 입출력을 확인했습니다
  5. UI 기초: 아이콘 번호, 저장 폭, 그리기 규칙을 확인했습니다
  6. K-3 Mark III와 무엇이 다른지
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 업데이트 파일 안의 압축 블록 448개를 풀었다가 다시 써서 원본과 완전히 같은 파일을 얻었습니다. 압축 형식을 정확히 이해했다는 뜻입니다.
  • 명령 하나(버전 정보 함수의 반환값 0을 1로)를 바꾼 파일도 크기와 배치를 그대로 둔 채 만들었습니다. 이 파일을 다시 풀어 PC 에뮬레이터에서 실행하니 1이 반환됐습니다.
  • 카메라 본 프로그램의 파일 검사 함수는 파일 끝 32바이트에 있는 식별자 3개와 바이트 합계만 확인합니다. 로더는 헤더의 종류 값에 따라 기록 함수를 고릅니다. 실제 파일의 값은 NAND 기록 함수를 가리킵니다.
  • AF의 초점 위치 추정 함수와 화면 아이콘 그리기 함수도 원본 코드로 실행해 입출력 규칙을 확인했습니다. AF나 화면을 바꾼 펌웨어를 만든 것은 아닙니다.
  • 모든 실험은 PC에서 했습니다. 바꾼 파일을 카메라가 받아들이는지, 기록하고 부팅하는지는 확인하지 않았습니다.

확인 파일 대조와 원본 코드 실행

  • 448블록을 다시 쓴 파일과 원본의 SHA-256 일치
  • 명령을 바꾼 파일을 전부 다시 풀어 대조, 바꾼 함수의 반환값 0 → 1
  • 파일 검사 함수 13사례, 로더의 기록 함수 선택 5사례
  • AF 추정 6사례, 아이콘 크기 조회 6사례, 아이콘 그리기 2사례

정적 분석 코드를 읽어 판단

  • 검사 함수가 파일 준비·업데이트 실행보다 먼저 호출되는 순서
  • 로더의 MD5 비교 코드가 있다는 사실(이 문서에서는 실행하지 않음)
  • AF 추정값 이후의 보정 분기, 메뉴와 입력의 연결

모델 시험 조건으로 정한 것

  • 검사 함수에 넣은 합성 96바이트 파일과 파일 읽기·메모리 할당
  • 종류 값과 해시 플래그를 바꾼 합성 헤더
  • 합성 대비 곡선, 합성 화면 버퍼

미확인 확인하지 않은 것

  • 카메라가 바꾼 파일을 받아들이는지, 플래시 기록·부팅·촬영
  • 검사 함수 이후 단계의 다른 조건(버전 검사 등)
  • 실제 렌즈 구동과 LCD 출력

배경: 펌웨어를 고치기 전에 확인할 것

Q7의 업데이트 파일 fwdc603p.bin은 여러 실행 파일(ELF)을 묶은 꾸러미입니다. 카메라 본 프로그램의 코드 대부분은 압축돼 있고, 압축은 블록 448개로 나뉘어 있습니다. 블록 하나는 머리말, 부호표 두 개, 압축 비트열로 이루어집니다. 압축을 푸는 방법은 압축 복원과 주요 함수 300개에서 다룹니다.

코드를 한 줄이라도 바꾸려면 푼 내용을 다시 같은 형식으로 묶어야 합니다. 이 작업을 재패킹이라고 부릅니다. 압축 비트열은 토큰의 나열입니다. 토큰은 바이트 하나를 그대로 적는 “리터럴”과 앞에 나온 내용을 가져오는 “복사” 두 종류입니다.

참고

업데이트가 카메라 안에서 어떤 순서로 진행되는지는 업데이트·재패킹 안내의 전체 그림에 있습니다. 여기서 만든 재패킹 도구로 C로 다시 짠 함수를 넣어 본 결과는 색 행렬 함수 C 재컴파일에 있습니다.

448개 압축 블록을 원본과 똑같이 다시 만들었습니다

압축 블록을 모두 풀어 토큰으로 바꾼 뒤 같은 토큰으로 다시 쓰면 원본과 한 바이트도 다르지 않습니다. 명령 하나를 바꾼 경우에도 블록 하나와 합계 4바이트만 달라졌습니다.

왕복 검증

도구는 블록마다 압축 비트열을 토큰으로 해석하고, 그 토큰을 다시 비트열로 적습니다. 부호표와 블록 자리는 건드리지 않습니다. 이렇게 만든 파일은 전체 SHA-256이 원본과 같았습니다. 압축을 푼 내용으로 만든 분석용 ELF도 원본에서 만든 것과 같았습니다. [근거: roundtrip]

본 프로그램의 파일 검사

카메라 본 프로그램에는 UpdateFW_IsCorrectUpdateFirmware라는 함수가 있습니다. 이 함수는 파일의 마지막 32바이트(이 문서에서는 “꼬리표”라고 부릅니다)를 읽어 세 식별자를 비교하고, 꼬리표 앞의 모든 바이트를 더한 값을 꼬리표에 적힌 합계와 비교합니다. 호출 순서를 보면 이 검사는 파일 준비(UpdateFW_LoadFirmware)와 업데이트 실행(UpdateFW_UpdateFirmware)보다 앞에 있습니다.

꼬리표 = 파일의 마지막 32바이트
꼬리표[0:8], [8:16], [16:24] = "ORION", "KB538", "77690"
꼬리표[24:28] (리틀엔디언 32비트) == 꼬리표 앞 모든 바이트의 합 mod 2^32
꼬리표[28:32] = 01 01 17 0a   ← 이 함수는 비교하지 않음

이 함수를 원본 코드 그대로 13가지 입력으로 실행했습니다. 입력은 본문 64바이트에 꼬리표 32바이트를 붙인 합성 96바이트 파일입니다. 파일 읽기와 메모리 할당은 모델이 대신했고, 식별자 비교와 합계 계산은 원본 명령이 수행했습니다.

로더의 기록 함수 선택

업데이트 파일 맨 앞에는 본 프로그램과 별개인 실행 파일이 하나 들어 있습니다. 내장 ELF 가운데 첫째여서 E01이라 부르며, 저장장치에 기록하는 코드를 담은 로더입니다. 로더는 파일 오프셋 0x100000에 있는 192바이트 헤더(burn header)를 읽습니다. 로더의 BurnGetHandle은 헤더의 종류 값(+0x08)에 따라 기록 함수를 하나 골라 작업용 구조체(핸들)에 적어 둡니다.

{{header_rows}}
원본 BurnGetHandle 5사례. 선택된 기록 함수 자체는 실행하지 않았습니다
종류 값해시 플래그핸들에 적힌 기록 함수 (E01 안의 주소)

헤더 +0x3c에는 해시 플래그가 있습니다. 이 값이 0이 아니면 로더는 MD5 계산을 맡는 작업자를 따로 준비하고 16바이트를 비교합니다. 실제 파일의 값은 0이어서 이 경로를 쓰지 않습니다. 플래그가 켜졌을 때의 코드는 읽어서 확인했고, 실제 계산은 기록 헤더와 MD5 경로에서 실행했습니다. 플래그가 0이라고 해서 다른 무결성 검사나 저장장치 조건이 없다고 볼 수는 없습니다. [근거: boot_dispatch] · [재현 도구]

주소를 읽을 때

E01의 주소는 본 프로그램의 주소와 일부 겹칩니다. 그래서 E01의 명령은 E01 이미지 안의 주소와 원본 파일 오프셋을 함께 적어 구분했습니다. E01 함수의 범위는 ELF 심볼(STT_FUNC)에 적힌 크기를 썼습니다. 본 프로그램에도 이름이 같은 BurnGetHandle·BurnNand가 따로 있습니다. 이 차이는 메인 업데이트 진입과 반환값에서 다룹니다.

AF 기초: 초점 위치 추정 함수의 입출력을 확인했습니다

추정 함수는 렌즈 위치와 대비 값의 표본을 받아 대비가 가장 높을 위치를 계산합니다. 이 함수를 바꾸려면 함께 지켜야 할 조건이 여럿 있다는 것도 확인했습니다.

Q7은 이미지 센서의 영상으로 초점을 맞추는 콘트라스트 AF를 씁니다. 렌즈를 움직이며 대비를 재면 초점 근처에서 값이 봉우리 모양을 그립니다. 펌웨어의 Approximation 함수는 측정한 점들에 2차 곡선을 맞추고 그 꼭짓점을 초점 위치로 추정합니다.

렌즈 구동 요청

추정값은 LensDriveControl이라는 함수가 렌즈 구동 요청으로 바꿉니다. 이 함수는 모드·방향 같은 8비트 값, 16비트 값 하나, 32비트 위치 차이를 공유 구조체에 적고 등록된 콜백에 알립니다. 요청은 렌즈 통신 함수 LensCommunication 쪽으로 넘어갑니다. 하위 제한 모드가 켜진 조건에서는 요청을 큐에 넣지 않고 상태 8을 돌려주며, 관측한 대기 시간 초과 경로는 상태 6을 돌려줍니다. 여기서 본 것은 메모리에 적힌 인수입니다. 실제 통신선에서 잡은 신호가 아닙니다. [근거: 렌즈 경로] · [근거: af.lens_abi]

리코의 공식 자료에 따르면 01·02 Q 마운트 렌즈는 AF 모터가 렌즈 안에 있고, K 마운트 렌즈를 어댑터 Q로 붙이면 수동 초점만 쓸 수 있습니다. 따라서 Q7의 AF 계산을 연구할 때 K 마운트 바디의 구동 방식을 그대로 가져올 수 없습니다. [리코: Q 마운트 렌즈 발표] · [리코: Q7 FAQ]

이어지는 문서

AF를 바꾸는 일은 이 문서의 범위가 아닙니다. 렌즈가 AF를 지원하는지 판정하는 조건은 Loader 입력 검증과 렌즈 정책, 명령과 완료 판정은 AF 명령과 완료 판정에서 이어집니다. 전체 지도는 AF·렌즈 안내에 있습니다.

UI 기초: 아이콘 번호, 저장 폭, 그리기 규칙을 확인했습니다

Q7의 화면 아이콘은 색 대신 팔레트 번호 한 바이트씩을 화면 버퍼에 씁니다. 번호 0은 투명이고, 재색칠 스타일에서는 번호 1만 남기고 나머지를 지정한 번호로 바꿉니다.

  1. 버튼 입력4방향 키, 전자 다이얼, OK, MENU
  2. 메뉴 부품Canvas·Popup과 설정 번호. 포커스와 명령을 처리
  3. 아이콘 자원RLE 묶음 또는 Zoran 묶음. 번호로 크기와 데이터를 찾음
  4. 인덱스 그리기팔레트 번호를 화면 버퍼에 기록
  5. 팔레트와 LCD실제 색과 화면 출력은 확인하지 않음

아이콘은 두 묶음에 들어 있습니다. 아이콘 초기화 함수 ResourceIcon_InitializeBootStill(이하 BootStill)이 만드는 표의 항목 수로 확인한 범위는 RLE 묶음이 번호 1…248, Zoran 묶음이 번호 1001…1546입니다. 번호를 고르는 함수만 보아서는 두 범위 사이의 잘못된 번호가 안전하게 처리된다고 말할 수 없습니다.

아이콘에는 폭이 두 가지 있습니다. 화면 배치에 쓰는 논리 폭과, 압축을 푼 데이터의 저장 폭입니다. 두 값은 서로 다릅니다.

색 처리 연구와의 관계

색 보정 계수(FC1)를 다룬 분석은 계수 생성, 패스별 활성화, 최종 제어값 전달을 확인했습니다. 그 값이 RAW 현상용 카메라 프로파일(DCP)에 필요한 색 좌표 변환과 같은 뜻인지는 확인할 근거가 없습니다. RAW 정규화와 화이트밸런스, 행렬의 입력·출력 좌표계, 카메라 JPEG와의 대응을 따로 검증해야 합니다. [HDR 제출 분기와 FC 계수] · [FC1 유형과 비트의 한계]

한계와 재현 방법

이 문서의 검증은 파일 구조, 원본 MIPS 명령, 합성 메모리에 한정됩니다. 카메라의 플래시 기록, 부팅, 센서 픽셀, 실제 렌즈 구동, LCD 출력은 실행하지 않았습니다.

  • 재패킹: 448블록을 모두 다시 풀어 원본과 바이트 단위로 일치함을 확인했고, 바꾼 코드의 반환값 0 → 1을 실행으로 확인했습니다. 지원하는 편집은 크기가 같은 교체뿐입니다.
  • 파일 검사: 13사례. 파일 입출력·메모리 할당·진단 출력은 모델이고, 비교와 합산은 원본 코드입니다.
  • 로더 헤더: 5사례. 메모리 할당과 진단 출력만 모델로 바꿨고, 기록 함수를 부르기 전에 멈췄습니다.
  • AF·UI: AF 6사례, 크기 조회 6사례(아이콘 5개와 LCD 좌표 1개), 그리기 2사례. 화면 버퍼를 돌려주는 함수 한 곳을 모델로 바꿨습니다.
  • 남은 일: 로더가 기록할 위치·보호 조건·실제 적용 조건, 카메라의 파일 수용과 부팅. 앞의 둘은 업데이트·재패킹 안내의 뒤 문서들이 이어서 다룹니다.

원본 펌웨어, 추출한 자원, 바꾼 파일은 비공개 분석 폴더에만 둡니다. 공개 저장소에는 도구와 주소·해시·검증 결과만 있습니다.
