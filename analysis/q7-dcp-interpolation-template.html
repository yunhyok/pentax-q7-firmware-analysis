Q7 DCP의 LUT 좌표와 보간

Adobe DNG SDK 1.7.1 원본과 설치된 Q7 Adobe Standard DCP를 대조했습니다. encoding 태그의 기본값, 저장 축 순서, hue 경계와 V 배율의 적용을 소스로 확인하고 합성 HSV 15건을 수식으로 재현했습니다.

좌표와 이웃적용 위치확인한 결과수치 표본한계와 다음 단계출처·재현

같은 HSV 축, 서로 다른 이웃 수

SDK 내부 hue 범위는 0–6이며 이 보고서의 입력은 읽기 쉬운 도 단위를 씁니다. H 좌표는 H×hueDivisions/360, S 좌표는 S×(satDivisions−1), V 좌표는 V×(valDivisions−1)입니다. 마지막 S·V 격자점은 마지막 구간의 가중치 1로 처리합니다. H의 마지막 구간은 첫 hue로 이어집니다.

node = ((vIndex × Hdiv + hIndex) × Sdiv + sIndex)
scalar offset = 3 × node + component
component: 0=ΔH(도), 1=S 배율, 2=V 배율

근거: dng_camera_profile.cpp 1467–1502; dng_hue_sat_map.cpp 125–130, 200–206; dng_reference.cpp 1529–1745.

렌더 경로 안의 서로 다른 적용 위치

아래는 SDK 예제 렌더러의 관련 순서입니다. 카메라 펌웨어의 HDR 패스 순서나 Lightroom 내부 실행을 나타내지 않습니다. ColorMatrix·ForwardMatrix는 camera/PCS 변환에 관여하고, white는 HueSatMap1/2의 선택·보간에도 사용됩니다. As Shot 값이 LUT 좌표로 직접 들어가는 구조로 해석하지 않았습니다.

근거: dng_render.cpp 925–1002, 1862–2030; dng_color_spec.cpp 530–609. 노드 6은 후속 범위가 남아 있음을 표시하며 전체 출력 경로를 복원한 것으로 세지 않습니다.

확인한 결과와 근거

F1

encoding 태그가 없으면 SDK는 HueSatMap과 LookTable에 encoding_Linear(0)를 유지한다. 별도 encode/decode 곡선이 없다는 의미이며 LUT의 항등성을 뜻하지 않는다.

근거: dng_shared.cpp:126-135; dng_shared.cpp:992-1032; dng_shared.cpp:1124-1164; dng_camera_profile.cpp:1734-1736; dng_camera_profile.cpp:2366-2419; dng_tag_values.h:385-394

F2

차원 표기는 H,S,V이지만 메모리와 DCP 직렬화 순서는 V 바깥, H 중간, S 안쪽이다. 노드마다 hue shift(도), saturation scale, value scale 순으로 저장한다.

근거: dng_camera_profile.cpp:1467-1502; dng_hue_sat_map.cpp:125-130; dng_hue_sat_map.cpp:200-206; q7-dcp-interpolation.json:observations.dcp.tables

F3

HueSatMap [90,30,1]은 H,S의 네 이웃을 보간한다. LookTable [36,8,16]은 H,S,V의 여덟 이웃을 보간한다. 마지막 hue의 다음 이웃은 hue 0이다. shift 값 자체는 일반 선형 가중합이며 각도 최단호 보간을 하지 않는다.

근거: dng_reference.cpp:1529-1545; dng_reference.cpp:1590-1645; dng_reference.cpp:1649-1731; test_q7_dcp_interpolation.py

F4

보간한 hue shift를 H에 더하고 S와 V에는 각각 배율을 곱한다. S의 상한은 1, V는 [0,1]로 제한한다. 최종 RGB 변환에서 hue를 주기 6으로 감싼다. V 차원이 1이어도 V 배율은 적용된다.

근거: dng_reference.cpp:1735-1745; dng_utils.h:941-999; test_q7_dcp_interpolation.py

F5

SDK 예제 렌더러는 camera white와 CameraToPCS를 거쳐 ProPhoto RGB 공간으로 변환한 뒤 HueSatMap을 적용한다. 선택적인 ProfileGainTableMap과 exposure 처리를 거친 뒤 LookTable, baseline tone 순으로 진행한다. 이번 표본은 각 LUT 입구에서 별도로 주입했으며 이 전체 경로를 실행하지 않았다.

근거: dng_render.cpp:925-1002; dng_render.cpp:1862-2030; dng_color_spec.cpp:530-609

F6

HueSatMap1/2는 white의 색온도와 두 calibration temperature에 따라 선택·보간된다. 유효한 서로 다른 온도 사이에서는 역색온도로 첫 표의 가중치를 계산한다. 이번에는 각 표를 독립 평가했으며 As Shot으로 실제 가중치를 산출하지 않았다.

근거: dng_camera_profile.cpp:1861-1974; dng_render.cpp:925-971

F7

명시한 합성 HSV 5개를 세 표에 넣은 15건에서 binary64 구현과 50자리 Decimal 전체 격자 가중합의 최대 절대 차이는 1.9539925233402755e-14이다. SDK real32의 비트 일치나 Lightroom의 구현 일치를 뜻하지 않는다.

근거: q7-dcp-interpolation.json:observations; q7_dcp_interpolation_math.py; test_q7_dcp_interpolation.py

F8

이 고정 DCP의 LookTable에서 모든 저장 value scale은 1이다. 반면 HueSatMap1/2에는 1이 아닌 value scale이 있다. LookTable 단독의 정규 SDR 범위에서 V가 유지되는 수식상 성질은 이 저장값에서 나오며 encoding 태그 부재 때문이 아니다. H,S 변화에 따라 RGB와 휘도는 달라질 수 있다.

근거: q7-dcp-interpolation.json:observations.dcp.tables; dng_reference.cpp:1735-1745; dng_utils.h:941-999

합성 HSV에 대한 소수의 가중 보간 결과

표의 Map1·Map2·Look은 서로 연결된 픽셀 처리 결과가 아닙니다. 각 LUT에 같은 다섯 입력을 별도로 넣었습니다. 출력 HSV는 선택한 SDR·linear 가정 아래의 수식값이며 RGB 이미지나 카메라의 최종 색을 관측한 값이 아닙니다. 표시는 9자리 유효숫자로 줄였으며 JSON에는 계산값을 보존했습니다.

{{PROBES}}
ΔH는 도, S·V 계수는 곱셈 배율
표입력 H,S,VΔH, S배율, V배율수식상 출력 H,S,V

공개 패키지의 테스트 16개가 통과했습니다. 보간 경계와 원정본 전체 검사, 입력·출력 보호를 자산 없이 검사하며 아래 명령으로 실행할 수 있습니다. 보간 기준 구현은 모든 격자점에 Decimal 가중치를 적용하여 직접 구현의 셀 선택·stride 계산을 공유하지 않습니다. 15건의 최대 차이는 1.9539925233402755e-14입니다.

입력·집계·표본 JSON · 자산 없는 경계 검사 · 직접 보간 · Decimal 기준 구현

해석 범위와 다음 단계

  • 공통 전제는 finite normalized SDR HSV, linear encoding, supportOverrange=false다. profile.IsHDR()의 실제 분기나 overrange encode/decode는 이번 수치 실험에서 실행하지 않았다.
  • HSV의 V는 RGB의 최댓값이다. 광도·휘도·노출값과 같은 물리량으로 해석하지 않는다. S=0일 때 H는 색 관측값으로 의미가 없고 SDK RGB→HSV는 H=0을 사용한다.
  • SDK RefBaselineHueSatMap의 real32 연산을 Python binary64로 옮겼다. Decimal 교차 검증은 같은 수식의 독립 구현이며 native SDK 실행 검증이 아니다.
  • SDK의 SetDelta는 S=0 노드의 value scale을 1로 보정한다. 이 DCP의 해당 값들은 이미 모두 1이며 생략된 S=0 행도 없다. 범용 DCP의 생략 행 재구성은 구현하지 않았다.
  • ColorMatrix, ForwardMatrix, CameraNeutral/As Shot, exposure, ProfileToneCurve, gamut/clipping, 후속 출력 색 공간을 적용한 결과가 아니다. 테이블별 출력들을 서로 이어 붙이지 않았다.
  • III75의 원본 SDK ZIP과 source pins를 재사용했지만 III75 Stage 2 검증이 Q7 LUT·Stage 3·Lightroom 렌더링을 검증해 주지는 않는다. 카메라 FC1/HDR 패스와도 대응시킨 결과가 아니다.
  • 원래 연구는 Q7-28 도구와 설치 DCP를 읽기 전용으로 사용했다. 공개 재현은 현재 구조 도구와 외부 III 파서를 재사용한다. 전체 LUT·행렬·원본 코드·이미지를 복사하거나 배포하지 않았다. 표의 수치는 합성 입력에 대한 소수의 가중 보간 결과다.

후속 검증

  1. 동일한 합성 RGB와 고정 표를 원본 SDK의 RefBaselineHueSatMap 또는 DoBaselineHueSatMap에 넣어 real32 출력·클리핑·hue wrap을 교차 확인한다. native SDK 함수 실행은 이번 연구 범위 밖이며 후속 검증 항목이다.
  2. 명시한 white XY를 사용해 HueSatMapForWhite_Dual의 가중치와 생성 표를 재현한다. CameraNeutral→WhiteXY 추정과 두 calibration illuminant 변환은 각각 검증한다. Lightroom에 표시된 색온도를 SDK의 white XY/As Shot과 동일시하지 않는다.
  3. 색 변환, HueSatMap, exposure, LookTable, tone을 단계별로 분리한 수치 추적을 설계한다. RAW·Lightroom 신규 실행이나 완성 렌더 비교는 현재 범위 밖이다.

이번 연구는 K-3 III의 SDK75 출처와 Q7의 DCP28 입력 검증을 함께 사용했습니다. III의 Stage 2 native 실행과 이번 LUT 수식 검증은 서로 다른 증거입니다. 실기 FC1 제어 비트나 HDR task 완료 경로에 관한 새 결론은 추가하지 않았습니다.

고정한 소스와 재현

공개 검증기는 29번 관측의 모든 필드·타입·직렬화 해시를 검사한 뒤 표본과 문서를 만듭니다. 원정본의 sources, 이전 helper 해시와 scope는 역사적 출처·전제입니다. 현재 실행의 입력·모듈 해시는 별도 _reproduction에 기록하며 원래 환경을 다시 관측했다고 주장하지 않습니다.
