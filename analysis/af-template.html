AF와 렌즈 제어 · 명령 한 번이 완료 알림이 되기까지

AF 명령의 처리 결과와 렌즈 이동 완료는 다른 판정입니다

카메라가 “초점 맞추기 명령이 성공했다”고 판단하는 것과 “렌즈가 다 움직였다”고 판단하는 것은 펌웨어 안에서 서로 다른 코드가 다른 근거로 내립니다. 두 판정이 어디서 갈라지는지, 그리고 완료 표시가 무엇을 보장하지 않는지 원본 코드로 확인했습니다.

핵심 요약

  • AF 작업이 보낸 검색·정지 요청이 캡처 서비스를 거쳐 렌즈 큐 작업자에 닿는 길을 원본 코드로 이었습니다. 큐·대기·하위 통신은 모델로 대신했습니다. 실행한 사례는 {{total_cases}}개(명령·완료 {{command_count}}, 캐시 대기 {{wait_count}}, 취소 {{abort_count}})입니다.
  • 명령의 처리 결과(성공·거부·링크 실패·시간 초과)와 이동 완료는 따로 판정합니다. 검색 명령이 거부되거나 시간 초과로 끝나도 완료 확인 절차는 시작됐습니다.
  • 이동 완료는 렌즈 정보 캐시의 “이동 중” 바이트가 0이 되는 것으로 판정합니다. 캐시가 유효한지 알려 주는 값은 이 판정에 쓰지 않습니다. 통신 실패나 리셋으로 캐시가 0이 되어도 완료 알림이 나갔습니다.
  • 완료 알림이 세우는 blFocusCompleteflag는 소프트웨어 표시입니다. 초점이 실제로 맞았거나 렌즈가 기계적으로 멈췄다는 증거가 아닙니다. 이 연구에서 실제 렌즈를 움직인 일은 없습니다.

배경: AF 요청이 렌즈에 닿는 길

Q7은 촬상 센서의 영상으로 초점을 찾는 콘트라스트 검출 AF를 씁니다(리코 공식 사양). 초점용 모터는 바디에 없고 AF 렌즈 안에 있습니다. 그래서 카메라는 “초점 렌즈를 움직여라”를 렌즈 통신 명령으로 보냅니다. 이 문서는 AF 계산이 끝난 뒤 그 명령이 렌즈 쪽으로 나가고 결과가 돌아오는 구간을 다룹니다. AF 전체의 지도는 AF·렌즈 안내에 있습니다.

  1. AF 작업초점 위치 계산 후 LensDriveControl 호출 — 주요 함수 분석
  2. 캡처 서비스알림 0x6003c를 받아 검색·정지 setter 선택
  3. 렌즈 큐메시지 6(검색) 또는 8(정지)
  4. 렌즈 큐 작업자하위 렌즈 통신 호출, 결과 기록
  5. 완료 확인라이브뷰 콜백이 캐시의 이동 상태를 봄
  6. 실제 렌즈이 연구에서 움직이지 않음

읽기 전에 알아 둘 말이 몇 개 있습니다.

setter
검색이나 정지 메시지를 큐에 넣고 작업자가 결과를 기록할 때까지 기다린 뒤 결과값을 돌려주는 함수입니다.
pending
“이 명령의 결과를 아직 받지 못했다”는 표시 바이트입니다. 작업자가 결과를 기록하면서 지웁니다.
렌즈 정보 캐시
정기 통신으로 받은 렌즈 상태의 사본입니다. 그중 VDRC 이동 바이트가 “초점 렌즈가 움직이는 중”을 나타냅니다. 값과 별도로 “캐시가 유효한가”를 나타내는 바이트가 있습니다.
완료 확인 상태
캡처 쪽이 이동 완료를 판정하려고 두는 0·1·2 단계입니다. 0은 확인하지 않음, 1은 이동 시작 대기, 2는 이동 끝 대기입니다.
쉽게 말하면

택배를 보냈을 때 “접수됐습니다”와 “배달 완료”는 다른 알림입니다. Q7 펌웨어도 렌즈에 보낸 명령이 접수됐는지(setter 결과)와 렌즈가 움직임을 마쳤는지(캐시 기반 완료)를 따로 판정합니다. 그리고 “배달 완료” 알림조차 실제 물건이 문 앞에 있다는 사진은 아닙니다. 완료 플래그는 캐시 값을 보고 소프트웨어가 내린 결론일 뿐입니다.

요청이 렌즈 작업자에 닿고 결과가 돌아오는 길

AF 요청은 캡처 서비스의 원본 분기표를 거쳐 검색·정지 setter에 닿고 setter가 큐에 넣은 메시지를 원본 렌즈 작업자가 처리했습니다. setter의 결과값과 바깥 수신자의 반환값 1은 다른 값입니다.

  1. 요청 기록 LensDriveControl이 모드, 대기 플래그, 인수를 공유 구조체 tFocusControlInfo에 쓰고 blFocusCompleteflag를 지웁니다. 그 뒤 캡처 서비스에 (0x6003c, 0)을 보냅니다.
  2. 분기 캡처 수신자의 원본 분기표가 0x6003c를 ExecuteFocusControl로 보냅니다. 모드 0은 검색, 모드 1은 정지 setter를 부릅니다.
  3. 제출 setter가 pending 바이트를 세우고 메시지 6 또는 8을 큐에 넣습니다. 큐 모델이 받아들이면, 정해 둔 대기 회차에 그 메시지를 원본 작업자에게 넘깁니다.
  4. 작업자 처리 원본 LensComThreadMain이 메시지를 받고 이전 통신이 끝났는지 확인한 뒤 검색 또는 정지 작업 함수를 고릅니다. 작업 함수는 하위 통신 LensCommunication을 부르고 결과 바이트를 쓴 뒤 pending을 지웁니다. 시험은 작업자가 다음 메시지를 기다리기 전에 멈춥니다.
  5. 결과 반환 setter는 결과값을 돌려줍니다. 시험 도구는 캡처 수신자가 바깥에 자기 반환값 1을 돌려주기 전 지점에서 이 결과값을 읽었습니다.

setter 결과값의 뜻

원본 setter가 돌려준 값. 바깥 수신자의 반환값은 모든 사례에서 1이었습니다.
값관측한 조건
1작업자가 성공을 기록함
4하위 렌즈 통신이 실패를 돌려줌
6대기 101회째에도 결과를 받지 못한 것으로 판정(시간 초과)
7렌즈의 연산 맵이 그 명령을 허용하지 않음. 하위 통신 없음
8구동 제한 바이트가 정확히 1. 큐에 넣지 않음

시간 초과 판정에는 두 가지 사례가 있습니다. 하나는 작업자가 101번째 대기에서 성공 1을 기록하고 pending을 지웠는데도 setter가 6을 돌려준 경우입니다. 다른 하나는 큐가 제출에 0을 돌려주고 메시지를 전달하지 않은 경우입니다. 이때 setter는 하위 통신 없이 101회 기다린 뒤 6을 돌려줬고 pending은 1로 남았습니다. 101회는 대기 함수 호출 횟수이며 경과 시간은 재지 않았습니다. [근거: findings.admission] · [재현 도구: CASES, run_worker]

연산 맵이 준비되지 않은 상태(map-ready 0)에서 AF 지원 getter도 0을 돌려줬지만 검색 요청은 하위 API까지 전달됐습니다. AF 지원 판정과 명령 허용이 서로 다른 검사라는 점은 렌즈 준비 상태 분석에서 자세히 다룹니다.

큐 거부 사례의 회귀 검사

큐 거부 사례에서는 원본 전송 래퍼가 0을 0x801134ec로 돌려주고 setter는 pending을 다시 읽어 제한된 대기에 들어갑니다. 바깥 반환값과 완료 확인 상태는 모두 1이었습니다.

이 시험이 실제로 무엇을 잡는지 확인하려고 전달 예약을 첫 대기로 해 둔 채 큐 거부를 공급했습니다. 그리고 큐 승인 조건(queue_send_result==1)을 지운 시험용 변형을 만들어 비교했습니다. 변형은 첫 대기에서 작업자를 실행하므로 실패해야 합니다.

명령의 성공과 이동 완료는 다른 판정입니다

완료 확인은 setter 결과와 상관없이 대기 플래그로 시작하고 캐시의 이동 바이트가 0이 되면 끝납니다. 캐시의 유효성은 보지 않습니다.

완료 확인 상태와 시작 횟수는 ExecuteFocusControl이 렌즈 명령을 내기 전에 지웁니다. 검색 뒤 대기 플래그(request+1)가 1이면 setter가 7·4·6을 돌려줘도 상태 1로 들어갔습니다. 정지는 대기 플래그가 1이어도 성공·거부·시간 초과 모두 상태를 0으로 남겼습니다. 대기 플래그 0, 구동 제한 1인 검색은 큐 작업 없이 바로 완료 알림을 냈습니다. 바깥 명령과 원본 완료 수신자는 대체하지 않고 실행했습니다. [근거: findings.arm]

캐시 getter 0x80112514:
  출력 바이트 ← VDRC 이동값 (0x80c2a748)
  반환값      ← 유효성 (0x80c2a746)
라이브뷰 콜백 0x8042e5ac: 출력 바이트만 사용, 반환값은 쓰지 않음
정지 요청: 캡처 쪽 완료 확인 상태를 지움

캐시가 0이 되는 다른 이유

이동값 0을 계속 넣은 사례는 일곱 번째 콜백에서 상태 2가 되고 여덟 번째 콜백에서 완료됐습니다. 시작 횟수가 6에 이르러 상태 2로 넘어갔기 때문입니다. 렌즈가 한 번도 “움직이는 중”을 보고하지 않아도 완료가 나옵니다.

  • 검색 링크가 실패한 뒤 원본 정기 통신도 실패하자 캐시의 이동값이 0이 됐고 이전 유효성 1은 남았습니다.
  • 상태 2에서 렌즈 제어를 리셋하자 이동값과 유효성이 모두 0이 됐습니다. 캡처 쪽 상태 2는 지워지지 않았으므로 다음 콜백이 완료를 알렸습니다.
주의

이 결과는 합성 상태에서 재현한 소프트웨어 판정입니다. 광학적으로 초점이 맞았거나 렌즈가 기계적으로 멈췄다는 증거가 아닙니다. 통신 실패나 리셋 뒤에도 완료 알림이 나갈 수 있다는 점은, 완료 플래그만 보고 “초점이 맞았다”고 해석하면 안 되는 이유입니다. [근거: findings.samples, command_cases]

유효성을 무시한다는 결론을 모든 AF 코드로 넓히지 않습니다. 여기서는 CaptureLensControlService_CallBackLiveView와 아래 WaitForFocusStop의 확인한 본문만 말합니다.

완료 플래그와 촬영 단계는 따로 바뀝니다

이동이 완료되면 알림 두 개가 나갑니다. 하나는 완료 플래그를 세우고 다른 하나는 캡처 단계가 4일 때만 단계를 5로 바꿉니다.

단계 2로 시작한 일반 사례들은 AF 완료 뒤에도 단계 3이었습니다. 단계 4는 시험 입력으로 직접 넣었습니다. 실제 촬영이 단계 3에서 4로 진행하는 과정은 실행하지 않았습니다. [근거: findings.capture_phase]

AF 호출자의 다른 모드(mode 2)가 0x8038402c에서 완료 플래그를 읽는 정적 사례도 있습니다. 이 호출은 이번에 실행한 mode 0·1 사례와 따로 봅니다. [근거: findings.caller, evidence 첫 항목]

렌즈 정지 요청과 AF 시퀀스 종료는 다른 일입니다

렌즈 쪽의 “이동 멈춤 대기”와 AF 쪽의 “시퀀스 끝내기”는 서로 다른 함수와 신호를 씁니다. 어느 쪽도 모터가 실제로 멈췄다는 증거는 아닙니다.

이동이 멈출 때까지 기다리기

WaitForFocusStop도 캐시 getter의 유효성 반환값을 쓰지 않습니다. 이동값이 0이 아닌 동안 인수 1로 대기 함수를 부르며 기다립니다. 확인한 함수 본문에는 고정 횟수 제한이 없습니다. [근거: findings.focus_stop, wait_cases]

한계와 남은 과제

  • 원본 MIPS 코드를 VEX로 실행했습니다. 큐·대기·이벤트·하위 링크 API {{boundary_count}}개는 모델이 대신했습니다(아래 표). 실제 렌즈, AF 센서 입력, RTOS 동시성, 실제 시간, 기계적 이동은 측정하지 않았습니다.
  • 원본 수신자 getter와 CaptureLensControlService 초기화는 실행했습니다. 다만 AF 초기화 전체 대신, 따로 확인한 초기화 바인딩대로 콜백 슬롯에 getter 값을 넣었습니다. AF 알고리즘 스레드 전체는 시작하지 않았습니다.
  • 초기 준비 상태, 캡처 단계, 온도 바이트와 설정은 합성 값입니다. 정기 통신을 흉내 낸 이동값 표본은 명시적 입력이며 실패·리셋 사례만 원본 코드가 캐시를 바꿉니다.
  • 작업자는 렌즈 제어 RAM을 복사한 별도 실행 환경에서 큐 메시지 하나를 받습니다. 다음 수신에서 작업자의 스택·레지스터는 버립니다. 실제 스케줄러나, 시험한 같은 회차 이후의 늦은 전달은 추론하지 않았습니다.
  • 단계 4 사례는 그 단계를 직접 넣었을 뿐 촬영 수명주기 전체를 실행하지 않았습니다. 완료 플래그, ACK, 이동 완료는 서로 다른 소프트웨어 경계로 남습니다.
이후 변경을 설계할 때

AF 동작을 바꾸려면 명령 결과, 캐시 유효성, 완료 플래그를 각각 다른 조건으로 검토해야 합니다. 이 문서는 그 판단을 위한 기초 자료이며 수정한 코드나 실제 렌즈 실험은 없습니다.
