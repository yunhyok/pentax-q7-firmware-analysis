첫 기록 전의 저장장치 검사와 렌즈 준비 상태

이 문서에는 서로 다른 두 조사가 들어 있습니다. 1부는 업데이트 로더가 첫 블록을 쓰기 전에 저장장치에 무엇을 요청하고, 쓴 뒤에 어떻게 확인하는지입니다. 2부는 렌즈가 붙고, 응답이 실패하고, 떨어질 때 카메라가 기억해 둔 렌즈 상태가 어떻게 바뀌는지입니다.

이 문서에서

  1. 배경: 두 부분을 읽는 데 필요한 것
  2. 1부 저장 ① 첫 기록 전에 모든 블록을 살피고 지우기를 요청합니다
  3. 1부 저장 ② 기록한 뒤 다시 읽어 바이트를 비교합니다
  4. 2부 렌즈 ① AF 지원 판정과 명령 허용은 서로 다른 조건을 봅니다
  5. 2부 렌즈 ② 응답이 실패해도 캐시가 전부 지워지지는 않습니다
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 1부 저장 — 로더는 첫 블록을 쓰기 전에 1,024블록 전부의 예비 영역을 읽고, 보호 구간이 아닌 640블록에 지우기를 요청합니다. 첫 기록 요청 전까지 나온 요청은 3,331개였습니다.
  • 1부 저장 — 블록을 쓰는 함수는 기록이 성공했다는 응답만 믿지 않습니다. 같은 자리를 다시 읽어 바이트를 비교하고, 하나라도 다르면 블록 맵에 실패를 적습니다. 이 함수를 8사례로, 사용자 영역 판정을 7사례로 실행했습니다.
  • 2부 렌즈 — “AF를 지원하는가”와 “이 명령을 보내도 되는가”는 서로 다른 조건을 봅니다. 그래서 AF 지원이 0인데 검색 요청이 전달되는 상태와, 그 반대 상태가 있습니다.
  • 2부 렌즈 — 응답이 실패했을 때 지워지는 범위는 함수마다 다릅니다. 값은 0인데 “유효”로 남기도 하고, 값은 남았는데 “무효”가 되기도 합니다. 전부 지우는 것은 전체 리셋뿐입니다. 초기화·실패·리셋 17사례로 확인했습니다.
  • 저장장치와 렌즈의 응답은 모두 시험용으로 넣은 값입니다. 실제 NAND에 쓰거나 렌즈를 움직인 적이 없습니다.
이 문서의 2부는 다른 주제에 속합니다

2부(렌즈)는 AF와 렌즈 제어 주제의 문서입니다. 그 주제의 지도는 AF·렌즈 안내에 있습니다. 1부(저장)는 이 주제, 곧 업데이트와 재패킹에 속합니다. 두 부분은 서로 기대지 않으므로 필요한 쪽만 읽어도 됩니다. 1부로 가기 · 2부로 가기

배경: 두 부분을 읽는 데 필요한 것

1부에 필요한 말

  • 로더(E01): 업데이트 파일 맨 앞에 든 별도 실행 파일입니다. 이 문서가 실행한 BurnNand는 이 로더의 함수입니다.
  • 섹터와 블록: 섹터는 512바이트입니다. 시험 조건에서는 256섹터(131,072바이트)를 블록 하나로 두었습니다.
  • 예비 영역(spare): NAND에서 데이터 옆에 딸린 작은 영역입니다. 대부분의 NAND 칩은 불량 블록 표시를 이곳의 정해진 자리에 둡니다. 이 문서의 요청에서는 16바이트입니다. [리눅스 커널 문서: MTD NAND]
  • 설치된 헤더: 카메라의 저장장치에 이미 기록돼 있는 배치 정보입니다. 이 문서에서는 시험용으로 만든 값을 넣었습니다.
  • 사용자 영역: 설치된 헤더가 시작 블록과 길이로 가리키는 구간입니다. 로더는 이 구간을 보호 대상으로 다룹니다.
  • 연산 번호: 로더가 저장 계층에 보내는 요청의 내부 번호입니다. 4는 읽기, 5는 기록, 6은 예비 영역 읽기, 8은 지우기입니다. NAND 칩에 보내는 명령 바이트가 아닙니다.

2부에 필요한 말

  • 통신 상태 바이트: 렌즈 초기화가 단계를 통과할 때마다 비트를 하나씩 켜 두는 한 바이트입니다. AF 지원 판정은 이 가운데 0x08 비트를 봅니다.
  • 기능 표: 렌즈가 초기 통신에서 “어떤 그룹의 어떤 연산을 할 수 있다”고 알려 준 것을 카메라가 칸마다 0 또는 1로 펼쳐 둔 표입니다. 검색 명령은 그룹 2, 연산 4의 칸을 씁니다.
  • 표 준비 플래그: 기능 표를 다 펼친 뒤에 1이 되는 바이트입니다. 근거 파일에서는 map_ready입니다.
  • 캐시와 유효 상태: 렌즈가 보낸 값을 카메라가 메모리에 보관해 둔 것이 캐시입니다. 값과 별도로 “유효한지”를 나타내는 상태가 있습니다. 이 문서는 사양 데이터, 표준 데이터, VD 동기 데이터(펌웨어의 이름은 VDRC) 세 가지를 봅니다.
  • primary와 regular: 펌웨어가 렌즈 통신을 나누는 이름입니다. primary는 렌즈의 사양·표준 데이터를 받고, regular는 위치 같은 현재 값을 받습니다.
시험 조건

1부의 저장장치는 512바이트 섹터 256개가 한 블록인 1,024블록짜리 합성 장치입니다. 설치된 헤더는 사용자 영역을 블록 640부터 384블록으로 둔 시험용 값입니다. 2부에서는 렌즈의 응답과 전원·핀 입력을 사례마다 정해서 넣었습니다. 아래 결과는 이 조건에서 원본 코드가 한 일입니다.

1부 저장 ① 첫 기록 전에 모든 블록을 살피고 지우기를 요청합니다

로더는 첫 블록을 쓰기 전에 블록 1,024개의 예비 영역을 모두 읽고, 사용자 영역이 아닌 블록 0~639에 지우기를 요청했습니다. 요청은 모두 3,331개입니다.

요청의 순서. B는 블록 번호입니다. 예비 영역 읽기는 섹터 번호로, 지우기는 블록 번호로 위치를 줍니다
블록 범위블록마다 낸 요청요청 수
0~639 (640블록)연산 6: 섹터 B×256, B×256+1, B×256 → 연산 8: 블록 B2,560
640~1023 (384블록)연산 6: 섹터 B×256, B×256+1768

BurnNand(0x80012654)는 원본 패키지의 첫 131,072바이트와 합성 설치 헤더, 저장장치 형상을 받습니다. 먼저 원본 BurnGetSectionsMap(0x8001a710)으로 배치표를 만들고, 이어서 위의 사전 검사를 합니다. 요청을 내는 반복과 순서는 원본 코드가 실행했고, 요청의 결과는 모델이 응답했습니다. 예비 영역은 모두 0xff, 상태는 성공으로 응답했습니다. [근거: findings.preflight, replay.preflight]

사용자 영역은 지우지 않습니다

합성 설치 헤더의 사용자 영역은 시작이 640블록, 길이가 384블록입니다. 원본 BlockUserArea(0x800117d0)는 헤더의 길이와 모드 바이트가 0이 아닌지 먼저 봅니다. 그다음 블록 번호가 시작부터 시작+길이−1까지의 범위에 드는지, 양 끝을 포함해 검사합니다. 경계와 모드, 길이를 바꾼 7사례로 실행했습니다.

모드 바이트가 2인 사례도 사용자 영역으로 판정했습니다. 이 함수는 “0이 아닌가”만 봅니다. “정확히 1인가”를 보는 다른 보호 판정 함수(Loader 입력 검증에서 다룸)와 혼동하면 안 됩니다. 설치 헤더에서 이 값들이 있는 자리는 +0x310(시작 640), +0x314(길이 384), +0x234(모드 바이트 1)이고, 핸들 +0x1268의 바이트도 1로 두었습니다.

주의

블록 640~1023에 지우기 요청이 없었다는 것은 이 합성 조건에서의 결과입니다. 실제 저장장치가 보호된다는 보장이 아닙니다. 이 구간에도 예비 영역 읽기는 나갔습니다. [근거: findings.user_area, replay.user_range_cases]

첫 기록 요청에서 멈춘 자리

사전 검사가 끝나면 원본 코드는 첫 기록 요청을 냅니다. 연산 5, 섹터 0, 256섹터이고 예비 영역 버퍼 16바이트가 딸려 있습니다. 요청을 부르는 명령과 그 지연 슬롯까지 실행하고, 저장 계층의 진입점 0x8008249c에서 멈췄습니다. 연산 5의 처리는 실행하지 않았습니다.

이때 기록하려고 준비한 버퍼는 카드에서 읽은 청크와 281바이트가 다릅니다. 무엇이 왜 달라지는지는 기록 헤더와 MD5 경로에, 이 뒤의 기록과 재시도는 NAND 재시도와 최종 반환에 있습니다. [근거: findings.program_boundary]

1부 저장 ② 기록한 뒤 다시 읽어 바이트를 비교합니다

블록을 쓰는 함수는 기록 요청이 성공했다는 응답에서 끝내지 않습니다. 같은 자리를 다시 읽어 한 바이트씩 비교하고, 하나라도 다르면 실패로 처리합니다.

이 함수(0x80011da8~0x80011f00)에는 이름이 남아 있지 않습니다. 블록 번호에 핸들 +0x1238의 값(블록당 섹터 수)을 곱해 섹터 위치를 정하고, 그 값을 개수로 써서 연산 5를 요청합니다. 상태가 0이면 핸들 +0x1250의 버퍼로 연산 4를 요청해 다시 읽습니다. 두 상태가 모두 0이면 개수×512바이트를 첫 불일치가 나올 때까지 비교합니다. [근거: findings.program_helper]

연산 번호가 가는 곳

요청은 FcuNandOperation(0x8008249c)으로 들어가 기본적으로 FcuNandOperationEx(0x80081808)로 넘어갑니다. 이 함수는 연산 번호에서 4를 뺀 값으로 분기표 0x800a4e24를 찾아 처리 코드를 고릅니다. 연산 4만은 전역 바이트 0x800b785b가 1일 때 FcuSsfdcOperationEx(0x80080de0)라는 다른 경로로 갑니다. 아래 표는 코드를 읽어서 정리한 것이며 실행한 결과가 아닙니다.

참고

지우기 경로의 설정 바이트 0xd0은 표준 NAND 명령에서 블록 지우기의 둘째 명령 바이트와 같은 값입니다(리눅스 커널 rawnand.h의 NAND_CMD_ERASE2). 값이 같다는 점만 적어 둡니다. Q7의 제어기가 이 바이트를 칩에 그대로 보내는지는 확인하지 않았습니다.

2부 렌즈 ① AF 지원 판정과 명령 허용은 서로 다른 조건을 봅니다

AF 지원 판정은 통신 상태의 0x08 비트와 기능 표를 봅니다. 명령 허용은 표 준비 플래그와 기능 표를 봅니다. 보는 조건이 달라서 두 결과가 어긋나는 상태가 있습니다.

렌즈가 붙어 있는지 묻는 ExGetLensAttached(0x80114894)는 0x08 비트만 봅니다. ExGetAfEnable(0x80114b08)은 여기에 기능 표의 검색 연산 칸을 더 봅니다. 명령을 보내는 LensCommunication(0x80111214)은 표 준비 플래그가 정확히 1일 때만 기능 표로 요청을 거르고, 거부한 요청에는 7을 반환합니다. [근거: findings.two_gates]

  • 기능 표를 받다가 실패: 초기화가 전원을 끄고 리셋해 모든 값이 0이 됩니다. 표 준비 플래그가 0이므로 검색 요청은 검사 없이 전달됩니다. 이 사례에서 렌즈 스레드에 재시도 메시지 1이 한 번 나갔습니다.
  • 이미 전원이 켜져 있음: 초기화 함수가 2를 반환하고, 새로 탐색하지 않은 채 미리 넣어 둔 상태를 그대로 둡니다.
주의

표의 “전달”은 요청이 모델로 대신한 하위 경계에 도달했다는 뜻입니다. 실제 직렬 전송이나 렌즈의 이동을 본 것이 아닙니다. 부팅 때 쓰는 InitializeLens(0x8011190c)에도 같은 4·8 검사가 있지만, 그쪽은 코드를 읽어 확인했을 뿐입니다. [근거: findings.startup_disagreement, replay.startup_cases]

2부 렌즈 ② 응답이 실패해도 캐시가 전부 지워지지는 않습니다

응답 하나가 실패했을 때 지워지는 범위는 통신 함수마다 다릅니다. 값과 유효 상태가 따로 움직이므로 둘을 함께 봐야 합니다. 전부 지우는 것은 전체 리셋뿐입니다.

응답이 실패했을 때

  • SingleRegular(0x80115f50) 실패: VD 데이터 버퍼 세 개를 0으로 만듭니다. 그러나 앞서 1이던 유효 상태는 그대로 둡니다. 그래서 위치를 묻는 함수는 “유효”와 함께 위치 0을 돌려줍니다.
  • VD-sync(0x80115c8c) 실패: 이 함수는 이전 수신 버퍼 256바이트를 복사한 뒤, 다른 수신 버퍼의 앞 5바이트를 덮어씁니다. 하위 상태가 성공이 아니어도 그렇게 합니다. 새 바이트가 없으면 이전 위치와 꼬리가 그대로 남습니다. 앞 5바이트만 새 값으로 주면 이동 상태와 위치는 바뀌고 꼬리는 이전 값으로 남아, 서로 다른 때의 값이 섞입니다.
  • Primary 갱신(0x80113eac) 실패: 들어가자마자 사양·표준 데이터의 유효 상태와 VD 상태를 지우고, 실패한 응답의 버퍼를 0으로 만듭니다. 이전 VD 바이트는 남습니다. 위치를 묻는 함수는 “무효”와 함께 이전 값을 돌려줍니다. 통신 상태와 기능 표, AF 지원은 그대로입니다.
  • 수신 복사: LensCommunication은 명령에 설정된 수신 길이(0x801175e0의 반환값)가 0이 아니면 수신 바이트를 호출한 쪽으로 복사합니다. 반환 상태가 실패여도 복사를 막지 않습니다.
주의

실패 상태와 함께 앞 5바이트를 준 사례는 코드가 허용하는 조합을 합성 입력으로 만든 것입니다. 실제 렌즈가 그런 응답을 보낸다거나 얼마나 자주 일어난다는 뜻이 아닙니다. [근거: findings.cache_failure, findings.vd_failure] · [재현 도구]

전체 리셋과 그것을 부르는 길

전체 리셋(0x8010f598)은 통신 상태 바이트, 기능 표의 두 비트맵, 표 준비 플래그를 지웁니다. 이어서 0x80111f74로 넘어가 사양·표준·VD 데이터와 유효 상태를 지웁니다. 리셋 뒤에는 표 준비 플래그가 0이므로, 기능 표와 AF 지원이 0이어도 검색 요청은 검사 없이 전달됩니다.

  • 전원 끄기: PowerOffSequence(0x8010fa10)는 전원을 끄고 전체 리셋을 부릅니다.
  • 마운트 스위치: LensSwControl(0x80110b34)은 스위치 입력이 1이 아니고 감지 입력이 0인 조건에서 전원 끄기를 실행하고 분리 래치를 1로 둡니다.
  • 감지 인터럽트: LensDetInt(0x8011045c)는 감지 입력이 1이고, 스위치가 1이 아니고, 래치가 1일 때만 같은 리셋에 이르고 래치를 지웁니다. 래치가 0인 사례에서는 캐시가 그대로 남았습니다.
  • 타임아웃: 통신 대기 지점에 이벤트 마스크 0x100을 넣으면 LensCommunicationBase는 두 사례 모두 5를 반환했습니다. 표 준비 플래그가 0이던 사례는 리셋하지 않았습니다. 1이던 사례는 전체 리셋(0x80110fdc)을 하고 초기화에 다시 들어갔습니다(0x80110ffc). 시험 도구는 다시 들어간 초기화의 상태를 기록하고 거기서 멈췄습니다.

실패 응답과 전체 리셋은 같은 일이 아닙니다. 이 상태들이 실제로 어떤 순서로, 얼마나 자주 생기는지는 재지 않았습니다. [근거: findings.dismount, findings.timeout]

한계와 재현 방법

  • 저장: 요청의 상태값과 예비 영역의 내용, 설치된 헤더와 형상은 넣어 준 값입니다. 실제 설치 헤더와 불량·지우기 상태는 알지 못합니다.
  • 저장: 사전 검사는 첫 연산 5 앞에서 멈춥니다. 기록·비교 8사례는 1~2섹터짜리 합성 요청입니다. 256섹터 요청의 처리, 모든 청크, 업데이트의 확정, 저장장치에 남는 결과는 다루지 않았습니다.
  • 저장: 사용자 영역 판정과, 이 조건에서 연산 8이 그 구간에 나오지 않았다는 사실은 장치 수준의 보호 보장이 아닙니다.
  • 렌즈: 원본 코드가 다룬 것은 소프트웨어 상태와 선택한 호출입니다. GPIO, 전원, 큐, 타이머, 렌즈 응답은 합성 값입니다. 실제 렌즈나 카메라의 데이터를 받은 것이 없습니다.
  • 렌즈: 검색 요청은 상위 검사를 통과해 모델 경계에 도달했는지만 봤습니다. 타임아웃은 정해 둔 이벤트 마스크 하나의 경로만 실행했고, 겹친 재초기화는 모델에서 멈췄습니다.
  • 렌즈: 캐시가 섞이는 상태는 차례로 넣은 합성 상태에서 나온 것입니다. 타이밍, 실제 발생 여부, 끼어들기, 렌즈를 꽂고 빼는 전체 복구는 범위 밖입니다.
