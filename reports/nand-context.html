PENTAX Q7 firmware analysis · fwdc603p.bin v1.01

NAND context 생성과 media-info 탐색

FileX 인수를 바꾼 context 생성 시험과 원본 media-info 선택 경로를 따르는 탐색 시험입니다. 두 기록은 별도 실행이며 이어진 전체 부팅이나 FileX 초기화의 성공을 입증하지 않습니다.

두 실험의 범위

실험 A는 TlInitUserPartitionBlocks가 media-info +0xc84의 0 포인터를 읽은 뒤 멈췄습니다. 실험 B는 해당 포인터의 생산자를 추적합니다. 원본 AppFcuMediaInfoInit(8)을 실행하면 AppResourceToMediaType이 FcuMediaInfoInit(1,1)을 선택합니다. 합성 ID 응답과 할당·동기화 모델 아래에서 원본 0x8005635c가 할당된 0x400바이트 버퍼를 record +0xc84에 등록했습니다. [재현 기록]

원본 상위 호출 AppFcuInit은 먼저 FcuInit을 호출합니다. 이번 재현은 AppFcuMediaInfoInit에서 시작했으며 앞선 하드웨어 초기화와 실제 부팅 중의 registry 상태를 재현하지 않았습니다. AppFb·FileX·TlDriverInit까지 이어지는 연속 실행도 수행하지 않았습니다. [원본 경로]

원본 0x80003c80의 심벌 이름은 HceGetResidentMemoryType이며 반환값은 8입니다. 0x80003c78의 HceGetResDriveInfo는 별도 함수로 값 2를 반환합니다.

A. FileX 인수를 바꾼 context 생성

FileX 진입 0x80067700에서 7번째 인수만 0x80000000 → 0으로 바꿨습니다. 그 뒤 원본 요청 4가 TlDriverInit(HANDLE,&hNandTlInfo,0,1)을 호출했습니다. 원본 0x80084d40은 할당된 context에 kind 1을 쓰고 0x80084c40은 hNandTlInfo(0x8008c14c)에 그 포인터를 등록했습니다. [실행 기록] [원본 명령]

이후 TlInitUserPartitionBlocks가 현재 시험의 media-info +0xc84에서 0을 읽었습니다. 다음 명령 0x80084ac0은 0x220을 읽게 되므로 그 명령 직전에 멈췄습니다. 이 접근은 실행하지 않았습니다. 생성자는 아직 성공 반환하지 않았고 FileX 요청 5에도 도달하지 않았습니다.

zone 함수는 native lookup으로 기존 media-info record를 찾았습니다. 이 record의 +0xc88=0과 +0xc8c=24에서 1024·1000을 계산하고 핸들 용량 필드를 다시 썼습니다. context +4/+8/+0xc는 각각 4000/4096/4, +0x10/+0x14/+0x18은 256/1000/1024입니다. 이 값은 합성 ID로 만든 내부 필드이며 실제 NAND geometry 측정값이 아닙니다.

생성자 진입부터 등록 직후까지 VEX 이벤트 4057건, 최종 정지까지 12196건입니다. kind store, 전역 등록, byte +0x80의 0→1과 +0x81의 0 저장을 각각 추적했습니다. VEX 이벤트 수는 CPU 명령 수나 시간이 아닙니다. [독립 실행 검토]

B. 원본 선택 경로의 media-info 탐색

헤더에서 사용하는 바이트

선택한 원본 helper는 spare+5 바이트가 0xff인지 확인합니다. 값이 다르면 stride만큼 다음 후보로 이동합니다. op 4 읽기 성공 뒤 헤더 +0x14의 bit 31이 켜져 있으면 하위 31비트 값을 stride로 나눈 정수 몫을 새 시작 인덱스로 사용합니다. NAND ABI에 전달하는 위치는 이 인덱스에 stride를 곱한 값이며 spare 조건에 따라 더 전진할 수 있습니다. 이 helper 구간에는 헤더 magic·CRC·서명을 검사하는 분기가 없습니다. 이는 전체 부팅 체인의 검증 부재를 뜻하지 않습니다. [선택 명령 구간]

후속 helper는 ((header[220]+stride−1) mod 2³²)/stride와 header[230]/stride를 계산합니다. 실제 NAND에서 읽은 필드와 범위를 확보하지 못했으므로 임의값으로 table 쓰기를 계속하지 않았습니다. helper의 반환과 카메라의 partition 배치를 연결하려면 실제 입력의 근거가 더 필요합니다.

업데이트 패키지와 설치된 매체의 구분

패키지의 0x1000c0에 대응하는 헤더 템플릿은 있습니다. 첫 0x400바이트 SHA-256은 a13cfeb149310c4f692811780e98581dda9b713aef5ec3ea8b3fbacf6a6da623입니다. 원본 값은 +220=0x18000, +230=0xffffffff, +310/+314/+3a8/+3ac=0xadadadad입니다. [패키지 바이트 대조]

기존 E01 모델 재현은 프로그램 버퍼에서 +310/+314를 640/384로, +3a8/+3ac를 1/0으로 바꿨습니다. 이는 업데이트 과정에서 값이 구성되는 템플릿임을 뒷받침합니다. 해당 과거 시험도 합성 geometry와 설치 헤더를 사용했습니다. 카메라에 기록된 실제 바이트나 현재 bad-block 배치는 관측하지 않았습니다. 이 재현은 패키지 템플릿을 NAND 응답으로 공급하지 않았습니다. [기존 E01 검사]

두 시험은 NAND ID 8바이트, spare 16바이트, 데이터 0x400바이트와 각각 status 0을 공급했습니다. 임의 패턴 시험은 +14=0, +220=0xdeadbeef, +3a8=0x12345678, +3ac=0x76543210이며 나머지는 A5 패턴입니다. 두 경우 모두 원본 반환은 1이었고 +220은 생산자에서 읽지 않았습니다. 임의 패턴의 실제 형식 유효성은 판단하지 않았습니다.

재현은 FcuNandOperationEx=0x80053124 안으로 들어가지 않고 응답을 모델링합니다. 이 지점은 하드웨어를 향하는 ABI 경계이며 물리 MMIO 그 자체는 아닙니다. 원본 하위 경로에는 clock 조회, lock, clock enable, controller operation이 있습니다. 선택된 driver 행의 clock index는 2입니다. 참조 바이트가 0이면 CguUnitSetEnabled는 0x8000f87c에서 0xb0008228로 먼저 씁니다. 공통 validation 경로에는 0x8000f63c의 0xb000800c 읽기가 있습니다. 실제 선행 초기화 상태를 모르므로 어느 접근이 카메라에서 최초인지 단정하지 않습니다. 이 MMIO들은 실행하지 않았습니다. [하위 경로 근거]

선택된 controller 데이터 경로

정적으로 추적한 op 2는 FcuOperation(dev,0x106,desc,8,1,id)로, 합성 ID 조건의 op 6은 FcuOperation(dev,0x103,desc,0,2,spare)로 이어집니다. controller offset 0인 구성에서는 0x80050098에 0xb0080000 store가 있습니다. 선택된 op 6 완료 뒤 0x80053bf0은 0xb0080600 + 16×(position & 3)에서 spare 데이터를 읽습니다. 이 controller 동작과 data-RAM 읽기는 실행하지 않았습니다. [원본 하위 경로]

재현과 검증

전체 firmware와 분석 ELF의 SHA-256을 확인한 뒤 프로젝트 의존 소스 11개를 모두 해시 검사합니다. 검사한 소스 바이트를 직접 컴파일하므로 기존 모듈 캐시와 .pyc를 사용하지 않습니다. 원본 plain 구간 전체와 새로 디코딩한 E05 전체를 ELF와 대조한 다음 angr를 불러옵니다. 두 실험은 CLI에서 순차 실행하며 동시 실행 서비스로 제공하지 않습니다.

각 실험의 전체 JSON 기록을 고정된 정규화 SHA-256과 비교하고 메타데이터를 포함한 전체 보고서도 별도로 검사합니다. 출력은 새 경로만 허용하며 생성 시점에도 exclusive create를 사용합니다. -O 실행은 거부합니다. [공개 CLI] · [보호 테스트]

python -B tools/check_nand_context.py fwdc603p.bin main-expanded.elf --output new-context-report.json
python -B tools/build_nand_context_report.py
python -B -m unittest discover -s tests -p test_nand_context.py

펌웨어 원본과 분석 ELF는 저장소에 포함하지 않습니다. 첫 명령에는 본인이 확보한 파일을 지정해야 합니다. 파일의 해시는 고정 해시와 일치해야 합니다. HTML builder와 JSON 검증에는 firmware나 angr가 필요하지 않습니다.

확인하지 못한 연결

A는 전역 context 등록 뒤 0x80084ac0의 null 설정 포인터 접근 직전에 멈춥니다. 그 접근은 실행하지 않았으며 생성자 성공 반환과 후속 FileX 요청 5에 도달하지 않았습니다. B는 별도 레코드 생성 경로에서 합성 ID·spare·헤더 응답을 사용했습니다. B의 반환값 1을 A의 초기화 완료로 연결할 수는 없습니다.

실제 NAND ID·spare·헤더·status, 선행 FcuInit 상태, registry 재사용, 물리 단위·주소 alias·cache·DMA와 카메라 부팅은 미확인입니다. 실제 allocator·mutex·semaphore·counter를 실행하지 않았으며 실패 정리와 controller MMIO도 이번 재현에 포함하지 않았습니다. 패키지의 헤더 템플릿은 현재 설치된 NAND 내용의 증거가 아닙니다.
