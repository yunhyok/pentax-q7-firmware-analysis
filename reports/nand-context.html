업데이트와 재패킹 · MAIN 매체 열기 아래의 NAND 계층 ③

NAND 컨텍스트 등록과 별도로 실행한 매체 발견

부트 읽기 요청이 쓰는 NAND 컨텍스트를 원본 코드가 언제 만들고 등록하는지 실행해 봤습니다. 그 컨텍스트가 기대는 매체 정보는 다른 원본 경로가 채우므로 그 경로도 따로 실행했습니다.

이 문서에서

  1. 배경: 컨텍스트와 매체 정보 기록
  2. A. 인수 하나를 바꾸자 원본 코드가 컨텍스트를 등록했습니다
  3. B. 원본 선택 경로가 매체 정보를 채웠습니다
  4. 헤더의 어느 바이트를 누가 쓰는지
  5. 업데이트 파일의 템플릿과 설치된 헤더는 다른 근거입니다
  6. NAND 연산 아래의 하드웨어 경로는 실행하지 않았습니다
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • 실험 A: FileX의 일곱째 인수를 원래 특수값에서 0으로 바꾸는 대조 조건을 만들었습니다. 그러자 원본 드라이버 초기화가 컨텍스트를 만들어 kind 1로 표시하고 전역 변수에 등록했습니다.
  • A는 등록 뒤 계속 실행됐지만 매체 정보의 설정 포인터가 비어 있어 빈 포인터를 읽기 직전에 멈췄습니다. 생성자는 성공 반환하지 못했고 부트 읽기 요청에도 닿지 않았습니다.
  • 실험 B: 설정 포인터를 채우는 원본 매체 정보 탐색을 따로 실행했습니다. 시험용 식별값·예비 영역·헤더 응답 아래에서 원본 코드가 헤더 버퍼를 기록에 등록하고 헤더의 두 필드를 기록으로 복사했습니다.
  • A와 B는 하나의 부팅 순서가 아닙니다. B가 1을 돌려준 결과를 A의 초기화 완료로 이을 수 없습니다.
  • 업데이트 파일 안의 헤더 템플릿은 직접 읽었지만 카메라에 설치된 NAND 헤더와 같은지는 모릅니다. 실제 NAND는 읽거나 쓰지 않았습니다.

확인 원본 코드 실행으로 확인

  • A: 드라이버 초기화 요청 → TlDriverInit → 컨텍스트 kind 기록과 전역 등록
  • B: 매체 정보 선택, 식별값 해석, 헤더 버퍼 등록과 필드 복사(2조건)
  • 업데이트 파일의 헤더 템플릿 1,024바이트를 직접 읽어 대조

정적 분석 코드를 읽어 판단

  • 상위 호출 AppFcuInit → FcuInit
  • 헤더 필드를 쓰는 파티션 함수의 계산
  • NAND 연산 아래의 클록·컨트롤러 접근

모델 시험 조건으로 정한 것

  • FileX 일곱째 인수 0(원래 값과 다른 대조 조건)
  • 식별값, 예비 영역, 헤더, 응답 상태
  • 0으로 채운 할당, 세마포어·뮤텍스·카운터 응답

미확인 확인하지 않은 것

  • 생성자의 성공 반환, 원래 흐름의 부트 읽기 요청
  • 실제 NAND의 식별값·예비 영역·헤더·상태
  • 선행 FcuInit 상태, 컨트롤러 MMIO, 카메라 부팅

배경: 컨텍스트와 매체 정보 기록

NAND 드라이버 아래에는 두 가지 상태 구조가 있습니다. 변환 계층이 쓰는 컨텍스트와, 매체마다 하나씩 있는 매체 정보 기록입니다. 부트 읽기와 파티션 계산은 둘 다 있어야 진행됩니다.

컨텍스트
전역 변수 hNandTlInfo(0x8008c14c)가 가리키는 구조체. 첫 워드가 kind이며 부트 읽기 문서에서는 시험용 포인터를 넣었던 자리입니다.
매체 정보 기록
매체 종류마다 하나씩 등록되는 레코드. +0xc84에 설정 포인터(부트 헤더를 담은 0x400바이트 버퍼)가, +0xc88·+0xc8c에 헤더에서 옮긴 값이 들어갑니다.
flags
매체 정보 초기화에 넘기는 값. bit 1이 0이면 탐색을 하고 bit 0이 1이면 기록 +0xc20에 0x100을 넣습니다. MAIN의 Burn이 쓰는 flags 2는 설정 포인터를 채우는 부분을 건너뜁니다.
FileX 일곱째 인수
Burn은 0x80000000을 넘깁니다. 이 특수값이면 드라이버 초기화의 TlDriverInit 호출과 부트 읽기 요청이 생략됩니다. 공개 FileX의 fx_media_open에는 없는 인수입니다.

원본 심벌 이름으로는 0x80003c80이 HceGetResidentMemoryType이며 8을 돌려줍니다. 0x80003c78의 HceGetResDriveInfo는 다른 함수로 2를 돌려줍니다. B는 이 값 8에서 출발합니다.

A. 인수 하나를 바꾸자 원본 코드가 컨텍스트를 등록했습니다

FileX 진입 0x80067700에서 일곱째 인수만 0x80000000 → 0으로 바꿨습니다. 원본 요청 4가 TlDriverInit(HANDLE, &hNandTlInfo, 0, 1)을 불렀습니다. 원본 코드는 할당된 컨텍스트에 kind 1을 쓴 뒤 전역 변수에 포인터를 등록했습니다.

등록은 생성자가 끝나기 전에 일어납니다. 그래서 전역 포인터가 채워졌다는 사실만으로 초기화 전체가 성공했다고 말할 수 없습니다. 원래 MAIN의 Burn은 flags 2로 매체 정보를 만들기 때문에 이 시험의 기록에는 설정 포인터가 없습니다. 원본 0x80084ac0의 다음 명령은 그 빈 포인터에서 0x220을 읽게 되므로 실행하기 전에 멈췄습니다. [근거: context.final, context.writes]

B. 원본 선택 경로가 매체 정보를 채웠습니다

원본 AppFcuMediaInfoInit(8)을 실행하자 AppResourceToMediaType이 FcuMediaInfoInit(1,1)을 골랐습니다. 시험용 응답 아래에서 원본 코드가 0x400바이트 헤더 버퍼를 기록 +0xc84에 등록했습니다.

원본 상위 호출 AppFcuInit은 먼저 FcuInit을 부릅니다. B는 AppFcuMediaInfoInit에서 시작했으므로 그 앞의 하드웨어 초기화와 실제 부팅 중의 registry 상태는 재현하지 않았습니다. AppFb·FileX·TlDriverInit으로 이어지는 실행도 하지 않았습니다. [근거: discovery.cases]

헤더의 어느 바이트를 누가 쓰는지

헤더를 고르는 함수는 예비 영역의 한 바이트와 헤더 +0x14만 봅니다. 파티션 계산은 다른 함수가 헤더를 다시 조회해 +0x220·+0x230·+0x310·+0x314를 씁니다.

재지정이 켜지면 하위 31비트를 간격으로 나눈 몫이 새 시작 인덱스가 됩니다. NAND 요청에 넘기는 위치는 이 인덱스에 간격을 곱한 값이고 예비 영역 조건에 따라 더 나아갈 수 있습니다. 이 함수 구간에는 헤더 magic·CRC·서명을 검사하는 분기가 없습니다. 부팅 체인 전체에 검증이 없다는 뜻으로 읽으면 안 됩니다. [근거: source.focused_ranges]

파티션 함수는 ((header[220]+stride−1) mod 2³²)/stride와 header[230]/stride를 계산합니다. 실제 NAND에서 읽은 필드와 범위를 모르므로 임의값으로 표 쓰기를 이어 가지 않았습니다. 이 함수의 결과를 카메라의 파티션 배치와 이으려면 실제 입력이 더 필요합니다.

업데이트 파일의 템플릿과 설치된 헤더는 다른 근거입니다

업데이트 파일의 오프셋 0x1000c0에는 같은 칸을 가진 헤더 템플릿이 있습니다. 카메라에 이미 설치된 NAND 헤더와 같은지는 확인하지 못했습니다.

기존 E01 모델 재현은 프로그램 버퍼에서 +310/+314를 640/384로, +3a8/+3ac를 1/0으로 바꿨습니다. 업데이트 과정에서 값을 채워 넣는 템플릿이라는 해석을 뒷받침합니다. 그 재현도 합성 저장장치와 설치 헤더를 썼고 카메라에 기록된 실제 바이트나 불량 블록 배치는 보지 않았습니다. 이 문서의 시험은 패키지 템플릿을 NAND 응답으로 넣지 않았습니다. [기존 E01 검사]

NAND 연산 아래의 하드웨어 경로는 실행하지 않았습니다

재현은 FcuNandOperationEx(0x80053124) 안으로 들어가지 않고 응답을 모델로 넣었습니다. 이 자리는 하드웨어 쪽으로 가는 함수 경계이며 MMIO 레지스터 자체는 아닙니다.

원본 하위 경로에는 클록 조회, 잠금, 클록 켜기, 컨트롤러 연산이 있습니다. 정적으로 확인한 내용은 아래와 같습니다. 이 MMIO 접근은 하나도 실행하지 않았습니다. 실제 선행 초기화 상태를 모르므로 어느 접근이 카메라에서 처음 일어나는지도 단정하지 않습니다. [근거: source.focused_ranges]

  • 선택된 드라이버 행의 클록 번호는 2입니다. 참조 바이트가 0이면 CguUnitSetEnabled가 0x8000f87c에서 0xb0008228에 먼저 씁니다.
  • 공통 검사 경로에는 0x8000f63c의 0xb000800c 읽기가 있습니다.
  • 연산 2는 FcuOperation(dev,0x106,desc,8,1,id)로, 시험용 식별값 조건의 연산 6은 FcuOperation(dev,0x103,desc,0,2,spare)로 이어집니다.
  • 컨트롤러 오프셋 0 구성에서는 0x80050098에 0xb0080000 쓰기가 있습니다.
  • 연산 6이 끝나면 0x80053bf0이 0xb0080600 + 16×(position & 3)에서 예비 영역 데이터를 읽습니다.

한계와 남은 과제

  • A는 전역 등록 뒤 0x80084ac0의 빈 설정 포인터 접근 직전에 멈췄습니다. 생성자 성공 반환과 FileX 요청 5에는 닿지 않았습니다.
  • A의 FileX 일곱째 인수 0은 의도적으로 만든 대조 조건입니다. 원래 Burn의 특수값 경로가 아닙니다.
  • B는 별도 기록 생성 경로에서 시험용 식별값·예비 영역·헤더 응답을 썼습니다. 그 결과를 A의 완료로 이을 수 없습니다.
  • 실제 NAND의 식별값·예비 영역·헤더·상태, 선행 FcuInit 상태, registry 재사용, 물리 단위·주소 별칭·캐시·DMA, 카메라 부팅은 미확인입니다.
  • 실제 할당기·뮤텍스·세마포어·카운터는 실행하지 않았습니다. 카운터 모델은 1을 여덟 번 돌려줍니다. 실패 정리와 컨트롤러 MMIO도 범위 밖입니다.
  • 패키지의 헤더 템플릿은 현재 설치된 NAND 내용의 증거가 아닙니다.

재현 방법

python -B tools/check_nand_context.py fwdc603p.bin main-expanded.elf --output new-context-report.json
python -B tools/build_nand_context_report.py
python -B -m unittest discover -s tests -p test_nand_context.py

재현기는 펌웨어 전체와 분석 ELF의 SHA-256을 확인한 뒤 의존하는 프로젝트 소스 11개를 모두 해시로 검사합니다. 검사한 소스 바이트를 직접 컴파일하므로 기존 모듈 캐시와 .pyc는 쓰지 않습니다. 원본 plain 구간 전체와 새로 풀어 낸 E05 전체를 ELF와 대조한 다음에야 angr를 불러옵니다. 두 실험은 CLI에서 순차 실행하며 동시 실행 서비스로 제공하지 않습니다.

각 실험의 전체 JSON 기록을 고정된 정규화 SHA-256과 비교하고 메타데이터를 포함한 전체 보고서도 따로 검사합니다. 출력은 새 경로만 허용하고 만들 때도 exclusive create를 씁니다. -O 실행은 거부합니다. 펌웨어와 분석 ELF는 저장소에 없으니 첫 명령에는 직접 확보한 파일을 지정해야 하며 해시가 고정값과 같아야 합니다. HTML 빌더와 JSON 검증에는 펌웨어나 angr가 필요 없습니다. [공개 CLI] · [보호 테스트]

angr 10.0.5의 MIPS32LE/VEX로 검증했습니다. Unicorn DLL은 쓸 수 없었습니다. 소스 해시 고정은 설치된 외부 Python·angr 패키지의 공급망 검증을 대신하지 않습니다.
