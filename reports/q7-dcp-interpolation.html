DCP 표의 좌표와 보간

DCP의 HueSatMap과 LookTable은 색상·채도·명도 격자에 보정값을 적어 둔 표입니다. 픽셀 색이 격자점 사이에 놓일 때 어떤 이웃을 어떻게 섞는지 Adobe의 공개 SDK 소스로 확인하고, Q7 Adobe Standard의 표로 직접 계산해 보았습니다.

이 문서에서

  1. 배경: HSV 표와 보간
  2. 표본 하나가 놓이는 칸과 이웃
  3. 렌더 경로 안에서 두 표의 위치
  4. 소스에서 확인한 여덟 가지
  5. 합성 HSV 15건의 계산 결과
  6. 한계와 남은 과제
  7. 재현 방법과 고정한 소스
  8. 근거 파일과 참고 자료

핵심 요약

  • Adobe DNG SDK 1.7.1의 소스를 읽어 표 보간 규칙을 확인했습니다. HueSatMap(90×30×1)은 이웃 네 개, LookTable(36×8×16)은 이웃 여덟 개를 섞습니다. 마지막 색상 칸 다음은 첫 칸으로 이어집니다.
  • Q7 Adobe Standard의 세 표에 합성 HSV 다섯 개를 넣어 모두 15건을 계산했습니다. Python 배정밀도(binary64) 구현과 50자리 Decimal 기준 구현의 차이는 최대 1.95×10⁻¹⁴였습니다.
  • encoding 태그가 없으면 SDK는 linear(0)를 씁니다. 이것은 “명도에 별도 곡선을 씌우지 않는다”는 설정일 뿐입니다. 표가 색을 바꾸지 않는다는 뜻과는 다릅니다.
  • SDK 코드를 직접 실행하지 않았고 RAW 현상도, Lightroom 출력도 만들지 않았습니다. 세 표는 서로 이어 붙이지 않고 따로 평가했습니다. Adobe 표의 값 자체는 저장소에 싣지 않았습니다.
  • 이 계산은 표 하나의 수식을 재현한 것입니다. 이 프로파일이나 계산 결과가 카메라의 색을 재현한다는 근거는 아닙니다.

확인 파일과 계산으로 확인한 것

  • DCP 파일의 표 크기·노드 수·encoding 태그 부재와 해시
  • SDK ZIP 안 소스 8개의 바이트와 구간 해시
  • 두 독립 구현의 15건 계산 결과 일치(PC에서 실행)

정적 분석 소스를 읽어 판단한 것

  • 저장 순서, 이웃 선택, 색상 경계 처리, 배율 적용과 클리핑
  • SDK 예제 렌더러에서 두 표가 놓이는 위치

모델 시험 조건

  • 합성 HSV 입력 다섯 개, 각 표의 입구에 직접 넣음
  • linear encoding, 정규 SDR 범위, 범위 초과 값 처리 없음

미확인 확인하지 않은 것

  • SDK 원본 함수의 real32 출력과의 비트 일치
  • 행렬·노출·톤 곡선까지 이어진 전체 경로, RAW 현상, Lightroom 출력
  • 화이트밸런스에 따른 HueSatMap 1·2의 실제 혼합 비율

배경: HSV 표와 보간

표(LUT)는 격자점에만 값을 적어 두므로 그 사이의 색은 가까운 격자점들을 거리에 따라 섞어서 정합니다.

앞 문서에서 본 대로 Q7 Adobe Standard에는 HueSatMap 두 장과 LookTable 하나가 있습니다. DNG 규격에 따르면 표의 노드마다 색상 이동(도), 채도 배율, 명도 배율의 세 값이 들어 있습니다. 표는 선형 ProPhoto RGB를 HSV로 바꾼 좌표에서 찾습니다.

격자는 듬성듬성합니다. HueSatMap은 색상을 90칸(4°마다), 채도를 30칸으로 나누고 명도 칸은 1개입니다. 픽셀이 격자점 사이에 놓이면 주변 격자점의 값을 거리 비율로 섞습니다. 이것을 선형 보간이라고 합니다. 축이 둘이면 이웃 네 개, 셋이면 여덟 개가 필요합니다.

규칙을 정확히 알아야 표 값에서 실제 색 변화를 계산할 수 있습니다. 같은 SDK를 쓴 K-3 Mark III 쪽 연구와 비교할 때도 이 규칙이 기준이 됩니다.

읽는 순서: 격자 칸과 이웃 → 렌더 경로 안의 위치 → 소스에서 확인한 내용 → 15건 계산 → 한계 → 재현

표본 하나가 놓이는 칸과 이웃

HueSatMap은 색상·채도 두 축에서 이웃 네 개를, LookTable은 명도까지 세 축에서 이웃 여덟 개를 섞습니다.

입력은 읽기 쉽게 도 단위로 썼습니다. SDK 내부의 색상 범위는 0~6입니다. 좌표는 아래 식으로 정합니다.

H 좌표
H × 색상 칸 수 / 360. 마지막 칸 다음은 첫 칸으로 돌아갑니다.
S 좌표
S × (채도 칸 수 − 1). 마지막 격자점에서는 마지막 구간의 가중치 1로 처리합니다.
V 좌표
V × (명도 칸 수 − 1). 명도 칸이 1개인 HueSatMap에서는 명도 방향으로 보간하지 않습니다.

표는 V가 가장 바깥, H가 가운데, S가 가장 안쪽인 순서로 저장됩니다. 차원은 H, S, V 순서로 표기하므로 읽을 때 헷갈리기 쉽습니다.

노드 번호   = (vIndex × Hdiv + hIndex) × Sdiv + sIndex
저장 위치   = 3 × 노드 번호 + 성분
성분        0 = 색상 이동(도), 1 = 채도 배율, 2 = 명도 배율

근거: dng_camera_profile.cpp 1467~1502, dng_hue_sat_map.cpp 125~130·200~206, dng_reference.cpp 1529~1745

렌더 경로 안에서 두 표의 위치

SDK 예제 렌더러에서 HueSatMap과 LookTable은 서로 다른 단계에 놓입니다. 이 문서는 두 표의 수식만 따로 계산했습니다.

  1. 1. 카메라 white·CameraToPCSProPhoto RGB로 변환. 이 표본에서는 하지 않음
  2. 2. HueSatMapwhite로 1·2를 고르거나 섞음. 여기서는 두 장을 따로 평가
  3. 3. GainTableMap·노출선택 단계. 하지 않음
  4. 4. LookTable같은 보간 함수. 별도 합성 입력으로 평가
  5. 5. 기본 톤ProfileToneCurve와 구분. 태그가 없다고 항등으로 보지 않음
  6. 6. 이후 RGB 처리·출력출력 색공간 등. 이 연구 범위 밖

이 순서는 SDK 예제 렌더러의 것입니다. 카메라 펌웨어의 HDR 패스 순서도, Lightroom 내부의 실제 실행 순서도 아닙니다. ColorMatrix·ForwardMatrix는 카메라 색을 기준 색공간으로 옮기는 데 관여합니다. white 값은 HueSatMap 1·2를 고르고 섞는 데에도 쓰입니다. As Shot 값이 표의 좌표로 바로 들어가는 구조는 아닙니다.

근거: dng_render.cpp 925~1002·1862~2030, dng_color_spec.cpp 530~609

기본 encoding과 항등 표는 다릅니다

encoding은 표를 찾기 전에 명도 좌표를 어떻게 바꿀지 정하는 설정입니다. linear(0)는 좌표를 그대로 씁니다. 항등 표는 모든 노드가 (0, 1, 1)이라 색을 전혀 바꾸지 않는 표입니다. Q7 Adobe Standard의 표는 encoding이 기본값 linear이면서 항등 표가 아닙니다. 항등 노드는 일부뿐입니다(구조 문서의 값 범위 표).

한계와 남은 과제

표 하나의 수식을 재현한 결과입니다. SDK 원본 실행, 전체 렌더 경로, RAW·Lightroom 출력은 아직 없습니다.

  • 공통 전제는 유한한 정규 SDR HSV, linear encoding, supportOverrange=false입니다. profile.IsHDR()의 실제 분기와 범위 초과 값의 encode/decode는 실행하지 않았습니다.
  • HSV의 V는 RGB의 최댓값입니다. 광도·휘도·노출값 같은 물리량으로 읽으면 안 됩니다. S=0이면 H는 색으로서 의미가 없습니다. SDK의 RGB→HSV는 이때 H=0을 씁니다.
  • SDK RefBaselineHueSatMap의 real32 연산을 Python binary64로 옮겼습니다. Decimal 교차 검증은 같은 수식의 독립 구현이며 SDK를 직접 실행한 검증과는 다릅니다.
  • SDK의 SetDelta는 S=0 노드의 명도 배율을 1로 보정합니다. 이 DCP의 해당 값은 이미 모두 1이고 생략된 S=0 행도 없습니다. 일반 DCP의 생략 행 재구성은 구현하지 않았습니다.
  • 적용하지 않은 단계: ColorMatrix, ForwardMatrix, CameraNeutral/As Shot, 노출, ProfileToneCurve, 색역 클리핑, 출력 색공간. 표별 결과도 서로 이어 붙이지 않았습니다.
  • K-3 Mark III 연구의 SDK ZIP과 소스 고정값을 다시 썼습니다. 그 연구의 SDK 실행 검증이 Q7 표, 전체 렌더 경로, Lightroom 출력을 검증해 주지는 않습니다. 카메라 FC1·HDR 패스와도 대응시키지 않았고 펌웨어 쪽 새 결론도 없습니다.
  • 전체 표·행렬·SDK 원본 코드·이미지는 복사하거나 배포하지 않았습니다. 표의 수치는 합성 입력 다섯 개의 가중 보간 결과뿐입니다.

다음에 확인할 것

  1. SDK 함수 직접 실행 같은 합성 RGB와 고정 표를 SDK의 RefBaselineHueSatMap 또는 DoBaselineHueSatMap에 넣어 real32 출력·클리핑·색상 감싸기를 대조합니다.
  2. 두 HueSatMap의 혼합 명시한 white XY로 HueSatMapForWhite_Dual의 가중치와 만들어지는 표를 재현합니다. CameraNeutral→WhiteXY 추정과 두 보정 광원 변환은 따로 검증합니다. Lightroom에 표시된 색온도를 SDK의 white XY나 As Shot과 같다고 보지 않습니다.
  3. 단계별 수치 추적 색 변환, HueSatMap, 노출, LookTable, 톤을 단계별로 나눈 추적을 설계합니다. RAW·Lightroom 실행이나 완성 렌더 비교는 지금 범위 밖입니다.

재현 방법과 고정한 소스

공개 기록 검사와 테스트는 원본 자료 없이 돌아갑니다. 전체 재현에는 SDK ZIP, 설치된 DCP, K-3 Mark III 쪽 파서가 필요합니다.

python -B -m unittest discover -s tests -p test_q7_dcp_interpolation.py -v

원래 관측과 공개 검증의 관계

공개 검증기는 원래 관측의 모든 필드·타입·직렬화 해시를 검사한 뒤 표본과 문서를 만듭니다. 원래 기록의 sources, 예전 helper 해시, scope는 당시의 출처와 전제입니다. 현재 실행의 입력·모듈 해시는 _reproduction에 따로 적으며 원래 환경을 다시 관측했다고 주장하지 않습니다.

예전 helper(059b7cda…)와 현재 공개 helper(c62f899a…)는 서로 다른 파일입니다. 공개 소스 고정값과 모듈 변경 정보는 _publication에서 따로 관리합니다.
