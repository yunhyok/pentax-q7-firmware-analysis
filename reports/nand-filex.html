AppFb의 FileX 열기와 NAND 응답 경계

MAIN의 Burn 말고도 FileX로 NAND 매체를 여는 원본 코드가 있습니다. 부팅 쪽 구역 로더 AppFb가 FileX에 무엇을 넘기는지, 그리고 원본 코드가 어디까지 가면 실제 NAND 응답 없이는 더 나아갈 수 없는지 확인했습니다.

이 문서에서

  1. 배경: FileX 매체 열기와 기호값
  2. AppFb는 FileX 열기의 인수를 직접 만듭니다
  3. 임시 헤더의 예비 영역 읽기에서 멈췄습니다
  4. 멈춘 뒤에 원본 코드가 입력을 쓰는 순서
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 원본 AppFbLoader를 따로 진입시켜 실행했습니다. FileX 매체 열기의 인수 7개는 원본 명령이 직접 만들었고 일곱째 인수는 1이었습니다. MAIN의 Burn은 같은 자리에 특수값을 넘깁니다.
  • 그 뒤 원본 코드는 시험용 식별값으로 매체 크기와 간격을 정했습니다. 이어서 헤더 함수에 들어가 임시 버퍼를 할당한 다음 예비 영역 읽기를 요청했습니다.
  • 그 요청의 응답 상태와 예비 영역은 어떤 값이든 될 수 있는 기호값으로 두었습니다. 상태를 검사하는 첫 분기 직전에서 멈췄고 성공도 실패도 가정하지 않았습니다.
  • 그 뒤의 헤더 복사, 매체 정보 사용, 파티션 계산, 부트 섹터 검사는 원본 명령을 읽어서만 정리했습니다.
  • 할당·동기화 응답과 식별값은 시험용 값입니다. 실제 NAND, 컨트롤러 MMIO, 카메라 부팅은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • AppFb가 만든 FileX 인수 7개
  • 매체 초기화 → 헤더 함수 → 임시 버퍼 할당 → 연산 6 요청
  • 상태 분기 직전의 레지스터가 넣은 기호값과 같고 경로 제약이 0개임

정적 분석 코드를 읽어 판단

  • FB/AFB 선택과 부팅 쪽 상위 경로
  • 멈춘 뒤의 분기, 헤더 복사, 파티션 표 해석

모델 시험 조건으로 정한 것

  • AppFbLoader 따로 진입, 열린 매체 목록 포인터 0
  • 할당·뮤텍스·부트 이벤트 응답
  • 시험용 식별값과 상태 0(앞 단계와 같은 값을 다시 씀)
  • 연산 6의 상태·예비 영역: 정하지 않은 기호값

미확인 확인하지 않은 것

  • 연산 6의 실제 응답과 그 뒤 실행
  • 실제 헤더 +0x398과 FB/AFB 선택 순서
  • NAND·MMIO·전체 부팅, FileX와 변환 계층 초기화의 성공

배경: FileX 매체 열기와 기호값

공개 FileX의 fx_media_open은 매체 구조체, 매체 이름, 드라이버 함수, 드라이버 정보 포인터, 캐시 메모리 주소와 크기를 받습니다. 드라이버 정보 포인터는 FileX가 해석하지 않고 드라이버에 그대로 넘깁니다. Q7 펌웨어의 _fx_media_open은 그 뒤에 일곱째 인수를 하나 더 받아 핸들에 저장합니다. NAND 드라이버와 FileX는 그 값을 특수값 0x80000000과 비교합니다.

AppFb
원본 함수 이름이 AppFb…로 시작하는 구역 로더. AppFbLoadSection과 AppFbLoader가 FileX로 매체를 엽니다.
기호값
에뮬레이터 angr가 "아직 정하지 않은 값"으로 다루는 변수(BVS). 원본 코드가 이 값을 그대로 들고 분기에 이르면 결과는 입력에 달려 있습니다.
registry 헤더
컨텍스트 문서의 실험 B처럼 매체 정보 생성자가 기록 +0xc84에 등록한 0x400바이트 헤더 버퍼.
임시 헤더(TEMP)
헤더 함수가 매체 열기 때 따로 할당하는 0x400바이트 버퍼. registry 헤더와 주소도 내용도 다릅니다.

AppFb는 FileX 열기의 인수를 직접 만듭니다

원본 AppFbLoadSection은 0x800e7a54, AppFbLoader는 0x800e7e24에서 _fx_media_open을 부릅니다. 두 호출 모두 지연 슬롯에서 일곱째 인수로 1을 저장합니다.

실행은 AppFcuMediaInfoInit(8)부터 시작했습니다. 생성자에는 시험용 식별값, FF 예비 영역, 상태 0을 넣었고 registry 헤더는 재지정하지 않는 +0x14=0만 고정했습니다. +0x220/+0x398/+0x3a8/+0x3ac를 포함한 나머지 바이트는 기호값으로 남겼습니다. 생성자가 돌려준 상태를 복사한 뒤 AppFbLoader(1)에 따로 들어갔습니다. 상위의 FB/AFB 선택과 실제 부팅 순서는 실행하지 않았습니다. 실행과 입력 모델

_fx_media_open_ex는 0x80066a68에서 열린 매체 목록 포인터를 읽습니다. 그 직전에 멈춘 뒤 0을 대조값으로 넣었습니다. 다음 0x80066ac0 비교는 포인터가 새 매체 주소와 다르면 통과합니다.

참고

정적으로 본 상위 경로에서 AppLoadSegment는 헤더 +0x398=0일 때 FB를 고릅니다. AppBootPrimary의 NAND 분기는 같은 바이트가 1이면 eBootType=2, 그 밖에는 1을 기록합니다. AppLoadSecondarySegments는 AFB와 FB를 각각 부릅니다. 두 경로에 필요한 실제 +0x398과 선행 상태는 미확인입니다. 상위 선택 명령

임시 헤더의 예비 영역 읽기에서 멈췄습니다

원본 코드는 registry 헤더와 다른 임시 버퍼를 할당하고 연산 6을 요청했습니다. 응답을 정하지 않았으므로 상태를 검사하는 첫 분기가 앎의 경계입니다.

드라이버의 연산 2에는 앞 단계와 같은 시험용 식별값 ecdc000100000000과 상태 0을 다시 넣었습니다. 원본 TlMediaInit 경로가 매체 +0xbf4=1048576, +0xc18=0x105, +0xc14=8을 정했으며 이 필드는 시험용 입력에서 나온 해석 결과입니다.

멈춘 뒤에 원본 코드가 입력을 쓰는 순서

아래는 원본 명령을 읽어 정리한 순서입니다. 실행한 것은 첫 행의 분기 직전까지입니다.

멈춘 뒤의 분기와 데이터 사용 순서(정적 분석)
원본 주소조건과 다음 동작
0x80055aac연산 6 상태가 0이면 예비 영역 검사로, 0이 아니면 실패 경로로 갑니다. 재현은 이 분기와 지연 슬롯 직전에서 멈췄습니다.
0x80055ab4 / 0x80055abcspare+5가 FF이면 연산 4를 요청합니다. 아니면 위치에 간격을 더해 연산 6을 다시 요청합니다.
0x80055c10 / 0x80055c28연산 4가 성공하면 TEMP +0x14의 bit 31을 검사합니다. 켜져 있으면 하위 31비트를 간격으로 나눈 몫이 두 번째 탐색의 시작 인덱스가 됩니다.
0x80084120 / 0x80084128헤더 함수가 포인터를 돌려주면 TEMP +0x200의 32비트를 MEDIA+0xc10으로 복사하고 TEMP 해제를 요청합니다.
0x80055608 / 0x80055628새 변환 계층 생성과 kind 1 조회가 먼저 끝나면 기록 +0xc88을 복사해 분기합니다. +0xc8c는 지연 슬롯 0x8005562c에서 읽습니다.
0x80084ac0 / 0x80084af4파티션 함수가 registry 헤더를 다시 조회해 +0x220/+0x314/+0x230/+0x310을 씁니다. +0x310 읽기는 0x80084af4 분기의 지연 슬롯 0x80084af8에 있습니다.

요청 4의 0x800643dc와 요청 5의 0x80066bb4는 일곱째 인수를 특수값 0x80000000과 비교합니다. 이 범위에서는 AppFb의 1과 컨텍스트 시험의 0이 같은 분기를 탑니다. 그 뒤 kind 1 읽기가 성공하면 두 값은 0x8008466c의 _fx_partition_offset_calculate에 서로 다른 index로 전달됩니다.

요청 5의 섹터 읽기가 성공해도 먼저 +0x1fe=0x55, +0x1ff=0xaa여야 합니다. 첫 바이트가 0xe9이거나, 첫 바이트 0xeb와 +2=0x90이 함께 나오면 exFAT/FAT 형태 검사로 들어갑니다. 이 검사가 성공하면 표의 index 1을 고르지 않고 돌아갈 수도 있습니다.

네 칸짜리 표 경로에서 index 1은 0x1ce 칸을 고릅니다. 종류는 섹터 +0x1d2, 시작 위치는 LE32 +0x1d6, 개수는 LE32 +0x1da입니다. 종류 0인 칸도 개수에 들어가며 시작 위치와 개수는 0으로 기록됩니다. 이 호출은 개수 출력 포인터가 0이므로 파서 반환값 0만으로 유효한 파티션이나 다음 읽기의 성공을 정할 수 없습니다. partition parser 원본

한계와 남은 과제

  • AppFbLoader에는 따로 진입했습니다. 할당·뮤텍스·이벤트 응답과 열린 매체 목록 0은 그 이전 실행과 같은 대조 조건입니다.
  • 연산 2의 식별값과 상태 0은 앞 단계의 시험값을 다시 쓴 것입니다.
  • 연산 6의 예비 영역과 상태는 모릅니다. 상태 성공, spare+5, 임시 헤더 +0x14·+0x200의 값은 아무것도 가정하지 않았습니다.
  • 임시 할당은 기호값이며 registry 헤더와 독립입니다. 연산 4에는 닿지 않았습니다.
  • 그 뒤의 복사, zone, 파티션 index 처리는 정적 분석뿐입니다. 카메라·부팅·MMIO의 성공은 확인하지 않았습니다.

재현 방법

python -B tools/check_nand_filex.py fwdc603p.bin main-expanded.elf --output new-filex-report.json
python -B tools/build_nand_filex_report.py

첫 명령에는 해당 SHA-256의 원본 펌웨어와 분석 ELF가 필요합니다. HTML 빌더는 공개 JSON과 템플릿만으로 돌아갑니다.

처음 진단 실행은 분기 직전까지 간 뒤 SAT 질의에서 Windows 종료 코드 -1073741819로 중단됐습니다. 확정 실행은 SAT 질의를 하지 않았습니다. 대신 상태가 독립된 32비트 BVS이고 원본 v0가 같은 기호를 가지며 경로 제약이 0개임을 확인했습니다. 0과 1은 그 정의에서 허용되는 대입의 예입니다.

공개 근거에는 정적 분석의 E03 60개 구간과 새로 풀어 낸 E05 1개 구간을 실었습니다. 파일과 ELF의 오프셋, 구간 해시, 고른 명령의 mnemonic과 operand가 들어 있고 원본 바이트 배열과 설치된 NAND 덤프는 없습니다.
