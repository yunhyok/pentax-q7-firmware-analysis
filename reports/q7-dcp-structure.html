색 처리와 HDR · Lightroom 쪽 프로파일 파일 분석

Q7용 DCP 두 개에 저장된 태그와 표

Lightroom은 RAW의 색을 DCP라는 프로파일 파일로 해석합니다. Q7용 프로파일 두 개를 열어 어떤 색 처리 요소가 들어 있는지 비교했습니다. 카메라 펌웨어가 아니라 PC 쪽 파일을 다루는 문서입니다.

이 문서에서

  1. 배경: DCP가 RAW의 색을 정하는 방식
  2. 두 파일에 들어 있는 태그
  3. 행렬과 표의 값 범위
  4. ToneCurve가 없다는 것의 의미
  5. K-3 Mark III 자료와 As Shot 기록
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • Q7용 DCP 파일 두 개의 바이트를 직접 읽어 구조를 비교했습니다. Adobe Standard는 태그 16개로 이루어집니다. 색 행렬 네 개, HueSatMap 표 두 개(각 2,700노드), LookTable 하나(4,608노드)가 들어 있습니다.
  • 연구용 matrix-test는 태그가 6개뿐입니다. ColorMatrix 두 개와 광원·이름 태그만 있고 ForwardMatrix와 표는 없습니다.
  • 두 파일 모두 ProfileToneCurve가 없습니다. 이때 렌더러가 대신 쓰는 기본 곡선이 무엇인지는 이 문서에서 확인하지 않았습니다.
  • 확인한 것은 파일 구조와 값의 범위까지입니다. RAW를 현상하지 않았고 Lightroom도 다시 실행하지 않았습니다. Adobe의 행렬과 표 값 자체는 저장소에 싣지 않았습니다(범위와 해시만 공개).
  • 어느 프로파일도 카메라가 만든 JPEG의 색을 재현한다고 판단할 근거는 없습니다. 펌웨어의 색 처리 경로와도 연결하지 않았습니다.

확인 파일 바이트에서 직접 읽은 것

  • 두 DCP의 크기·SHA-256과 IFD 엔트리 전체
  • 태그의 유무, 행렬 원소의 범위와 행렬식
  • 세 표의 노드 수와 색상·채도·명도 값의 범위

모델 시험용으로 만든 것

  • ToneCurve 검사기의 동작 확인용 합성 곡선 8개(실제 Q7 곡선이 아님)

미확인 확인하지 않은 것

  • RAW 현상 결과와 Lightroom의 현재 출력
  • ToneCurve가 없을 때 렌더러가 쓰는 기본 곡선과 노출 처리
  • 카메라 JPEG 색과의 일치, 펌웨어 Custom Image와의 관계
  • 끝에 공백이 붙은 모델 이름이 프로파일 선택에 주는 영향

배경: DCP가 RAW의 색을 정하는 방식

DCP는 “이 카메라의 센서 값은 어떤 색인가”를 적은 작은 파일입니다. 내용은 이름 붙은 값(태그)의 모음입니다.

RAW 파일에는 센서가 받은 빛의 양만 들어 있습니다. 이를 사람이 보는 색으로 바꾸려면 해석 규칙이 필요합니다. Adobe의 RAW 현상기(Lightroom, Camera Raw)는 그 규칙을 DCP 파일에서 읽습니다. 현상 화면에서 고르는 “프로파일”이 이것입니다.

DCP는 TIFF와 같은 구조로 태그를 늘어놓은 파일입니다. 각 태그의 뜻과 적용 순서는 DNG 규격 1.7.1.0이 정합니다. 색에 영향을 주는 태그는 다음과 같습니다.

색 처리에 관여하는 DCP 태그 (DNG 규격 1.7.1.0 기준)
태그하는 일규격 쪽
ColorMatrix1·2XYZ 색 좌표를 카메라 고유 색공간 값으로 바꾸는 3×3 행렬입니다. 숫자 1·2는 서로 다른 보정 광원(CalibrationIlluminant1·2)에 대응합니다.32~33
ForwardMatrix1·2화이트밸런스를 맞춘 카메라 색을 XYZ D50으로 보내는 행렬입니다. 없어도 되는 선택 태그입니다.52~53
ProfileHueSatMap색상(H)·채도(S)·명도(V) 격자마다 “색상을 몇 도 돌리고 채도·명도를 몇 배 할지”를 적은 표입니다. 광원별로 두 장을 둘 수 있습니다.49~50
ProfileLookTableHueSatMap과 같은 형식의 표입니다. 노출 보정 뒤, 톤 곡선 앞의 더 늦은 단계에서 적용해 “인상”을 입힙니다.56~57

이 문서가 다루는 파일은 두 개입니다. 하나는 Adobe가 Q7용으로 배포한 Adobe Standard입니다. 다른 하나는 행렬만 넣어 만든 연구용 시험 파일 matrix-test입니다. 두 파일 모두 PC의 Lightroom 쪽 자료이며 카메라 펌웨어 안에 들어 있지 않습니다.

쉽게 말하면

행렬은 색 전체를 한꺼번에 비트는 큰 손잡이입니다. HueSatMap과 LookTable은 색상·채도 구역마다 따로 손보는 세밀한 표입니다. ToneCurve는 사진 전체의 밝고 어두운 정도를 정합니다.

두 파일에 들어 있는 태그

Adobe Standard는 행렬과 표를 모두 갖췄습니다. matrix-test는 ColorMatrix만 가진 최소 구성입니다. 두 파일 모두 ToneCurve가 없습니다.

그림은 파일 안의 구성만 보여 줍니다. 위아래 순서는 렌더러의 처리 순서도, 펌웨어의 호출 관계도 아닙니다. 두 파일의 모델 이름도 다릅니다. Adobe 쪽은 "PENTAX Q7"이고 matrix-test는 끝에 공백이 하나 붙은 "PENTAX Q7 "입니다(그림의 ␣). 이 차이가 프로파일 선택에 영향을 주는지는 확인하지 않았습니다.

표의 노드 하나에는 색상 이동(도)·채도 배율·명도 배율의 세 값이 들어 있습니다. “변화 없는 노드”는 저장값이 정확히 (0, 1, 1)인 노드만 셌습니다. 세 표 모두 채도 0(S=0) 위치의 명도 배율이 1입니다. 채도·명도 배율이 음수인 노드는 없습니다.

LookTable은 모든 노드에서 명도 배율이 1입니다. 그래도 색상과 채도는 바뀌므로 RGB 값과 밝기는 달라질 수 있습니다. 이 사실만으로 렌더링 전체의 밝기가 유지된다고 판단할 수는 없습니다. 표 안의 값을 실제로 보간한 결과는 DCP 표의 좌표와 보간에서 다룹니다.

ToneCurve가 없다는 것의 의미

두 파일에는 저장된 톤 곡선이 없으므로 곡선을 검사할 대상도 없습니다. 기본 곡선이 무엇인지는 이 문서의 범위 밖입니다.

ProfileToneCurve(태그 50940)가 없으므로 곡선 지표는 모두 “계산 대상 없음(null)”으로 기록했습니다. 0~1 범위, x의 증가, y의 비감소, 항등 곡선과의 차이가 여기에 해당합니다. 검사기 자체는 합성 곡선 8개로 경계 이탈·중복 x·감소하는 y·유한하지 않은 값을 잡아내는지 시험했습니다. 이 합성 시험이 실제 Q7 곡선을 검증한 것은 아닙니다.

규격에는 빠진 태그의 기본값이 적혀 있습니다. 아래는 규격을 읽은 내용이며 Lightroom의 실제 기본 동작을 측정한 결과가 아닙니다.

K-3 Mark III 자료와 As Shot 기록

K-3 Mark III의 Adobe Standard와 비교하면 표 크기와 광원은 같습니다. 행렬과 표의 데이터는 모두 다릅니다.

K-3 Mark III 저장소에 남아 있는 Adobe Standard 메타데이터 기록과 태그별 저장 바이트의 해시를 비교했습니다. K-3 Mark III의 DCP 원본을 다시 읽지는 않았습니다.

이전 Lightroom 기록 (다시 재지 않음)

K-3 Mark III 저장소의 As Shot 기록에는 Q7 사례가 하나 있습니다. Lightroom 16.0의 표시 화이트밸런스는 기준 상태에서 5100 K / Tint −17이었습니다. Adobe Standard를 적용한 상태에서는 4900 K / Tint −7이었습니다. 그 기록의 strict_profile_only_passed는 false입니다. 화이트밸런스를 고정하고 프로파일만 바꾼 비교가 아니므로 프로파일 단독의 효과로 보지 않습니다. 이 문서에서 Lightroom을 다시 실행하지는 않았습니다.

  1. 이 문서DCP 태그·해시·값 범위. RAW와 렌더러 실행 없음
  2. 별도 조건As Shot 변화와 프로파일·화이트밸런스의 결합
  3. 확인하지 않음최종 픽셀 일치, 펌웨어 Custom Image와의 일치

한계와 남은 과제

태그 구성만으로는 Lightroom의 기본 곡선·노출 처리·출력 색공간도, 카메라의 Custom Image도 복원할 수 없습니다.

  • 같은 RAW를 고정한 화이트밸런스·노출·Process Version·출력 프로파일로 현상해 표를 넣고 뺀 결과를 단계별로 비교해야 합니다. 이 문서에서는 하지 않았습니다.
  • 끝에 공백이 있는 모델 이름의 호환성은 따로 확인할 항목입니다.
  • Adobe 프로파일 원본과 행렬·곡선·표의 값, RAW와 사진은 저장소에 넣지 않았습니다.
  • 펌웨어의 FC1 비트 의미나 HDR task 경로에 관한 새 근거는 이 문서에 없습니다. 펌웨어 쪽 색 처리는 색 처리·HDR 안내에서 시작합니다.

검사기는 K-3 Mark III 저장소의 inspect_adobe_profiles.py를 그대로 다시 씁니다. 줄바꿈을 LF로 맞춘 SHA-256으로 그 파일을 고정합니다. 출력 파일은 아직 없는 새 경로여야 합니다.

git clone https://github.com/yunhyok/pentax-k3iii-firmware-analysis.git k3-reference
git -C k3-reference checkout 2b50cf4f46a61b077789692b3ccc851d4d8d65b9
python -B tools/check_q7_dcp_structure.py --check-record
python -B -m unittest discover -s tests -p test_q7_dcp_structure.py -v
python -B tools/check_q7_dcp_structure.py --k3-root k3-reference \
  --adobe <Adobe-DCP> --matrix <matrix-test-DCP> \
  --output q7-dcp-structure.replay.json
python -B tools/build_q7_dcp_report.py

전체 재현에는 위 커밋의 inspect_adobe_profiles.py, analysis/adobe-profiles.json, analysis/lightroom-as-shot.json이 필요합니다. matrix-test도 기록된 SHA-256과 같은 로컬 파일이 있어야 하며 저장소에 넣지 않았습니다. 보고서 빌더는 analysis/q7-dcp-structure.json과 analysis/q7-dcp-template.html만 읽습니다.

공개판이 원래 관측을 보존하는 방식
  • 원래 연구 코드의 SHA와 공개 코드의 LF SHA는 JSON의 _publication에 따로 적었습니다. 원래 관측은 그대로 두고 관측 객체의 canonical SHA-256으로 전체를 검사합니다. 공개 JSON canonical SHA-256: 23b2e830aa89b48ffc5221bb96fd0651c6839169eb80dc6aea70add6e23d5530
  • 입력 파일은 한 번만 엽니다. 일반 파일인지와 2,000,000바이트 상한을 확인한 뒤 상한+1바이트까지 한 번 읽습니다. 해시 검사와 해석은 그 한 버퍼에서 합니다.
  • 출력 경로는 입력을 읽기 전과 쓰기 직전에 lexists로 검사해 끊어진 심볼릭 링크도 거부합니다. 두 검사 사이의 경합까지 막는 원자적 보장은 주장하지 않습니다. 검사기의 assert가 빠지는 -O 실행은 거부합니다.
  • source_reports.*.sha256은 출처 파일의 실제 바이트 해시이고 sha256_lf는 CRLF를 LF로 바꾼 뒤의 해시입니다. 파서와 두 출처 JSON은 LF 해시로 고정합니다. 재현 비교에서는 이 항목과 사용자가 정한 파일 이름(profiles.*.file)만 빼고 모두 대조합니다. 실제 파일 이름과 원래 해시는 _reproduction에 남깁니다.
  • inputs_unchanged_after_analysis=true는 원래 연구에서 분석 전후 해시를 비교한 기록입니다. 공개판은 입력을 한 번만 읽으므로 이 사후 검사를 다시 했다고 주장하지 않고 post_analysis_input_reread=false로 적습니다.
