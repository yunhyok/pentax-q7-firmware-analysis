01 / FILE EXTENT AND NATIVE LOADER

할당 체인에서 파일을 고정하고 원본 로더에 공급한다

패키지의 FAT16 루트에서 FONTDATA 디렉터리를 찾고 LATINF~6.BIN의 할당 체인을 읽었습니다. 파일 크기는 디렉터리에 기록된 130,886바이트이며 첫 원본 오프셋은 0x9d1ac0입니다. 체인 끝과 전체 SHA-256을 확인해 글꼴 범위를 고정했습니다. 글꼴 원본과 생성된 픽셀은 공개 자료에 포함하지 않습니다. [G1: resource]

원본 DirectLoadFontEx에 A:\FontData\LatinFont.bin을 넘기면 AppResourceGetPath가 드라이브 선택값 2와 \FontData\LatinFont.bin 경로를 만듭니다. 파일 조회·열기·읽기·닫기와 할당·해제·로그는 모델로 처리했습니다. 원본 GdiCreateFont는 파일 내부의 오프셋을 포인터로 바꾸고 타입 0x202에 함수 테이블 0x80236538을 연결합니다. 정적 글꼴 선택 크기는 0이었으며 원본의 파일 API 호출 경로를 통과했습니다. [G2: prepare_font·loader_events]

02 / ORIGINAL TEXT CONVERSION AND INDIRECT CALL

갱신 단계에서 포착한 요청을 원본 GDI에 연결한다

네 글리프 사례는 AppDBTextOutByBufferID에서 시작합니다. 인수 (0, 0xffff, source, 96, 64, 4, 1)는 앞선 갱신에서 관측한 값입니다. 타입 접두어 1 뒤에 원본 sRGB의 네 16비트 단위와 NUL을 넣었습니다. 원본 GdiTextOutDB의 변환과 간접 호출을 거쳐 FntDrawTextEx가 동일한 네 단위를 받았습니다. 이 재진입 앞의 전체 UI 갱신은 별도 분석이며 하나의 연속 실행으로 합치지 않았습니다. [G1: text_draw_call] · [R1: 앞선 refresh_cases]

글꼴 셀은 64×48이고 원본 데이터는 픽셀당 2비트, 행당 16바이트입니다. 이번 항등 배율 경로는 컨텍스트 +0x88c의 0x8022607c를 호출합니다. 독립 계산은 바이트의 상위 2비트부터 코드를 읽습니다. 기본 컨텍스트에서 코드 0은 기존 픽셀을 보존하고 코드 1·2·3은 인덱스 2·1·3으로 바뀝니다. 이 값은 실제 RGB 색이 아닙니다. [G2: packed_oracle]

03 / WHOLE FRAME AND GUARDS

투명 픽셀과 그리지 않은 영역도 함께 비교한다

sRGB의 단위 84·51·40·35는 폭 24·29·34·29를 사용하며 x=96·120·149·183에 그려집니다. 한 글리프 사례에서 바뀐 바이트는 563개, 네 글리프 사례는 3,346개입니다. 각 실행에서 736×176, 총 129,536바이트 전체와 양쪽 8바이트 보호 영역을 대조했습니다. 그리지 않은 픽셀과 투명 코드가 남긴 값도 일치했습니다. [G1: cases·renderer_calls]

04 / K-3 MARK III COMPARISON

공통 UI 항목과 기종별 표현을 구분한다

K-3 Mark III 자료는 Color Space의 텍스트 ID·아이콘·선택값과 갱신 경계를 제공합니다. Q7은 이에 대응하는 항목에서 실제 글꼴 파일의 위치, 포인터 재배치, 텍스트 변환과 2비트 글리프 쓰기까지 확인했습니다. 두 기종의 선택·확정·취소 정책 차이는 유지해야 하며 이번 결과가 K-3 렌더러나 리소스 ABI의 직접 이식을 보장하지는 않습니다. [K1: 고정 커밋의 Color Space]

05 / SCOPE AND REPRODUCTION

원본 실행과 모델이 공급한 조건을 명시한다

이번 사례는 LatinFont의 선택한 네 글리프와 항등 배율, 기본 인덱스 매핑만 검증합니다. 다른 언어·범위 끝 단위·배율 변경·실제 RGB 팔레트·화면 등록·DMA·LCD는 미검증입니다. 파일 읽기 모델은 원본 파일을 공급하지만 실제 FileX나 저장장치의 동작을 실행한 것은 아닙니다. 다음 연결 지점은 화면 갱신 전체와 글꼴 크기·색 속성을 같은 상태에서 재현하는 과정입니다. [G1: limitations]
