화면과 글꼴 · 글자 한 줄이 픽셀이 되기까지

글꼴 파일을 읽어 글자 픽셀을 그리는 과정

색공간 메뉴에 보이는 “sRGB” 글자는 글꼴 파일에서 나옵니다. 펌웨어 속 글꼴 파일을 찾아 원본 코드로 읽고, 글자가 화면 버퍼에 어떤 값으로 찍히는지 확인했습니다.

핵심 요약

  • 펌웨어 파일 안의 FAT16 영역에서 라틴 글꼴 파일(130,886바이트)을 찾아 위치와 해시를 고정했습니다.
  • 원본 글꼴 로더와 글자 그리기 코드를 PC 에뮬레이터에서 실행해 글자 1개와 “sRGB” 4글자를 그렸습니다. 두 경우 모두 736×176 버퍼 전체(129,536바이트)가 따로 계산한 결과와 같았습니다.
  • 글꼴 데이터는 픽셀당 2비트입니다. 값 0은 투명(기존 픽셀 유지)이고 1·2·3은 팔레트 번호 2·1·3으로 찍힙니다.
  • 시험은 새로 만든 기본 배율 화면 상태에서 했습니다. 실제 메뉴 화면의 상태를 이어받은 실행이 아니며, 화면에 보이는 실제 색과 LCD 출력은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 글꼴 로더, 텍스트 변환, 글리프 렌더러의 동작
  • 두 사례의 버퍼 전체와 앞뒤 보호 영역 일치
  • 원본 코드 62개 워드와 함수 구간 10개를 주소·해시로 대조

모델 시험 조건으로 정한 것

  • 파일 찾기·열기·읽기·닫기(글꼴 바이트는 원본 그대로 공급)
  • 메모리 할당·해제, 로그 출력
  • 화면 상태: 736×176 합성 버퍼, 기본 배율
  • 그릴 글자: 앞선 분석에서 관측한 “sRGB”를 다시 입력

미확인 확인하지 않은 것

  • 실제 메뉴의 글꼴 크기·속성을 이어받은 연속 실행
  • 팔레트의 실제 RGB 색, 화면 전송(DMA), LCD 출력
  • 다른 언어 글꼴, 배율 변경, 글꼴 범위 끝(0xaa) 처리
  • 실제 FileX와 저장장치의 동작

배경: 메뉴 글자가 그려지는 순서

카메라 메뉴의 글자는 그림 파일이 아닙니다. 펌웨어가 글꼴 파일에서 글자 모양(글리프)을 꺼내 화면용 메모리에 점을 찍어 만듭니다. Q7은 화면 버퍼에 색을 직접 쓰지 않고 팔레트 번호(인덱스)를 씁니다.

색공간 메뉴 화면은 네 문서에 걸쳐 따라갔습니다. 이 문서는 그중 “글자를 그리는” 단계입니다.

  1. 화면 갱신 요청어떤 글자를 어디에 그릴지 결정 — 그리기 경로
  2. 글꼴 로딩과 글자 그리기이 문서
  3. 선택 강조 도형선택된 줄의 배경 — 선택 강조의 픽셀
  4. 팔레트·LCD 출력실제 색으로 바뀌어 화면에 나가는 단계
이 문서의 시험이 실제 화면과 다른 점

글자 그리기 코드만 따로 떼어 새 화면 상태에서 실행했습니다. 실제 메뉴가 쓰는 글꼴 크기와 속성(48×48 요청과 축소)은 48×48 요청과 컨텍스트 선택에서 따로 다룹니다.

글꼴 파일을 찾고 원본 로더로 읽기

글꼴은 펌웨어 속 FAT16 영역의 파일 하나이며, 원본 로더가 이 파일을 읽어 메모리에서 바로 쓸 수 있는 형태로 바꿉니다.

파일의 위치를 고정하기

패키지 안 FAT16의 루트에서 FONTDATA 디렉터리를 찾고, 그 안 LATINF~6.BIN의 할당 체인을 따라갔습니다. 체인의 끝과 파일 전체의 SHA-256을 확인해 글꼴 범위를 고정했습니다.

파일
FONTDATA/LATINF~6.BIN (긴 이름 LATINFONT.BIN)
크기
130,886바이트 (디렉터리에 기록된 값)
첫 원본 오프셋
0x9d1ac0

글꼴 원본과 생성된 픽셀은 공개 자료에 넣지 않았습니다. [근거: resource]

원본 로더가 하는 일

  1. 경로 만들기 원본 DirectLoadFontEx에 A:\FontData\LatinFont.bin을 넘기면, AppResourceGetPath가 드라이브 선택값 2와 경로 \FontData\LatinFont.bin을 만듭니다.
  2. 파일 읽기 파일 조회·열기·읽기·닫기와 메모리 할당·해제·로그는 모델이 대신했습니다. 읽기 모델은 위에서 고정한 원본 글꼴 바이트를 그대로 돌려줍니다.
  3. 글꼴 객체 만들기 원본 GdiCreateFont가 파일 안의 오프셋을 메모리 포인터로 바꾸고, 글꼴 타입 0x202에 함수 테이블 0x80236538을 연결합니다.

정적 글꼴 선택 크기는 0이었고, 원본 코드가 파일 API를 부르는 경로를 그대로 통과했습니다. [재현 도구: prepare_font, loader_events]

글자 요청이 글리프 렌더러에 닿기까지

앞선 분석에서 관측한 “sRGB” 요청을 원본 텍스트 함수에 다시 넣었고, 같은 네 글자가 글리프 렌더러까지 전달됐습니다.

네 글자 사례는 AppDBTextOutByBufferID에서 시작합니다. 인수 (0, 0xffff, source, 96, 64, 4, 1)은 화면 갱신 분석에서 관측한 값입니다. 입력 문자열은 타입 접두어 1 뒤에 원본 “sRGB”의 16비트 단위 네 개와 끝 표시(NUL)를 붙인 형태입니다.

원본 GdiTextOutDB가 이 문자열을 변환한 뒤 글꼴의 함수 테이블을 거쳐 간접 호출하고(0x8022968c → 0x8022c058), FntDrawTextEx가 같은 네 단위를 받았습니다.

주의

이 실행 앞의 화면 갱신 전체는 별도 분석입니다. 두 분석을 하나의 연속 실행으로 합친 것이 아닙니다. [근거: text_draw_call] · [앞선 분석의 refresh_cases]

2비트 글리프가 팔레트 번호로 바뀌는 규칙

글꼴은 픽셀 하나를 2비트로 저장합니다. 0은 “그리지 않음”이고, 1·2·3은 각각 팔레트 번호 2·1·3으로 찍힙니다.

이번 경로는 배율을 바꾸지 않는 항등 배율 경로입니다. 화면 상태(컨텍스트)의 +0x88c에 들어 있는 함수 0x8022607c가 호출됩니다. 대조용 독립 계산도 바이트의 상위 2비트부터 코드를 읽도록 만들었습니다.

두 사례에서 실제로 나온 코드는 1과 2입니다. 코드 3의 대응은 원본 경로를 읽은 결과와, 원본 데이터 대신 만든 2비트 표본을 쓴 시험으로 대조했습니다. [재현 도구: packed_oracle]

결과: 버퍼 전체가 독립 계산과 일치

글자가 찍힌 곳만 본 것이 아니라, 그리지 않은 픽셀과 버퍼 앞뒤의 보호 영역까지 전부 비교했습니다.

“sRGB”의 네 단위 84·51·40·35는 폭 24·29·34·29를 쓰고 가로 위치 96·120·149·183에 그려집니다. 실행마다 736×176, 모두 129,536바이트인 버퍼 전체와 앞뒤 8바이트 보호 영역을 대조했습니다. 투명 코드가 남긴 기존 값도 일치했습니다.

두 사례의 측정값
사례시작 주소바뀐 바이트VEX 블록 이벤트전체 버퍼 SHA-256 (앞 16자리)
글자 한 개 (직접 호출)0x8022c05856316,4472f0ba3233cce5271…
“sRGB” 네 글자 (텍스트 요청)0x8024928c3,34679,513bd25eb5b6eae638b…

VEX 블록 이벤트는 에뮬레이터가 센 실행 블록 수입니다. 실물 CPU의 명령 수나 실행 시간이 아닙니다. [근거: cases, renderer_calls]

검사기는 주소가 기호식으로 남거나 허용 범위를 벗어난 접근을 거부합니다. 글꼴의 포인터 변환이 끝난 뒤에는 글꼴 영역을 읽기 전용으로 다룹니다. [표본·출력 경로 검사]

K-3 Mark III와 비교

K-3 Mark III 자료는 색공간 화면의 텍스트 ID, 아이콘, 선택값, 갱신 범위를 알려 줍니다. Q7에서는 같은 화면 항목을 글꼴 파일의 위치, 포인터 변환, 텍스트 변환, 2비트 글리프 쓰기까지 더 내려가 확인했습니다.

두 기종은 선택·확정·취소 방식이 다릅니다. 이 결과가 K-3 Mark III의 렌더러나 자원 형식을 Q7에 그대로 옮길 수 있다는 뜻은 아닙니다. [고정 커밋의 K-3 Mark III 색공간 근거]

한계와 재현 방법

  • 확인한 범위는 라틴 글꼴의 글자 네 개, 항등 배율, 기본 인덱스 대응입니다.
  • 다른 언어, 글꼴 범위 끝 단위, 배율 변경, 실제 RGB 팔레트, 화면 등록, DMA, LCD는 확인하지 않았습니다. 글꼴 설명 정보는 상한을 0xaa로 적고 있는데 파일에는 셀이 170개 있어, 끝 단위의 처리는 풀리지 않았습니다.
  • 파일 읽기 모델은 원본 파일 바이트를 공급할 뿐입니다. 실제 FileX나 저장장치의 동작을 실행한 것이 아닙니다.
  • 다음 단계는 화면 갱신 전체와 글꼴 크기·색 속성을 같은 상태에서 이어서 재현하는 일입니다.
