01 / CONTROL WORD PROVENANCE

입력 유형에 따른 소프트웨어 조건까지 확인했다

FIPLIB의 해당 분기에서 FC1 bit 0은 저장된 토폴로지 입력 유형이 0인지 나타냅니다. 이 유형의 심볼은 fiplib_pass_input_type입니다. 입력 형식과 관계가 있지만 RGB·YUV라는 이름만으로 값이 나뉘지는 않습니다. 비트가 ISP 내부에서 수행하는 연산은 아직 확인하지 못했습니다. [S1: 형식·유형·소비 지점]

기본 생성자의 심볼 서명과 object+0x18 기록으로 T의 enum 유형을 확인했습니다. 파생 IPU 생성자는 input_format_mode를 분류해 T를 저장합니다. 이후 SetInputFormat은 +0x50만 바꾸므로, T를 매번 최신 형식에서 다시 계산한다고 보면 안 됩니다. [S1: 생성자·setter]

따라서 bit 0을 RGB/YUV 선택, 행렬 bypass, 반올림 또는 clipping으로 명명할 근거는 확보하지 못했습니다. 적용되는 패스 분기 안에서는 “T가 0인지를 나타내는 비트”로 설명할 수 있습니다. 1x0·기본 5x1 등 강제로 0을 쓰는 분기도 있으며, 이번 HDR 네 패스의 제어 워드는 모두 0입니다.

02 / WRAPPERS BECOME TASKS

네 FIPLIB 패스는 공통 task 클래스로 변환된다

FIPLIB 패스 클래스와 드라이버 task 클래스는 서로 다릅니다. 네 HDR 패스는 각각의 입력·출력 설정을 유지하면서 공통 CIpuTaskC12 객체로 구성됩니다. 마지막 인덱스 3에는 최종 출력용 토폴로지 설정이 적용됩니다. 슬롯이 비어 있으면 뒤의 변환·제출 루프는 그 슬롯을 건너뜁니다. [T1: task 생성·최종 출력]

네 task의 +0x228(모드)와 +0x234 필드는 모두 0이었고, processor의 완료 목표 +0x2f0는 1이었습니다. 이어 같은 processor의 Go를 호출하자 큐에 task ID 0→1→2→3이 들어갔습니다. 최종 플래그는 “이 패스만 제출”한다는 뜻이 아니며, 이 조건에서는 네 패스 모두 제출됩니다. [T1: replay.result]

FC1 UID 9·35·61·87은 이 합성 실행에서 생성된 값이며 카메라 전체의 고정 식별자가 아닙니다. WriteAll은 필터 UID를 드라이버에 기록된 UID와 비교해 writer 호출을 결정합니다. task ID는 별도 필드에 저장됩니다. 활성화값 0·1·0·1과 제어 워드 0·0·0·0은 이전 패스 분석과 일치했습니다. [T1: uid_boundary]

kind 0 생성 코드에서 메모리 할당 실패 후 복구하는 경로는 확인하지 못했습니다. 뒤 루프의 NULL 슬롯 검사를 생성 실패 복구와 같은 동작으로 해석하지 않습니다. 재사용·다른 wrapper kind·다른 디스크립터는 별도 분기입니다.

03 / QUEUE AND HARDWARE START

Go는 큐에 등록하고 드라이버가 실행한다

task의 Go는 포인터를 큐에 넣습니다. 드라이버 스레드는 포인터를 꺼낸 뒤 필터와 영상 설정을 기록하고 하드웨어 시작 기록을 수행합니다. 큐 등록 성공, 시작 기록, 완료 이벤트는 서로 다른 단계입니다. 큐 전송 오류와 완료 대기 오류는 정상 완료 통지로 처리되지 않습니다. [D1: queue_and_start·worker_wait]

CIpuTask::Go → CIpuDriver::AddTask
  queue = driver+0x224, message = task pointer, wait = 0
ThrIpuDriver: receive → mutex → clear completion bit → RunTask
RunTask: WriteAll → RunPreActivation → IRQ 설정
  MMIO[0xb60001cc] = 1
  read MMIO[0xb0802024]
  MMIO[0xb6000000] = 0
worker: wait(driver+0x30c, bit 0, option 1, 5000 ticks)

RunTask의 vtable+0x2c는 C12의 WriteAll 0x80357098로 연결됩니다. WriteAll은 드라이버의 관찰자 포인터를 현재 task+8로 등록합니다. 이 연결로 완료 통지가 현재 task의 Update에 도달합니다. 완료 대기에 성공하면 PowerOff 뒤 event 2를 통지하고, 실패하면 OsSysHaltEx 경로로 들어갑니다. [D1: observer_chain·실행 분기]

대기값 5000은 tick 수입니다. tick 주기를 검증하지 않았으므로 밀리초로 환산하지 않았습니다. option 1과 2는 공식 ThreadX 헤더의 OR_CLEAR·AND 상수와 대조했으며, 이 최신 헤더를 Q7의 RTOS 버전 증거로 사용하지는 않았습니다.

04 / COMPLETION IS LAYERED

IRQ 완료, task 완료, HDR 대기 해제를 구분한다

완료 인터럽트는 우선 드라이버 이벤트를 깨웁니다. task는 남은 하위 이미지가 있으면 자신을 다시 큐에 넣고, 처리가 끝나면 processor에 알립니다. processor는 패스 완료 수와 별도 완료 횟수를 확인합니다. 따라서 한 번의 인터럽트를 HDR 전체 완료로 해석할 수 없습니다. [D1: 완료 집계]

이벤트 주소와 마스크 — 서로 다른 완료·보조 신호

task의 +0x220은 완료한 하위 이미지 수, +0x224는 비교 대상 수입니다. 모드 +0x228 == 0에서 아직 남았으면 CommitSubImage 후 같은 task를 재큐잉하고 event 4를 보냅니다. 모두 끝나면 OnProcessingDone이 event 2를 processor에 전달합니다. 모드 1·2는 별도 분기입니다. [D1: subimage_completion]

mode 0·CBC 0, 네 task 슬롯이 모두 존재하고 task당 하위 이미지가 하나인 재실행에서는 processor의 완료 수가 1→2→3→4로 증가했습니다. 두 번째 통지는 NR phase 보조 이벤트를 만들고, 네 번째 통지가 최종 path bit 0을 설정했습니다. 마지막에는 별도 완료 횟수 +0x2f4와 목표 +0x2f0도 비교하며, 조건에 따라 임시 자원 정리와 phase 3 설정을 거칩니다. [17사례 재현 도구]

type 0의 PathWait은 0x815a1bc4의 bit 0을 기다립니다. fresh path의 제한 시간은 path+0xac = 40000 ticks입니다. IpuToneMapRgb는 PathGo 다음 PathWait의 성공 분기를 거쳐 정리·성공 반환으로 이어집니다. 보조 이벤트가 먼저 설정됐다는 사실만으로 이 대기를 통과한 것은 아닙니다. [D1: path_wait_binding]

05 / K-3 MARK III COMPARISON

같은 질문을 기종별 근거로 대조했다

K-3mk3에서는 R2y 제어 비트와 별도 행렬 모드, RAW·JPEG 작업 큐와 JPEG 완료 콜백을 대조했습니다. 두 기종 모두 설정·제출·완료를 나누어 추적할 수 있지만, 주소와 작업 구조가 다릅니다. K-3의 비트 의미나 JPEG 완료 조건을 Q7 HDR에 그대로 적용하지 않았습니다. [K1: 고정 커밋·blob 해시]

06 / REPRODUCTION AND LIMITS

소프트웨어 분기와 실기 동작의 경계

선별 함수 후보 90개, 명령·데이터 워드 609건을 원본 펌웨어와 대조했습니다. 함수 후보 범위는 다음 sidecar 주소까지이며 공식 함수 크기가 아닙니다. 전체 디컴파일과 원본 BIN·추출 ELF는 공개하지 않습니다.

  • FC1 의미: 원본 형식 매핑·생성자·setter·writer 59사례. task 스케줄링이나 픽셀 연산을 실행하지 않았습니다.
  • task 생성·제출: 512×128 입력·합성 gamma LUT와 기본 HDR 보조 디스크립터를 사용했습니다. 원본 FIPLIB 기하 계산·Export·CalculateTopology·TranslateFilters·네 task의 가상 Commit을 실행한 뒤 같은 processor의 Go를 별도로 호출했습니다. 메모리 할당·환경 함수·큐 전송 성공은 대체했으며 task와 wrapper 결과는 주입하지 않았습니다. PathGo의 외부 동기화·실제 큐 소비는 제외했습니다. [T1: 전체 대체 함수·범위]
  • 완료 경로: IRQ 조건 7, 큐 전송 2, 드라이버 대기 2, 네 패스 콜백 4, 하위 이미지 2의 총 17사례. IRQ와 RTOS 결과를 주입했으며 WriteAll·기하 결과·정리 작업 일부를 모델링했습니다. 드라이버 루프와 콜백 체인은 별도 구간으로 실행했습니다.

원본 명령 재실행에는 합성 영상 크기와 객체, 모델링한 메모리 할당·RTOS 결과가 포함됩니다. 재실행 구간과 대체 함수는 근거 파일에 공개했습니다. 실제 인터럽트 발생 시각, DMA·캐시 일관성, 최종 픽셀 값은 관측하지 않았습니다.

FC1 제어 bit 0의 물리적 기능을 확정하려면 칩 레지스터 문서나 조건을 통제한 실기 레지스터·픽셀 관측이 추가로 필요합니다. 큐·콜백의 소프트웨어 성공은 영상 정확성의 증거가 아닙니다.
