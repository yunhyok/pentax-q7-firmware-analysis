색 처리와 HDR · HDR 색 단계 3/3: 제어 비트와 task

FC1 제어 비트의 출처와 HDR task의 생성·완료

FC1에는 계수와 별개로 제어 워드가 하나 있습니다. 그 비트가 무엇으로 정해지는지 따라가고, HDR의 네 패스가 하드웨어 작업으로 넘어가 끝났다고 알려지기까지의 과정을 정리했습니다.

이 문서에서

  1. 배경: 설정값이 하드웨어 작업이 되기까지
  2. FC1 제어 비트는 입력 유형이 0인지를 나타냅니다
  3. 네 패스는 같은 task 클래스로 만들어집니다
  4. task는 큐를 거쳐 드라이버 스레드가 시작합니다
  5. 인터럽트 하나는 HDR 완료가 아닙니다
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 해당 패스 분기에서 FC1 제어 워드의 bit 0은 패스에 저장된 입력 유형 값이 0인지를 나타냅니다. 이름이 RGB인 형식과 YUV인 형식이 같은 값으로 묶이므로, 이 비트를 “RGB/YUV 선택” 같은 이름으로 부를 근거는 없습니다. 하드웨어에서 하는 일은 확인하지 못했습니다.
  • HDR의 네 패스는 모두 같은 task 클래스(CIpuTaskC12)로 만들어지고 큐에 task 0→1→2→3 순서로 들어갑니다.
  • 완료는 세 층으로 나뉩니다. 하드웨어 인터럽트 하나는 하위 이미지 하나의 완료이고 task와 processor가 각각 개수를 센 뒤 네 번째 패스가 끝나야 HDR 경로의 대기(PathWait)가 풀립니다.
  • 원본 코드를 FC1 비트 59사례, task 생성 1회, 완료 경로 17사례로 실행했습니다. 인터럽트와 RTOS 결과는 주입한 값이며 실제 카메라의 동작이 아닙니다.

확인 원본 코드 실행으로 확인

  • 형식 이름·변환·토폴로지 생성자·FC1 setter·writer (59사례)
  • FIPLIB 계산부터 task 4개 생성·설정 변환·Commit, 같은 processor의 Go와 큐 전송
  • 큐 wrapper, IRQ 처리기, 드라이버 1회 반복, 콜백 체인 (17사례)

정적 분석 코드를 읽어 판단

  • RunTask의 시작 기록 순서와 드라이버 대기 분기
  • PathWait가 기다리는 이벤트 비트와 IpuToneMapRgb의 성공 분기

모델 시험 조건으로 정한 것

  • 512×128 합성 입력과 합성 감마 LUT, 대체 함수 24개
  • 인터럽트 호출과 이벤트 대기 결과(주입)
  • 레지스터 대신 RAM에 기록(MMIO 모델)

미확인 확인하지 않은 것

  • FC1 제어 bit 0의 하드웨어 기능
  • 실제 인터럽트의 발생 시각, tick 주기, DMA·캐시 일관성
  • 메모리 할당 실패 뒤의 복구, 최종 픽셀 값

배경: 설정값이 하드웨어 작업이 되기까지

앞의 두 문서에서 다음을 확인했습니다. HDR 계수는 FC1 레지스터까지 보존됩니다(출력 선택과 계수). 네 패스 중 두 패스에서 FC1이 켜지고 네 패스가 모두 제출 대상입니다(FC1 활성화와 제출 범위). FC1은 RGB를 밝기·색차(YUV)로 바꾸는 색 변환 단계로 보입니다. 다만 이 이름은 함수 이름과 계수에서 끌어낸 추정입니다.

이 문서는 남은 두 질문을 다룹니다. 하나는 제어 워드의 비트가 어디서 오는지이고 다른 하나는 “제출 대상”이 실제로 하드웨어에 넘어가고 끝났다고 알려지는 과정입니다.

FC1 제어 비트는 입력 유형이 0인지를 나타냅니다

해당 패스 분기에서 bit 0은 “저장된 토폴로지 입력 유형 T가 0인가”이며 직접 입력 경로에서는 상위 디스크립터의 32비트 값이 그대로 들어가기도 합니다.

FIPLIB의 해당 분기에서 FC1 bit 0은 저장된 토폴로지 입력 유형 T가 0인지를 나타냅니다. 이 유형의 원본 타입 이름은 fiplib_pass_input_type입니다. 입력 형식과 관계가 있지만 RGB·YUV라는 이름만으로 값이 갈리지는 않습니다. [근거: software_label, topology_type]

기본 생성자의 심볼 서명과 object+0x18 기록으로 T의 타입을 확인했습니다. 파생 IPU 생성자는 input_format_mode를 분류해 T를 저장합니다. 그 뒤 SetInputFormat은 +0x50만 바꾸므로, T가 매번 최신 형식에서 다시 계산된다고 보면 안 됩니다. [근거: format_mutators]

RGB_48과 YUV_444_16은 같은 형식 0xd, T=1이고 RGB_10_12_10과 YUV_422는 함께 T=0입니다. 그래서 bit 0을 RGB/YUV 선택, 행렬 bypass, 반올림, clipping 중 무엇으로도 이름 붙일 근거가 없습니다. 적용되는 패스 분기 안에서 “T가 0인지를 나타내는 비트”라고만 설명할 수 있습니다. 0x1 클래스의 operation-mode 함수 0x80178770은 같은 T를 2와 비교하는 별도 분기를 가집니다.

1x0이나 기본 5x1처럼 플래그를 늘 0으로 쓰는 분기도 있습니다. 이번 HDR 네 패스의 제어 워드는 모두 0입니다(패스별 값). location 10은 T=0이지만 플래그를 0으로 고정하는 5x1 기본 방식을 쓰고 마지막 0x1 패스는 Q=0·T=1이라 역시 0입니다.

마지막 index 3에는 최종 출력용 토폴로지 설정이 적용됩니다. 슬롯이 비어 있으면 뒤의 변환·제출 루프가 그 슬롯을 건너뜁니다. [근거: wrapper_to_task, task_class_id_and_callbacks]

주의

kind 0 생성 코드에서 메모리 할당이 실패했을 때 복구하는 경로는 확인하지 못했습니다. 뒤 루프의 NULL 슬롯 검사를 생성 실패 복구와 같은 동작으로 해석하지 않습니다. 재사용, 다른 wrapper kind, 다른 디스크립터는 별도 분기입니다.

task는 큐를 거쳐 드라이버 스레드가 시작합니다

Go는 task 포인터를 큐에 넣을 뿐이며 드라이버 스레드가 꺼내 필터·영상 설정을 기록하고 하드웨어 시작 기록을 합니다.

  큐 = driver+0x224, 메시지 = task 포인터, wait = 0
ThrIpuDriver: 받기 → mutex → 완료 비트 지우기 → RunTask

RunTask의 vtable+0x2c는 C12의 WriteAll 0x80357098로 이어집니다. WriteAll은 드라이버의 관찰자 포인터를 현재 task+8로 등록하고 이 연결로 완료 통지가 현재 task의 Update에 닿습니다. 사이의 읽기 0xb0802024에는 하드웨어 뜻을 붙이지 않았습니다. [근거: queue_and_start, observer_chain]

큐 등록 성공, 시작 기록, 완료 이벤트는 서로 다른 단계입니다. 큐 전송이 실패하면(0이 아닌 반환) OsSysHaltEx로 들어가고 완료 대기가 실패해도 진단을 출력한 뒤 OsSysHaltEx로 갑니다. 어느 쪽도 정상 완료 통지로 처리되지 않습니다. 대기에 성공하면 PowerOff 뒤 event 2를 통지합니다. [근거: worker_wait]

대기값 5,000은 tick 수입니다. tick 주기를 확인하지 않았으므로 밀리초로 바꾸지 않았습니다. option 1과 2는 ThreadX 공식 헤더의 OR_CLEAR·AND 상수와 대조했으며 이 최신 헤더를 Q7 RTOS 버전의 증거로 쓰지는 않았습니다.

인터럽트 하나는 HDR 완료가 아닙니다

IRQ 완료, task 완료, HDR 대기 해제는 서로 다른 단계이며 네 번째 패스가 끝나야 PathWait가 기다리는 비트가 켜집니다.

완료 인터럽트는 먼저 드라이버 이벤트를 깨웁니다. task는 남은 하위 이미지가 있으면 자신을 다시 큐에 넣고 다 끝나면 processor에 알립니다. processor는 패스 완료 수와 별도 완료 횟수를 확인합니다. [근거: done_irq_and_early_event, subimage_completion, processor_aggregation]

task의 +0x220은 끝난 하위 이미지 수, +0x224는 비교 대상 수입니다. 모드 +0x228 == 0에서 아직 남았으면 CommitSubImage 뒤 같은 task를 다시 큐에 넣고 event 4를 보냅니다. 다 끝나면 OnProcessingDone이 event 2를 processor에 전달합니다. 모드 1·2는 별도 분기입니다.

mode 0·CBC 0, task 슬롯 네 개가 모두 있고 task당 하위 이미지가 하나인 재실행에서 processor의 완료 수는 1→2→3→4로 늘었습니다. 두 번째 통지는 NR 단계 보조 이벤트를 만들고 네 번째 통지가 최종 경로 bit 0을 켰습니다. 마지막에는 별도 완료 횟수 +0x2f4와 목표 +0x2f0도 비교하며 조건에 따라 임시 자원 정리와 단계 3 설정을 거칩니다. [재현 도구]

type 0의 PathWait은 0x815a1bc4의 bit 0을 기다립니다. 새 경로의 제한 시간은 path+0xac = 40000 ticks입니다. IpuToneMapRgb는 PathGo 다음 PathWait의 성공 분기를 거쳐 정리와 성공 반환으로 갑니다. 보조 이벤트가 먼저 켜졌다고 해서 이 대기를 통과한 것은 아닙니다. [근거: path_wait_binding]

시험 조건

IRQ 호출과 이벤트 대기 결과는 주입한 값입니다. WriteAll, 기하 결과, 정리 작업 일부를 모델링했고 드라이버 루프와 콜백 체인은 따로 실행했습니다. 하위 이미지를 다시 큐에 넣으면 task 수와 IRQ 수가 달라집니다.

K-3 Mark III와 비교

K-3 Mark III에서는 R2y 제어 비트와 별도 행렬 모드, RAW·JPEG 작업 큐, JPEG 완료 콜백을 대조했습니다. 두 기종 모두 설정·제출·완료를 나눠 추적할 수 있지만 주소와 작업 구조가 다릅니다. K-3의 비트 뜻이나 JPEG 완료 조건을 Q7 HDR에 그대로 적용하지 않았습니다. 참조한 공개 커밋은 614d1fe46b0041819f70f61559dc5e267183f717이고 그 커밋의 파일 6개를 해시로 고정했습니다. [근거: comparisons, source_blobs]

한계와 재현 방법

  • FC1 비트: 원본 형식 매핑·생성자·setter·writer 59사례(형식 분류 28, 디스크립터 매핑 17, 직접 입력 기록 14). task 스케줄링이나 픽셀 연산은 실행하지 않았습니다.
  • task 생성·제출: 512×128 입력, 합성 감마 LUT, 기본 HDR 보조 디스크립터를 썼습니다. 원본 FIPLIB 기하 계산·Export·CalculateTopology·TranslateFilters·네 task의 가상 Commit을 실행했습니다. 그 뒤 같은 processor의 Go를 따로 호출했습니다. 메모리 할당·환경 함수·큐 전송 성공은 대체했고 task와 wrapper 결과를 주입하지는 않았습니다. PathGo의 외부 동기화와 실제 큐 소비는 빠져 있습니다. [근거: replay]
  • 완료 경로: IRQ 조건 7, 큐 전송 2, 드라이버 대기 2, 네 패스 콜백 4, 하위 이미지 2, 모두 17사례입니다. IRQ와 RTOS 결과를 주입했습니다.
  • FC1 제어 bit 0의 물리적 기능을 정하려면 칩 레지스터 문서나, 조건을 통제한 실기 레지스터·픽셀 관측이 더 필요합니다. 큐와 콜백이 소프트웨어에서 성공했다는 것은 영상이 정확하다는 증거가 아닙니다.
  • 실제 인터럽트 발생 시각, DMA·캐시 일관성, 최종 픽셀 값은 관측하지 않았습니다.
