화면과 글꼴 · ② 그리기 요청: 무엇을 어디에 그릴지

색공간 화면을 다시 그리라는 요청이 만들어지는 과정

선택지를 옮기면 화면이 다시 그려집니다. 이때 펌웨어가 어떤 글자·도형·아이콘을 어느 좌표에 그리라고 요청하는지 원본 코드로 따라갔습니다.

이 문서에서

  1. 배경: 화면은 요청을 모아 한 번에 다시 그립니다
  2. 갱신 요청 하나가 위젯 전체를 다시 쓰기까지
  3. 선택된 선택지만 강조·아이콘·안내문을 그립니다
  4. 글자 줄 요청과 선택 아이콘 픽셀
  5. 그리기 버퍼와 표시 버퍼를 맞바꾸는 요청
  6. K-3 Mark III와 비교
  7. 한계와 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 화면 갱신 요청을 원본 큐 생산자와 소비자에 통과시켜 갱신 4회를 실행했습니다. 갱신마다 위젯 갱신과 쓰기 패스 두 번이 이어졌습니다.
  • 네 갱신에서 글자 줄 25개와 선택 강조 도형 요청 20개(갱신마다 5개)의 좌표·길이·팔레트 번호를 기록했습니다. 강조·선택 아이콘·안내문은 선택된 선택지에서만 나옵니다.
  • 선택 아이콘은 별도로 원본 코드로 그려 보았습니다. 두 위치 모두 0이 아닌 팔레트 번호 330개가 합성 버퍼에 쓰였고, 버퍼 전체가 독립 계산과 같았습니다.
  • 이 문서가 다루는 것은 요청과 아이콘까지입니다. 강조 도형의 픽셀은 선택 강조의 픽셀, 글자 픽셀은 글꼴 로딩과 글리프 픽셀에서 다루며, 팔레트 색·LCD 출력은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 갱신 요청 생산·소비, 위젯 갱신, 쓰기 패스 0과 1
  • 글자 줄 준비와 강조 도형 요청의 인수, 그리기·표시 버퍼 교대 요청
  • 선택 아이콘의 RLE 풀기와 픽셀 쓰기(두 위치)

정적 분석 코드를 읽어 판단한 것

  • 표시 컨텍스트 선택과 LayerSetFrameBuffer·LayerMove 호출
  • 글자 요청 뒤의 GDI·글꼴 렌더러 연결

모델 시험 조건으로 정한 것

  • RTOS 큐 전달·대기·세마포어 (메시지 하나를 한 번 전달)
  • 합성 버퍼 ID 17·18과 버퍼 정보, 로케일 값
  • 요청을 기록하고 돌아오는 경계 (전체 24곳)

미확인 확인하지 않은 것

  • 물리 키 입력, 동시에 쌓인 큐 처리
  • 팔레트의 실제 RGB, DMA, LCD 출력

배경: 화면은 요청을 모아 한 번에 다시 그립니다

Q7의 메뉴 화면은 상태가 바뀌면 곧바로 픽셀을 칠하지 않습니다. 먼저 UI 서비스의 큐에 “다시 그려라”라는 메시지를 넣고, 소비자 쪽이 메시지를 꺼내 화면 위젯 전체를 차례로 다시 씁니다. 각 위젯은 직접 픽셀을 다루지 않고 글자 출력, 도형 그리기, 아이콘 그리기 함수에 요청을 넘깁니다. 이 문서는 그 요청을 붙잡아 기록했습니다.

색공간 화면 하나를 다섯 문서로 따라갔고, 이 문서는 두 번째 단계입니다. 앞 단계인 선택·확정·취소에서 선택을 바꾸면 설정 RAM이 바로 바뀐다는 것을 확인했습니다. 그 바뀐 값을 화면에 반영하는 과정이 여기서 시작합니다.

  1. ① 선택·확정·취소색공간 화면: 선택·확정·취소
  2. ② 그리기 요청이 문서
  3. ③ 강조 픽셀선택 강조의 픽셀
  4. ④ 글자 픽셀글꼴 로딩과 글리프 픽셀
  5. ⑤ 글자 크기·컨텍스트48×48 요청과 컨텍스트 선택
  6. 팔레트·LCD미확인

좌표는 모두 그리기 함수에 넘어간 논리 좌표이고, 색은 RGB가 아니라 팔레트 번호입니다. 화면 전체의 배치를 한 장으로 그린 개념도는 화면·글꼴 안내에 있습니다.

갱신 요청 하나가 위젯 전체를 다시 쓰기까지

갱신 함수가 만든 네 워드 메시지를 그대로 소비자에 건네면, 원본 코드가 화면 전체를 다시 쓰고 그 과정에서 네 종류의 요청을 내보냅니다.

UiService_Refresh(1)이 만든 메시지 [0x80, 1, 0, 0]은 원본 UiService_SendRequest를 지납니다. 소비자 UiService_Perform은 명령 0x80을 받아 UiService_DoRefresh(3)을 부릅니다. DoRefresh는 화면 전체를 갱신한 뒤 전체 다시 그리기 분기로 가서 GuiComponent_Write를 쓰기 패스 0과 1로 두 번 부릅니다.

RTOS의 대기·전달·수신·세마포어는 모델이 대신했고, 명령 하나를 처리한 직후 실행을 멈췄습니다. 네 갱신은 아래 표의 조건으로 따로 실행했습니다. [근거: findings.refresh, replay.refresh_cases]

선택된 선택지만 강조·아이콘·안내문을 그립니다

두 선택지의 글자는 매번 그리지만, 강조 사각형·선택 아이콘·안내문은 지금 선택된 쪽의 활성 그리기 목록에서만 나옵니다. 강조는 사각형 다섯 개를 겹쳐 그린 것입니다.

원본 키 이동이 활성 목록을 바꾸면 그리는 대상도 바뀝니다. 일반 선택지 아이콘은 0x586·0x588이고, 선택 아이콘은 두 선택지 모두 자원 번호 0x25입니다. 강조 위젯은 sRGB 쪽 0x0191d00c, AdobeRGB 쪽 0x0191d011이며 위젯 표의 종류는 0x11입니다.

그림은 가로를 논리 좌표 그대로, 세로를 2.5배로 늘려 요청 순서대로 겹쳐 그렸습니다. 칸의 색은 세 번호를 구분하려는 것이며 실제 팔레트 색이 아닙니다. 강조 영역은 x = 0, 폭 720, 높이 48이고, y = 64(sRGB) 또는 112(AdobeRGB)에 놓입니다. 선택지 글자는 그 안의 (96, y)에서 시작합니다.

글자 줄 요청과 선택 아이콘 픽셀

글자는 줄마다 좌표와 글자 단위 수를 담은 요청으로 넘어가며, 이 문서는 그 요청까지만 기록했습니다. 선택 아이콘은 원본 코드로 실제 픽셀을 써서 버퍼 전체를 대조했습니다.

글자 줄 요청

종류 9 라벨은 현재 설명자를 갱신하고, GuiStringLabel_WriteStringInfo가 ResourceString_DrawString/DrawStringChangeColor로 보냅니다. 이 함수는 로케일 값(0x80b7b32c)으로 원본 언어 표를 고르고, 설명자의 줄 수와 줄마다의 길이(1바이트)를 따라 돕니다. 글자 단위마다 2바이트를 한 줄짜리 스택 버퍼에 복사한 뒤 I43_DBTextOut과 AppDBTextOutByBufferID로 넘깁니다.

언어 표의 슬롯 0은 영어, 슬롯 1은 프랑스어입니다. 두 선택지 글자의 해시는 언어가 바뀌어도 같았습니다. 프랑스어 AdobeRGB 안내문은 y = 280과 328의 두 줄이고 영어는 y = 280의 한 줄입니다. 시험은 로케일 값을 직접 넣었고, 언어 선택이나 글꼴 등록은 실행하지 않았습니다. [근거: findings.text · locale, labels]

글자 모양은 여기서 정해지지 않습니다

요청에 담긴 것은 글자 번호의 나열입니다. 다음 단계는 GdiTextOutDB와 간접 글꼴 렌더러이며, 이 문서에서는 실행하지 않았습니다. 같은 “sRGB” 요청을 원본 글꼴 코드에 넣어 픽셀을 만든 시험은 글꼴 로딩과 글리프 픽셀, 이 줄에 함께 걸린 48×48 크기 요청은 48×48 요청과 컨텍스트 선택에 있습니다.

선택 아이콘의 픽셀

  1. RLE 원본296바이트 · 아이콘 0x25
  2. 원본 코드로 풀기1,008바이트 = 21×48
  3. 0이 아닌 번호만 쓰기330바이트, 0은 투명
  4. 합성 버퍼줄 간격 96바이트 · 높이 160

선택 아이콘의 논리 크기는 16×48이지만 비트맵은 21×48입니다. ResourceIcon_DrawIcon이 원본 RLE 쌍을 풀어 정확히 1,008바이트를 만들고, 그중 0이 아닌 팔레트 번호 330개를 각 선택 위치에 씁니다. 0은 투명이어서 기존 값(초기값 165)이 남습니다. 버퍼 정보를 돌려주는 GetBuffer 경계만 시험값으로 바꿨습니다.

그리기 버퍼와 표시 버퍼를 맞바꾸는 요청

갱신이 끝나면 원본 코드는 방금 그린 버퍼를 표시 버퍼로 넘기고 다른 버퍼를 다음 그리기에 씁니다. 그 뒤 표시 장치로 가는 경로는 코드를 읽어 연결만 확인했습니다.

  1. 갱신 마무리ScreenControl_Update 원본 실행
  2. 버퍼 교대ScreenOsdLayer_Roll · 캐시 정리 요청 · draw/show 교대
  3. 표시 요청 기록0x8029ef58에서 기록하고 복귀
  4. 표시 컨텍스트 선택정적 연결
  5. 프레임 버퍼 지정LayerSetFrameBuffer 0x800442f8 · LayerMove 0x80044370
  6. DMA · LCD미확인

ScreenOsdLayer_Roll 0x8043ca4c는 그리기 버퍼에 캐시 쓰기·무효화를 요청하고, ScreenOsdLayer_SetOsd와 I43_OSDSetShowBufferEx로 이전 draw 버퍼를 새 show 버퍼로 지정합니다. 합성 버퍼 ID 17과 18은 네 갱신마다 역할을 바꿨습니다. 원본 코드는 0x8043ca34에서 다시 이어져 갱신을 마치고 소비자로 돌아오며, 0x80adf980에서 멈춥니다.

정적 코드에서는 AppOsdSetShowBufferByLayerID가 표시 컨텍스트를 고르고 AppOsdSelectDisplayContextByLayerID가 컨텍스트의 메모리 포인터와 버퍼 속성을 읽은 뒤 LayerSetFrameBuffer와 LayerMove를 부릅니다. [근거: findings.buffer]

주의

캐시 요청은 합성 draw 주소와 460,800바이트(960 × 480) 범위로 기록됐습니다. 이것은 시험용 GetBuffer 정보이며 실제 패널 크기나 장치 줄 간격을 뜻하지 않습니다. 아이콘 시험의 96바이트 줄 간격, 픽셀 시험의 736×176 버퍼와도 다른 조건입니다.

정정

모델 목록의 0x800ec08c는 진단 함수가 아니라 I43_SetParam입니다. 이 시험은 그 호출에서 0을 돌려주므로 매개변수 0x1bc의 활성 그리기 컨텍스트 선택을 실행하지 않습니다. 요청·픽셀 결과는 그대로이지만, 이 시험만으로 실제 버퍼 ID와 컨텍스트의 연결을 입증할 수는 없습니다. 등록된 컨텍스트를 원본 선택기가 고르는 과정은 조건부 컨텍스트 선택에서 따로 확인했습니다. 17·18은 시험 입력이며 실제 초기 할당값이 아닙니다.

K-3 Mark III와 비교

동작의 이름은 대응시킬 수 있지만 숫자 ID·자원 구조·팔레트·이벤트를 그대로 옮길 근거는 없습니다. 화면을 다시 만들 때는 선택을 언제 확정할지부터 정해야 합니다.

한계와 재현 방법

  • 바깥 스레드 대기와 큐는 모델입니다. 요청 생산, 명령 분기, 갱신 한 번은 원본 코드로 실행했지만, 갱신마다 명령 하나만 전달하므로 비동기 타이밍·경합·큐 넘침은 시험하지 않았습니다.
  • 글자 줄과 도형은 지정한 함수 경계에서 요청으로 붙잡았습니다. 이 문서는 글자 픽셀이나 완성된 강조 픽셀을 주장하지 않습니다. 로케일 값과 0인 화면 배율은 좌표를 재기 위한 시험 조건입니다.
  • 픽셀까지 그린 것은 자원 0x25 하나입니다. 그 버퍼 대조는 인덱스 RAM이며 실제 패널 크기·색·DMA·화면 전송 시점을 뜻하지 않습니다.
  • 모드 0x53 구성·열기는 앞 문서의 검사 도구와 같은 모델로 실행했습니다. 물리 입력, DCF·매체 효과, 확정·취소 동작은 이 시험에 포함하지 않았습니다.

작업자와 조정자의 별도 실행에서 네 갱신과 두 픽셀 사례의 결과 전체가 일치했습니다. 원본 워드 139개, 함수 구간 47개, 자원 범위 38개의 위치와 해시를 다시 계산합니다.
