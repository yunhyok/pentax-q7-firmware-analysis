01 / REQUEST TO WORKER

제출 결과를 원본 수신자에 연결한다

LensDriveControl은 요청 정보를 기록하고 CaptureProcessService에 0x6003c를 보냅니다. 원본 점프 테이블이 ExecuteFocusControl을 선택하고 검색·정지 setter가 메시지 6 또는 8을 큐에 제출합니다. 시험 도구는 원본이 제출을 시도한 메시지를 기록하고 모델이 수락한 경우에만 원본 LensComThreadMain에 전달합니다. 작업자가 다음 수신에 도달하기 전에 실행을 멈춥니다. 큐 전달과 렌즈 RAM 복사는 직렬화한 모델입니다. [A1: findings.caller·queue]

작업자는 결과 바이트를 기록하고 pending을 지웁니다. 검색 거부 7, 링크 실패 4, 시간 초과 6은 setter의 결과이며 바깥 수신자의 반환값 1과 다릅니다. 101번째 대기에서 작업자가 성공 1을 기록하고 pending을 지운 사례에서도 setter는 시간 초과 6을 반환했습니다. 경과 시간은 측정하지 않았습니다. 큐가 제출에 0을 반환하고 전달하지 않은 별도 사례에서는 하위 링크 호출 없이 101회 대기한 뒤 setter가 6을 반환했습니다. pending·바깥 반환값·이동 확인 상태는 모두 1이었습니다. 이는 큐 거부를 실패 응답과 구분한 합성 사례입니다. 회귀 검사에서는 전달을 첫 대기에 예약한 상태로 큐 거부를 공급합니다. 큐 승인 조건을 제거한 시험용 변형은 첫 대기에 작업자를 실행하므로 실패해야 합니다. 원본 코드 재실행으로 이 변형의 1회 대기와 정상 시험의 101회 대기를 구별했습니다. [A2: CASES·run_worker]

검색 명령 (0,1,2,4)은 하위 모드 2, TX3/RX1을 사용했습니다. 정지 명령 (0,1,2,6)은 로컬 바이트에 0을 쓰지만 메타데이터의 TX0/RX0 때문에 이 바이트를 하위 TX 데이터로 복사하지 않습니다. 하위 모드는 1입니다. 이 길이는 원본 API에서 관측한 설정값이며 실제 통신선에서 수집한 바이트 수가 아닙니다. [A1: findings.transport·evidence]

02 / CACHED MOTION PREDICATE

명령의 성공과 이동 완료는 다른 판정이다

검색 뒤 request+1이 1이면 setter 결과가 7·4·6이어도 이동 확인 상태 1로 들어갔습니다. 정지는 성공·거부·시간 초과 모두 확인 상태를 0으로 남겼습니다. 콜백은 캐시의 이동 바이트를 읽지만 getter가 반환하는 유효성 값은 사용하지 않습니다. 상태 1은 이동 값 1, 시작 카운트 6 이상 또는 별도 우회 플래그에서 상태 2로 넘어갑니다. 상태 2에서 이동 값이 0이면 두 완료 알림을 보냅니다. [A1: findings.arm·samples]

이동 값 0을 계속 공급했습니다. 이 사례는 일곱 번째 콜백에서 상태 2가 됐고 여덟 번째에 완료됐습니다. 원본 정기 통신의 실패는 캐시를 0으로 지우면서 이전 유효성 1을 남겼습니다. 상태 2에서 렌즈 제어를 리셋한 사례는 캐시와 유효성이 모두 0이 됐고 다음 콜백이 완료를 알렸습니다. 이 결과는 합성 상태에서 재현한 소프트웨어 판정이며 광학적 초점이나 기계적 정지를 입증하지 않습니다. [A1: command_cases]

getter 0x80112514:
  output byte ← VDRC motion at 0x80c2a748
  return byte ← validity at 0x80c2a746
callback 0x8042e5ac: uses the output byte; ignores the return byte
stop request: clears capture-side motion check state

유효성 무시를 모든 AF 코드의 성질로 일반화하지 않습니다. 여기서는 CaptureLensControlService_CallBackLiveView와 아래 WaitForFocusStop의 확인된 본문을 말합니다.

03 / TWO NOTIFICATIONS

완료 플래그와 캡처 단계가 함께 바뀌지는 않는다

검색의 0x6003e 알림은 캡처 단계를 2에서 3으로 바꿉니다. 이동 완료의 0x6003f는 단계가 4일 때만 5로 바꿉니다. 별도 0x10060032 수신자는 blFocusCompleteflag를 설정합니다. 단계 2로 시작한 사례는 AF 완료 뒤에도 단계 3이었고, 단계 4를 직접 넣은 별도 사례에서만 5로 진행했습니다. 실제 촬영이 단계 4에 도달하는 전체 과정은 실행하지 않았습니다. [A1: findings.capture_phase]

AF 호출자의 다른 모드가 0x8038402c에서 완료 플래그를 읽는 정적 사례도 있습니다. 이 호출은 이번 mode 0/1 재현 사례와 구분합니다. [A1: evidence 첫 항목]

04 / MOTION WAIT AND SEQUENCE EXIT

렌즈 정지 요청과 AF 스레드 종료를 구분한다

WaitForFocusStop도 유효성 반환값을 사용하지 않고 이동 캐시가 0이 될 때까지 기다립니다. 유효하지 않은 0은 바로 반환했고, 유효하지 않은 이동 값은 0이 된 뒤 반환했습니다. 0x80을 유지한 사례는 대기 네 번 뒤 시험 도구가 중단했으며 다음 대기 분기가 계속 선택돼 있었습니다. 확인한 함수 본문에는 고정 횟수 제한이 없습니다. [A1: wait_cases]

AF 명령 0xe0002는 blBKControl이 1이면 취소 플래그만 설정합니다. 그 밖에는 StopAF(1)이 CAF enable을 지우고 quit을 설정합니다. 시퀀스가 활성 상태라면 정지 요청 플래그를 세우고 잠든 경우에만 이벤트 0x10으로 깨운 뒤 0x08을 mode 1, timeout 0xffffffff로 기다립니다. 모델의 wait 반환값이 0인 사례에서도 임시 blStopForRelease를 지웠습니다. 별도 WaitAFComplete는 같은 종료 이벤트를 쓰면서 CAF enable·quit은 유지했습니다. [A1: abort_cases]

명령의 취소 분기와 이벤트 값은 원본 코드·상수로 확인했습니다. 종료 이벤트를 실제 AF 스레드가 언제 설정하는지, 이벤트 대기 후 액추에이터가 정지했는지는 이번 재현 범위 밖입니다.

06 / PINNED K-3 MARK III COMPARISON

07 / EVIDENCE BOUNDARY

확인한 동작과 장치 경계를 명시한다

원본 MIPS를 VEX로 실행했고 큐·대기·이벤트·하위 링크 여섯 API 경계는 모델로 처리했습니다. 초기 설정과 캡처 단계도 합성 값입니다. 원본 수신자 getter와 CaptureLensControl 초기화를 실행했지만 AF 초기화 전체 대신 이미 확인한 콜백 슬롯에 getter 값을 넣었습니다. 전체 AF 알고리즘 스레드, 실제 RTOS 동시성, 센서 입력과 렌즈 이동은 미검증입니다. 이후 변경을 설계할 때 명령 결과와 캐시 유효성, 완료 플래그를 별도 조건으로 검토해야 합니다. [A1: limitations]
