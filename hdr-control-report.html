01 / CONCRETE HDR TOPOLOGY

HDR 보조 설정이 단계 선택값을 덮어써 네 패스를 만든다

대상은 W+0x208이 0일 때 IpuToneMapRgb를 호출하고 format 0x0f01로 새 type 0 경로를 만드는 HDR 분기입니다. 기존 경로를 재사용하거나 외부 설정으로 디스크립터를 추가한 경우에는 같은 결론을 적용하지 않습니다. [H1: HDR 입력과 기본값]

02 / PER-PASS FC1 CONTROLS

네 패스의 FC1 활성화는 꺼짐·켜짐·꺼짐·켜짐으로 갈린다

패스의 FC1 활성화와 제어 워드는 서로 다른 필드에서 나옵니다. 활성화는 패스 입력의 bypass 바이트를 거쳐 결정됩니다. 제어 워드는 별도 플래그에서 가져와 하위 비트에 넣습니다. 패스 클래스와 입력 조건을 함께 확인해야 두 값을 해석할 수 있습니다. [C1: Top_BlockControls 분기]

로컬 패스 입력은 pass+0x88c입니다. +0x24의 bypass 바이트는 general block을 거쳐 payload+0x44로 나가고, +0x28의 플래그는 FC mode 1에서 payload+0x12c의 bit 0으로 나갑니다. [C1: 설정·Export]

모든 패스의 Q=0, S=0, D=0은 같지만 T는 1·1·0·1이며, 클래스별 조건식도 다릅니다. 1x0과 5x1의 FC1은 비활성화되고, 1x1과 마지막 0x1의 FC1은 활성화됩니다. 이 결과를 다른 디스크립터나 재사용 경로로 일반화하지 않습니다. H의 전체 조건식과 경계 사례는 C1 근거에 기록했습니다.

마지막 0x1 패스의 제어 경로를 이전 계수 보존 경로와 합치면, 계수 9개와 보조값 2048, 2048을 유지하면서 활성화 값 0과 제어 워드 0을 설정하는 구성입니다. 이 설명을 앞선 세 패스의 계수까지 확대하지 않습니다. 고정소수점 분모나 bit 0의 하드웨어 기능은 여기서 새로 지정하지 않습니다.

03 / ENABLE EMISSION

활성화 기록은 제어 워드와 다른 주소를 쓴다

FC1 활성화 설정은 레지스터 0xb60000ec에 0을 기록하고 비활성화 설정은 1을 기록합니다. 제어 워드는 다른 주소인 0xb60000fc에 기록합니다. 계수값이 같아도 활성화 설정은 다를 수 있으므로 두 기록을 구분했습니다. [E1: 생성자·vtable·writer]

SetEnabled(u8[payload+0x44] == 0) → u8[filter+0x28] = enabled
FC1 constructor: address = 0xb60000ec, disabled = 1, enabled = 0
WriteEnable:       MMIO[0xb60000ec] = enabled ? 0 : 1
WriteEnableToCbc:   append(0xb60000ec, enabled ? 0 : 1)

FC mode 1 Export: u32[payload+0x12c] = u8[local+0x28] & 1
FC1 setter:       u32[filter+0x48] = u32[payload+0x12c]
FC1 writer (dirty): MMIO[0xb60000fc] = u32[filter+0x48]

FC1 생성자 0x8031f56c가 주소와 두 값을 정하고, vtable+0x24는 상속한 SetEnabled 0x804ff648로 연결됩니다. 직접 기록은 0x80332680, CBC 청크 기록은 0x80332700입니다. [E1: 원본 워드·전이]

원래 생성자와 FIPLIB 활성화 변환 함수, 직접 기록 함수, CBC 기록 함수를 연속 실행했습니다. payload의 하위 바이트만 읽는 경계 사례를 포함해 MMIO와 CBC의 주소·값이 일치하는지 확인했습니다. CBC 청크를 만드는 것과 하드웨어가 그 청크를 실행하는 것은 별개의 검증입니다.

04 / FINAL SUBMITTED PASS

mode 0은 네 패스를 고르고, 마지막 패스는 index 3이다

새 processor의 제출 모드는 0으로 초기화되며, 분석한 HDR 호출들은 이 값을 바꾸지 않습니다. Commit은 전체 패스 범위 [0,N)을 고릅니다. 마지막 패스만 선택하는 모드 2와 구분해야 합니다. CBC 선택값도 0이므로 이 경로는 task 큐를 통한 직접 제출을 사용합니다. [H1: 초기화·SetParam·Commit·Go]

processor 생성자는 +0x25c부터 파라미터 26개를 0으로 지웁니다. 따라서 mode ID 0xa / +0x284, CBC ID 0xb / +0x288, import·restore 조건 +0x2b0도 0입니다. 분석한 IpuSubmit의 SetParam 호출은 ID 1·2·3·5·6·7·0xd·0xe이며 mode와 CBC 선택값을 바꾸지 않습니다. [H1: 파라미터 출처]

N=4인 경우의 범위 비교 — 실제 새 HDR은 mode 0
mode범위의미
0 · 이번 HDR[0,4)전체 패스 선택 → index 0·1·2·3
1 · 비교[0,3)마지막 제외 → index 0·1·2
2 · 비교[3,4)마지막만 선택 → index 3

TranslateFilters의 마지막 패스 조건 i == N−1도 index 3에서 참입니다. 이 플래그, Commit 범위, FC1 활성화는 각각 다른 조건입니다. 선택 범위 안에서 task가 없는 슬롯은 건너뛰며, 직접 레지스터 기록에는 config·UID·dirty 조건이 추가됩니다. [이전 패스·writer 조건]

05 / K-3 MARK III COMPARISON

제출 범위와 비트 의미를 기종별로 대조한다

K-3 Mark III의 최신 공개 커밋에서 단계별 제출 설정과 R2y 제어값 근거를 대조했습니다. K-3의 제어 비트와 행렬 모드는 독립적으로 설정되지만, 그 비트의 하드웨어 의미가 Q7 FC1과 같다는 증거는 없습니다. 각 기종의 주소와 분기 조건으로 확인한 범위만 비교했습니다. [K1: 출처·해시]

고정한 공개 커밋은 c1db6f27f0f72b30f09c30ae55cf8525640016e4입니다. 비교에는 해당 커밋의 파일만 사용했습니다.

06 / VALIDATION AND LIMITS

분기별 재실행과 실제 촬영의 경계

원본 함수 후보 61개와 명령·데이터 워드 507건을 검증 대상으로 고정했습니다. 함수 범위는 다음 sidecar 주소까지이며 공식 함수 크기가 아닙니다. 공개 CI는 원본 없이 메타데이터·기준값·HTML·링크를 검사하고, 원본 워드 대조와 VEX 실행은 로컬에서 수행했습니다.

HDR 재실행은 합성 64×16 버퍼와 원본 명령으로 만든 기본 보조 설정을 사용했습니다. 토폴로지·wrapper 생성 뒤 FIPLIB Analyze·geometry·Export의 나머지 구간을 건너뛰고, 실제 출력 메모리를 유지한 채 Commit의 범위 선택을 실행했습니다. task 생성·TranslateFilters·Go는 이 재실행에 포함하지 않았으며, 마지막 플래그와 직접 제출 경로는 정적 코드로 연결했습니다. 전체 촬영 실행을 재현한 결과는 아닙니다.

정적 경로 추적과 제한된 원본 명령 실행으로 소프트웨어 선택 조건을 확인했습니다. 전체 카메라를 실행하거나 실제 HDR 촬영의 인터럽트·DMA·픽셀을 관측하지는 않았습니다. 최종 제출 대상으로 선택됐다는 사실이 하드웨어 처리 완료나 최종 영상의 정확성을 증명하지는 않습니다.

아직 명명하지 않은 packed control bit 0의 물리적 기능, 실제 센서 데이터에서의 처리 결과, DMA·캐시 일관성은 남은 과제입니다. 원본 BIN·추출 ELF·전체 디컴파일은 공개하지 않습니다.
