HDR 네 패스의 FC1 활성화와 제출 범위

FC1 계수가 보존된다는 것만으로는 색 변환이 실제로 적용되는지 알 수 없습니다. HDR 처리가 몇 개의 패스로 나뉘는지, 그중 어느 패스에서 FC1이 켜지는지, 어느 패스가 하드웨어에 제출되는지를 따라갔습니다.

  4. 활성화와 제어 워드는 다른 레지스터에 기록됩니다

핵심 요약

  • 분석한 HDR 경로에서는 HDR 보조 설정이 패스 구성 선택값을 바꿔, IPU 처리가 패스 4개로 나뉩니다.
  • FC1 색 변환은 네 패스에서 꺼짐·켜짐·꺼짐·켜짐으로 갈립니다. 마지막 패스에서는 켜지고, 계수와 별개인 제어 워드는 네 패스 모두 0입니다.
  • 제출 범위는 처음부터 끝까지 [0, 4)이어서 네 패스가 모두 제출 대상입니다. “마지막 패스”만 따로 고르는 방식이 아닙니다.
  • 원본 명령을 패스 제어 58사례, 활성화 기록 6사례로 실행해 확인했습니다. 실제 촬영의 인터럽트·DMA·픽셀은 관측하지 않았습니다.

확인 원본 코드 실행으로 확인

  • HDR 기본 보조 설정부터 패스 구성·wrapper 생성, Commit의 범위 선택까지
  • 다섯 가지 top-control 구현과 General·FC Export (58사례)
  • FC1 생성자·활성화 변환·직접 기록·CBC 기록 (6사례)

정적 분석 코드를 읽어 판단

  • 마지막 패스 표시(i == N−1)와 직접 제출(Go) 경로
  • processor 파라미터가 HDR 호출 동안 바뀌지 않음

모델 시험 조건으로 정한 것

  • 합성 64×16 버퍼와 감마 LUT, 대체 함수 19개
  • 패스 제어 시험의 합성 토폴로지·입력 값
  • 레지스터 대신 RAM에 기록(MMIO 모델)

미확인 확인하지 않은 것

  • 제어 워드 bit 0의 하드웨어 기능
  • 보조 설정이 없거나 다른 디스크립터를 쓰는 경로의 패스 구성
  • 실제 촬영의 인터럽트·DMA·캐시·픽셀

배경: 패스와 FC1 활성화

Q7의 HDR은 노출이 다른 세 장을 합친 뒤 IPU(이미지 처리 하드웨어)로 색 처리를 합니다(리코 Q7 소개). 펌웨어는 이 처리를 몇 번의 패스로 나누고, 패스마다 어떤 필터를 켤지 따로 정합니다. FC1은 그 필터 중 하나로, RGB를 밝기·색차(YUV)로 바꾸는 색 변환 단계로 보입니다. 이 해석이 추정인 이유는 출력 선택과 계수 문서에 정리했습니다.

그 문서에서 HDR 계수 9개와 보조값 2개가 FC1 레지스터 쓰기까지 보존된다는 것을 확인했습니다. 이 문서는 다음 질문을 다룹니다.

  1. 계수 보존값 11개가 레지스터까지 — 출력 선택과 계수
  2. 패스 구성과 활성화몇 개 패스, 어디서 켜지나 — 이 문서
  3. 제어 비트와 task비트의 출처, 큐 제출부터 PathWait 완료까지 — FC1 비트와 HDR task
쉽게 말하면

FC1에는 레지스터가 세 종류 있습니다. 계수 11개, 켜고 끄는 값 하나(0xb60000ec), 따로 쓰는 제어 워드 하나(0xb60000fc)입니다. 계수가 맞아도 켜는 값이 “꺼짐”이면 그 패스에서는 색 변환이 적용되지 않는 구성입니다. 이 문서의 “HDR 보조 설정”은 펌웨어 내부 디스크립터(ID 0x1f)를 말하며, 메뉴의 HDR 1·HDR 2와 어떻게 대응하는지는 확인하지 않았습니다.

대상은 W+0x208이 0일 때 IpuToneMapRgb를 호출하고, 형식 0x0f01로 새 type 0 경로를 만드는 HDR 분기입니다. 기존 경로를 재사용하거나 외부 설정으로 디스크립터를 더한 경우에는 같은 결론을 적용하지 않습니다. 색 처리 주제 전체는 색 처리·HDR 안내에서 볼 수 있습니다.

HDR 보조 설정이 패스 네 개를 만듭니다

HDR 보조 설정이 켜져 있으면 패스 구성 단계값이 0이 되고, 그 결과 location 0·6·10·5의 패스 4개가 만들어지며 mode 0이 그 전부를 선택합니다.

FIPLIB 입력 0x1738의 초기값은 1입니다. 이 값만 보고 패스 구성을 판단하면 틀립니다. 활성화된 HDR 보조 설정(ID 0x1f)이 있으면 PrepareCalculations가 이 값을 0으로 덮어쓰고, CreateTopology가 level 0을 1로 올려 패스 네 개를 만듭니다. [근거: topology_inputs, four_pass_topology]

네 패스의 FC1은 꺼짐·켜짐·꺼짐·켜짐입니다

켜짐 여부와 제어 워드는 패스 클래스별 조건식으로 정해지며, 이번 HDR에서는 꺼짐·켜짐·꺼짐·켜짐, 제어 워드는 모두 0입니다.

패스의 FC1 활성화와 제어 워드는 서로 다른 필드에서 나옵니다. 패스 입력은 pass+0x88c에서 시작합니다. 그 +0x24의 bypass 바이트가 general 블록을 거쳐 payload+0x44로 나가 켜짐 여부를 정하고, +0x28의 플래그는 FC mode 1에서 payload+0x12c의 bit 0으로 나갑니다. 두 경로는 아래 그림에 나눠 그렸습니다. [근거: export]

네 패스 모두 Q=0, S=0, D=0으로 같지만, T는 1·1·0·1이고 클래스별 조건식도 다릅니다. 그래서 1x0과 5x1 패스의 FC1은 꺼지고, 1x1과 마지막 0x1 패스의 FC1은 켜집니다. 이 결과를 다른 디스크립터나 재사용 경로로 넓히지 않습니다. H의 전체 조건식과 경계 사례는 [근거: helper, replay]에 있습니다.

마지막 0x1 패스의 제어 경로를 계수 보존 경로와 합치면, 계수 9개와 보조값 2048, 2048을 유지한 채 활성화 값 0(켜짐)과 제어 워드 0을 설정하는 구성입니다. 이 설명을 앞선 세 패스의 계수까지 넓히지 않습니다. 고정소수점 분모나 bit 0의 하드웨어 기능도 여기서 정하지 않습니다.

활성화와 제어 워드는 다른 레지스터에 기록됩니다

FC1을 켜면 0xb60000ec에 0, 끄면 1을 쓰고, 제어 워드는 별도 주소 0xb60000fc에 씁니다.

SetEnabled(u8[payload+0x44] == 0) → u8[filter+0x28] = enabled
FC1 생성자: 주소 = 0xb60000ec, 꺼짐 값 = 1, 켜짐 값 = 0
WriteEnable:       MMIO[0xb60000ec] = enabled ? 0 : 1
WriteEnableToCbc:   append(0xb60000ec, enabled ? 0 : 1)

FC mode 1 Export: u32[payload+0x12c] = u8[local+0x28] & 1
FC1 setter:       u32[filter+0x48] = u32[payload+0x12c]
FC1 writer (dirty): MMIO[0xb60000fc] = u32[filter+0x48]

FC1 생성자 0x8031f56c가 주소와 두 값을 정하고, vtable+0x24는 상속받은 SetEnabled 0x804ff648로 이어집니다. 직접 기록은 0x80332680, CBC 청크 기록은 0x80332700입니다. 계수 값이 같아도 활성화 설정은 다를 수 있으므로 두 기록을 나눠 봐야 합니다. [근거: observations, evidence]

네 패스가 모두 제출되고 마지막은 index 3입니다

새 processor의 제출 모드와 CBC 선택값은 0으로 시작해 바뀌지 않으므로, Commit은 전체 범위 [0, 4)를 고르고 task 큐를 통한 직접 제출을 씁니다.

processor 생성자는 +0x25c부터 파라미터 26개를 0으로 지웁니다. 그래서 mode ID 0xa(+0x284), CBC ID 0xb(+0x288), 가져오기·복원 조건 +0x2b0도 0입니다. 분석한 IpuSubmit의 SetParam 호출은 ID 1·2·3·5·6·7·0xd·0xe뿐이라 mode와 CBC 선택값을 바꾸지 않습니다. [근거: fresh_processor_defaults, hdr_mutators_and_submit]

TranslateFilters의 마지막 패스 조건 i == N−1도 index 3에서 참입니다. 이 마지막 패스 표시, Commit 범위, FC1 활성화는 각각 다른 조건입니다. 선택 범위 안에서 task가 없는 슬롯은 건너뛰고, 직접 제출에서 레지스터를 쓰는 WriteAll·WriteEnable에는 config·UID·dirty 조건이 더 붙습니다. 이 조건들은 패스 선택 문서에, task가 만들어져 큐에 들어가고 완료되는 과정은 HDR task 문서에 있습니다.

주의

task 생성과 설정 변환이 성공하고 해당 슬롯이 있다는 전제에서의 경로입니다. 최종 제출 대상으로 선택됐다는 사실이 하드웨어 처리 완료나 최종 영상의 정확성을 증명하지는 않습니다.

K-3 Mark III와 비교

K-3 Mark III의 공개 커밋 c1db6f27f0f72b30f09c30ae55cf8525640016e4에서 단계별 제출 설정과 R2y 제어값 근거를 대조했습니다. 비교에는 그 커밋의 파일만 썼습니다. K-3에서도 제어 비트와 행렬 모드가 따로 설정되지만, 그 비트의 하드웨어 뜻이 Q7 FC1과 같다는 증거는 없습니다. 각 기종의 주소와 분기 조건으로 확인한 범위만 비교했습니다. [근거: comparisons, source_blobs]

한계와 재현 방법

  • 정적 경로 추적과 제한된 원본 명령 실행으로 소프트웨어 선택 조건을 확인했습니다. 카메라 전체를 실행하거나 실제 HDR 촬영의 인터럽트·DMA·픽셀을 관측하지 않았습니다.
  • 패스 네 개와 범위는 추적한 새 HDR 구성에만 해당합니다. processor 파라미터, 디스크립터, 이미지 형식이 다르면 구성이 달라질 수 있습니다. 캐시된 보조 설정 변형은 재실행하지 않았습니다.
  • 제어 워드 bit 0의 물리적 기능, 실제 센서 데이터에서의 처리 결과, DMA·캐시 일관성은 남은 과제입니다.

HDR 재실행은 합성 64×16 버퍼와, 원본 명령으로 만든 기본 보조 설정을 썼습니다. 토폴로지·wrapper를 만든 뒤 FIPLIB Analyze·geometry·Export의 나머지 구간은 건너뛰고(0x8017cfd0), 실제 출력 메모리를 유지한 채 Commit의 범위 선택을 실행했습니다(0x8033ad88부터 0x80339040까지). task 생성·TranslateFilters·Go는 이 재실행에 없으며, 마지막 표시와 직접 제출 경로는 정적 코드로 연결했습니다. [근거: replay]

top-control 58사례에는 다섯 구현, 네 HDR 패스의 단계값 0 입력, 분류값의 기본·예외 분기, 도우미의 경계값, 실제 General·FC Export가 들어 있습니다. [근거: replay]
